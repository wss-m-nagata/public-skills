# pre-push-check

プッシュする前に、変わった領域ごとに、全テスト・AI のレビュー・規約への適合チェックを行い、結果をユーザーに報告するスキル。  
扱うのは、流す前の確認、テスト・レビュー・規約チェックの実行、報告までである。  
指摘を直す作業、コミット、プッシュ、PR の作成、PR へのコメントの投稿は扱わない。  
直したら、もう一度このスキルを呼んで流し直す。  

**規約の中身は、設定に写さない。** 設定には、規約・テストの進め方の「場所」だけを持つ。  
規約の中身は、毎回、その場所から読む。  
そのため、規約が変わっても、設定を直さずに、変わった内容で確認できる。  

## 0. 設定ファイルを確かめる（毎回、最初に行う）

設定ファイルは `.agents/config/pre-push-check/settings.md`（プロジェクトルート直下）である。  
**スキル自身のディレクトリの中には作らない。**（スキルを更新すると、上書きされるため）  

| 状態 | すること |
|---|---|
| 設定ファイルが無い | [references/interview.md](references/interview.md) に従う。プロジェクトから読み取れるものは、自分で調べて確定する。読み取れないものだけを質問する。結果は [assets/settings.template.md](assets/settings.template.md) の形で保存し、内容をユーザーに見せて、確認を取る。そのあと、手順1へ進む |
| 設定ファイルがある | 質問せずに、その内容を使う。下の「規約の変更の確認」を行ってから、手順1へ進む |
| 「設定を見直したい」と言われた | interview.md の質問をやり直し、変わった項目だけを、設定ファイルに反映する |

- 設定ファイルは、チームで共有する（Git に入れる）ものである。  
  保存したら、Git に入れるかどうかを、ユーザーに確かめる。  
- 設定ファイルに書いてある内容と、実際のプロジェクトが食い違ったとき（コマンドが無い、ブランチ名が違う、など）は、自分で直さずに、食い違いをユーザーに伝える。  

### 規約の変更の確認（設定ファイルがあるとき、毎回）

設定の「領域の表」にある、規約・テストの進め方の文書について、次を行う。  

1. 各文書を、実際に読む（読んだ内容を、以降の手順で使う）。  
2. 前回読んだ時点の最終更新（コミットID。リポジトリの外にある文書は、更新日時）と比べる。  

```bash
git log -1 --format=%h -- <文書のパス>   # 文書の最終更新のコミットID
```

- **変わっていた文書があるとき：**「規約が前回から変わっています：<文書名>」と、1行で知らせる。  
  質問はせずに、変わった内容で、このあとの手順を行う。  
- **文書が見つからないとき**（移動・削除など）：どこに移ったかを、ユーザーに聞く。  
  答えを、設定の「領域の表」に反映する。  
- **領域の表に無い、新しい領域のパスが差分に含まれるとき：**手順1で、ユーザーに伝える。  
- 実行が終わったら、読んだ時点の最終更新を、設定に書き戻す（書き戻したことを報告に1行で添える）。  

## いつ使うか

**プッシュする前**に使う。  
ブランチに、コミットまで済んだ状態で呼ぶ。  

- 取り込み先のブランチごとに、テスト・レビュー・規約チェックが要るかは、設定ファイルの「取り込み先ごとの扱い」に従う。  
- 要ると分かったら、そのことをユーザーに伝え、**始めてよいかを確かめてから**始める。  
  どれも数分かかることが多いため。  
- ユーザーが「手元のテストを流して」などと頼んだときは、時期に関係なく流す。  
- プッシュしたあとに自動で流れる確認（GitHub Actions など）が設定にあっても、このスキルは、その前に手元で流すためのものである。  

## 手順

### 1. 流す前に確かめる

取り込み先のブランチ（以下「宛先」）を決め、次の2点を確かめる。  
宛先は、設定ファイルの「取り込み先ごとの扱い」から、今のブランチに合うものを選ぶ。  
決められないときは、ユーザーに聞く。  
**1つでも合わなければ、自分で直さずに、何が合わないかをユーザーに伝えて止める。**  

```bash
git fetch origin
git merge-base --is-ancestor origin/<宛先> HEAD && echo 取り込み済み   # ① 宛先の最新を取り込んでいるか
git status --porcelain                                                 # ② 空であること（追跡していないファイルも数える）
```

- ① が合わないとき：宛先に何が入ったか（`git log --oneline HEAD..origin/<宛先>`）と、ぶつかるか（`git merge-tree --write-tree HEAD origin/<宛先>`）を添えて伝える。  
  取り込んでよいと言われたら、`git merge --no-edit origin/<宛先>` で取り込み、①②を確かめ直す。  
  取り込みがぶつかったら、`git merge --abort` で取り込む前に戻し、ぶつかったファイルをユーザーに伝えて止める（自分で解かない）。  
- ② が合わないとき：残っているファイルを伝える。  
  コミットに入れるなら、コミットし、入れないなら、消すか作業ツリーの外へ退避する。  
  どれにするかはユーザーが決め、指示を受けてから行う。  
  （テスト・レビュー・規約チェックが、コミットした内容だけを対象にするため）  
- 作業用の worktree で作業しているときは、その worktree の中で確かめ、流す。  

確かめたら、次の2つを決める。  

- **対象のコミット**（`git rev-parse --short HEAD`）。結果は、このコミットのものとして、報告する。  
- **変わった領域。** 差分のファイルを、設定の「領域の表」の「対象のパス」と照らして決める。  

```bash
git diff --name-only origin/<宛先>...HEAD   # 差分のファイル
```

- 差分が複数の領域にまたがるときは、**該当するすべての領域**について、手順2〜4を行う。  
- どの領域にも当たらないファイルがあるときは、そのファイルを伝え、どの領域として扱うかを、ユーザーに聞く。  
- 差分のある領域だけを対象にする（差分の無い領域のテストは流さない）。  

### 2. 領域ごとに、全テストを流す

領域ごとに、リポジトリ（worktree）のルートから、その領域の全テストを、裏で流す。  
全テストのコマンドは、設定の「領域の表」の「全テストの出どころ」から決める。  
出どころが文書（「テストの進め方」など）のときは、**その文書を読んで、コマンドを決める**。  
文書に書いていないときは、ユーザーに聞く。  
ログは作業用の一時フォルダ（scratchpad など、リポジトリの外）に書く。  
Windows の Git Bash を使うときは、パスの `\` を `/` に置き換え、引用符に入れる（`\` が取り除かれ、ログがリポジトリの中にできて「コミットしていない変更あり」になるため）。  

```bash
LOG="<一時フォルダ>/tests_<領域名>_<短いコミットID>.log"   # / 区切りで書く
<その領域の全テストのコマンド> > "$LOG" 2>&1; echo "exit=$?"
```

- 領域どうしは、同時に流してよい（テストは裏で動くため）。  
- 裏で流したら、終わるまで出力を何度も読みに行かない（終われば知らせが来る）。  
- **テストが終わるまで、作業ツリーのファイルを変えない。**  
  途中で直すと、直しかけの中身でテストされたのに、結果に印が付かないことがあるため。  
  レビューの指摘を直すのは、テストが終わってからにする。  
- 終わったら、終了コードで扱いを分ける。扱いは、設定ファイルの「終了コード」に従う。  
  設定が無いときの既定は、次のとおり。  

| 終了コード | 意味 | すること |
|---|---|---|
| 0 | すべて成功 | 結果の一覧を、ユーザーに報告する（手順5） |
| 0 以外 | 失敗したジョブがある | ログを読み、原因を見分ける。ダウンロードの失敗、ネットワーク・プロキシのエラー、ロックファイルの食い違いなど、環境の問題なら、そう伝える。それ以外は、「テストが失敗したときの扱い」（後述）に従う |

- 報告する一覧は、設定ファイルの「結果の報告範囲」に従う。  
  設定が無いときの既定は、ログの末尾の結果一覧（ブランチ・コミット・実行日時・ジョブごとの成否）である。  
  テストのコマンドが一覧を出さないときは、ジョブ（またはテストの種類）ごとの成否を表にする。  
- 一覧が途中で止まっていないか（中断・強制終了など）を確かめる。  
  止まっていたら、その中身は結果として扱わず、止まったことをユーザーに伝える。  
- 一覧に、テストしたコミットが書いてあるときは、手順1で控えたコミットと同じことを確かめる。  
  「コミットしていない変更あり」の印が付いていたら、その結果は使わずに手順1に戻る。  

### 3. 領域ごとに、AI のレビューを流す

設定ファイルの「レビューの方法」で、領域ごとに、レビューを流す。  
対象は、その領域の、宛先との差分（このブランチで、宛先に対して変わる内容）である。  
設定が無いときの既定は、Claude Code の `code-review` スキルを、強さ `high` で、宛先との差分を対象にして呼ぶ。  
強さは必ず書く（書かないと、前に使った強さで流れるため）。  
テストと同時に流してよい（テストは裏で動くため）。  
ただし、指摘を直す作業（このスキルの外）は、テストが終わってから始める（手順2）。  

- 指摘ごとに、事実を確かめてから「直す／直さない」の案を出す。  
  レビューは検証の工程を通していないことがあり、誤った指摘も混じる。  
  根拠のファイルと行を読み、合っているかを確かめる。  
- 次にあたる指摘は、直すかどうかをユーザーが決める。  
  - テストが確かめる内容（テストコード・期待値・テストデータ）を変えるもの。  
  - 設定ファイルの「ユーザーが決める指摘」に挙げたもの（未決の論点、他の担当の範囲など）。  
- 指摘を直すのは、このスキルの外の作業である。  
  直したら、もう一度このスキルを呼んで流し直す（手順6）。  
- 指摘と案は、領域ごとに、次の表にまとめて、ユーザーに見せる。  

```markdown
## AI のレビューの結果（<領域名>）

- 対象コミット：<短いコミットID>
- 指摘：<件数>件（<全体の見立て。例：通常の使い方で落ちる・誤った結果になるものは無い>）

| # | 指摘 | 確かめた結果 | 案 |
|---|---|---|---|
| 1 | <指摘を1文で> | <根拠のファイルと行、合っているか> | 直す。<どう直すか> ／ 直さない。<理由> ／ ユーザーが決める |
```

### 4. 領域ごとに、規約への適合を確かめる

バグを探すレビュー（手順3）とは別に、**規約に沿っているか**を確かめる。  
領域の規約・実装方針・テストの進め方の文書（設定の「領域の表」の「規約の場所」）を、**手順0で読んだ内容**のまま使い、その領域の差分と照らす。  

- 確かめる観点は、領域の規約の文書が定めるものである（例：コーディング規約、アーキテクチャ・実装方針、テストの書き方、画面設計規約）。  
  文書に書いていないことを、自分の好みで、規約として扱わない。  
- **外れている点だけを挙げる。** 各指摘に、次の3つを必ず添える。  
  - 規約の文書名と、該当する項目。  
  - 差分のファイルと行。  
  - どう外れているか。  
- 規約が曖昧で、外れているか判断できないものは、指摘にせず、「規約が曖昧」として別に挙げる。  
- 直す／直さないは、手順3と同じく、ユーザーが決める。  
  規約そのものが古い・誤っていると思うときは、規約を直す案を、ユーザーに出す（自分で規約を直さない）。  

```markdown
## 規約への適合（<領域名>）

- 対象コミット：<短いコミットID>
- 読んだ規約：<文書名の一覧>
- 外れている点：<件数>件

| # | 規約（文書名・項目） | 差分（ファイル・行） | どう外れているか | 案 |
|---|---|---|---|---|
| 1 | <文書名>の<項目> | <ファイル>:<行> | <1文で> | 直す／直さない／ユーザーが決める |
```

### 5. ユーザーに報告する

領域ごとに、テストの結果・レビューの表・規約への適合の表を、まとめて、ユーザーに伝える。  
**コミット・プッシュ・PR へのコメントは、このスキルでは行わない。**  
PR に結果を残したいときは、ユーザーが、報告の内容を使って行う（頼まれたときだけ、文面を作る）。  

伝える内容は、次のとおり。  

- 規約が前回から変わっていた場合は、その1行。  
- 設定に書き戻した内容（読んだ時点の最終更新）。  
- 領域ごとに、テストの結果（対象コミット・ジョブごとの成否）。  
- 領域ごとに、レビューの指摘の件数と、規約への適合の件数。「直す／直さない」の案（ユーザーが決める指摘は、それと分かるように）。  
- プッシュする前に残っていること（指摘を直す作業、直したあとの流し直し、ユーザーの判断待ちなど）。  

### 6. 直したあとに、もう一度呼ばれたとき（流し直し）

指摘を受けて直し、コミットしたあとにこのスキルが呼ばれたら、**手順0から流し直す**（テスト・レビュー・規約チェックのすべて）。  

- レビューの流し直しは、設定ファイルの「レビューの流し直しの回数」に従う（既定：**1回だけ**）。  
  流し直しで出た指摘は、正しさにかかわるもの（不具合・事実と違う記述・規約の外れ）だけを直し、残りは直さない理由を報告して終える。  
- 流し直しのあとに直した分でもう一度呼ばれたときは、**テストだけ**を流し直す。  
- 流し直しの前にも手順1の2点を確かめる（宛先が進んでいることがある）。  

プッシュは、ユーザーが行う。  
このスキルではプッシュしない。  

## テストが失敗したときの扱い

設定ファイルの「テストが失敗したときの扱い」に従う。  
領域の規約・テストの進め方の文書に、失敗したときの扱いが書いてあるときは、それを優先する。  
どちらにも無いときの既定は、次のとおり。  

- テストコード・期待値・テストデータを、自分の判断で変えない。  
- エラーメッセージ、特定した原因、どちらが誤りか（テストか、実装か）を、ユーザーに伝えて、指示を待つ。  
- 直すのは、ユーザーが承認したあと。直したら、何を変えたかを報告する。  

## やらないこと

- コミット、プッシュ、PR の作成、PR へのコメントの投稿。  
- レビュー・規約チェックの指摘を直すこと（このスキルの外で行い、直したらもう一度このスキルを呼ぶ）。  
- 規約の中身を、設定に写すこと。  
- 規約の文書を、自分で直すこと。  
- 差分の無い領域のテストを流すこと。  
- 手順1の2点が合わないまま流すこと、合わない点を断りなく直すこと（取り込みのぶつかりを自分で解くことを含む）。  
- テストが終わる前に、作業ツリーのファイルを変えること。  
- テストが失敗したときに、テストコード・期待値・テストデータを自分の判断で変えること。  
- レビューの流し直しを、設定の回数より多く行うこと。
