# 設定のための質問（初回だけ）

設定ファイル `.agents/config/pre-push-check/settings.md` が無いときに、1回だけ、この手順を行う。  
結果は、`assets/settings.template.md` の形で保存する。  
次回からは、質問せずに、保存した設定を使う（規約の中身は、毎回、設定に書いた場所から読む）。  

**方針：プロジェクトから読み取れるものは、自分で読んで確定する。聞くのは、読み取れないものだけにする。**  
**設定に書くのは、規約の「場所」だけである。規約の中身は、写さない。**  

## 手順1　先に読んで確定するもの

質問の前に、次を調べて、設定に書く内容を確定する。  
確定できたものは、質問しない（結果だけを伝える）。  

| 確定するもの | 探す場所の例 |
|---|---|
| 領域の分け方と、対象のパス | ディレクトリ構成（`nuxt/`・`frontend/`・`backend/`・`services/` など）、README、`AGENTS.md` |
| 領域ごとの、規約・実装方針・テストの進め方の文書 | `AGENTS.md`・README に書かれた資料の場所、`docs/`、領域ごとの `docs/`（`docs/20_rules/`・`docs/50_operation/`・`<領域>/docs/` など） |
| 領域ごとの、全テストのコマンド | 「テストの進め方」の文書、`package.json` の scripts、`Makefile`、`scripts/`、CI の定義（`.github/workflows/`） |
| 取り込み先のブランチの一覧 | `git branch -r`、`AGENTS.md`・`CONTRIBUTING.md`・README、CI の対象ブランチ |
| プッシュのあとに自動で流れる確認と、ワークフロー名 | `.github/workflows/` の、テストとレビューに関する定義 |
| 終了コードの意味 | テストのスクリプトの、`exit` の書き方 |

領域ごとに、次の種類の文書を探す（名前は、プロジェクトによって違う）。  

| 領域 | 探す文書の種類 |
|---|---|
| フロントエンド | 画面設計規約、フロントエンド実装方針、コーディング規約（CSS など）、テストの進め方 |
| バックエンド | 言語のコーディング規約、アーキテクチャ・実装方針、テストの進め方 |
| 共通 | 共通の指示書（`AGENTS.md`）、ブランチ・コミットの規約 |

- 読んでも見つからなかったものは、「このプロジェクトには無い」として、設定に書く。  
- 読んだ結果が複数ある（コマンド候補が2つ以上ある、領域の分け方が2通り読める、など）ときだけ、どれかを聞く。  
- 文書を見つけたら、その文書の最終更新（コミットID。リポジトリの外なら更新日時）を、設定の「領域の表」に書く。  

## 手順2　読み取れないときだけ聞くこと

| # | 質問 | 既定（答えが無いとき） |
|---|---|---|
| 1 | 領域は、どう分けるか（読み取れなかったとき） | フロントエンドとバックエンドの2つ |
| 2 | 領域ごとの、規約・テストの進め方の文書は、どこにあるか（見つからなかったとき） | なし（規約チェックは、その領域では行わない） |
| 3 | 全テストを、1つのコマンドで流せるか。無ければ、どのコマンドを、どの順に流すか | なし |
| 4 | 取り込み先のブランチごとに、プッシュ前のテスト・レビュー・規約チェックは要るか（決まりが文書に無いとき） | すべての取り込み先で、すべて要る |
| 5 | AI のレビューの方法は何か（決まりが文書に無いとき） | Claude Code の `code-review` スキル、強さ `high` |
| 6 | ユーザーが決める指摘は何か（未決の論点、他の担当の範囲など） | テストが確かめる内容を変えるもの |

## 手順3　既定を示して、差分だけ聞くこと

次は、既定を示したうえで、「変えたい点はありますか」と1問で聞く。  
変えると答えたものだけを、設定ファイルに書く。  

| 項目 | 既定 |
|---|---|
| 終了コード | 0 は成功、0 以外は失敗 |
| 結果の報告範囲 | ログの末尾の結果一覧（なければ、ジョブごとの成否の表） |
| レビューの流し直しの回数 | 1回だけ。流し直しでは、正しさにかかわる指摘だけを直す |
| テストが失敗したときの扱い | テストを直さず、原因を報告して、ユーザーの指示を待つ |

## 手順4　追加の項目を聞くこと

最後に、必ず、次を聞く。  

> ここまでで足りない項目はありますか。
> このプロジェクトに固有の決まり（例：流す前に必ず確かめること、報告に必ず書くこと）があれば、教えてください。

- 追加で出たものは、設定ファイルの「追加の項目」に、そのまま書く。  
- 追加の項目は、手順（SKILL.md）の該当する箇所で、必ず読み、従う。  

## 手順5　保存して確認を取る

1. `.agents/config/pre-push-check/settings.md` を作る（ディレクトリが無ければ作る）。  
2. 書いた内容を、ユーザーに見せて、確認を取る。  
   読んで確定した項目は、読んだ場所も添える。  
3. Git に入れるかどうかを、ユーザーに確かめる（チームで共有するため、入れることをお勧めする）。
