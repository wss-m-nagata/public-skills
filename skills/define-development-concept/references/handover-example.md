# 記載例：システム開発の引き継ぎ支援

架空の検討会で、作成者と、引き継ぎを行う関係者が基本方針をすり合わせる場面。
共有された支援案から想定した記載例であり、実際の業務や作成者の意図は未確認である。

## 概要

目的は、暗黙知や未整理の開発情報を形式知化し、前任者への依存を減らして、交代後も開発を継続できるようにすること。
As-Is図では、形式知・未整理情報・暗黙知が現在どの経路で後任者に伝わるか、後任者にどのような調査や確認が生じるかを示す。
課題は別に置き、開発の継続性が前任者に依存しているという主要課題と、暗黙知の消失などの個別課題を示す。

## スコープ

| 区分 | 範囲の案 |
| --- | --- |
| 対象 | 担当者の交代時に、開発の継続に必要な情報を引き継ぐ。 |
| 対象外 | 日常の資料管理、引き継ぎ後の開発そのもの。 |
| 要判断 | 最初に扱う開発体制と、前任者不在時の扱い。 |

## To-Be

目指す状態は、後任者と後任者のAIが整理された情報を活用して開発を継続でき、新たに判明した情報を次回の引き継ぎに生かせること。
スイムレーンは前任者・AIによる支援・後任者に分け、既存情報の調査、聞き取り、情報の整理、資料の確認・共有を示す。
資料を受け取った後の問い合わせ、回答の共有、資料更新、後任者による再確認を矢印でつなぐ。
前任者に聞けないケースを含める場合は、記録から分からない事項の扱いを補足する。

## 検討事項

- 完了条件：対象範囲と目指す姿を関係者が合意している。
- 完了条件：残った課題や持ち越し事項の扱いを関係者が合意している。
- 検討事項：個人開発のシステム全体と、チーム内の担当交代のどちらを優先するか。
- 課題：前任者不在時には、記録のない判断経緯を復元できない可能性がある。
- 持ち越し事項：実際の引き継ぎを完了とする判断基準は要求分析で扱う。
