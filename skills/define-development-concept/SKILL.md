# 開発構想・基本方針整理

- **目的**：要件定義の前に、解決したい課題、今回扱う範囲、目指す状態について関係者の認識を合わせ、基本方針を決める。
- **資料の読者**：基本方針を検討する会議に参加する関係者。企画・業務・開発などの立場が異なり、案件の資料や技術に詳しくない参加者も含む。
- **スキルの利用者**：資料を準備し、会議を進める企画者や担当者。

会議で初めて読む人が、図を見ながら話についていけて、何を決める場なのか分かる資料を作る。冒頭に、見る順序、決め方、次に進む条件を短く案内する。

## 進め方

1. **会議の判断を先に確かめる。** 誰が参加し、今回どの方針を決めたいかを聞く。既存の提案やツールは材料として読み、提案者の意図や実際の業務は根拠が得られるまで記載例・要確認として扱う。
2. **４項目を作る。** 下表を使う。情報を足す前に、その情報で会議の判断が変わるかを確かめる。図と同じ内容の一覧や細かな工程は元資料に残す。
3. **認識合わせに使える形にする。** 事実、提示側の記載例、相手の記入、合意内容を区別する。確認が必要な点は、会議で答えたい具体的な問いにする。
4. **基本方針を次の工程に渡す。** 目的・対象・目指す状態について合意した点と残る問いを示す。機能やデータの細かな定義、画面、保存形式、実装手順は要求分析・設計で扱う。

| 項目 | 決めることと表現 |
| --- | --- |
| [概要](references/overview.md) | 目的は取り組みの狙いが伝わるように書く。現状は、方針を判断するうえで重要な業務の流れや情報の受け渡しを図にする。課題は図の下の別項目にまとめる。 |
| [スコープ](references/scope.md) | 対象・対象外・未決定の境界と、担当ごとの役割・責任範囲を示す。工程の順序と受け渡しはTo-Be図で示す。 |
| [To-Be](references/to-be.md) | 目指す状態を短く示し、続けて目指す流れを図にする。受け渡しが重要なら、担当をレーン名で示し、方針の判断に関わる分岐や戻りを図に残す。前提が違うケースは、方針判断に必要な違いだけ示し、流れを比べないと判断できない場合に別図を使う。 |
| [検討事項](references/decisions.md) | 対象範囲や目指す状態など、基本方針を決めるためにステークホルダーが答える問いだけを載せる。「完了条件」「検討事項」「課題」「持ち越し事項」を一つの表にまとめる。完了条件を満たし、検討事項が解消されたことを確認してから次工程へ進む。 |

## 資料にする

[Markdownのひな形](assets/concept-template.md)で考えを整理し、[引き継ぎ支援の記載例](references/handover-example.md)を粒度の参考にする。
打ち合わせ用の成果物は、[Excelの作り方](references/excel-layout.md)に従って作る。
作成者用の記入欄を左の印刷範囲内に、提示側の図・記載例を対応する位置の右側に置く。
見直しでは、図から会話を始められるか、今日決める問いが分かるか、同じ説明が繰り返されていないかを確認する。
