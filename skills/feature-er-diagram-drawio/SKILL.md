# 機能別ER図の作成・更新

処理フロー図などの1まとまりが使うテーブルだけを載せ、現行DDLから何を変えるかを示すER図を作る。  
決まりの本体は [references/rules.md](references/rules.md) にある。  
作業の前に必ず読むこと。  

**見た目はスクリプトで決め、手で描かない。**  
人と Claude が決めるのは中身（どのテーブル・列・線・注記を載せるか）だけで、それを JSON（spec）に書く。  
手で描くと、色・書式・注記の色が図ごとに揺れるためである。  

## 0. 設定ファイルを確かめる（毎回、最初に行う）

設定ファイルは `.agents/config/feature-er-diagram-drawio/settings.md`（プロジェクトルート直下）である。  
**スキル自身のディレクトリの中には、設定も作業ファイルも作らない。**（スキルを更新すると、上書きされるため）  

| 状態 | すること |
|---|---|
| 設定ファイルが無い | [references/interview.md](references/interview.md) に従う。プロジェクトから読み取れるもの（まず、ハーネス：`AGENTS.md`・README・規約・設計の手順書・`docs/`・DDL の置き場の説明）は、自分で調べて確定する。ハーネスと外れている点と、ハーネスに無い点だけを質問する。結果は [assets/settings.template.md](assets/settings.template.md) の形で保存し、内容をユーザーに見せて、確認を取る。そのあと、手順1へ進む |
| 設定ファイルがある | 質問せずに、その内容を使う。下の「文書の変更の確認」を行ってから、手順1へ進む |
| 「設定を見直したい」と言われた | interview.md の質問をやり直し、変わった項目だけを、設定ファイルに反映する |

- 設定ファイルは、チームで共有する（Git に入れる）ものである。  
  保存したら、Git に入れるかどうかを、ユーザーに確かめる。  
- 設定ファイルに書いてある内容と、実際のプロジェクトが食い違ったとき（DDL のフォルダが無い、図の置き場が無い、など）は、自分で直さずに、食い違いをユーザーに伝える。  
- 設定の「追加の項目」は、このあとの手順の該当する箇所で、必ず読み、従う。  

### 文書の変更の確認（設定ファイルがあるとき、毎回）

設定の「場所の表」にある文書を実際に読み、前回読んだ時点の最終更新（コミットID。リポジトリの外にある文書は、更新日時）と比べる。  

```bash
git log -1 --format=%h -- <文書のパス>   # 文書の最終更新のコミットID
```

- 変わっていた文書があるときは、「決まりが前回から変わっています：<文書名>」と、1行で知らせる。  
  質問はせずに、変わった内容で、このあとの手順を行う。  
- 文書が見つからないときは、どこに移ったかをユーザーに聞き、設定に反映する。  
- 実行が終わったら、読んだ時点の最終更新を、設定に書き戻す。  

### 設定の値の使い方

スクリプトは、設定ファイルを読まない。  
設定の「スクリプトに渡す値」を、この文書の手順で読み、コマンドの引数として渡す。  

| 設定の項目 | 渡す先 |
|---|---|
| DDLのフォルダ | `--ddl-dir`（「なし」なら、`--ddl-dir` を付けない） |
| ALTER ファイルの名前の形 | `--alter-file-pattern`（「なし」なら付けない） |
| 作業フォルダ | 下の `$W`（spec・drawio・png を置く場所） |
| drawio の実行ファイル | 手順7 |

## 使うもの

- このスキルのディレクトリ（以下 `$K`）。  
  例：Claude Code なら、プロジェクトの `.claude/skills/feature-er-diagram-drawio/`。  
- 作業フォルダ（以下 `$W`）：設定の値。既定は `.agents/state/feature-er-diagram-drawio/<件名>/`。  
  spec JSON・生成した drawio・確認用の PNG・DDL の下書きを置く。使い捨てで、Git に入れない。  
  `.gitignore` に `.agents/state/` が無ければ、追加するよう、ユーザーに案内する（自分では書き換えない）。  
- Python 3.12 以上（標準ライブラリだけで動く）。  
  Windows では、`py -X utf8 -B`（文字化けと `__pycache__` を避ける）。ほかの OS では、`python3 -B`。  
- 画像での確認に、drawio デスクトップ版（設定の値。無ければ、画像の確認は人に頼む）。  
- 下のコマンド例の `py -X utf8 -B` は、環境に合わせて読み替える。  

## 手順

### 1. 入力をそろえて読む

1. その機能の処理フロー図（あれば）を読む。  
   処理フロー図を描くスキル（例：`process-flow-diagram`）があるときは、その「既にある図を読む」に従う。  
   無ければ、図を開いて、ページごとに、読み書きするテーブルと、未決の点（T.B.D など）を書き出す。  
2. 設定の「載せるテーブルの出どころ」から、図に載せるテーブルを集める（既定：処理フロー図に出てくるテーブル）。  
   出どころが無い、または決まらないときは、ユーザーに聞く。  
   API 仕様などの連携仕様があれば、各 API が読み書きする列も確かめる。  
3. DDL があるときは、そのテーブルの今の列を確かめる（手順4のコマンドで一覧できる）。  
   DDL が無いときは、設計書（テーブル定義書など）で確かめる。  
4. 変えること（列の追加・変更・削除、テーブルの新規・廃止）が**決まっているか**を確かめる。  
   決まっていないものは、箱や列として描かず、T.B.D の枠（`kind: tbd`）に「何を確認したいのか」を書く。  
   決まったら、枠を消して中身（箱・列・線）か point の注記に反映する（rules.md の 7）。  

読む文書がリポジトリの外にあるときは、作業フォルダにコピーしてから読む。  

### 2. 既にある図をどうするかを決める

同じ名前の `ER図_<件名>.drawio`（設定のファイル名の形）が既にある場合は、作業フォルダにコピーして読み、何が変わるのかを先に整理する。  
そのうえで、次のどちらにするかを**ユーザーに確かめる**。  

| 進め方 | 向いているとき | 気をつけること |
| --- | --- | --- |
| spec を作って作り直す | 変更が大きい。手描きの図で、決まりから外れた書き方が多い。 | 配置もセルIDも丸ごと変わる。変更箇所一覧を作るときは、図の差分ではなく、テーブル・列の単位で書く。 |
| 手で直す | 変更が小さい（列を1つ足す程度）。合意済みの配置を崩したくない。 | 色・書式は rules.md と `styles.py` の値に合わせる。直したあと、手順6の検査（`--spec` なし）を通す。 |

### 3. ページの分け方を決める

処理フロー図のページのうち、使うテーブルの組み合わせが同じものを1ページにまとめる（rules.md の 2）。  
処理フロー図が無いときは、使うテーブルの組み合わせが同じ処理を、1ページにまとめる。  
ページの分け方は、作り始める前にユーザーに示して合意を取る。  

### 4. DDLから箱の下書きを作る

**DDL が無いプロジェクト（設定のDDLのフォルダが「なし」）では、この手順をとばし、手順5で箱を spec に直接書く。**  

```bash
py -X utf8 -B $K/scripts/ddl_entities.py --ddl-dir <DDLのフォルダ> --list
py -X utf8 -B $K/scripts/ddl_entities.py --ddl-dir <DDLのフォルダ> shop.order shop.customer
```

ALTER TABLE を置くファイルがあるプロジェクトでは、設定の ALTER ファイルの名前の形を、`--alter-file-pattern "<正規表現>"` で添える。  
添えないときは、DDL に ALTER TABLE があると、読めない文として止まる。  

1本目でテーブルの一覧、2本目で指定したテーブルの箱（`entities`）と、テーブルどうしの外部キー（`edges`）の下書きが出る。  
自分自身を参照する外部キーは、線にせず `self_references` に出る（注記に書く候補）。  
下書きはそのまま使わない。  

- その機能が読み書きしない列を消す（rules.md の 4.2）。  
- 論理名が長すぎる・説明文になっているもの（DDLのコメントの書き方による）は、短い名前に直す。  
- 変える列に★・✕を付け、`status` を直す。既存の列を直す★には「（変更：…）」か「← 今回変更」を添える（何を変えるかを意味の言葉で書く。型・NULL可否そのものはテーブル定義書に書く）。  
- 新規のテーブルは DDL に無いので、spec に直接書く。  

### 5. spec JSON を書く

書き方は [references/spec_format.md](references/spec_format.md)、例は [assets/example_spec.json](assets/example_spec.json)。  
spec は `$W/ER図_<件名>.spec.json` として置く。  
次に図を直すときの元になるためである。  
spec をチームで共有するかは、設定の「共有する spec JSON の置き場」に従う（手順8）。  

注記は次を必ず確かめる（rules.md の 7）。  

- 「この図に載せていないもの」（scope）は、各ページに必ず書く（無いと生成が止まる）。  
- 値を読むだけでFKの無い関係があれば、「値を読むだけでFKの無い関係」（readonly）に書く。線は引かない。  
- 処理フロー図との食い違いがあれば、point の注記に「差異（訂正）」として、どちらが正しいかを書く。  
- **決めた日・確認した日は、どこにも書かない。**  
  ER図は、いつ決めたかを示す図ではないためである（rules.md の 7）。  
  年・月・日のそろった日付を書くと、「時点」が続く基準日を除いて、生成も検査も止まる。  

### 6. 生成して検査する

```bash
py -X utf8 -B $K/scripts/build_feature_er.py $W/ER図_<件名>.spec.json --out $W/ER図_<件名>.drawio
py -X utf8 -B $K/scripts/validate_feature_er.py $W/ER図_<件名>.drawio --spec $W/ER図_<件名>.spec.json
py -X utf8 -B $K/scripts/validate_feature_er.py $W/ER図_<件名>.drawio --ddl-dir <DDLのフォルダ> --spec $W/ER図_<件名>.spec.json
```

3本目（`--ddl-dir` 付き）は、DDL があるときだけ行う（2本目と同じ検査に、DDLとの照合を足したもの）。  
ALTER TABLE を置くファイルがあるときは、`--alter-file-pattern "<正規表現>"` も添える。  
DDL が無いときは、2本目だけを行う。  

生成で出た警告と、検査のエラーは、0件になるまで直す。  
生成スクリプトの終了コードは、0＝警告なし、1＝エラー（図を作らない）、2＝警告あり（図は作る）。  
検査スクリプトの終了コードは、0＝エラーなし、1＝エラーあり。  
検査の警告は1件ずつ読み、直すか、直さない理由をユーザーに伝える。  

| 検査の指摘 | 種類 | 意味と直し方 |
| --- | --- | --- |
| 列がDDLに無い | エラー | 物理名の誤りか、★の付け忘れ。DDLを見て直す。 |
| テーブルがDDLに無い | エラー | 物理名の誤りか、新しく作るなら［新規］にする。 |
| ★だがDDLにある／［新規］だがDDLにある | 警告 | 追加がDDLへ反映済み。★を外して区分を見直すか、合意の記録として残すかをユーザーと決める。既存の列を直す★なら「（変更：…）」を添える。 |
| ✕だがDDLに無い／［廃止］だがDDLに無い | 警告 | 削除がDDLへ反映済み。同上。 |
| 線がテーブルの上を横切っている／線どうしが重なっている／ラベルが重なっている | 警告 | 箱の並べ方（`groups` の順）を変えるか、`exit`・`entry`・`points` で通り道を直す。 |
| 図形が重なっている | エラー | 注記・箱の `pos` を直すか、`pos` を外して自動配置に戻す。drawio 上で図全体を囲む四角を描いたときにも出る（その四角を消す）。 |
| 最背面に、文字の無い塗りの無い四角がある | エラー | 出力用の枠は置かない決まりである。spec から作り直す。drawio で手で直す図なら、その四角を消す。 |
| [DDL] … | エラー | DDLを読めなかった（読めない書式、ALTER TABLE の食い違いなど）。メッセージの指す行を直すか、ALTER ファイルの名前の形を渡す。DDLとの照合はされていない。 |
| [spec] … | エラー | 図の中身（テーブル・区分・列・線・注記の見出し）が spec と違う。drawio 上で中身を手で直したか（T.B.D の枠を消した、など）、spec が古い。どちらが正しいかを確かめて、spec に写して作り直す。座標・見た目・注記の本文は比べない。 |

検査の線の判定は、drawio の線の引き方を近似したものである。  
そのため、次の手順の画像の確認は省かない。  

### 7. 画像で確かめる

```bash
"<drawio の実行ファイル>" --export --format png --page-index 1 --output $W/p1.png $W/ER図_<件名>.drawio
```

全ページを書き出して目で確かめる（`--page-index` は1始まり）。  
見る点は、線が箱や文字に重なっていないか、ラベルが読めるか、凡例と中身が合っているか。  
drawio の実行ファイルが無いときは、そのことを報告し、人に drawio で開いて確かめてもらう。  

### 8. 置く

完成した図の置き場所と置くときの決まりは、設定の「図と spec の置き場」に従う。  
設定が「ユーザーに聞く」のときは、置く前に、置き場所と決まりをユーザーに聞く。  
プロジェクトの設計書の運用の文書があれば、置く前に読み、手順と決めごとを確かめる。  

次は、どのプロジェクトでも守る決まりである（プロジェクトの決まりが、さらに厳しいときは、それに従う）。  

1. 共有の置き場のファイルを、直接直さない。作業フォルダにコピーしてから直す。  
2. 置く前に、今のファイルを退避する（旧版を残す。退避先と名前の付け方は、プロジェクトの決まりに従う。無ければ、ユーザーに聞く）。  
3. 置く直前に、原本が作業中に人に直されていないかを確かめる（コピーしたときと、最終更新日時・ハッシュ値が変わっていないか）。  
4. 置いたあと、置き場のファイルの更新日時とハッシュ値が、作業フォルダの版と一致することを確かめる。  
5. 共有の置き場への書き込み（コピー・移動・フォルダ作成）は、毎回ユーザーに確かめてから行う。ファイルは削除しない。  
6. 変更箇所一覧を作る決まりがあれば、それに従う（無ければ、テーブル・列の単位で、変えた内容をユーザーに報告する）。  

spec JSON を共有の置き場に置くかどうかは、設定の「共有する spec JSON の置き場」に従う（「共有しない」なら置かない）。  

**共有の置き場に置くとき、機能ごとに1ファイルにまとめる決まりがあるとき**（設定の「共有の置き場で、機能ごとに1ファイルにまとめる決まり」が「あり」のとき）は、次のようにまとめる。  
作業フォルダで項目ごとに分かれている図を1つの機能にまとめる。  

1. 項目ごとの spec の `entities` を1つに合わせる（同じテーブルの箱は1つにし、ページで載せる列や区分が違うときは `overrides` を使う。例：画面表示のページでは［変更］、CSV出力のページでは変更なし）。  
2. `pages` を、処理フロー図のページの順に並べる（ページ番号①②…は並べた順に付く）。  
3. 変更点の表（`changes`）は、合わせた全ページの変更を1つの表にする（表は最後のページに1枚だけ）。  
4. 合わせた spec から作り直し、手順6・7を通す。  

## drawio で人が手直ししたとき

`build_feature_er.py` は図を丸ごと作り直すため、drawio 上で動かした座標は消える。  

- 残したい手直しは、spec の `pos`（箱・注記）や `points`（線）に写してから作り直す。  
- 中身（列・テーブル）を drawio 上で直した場合は、`--spec` の検査が食い違いとして知らせる。spec に写してから作り直す。  
- 作り直さずに手直しした図を使い続けるときも、`validate_feature_er.py` は通す（グループにした図形も検査する）。  

## 見た目・決まりを変えたいとき

| 変えたいこと | 直す場所 |
| --- | --- |
| 色・書式・線の種類 | [scripts/styles.py](scripts/styles.py) と [references/rules.md](references/rules.md) |
| 配置 | [scripts/build_feature_er.py](scripts/build_feature_er.py) |
| 線の通り道 | [scripts/router.py](scripts/router.py)（経路の探索）、[scripts/geometry.py](scripts/geometry.py)（生成と検査で共通の、経路とラベルの見積もり） |
| 検査の内容 | [scripts/validate_feature_er.py](scripts/validate_feature_er.py) |
| DDLの読み取り | [scripts/parse_ddl.py](scripts/parse_ddl.py)（DDLの書式の前提は docstring にある。`CREATE TABLE IF NOT EXISTS スキーマ.テーブル (...)` の形だけを読み、`DROP TABLE` などの読めない書き方は、黙って読み飛ばさずにエラーで止める（文字列で組み立てた文は見つけられない）。`ALTER TABLE` は、`--alter-file-pattern` に合う名前のファイル（作り直さない DB を追いつかせるためのもの）にだけ置けて、図には使わず、足す列・外部キー・変える列が、型・NOT NULL・参照先・ON DELETE まで CREATE と同じであることを確かめる。パターンを渡さないときは、すべての `ALTER TABLE` をエラーで止める。[scripts/ddl_entities.py](scripts/ddl_entities.py) が戻り値の形に頼っている） |

**スキルのファイルを直すのは、スキルを保守する人だけである。** 使うだけの人は、直さずに、保守する人へ伝える。  
**決まりを変えたら、rules.md も同じ変更で直すこと。**  
図と文書が食い違うと、読み手はどちらが正しいか判断できない。  

## やらないこと

- 設定ファイルと作業ファイルを、スキルのディレクトリの中に作ること。  
- 見た目を手で描くこと（色・書式の揺れを防ぐため、spec から作る）。  
- システム全体のER図、業務向けの概要ER図を作ること（このスキルは、機能ごとの設計用の図だけを作る）。  
- 決まっていない変更を、箱や列として描くこと（T.B.D の枠に書く）。  
- 共有の置き場への書き込みを、確認なしに行うこと。ファイルを削除すること。  
- DDL を、自分で直すこと（図は DDL を読むだけである）。
