# 機能別ER図の決まり

この文書は、機能別ER図の見た目と書き方の決まりである。  
配色・書式の値そのものは `scripts/styles.py` にある。  
この文書と `styles.py` は、同じ変更の中で直すこと。  

プロジェクトが、この文書と違う決まりを持っているとき（ハーネスの設計規約など）は、プロジェクトの決まりを優先する。  
その場合は、スキルの設定（`settings.md`）の「追加の項目」に、違う点を書く。  

## 1. この図は何のための図か

**ある機能（処理フロー図などの1まとまり）が使うテーブルだけを載せ、現行DDLから何を変えるかを示す、設計用の図である。**  

- システム全体のER図ではない。  
  テーブル・列の全量の正は DDL である。  
  機能別ER図は、それに加えて、これから変える列・新しく作るテーブル・廃止するテーブルを描く。  
- 読み手は、その機能を実装する開発者と、設計を確認する人である。  
  処理フロー図・API仕様書と並べて読み、「この機能を作るには、どのテーブルのどの列を読み書きし、DDLをどう直すか」を合意するのに使う。  
- 列の型・桁・NULL可否は載せない。  
  それはテーブル定義書が持つ。  

## 2. ファイルとページ

| 項目 | 決まり |
| --- | --- |
| ファイル名 | `ER図_<件名>.drawio`（設定でファイル名の形を決めているときは、それに従う）。件名は、同じ機能の処理フロー図などの件名にそろえる。 |
| 載せるテーブル | 設定の「載せるテーブルの出どころ」から集める（既定：処理フロー図に出てくるテーブル）。 |
| ページの単位 | 処理フロー図のページのうち、**使うテーブルの組み合わせが同じもの**を1ページにまとめる。<br/>例：注文の一覧・詳細・取消（処理フロー①〜③）→ ER図①「注文の参照」、CSV出力（処理フロー④）→ ER図②。 |
| ページ名 | `①使うテーブル（<主題>）` |
| ページの見出し | `① <主題>で使うテーブル`（fontSize 22、太字、#263238） |
| 変更点の表のページ | 変更のあるテーブルが多いとき（目安は4つ以上）だけ、最後のページに `凡例・現行DDLからの変更点` を足す。 |
| 用紙 | 背景は白、グリッドは消す。用紙の大きさは中身に合わせる。 |
| 出力用の枠 | 置かない（図全体を囲む四角は描かない）。用紙の大きさは、全図形の右端・下端から 80px 以上の余白を取り、100px 単位に切り上げて決める。 |

## 3. ページの上部（見出し・説明・凡例）

- 見出しの下に説明を置く（fontSize 13、#37474F）。  
  説明には、次の順で書く。  
  1. 箱の並べ方（例：「左が商品マスタ、右が注文を受ける側のテーブル」）。  
  2. この図を読む前提（例：「サービス間に外部キーは張らない」）。  
  3. 決まり文句「箱の色は現行DDLからの変更の有無を示す。★の付いた列が追加・変更である。凡例はページ右上。」  
     生成スクリプトが、使っている記号に合わせて自動で付ける。  
- 凡例はページ右上に置く。  
  - 見本の箱（240×30）は、そのページで使っている区分だけを並べる。  
    「変更なし」は常に置く。  
  - 見本の下に、記号と線の読み方を書く（★・✕・PK/FK/U・実線と点線・読み取りのみの関係・廃止テーブルの扱い）。  
    そのページで使っているものだけを書く。  

## 4. テーブルの箱

### 4.1 色と見出し

| 区分 | 塗り | 枠 | 見出しの接頭辞 | 使いどころ |
| --- | --- | --- | --- | --- |
| 変更なし | #FFFFFF | #8C8C8C | なし | 現行DDLのまま使う。 |
| 変更 | #FFF7E6 | #E08A1E | ［変更］ | 列・制約を足す・消す・直す。 |
| 新規 | #E8F5E9 | #2E7D32 | ［新規］ | テーブルを新しく作る。 |
| 廃止 | #F5F5F5 | #BDBDBD（点線） | ［廃止］ | テーブルごと消す。文字は #9E9E9E。 |

- 枠線は 2px。  
- 見出しは2行で、1行目が論理名、2行目が `（スキーマ.物理名）`。  
  見出しの背景は #EFEFEF（廃止は #EAEAEA）。  
- 箱の中は3段に分け、段の間に枠と同じ色の細い線を引く。  
  1段目が見出し、2段目が主キー、3段目がそのほかの列。  

### 4.2 列の書き方

1行に1列を、`論理名（物理名）` で書く。  
論理名は DDL の `COMMENT ON COLUMN` から取る（`scripts/ddl_entities.py` が下書きを出す）。  
DDL が無いプロジェクトでは、設計書の項目名から取る。  

| 書き方 | 意味 |
| --- | --- |
| `… PK` | 主キー。2段目に置く。 |
| `… FK` | 外部キー。 |
| `… U` | 単独の一意制約。 |
| `U（a, b）` | 複数列の一意制約。列の並びの最後に置く。 |
| `… 値のみ` / `…（値のみ保持）` | 別テーブルの値を持つが、FKは張らない列。 |
| `…（キャッシュ）` | 別テーブルの値を写して持つ列。 |
| `… good／bad` | 取りうる値（列挙）を添える。 |
| `★ …` | 追加する列や制約。`← 今回追加` を添えてもよい。**［変更］の箱にだけ付ける。** |
| `★ …（変更：…）` / `★ … ← 今回変更` | 既存の列を直す。何を変えるのかを、意味の言葉で短く書く。例：`★ 合計金額（total_amount）（変更：キャンセル済みの行は空にする）`。型・桁・NULL可否そのものはテーブル定義書に書く（1 のとおり、この図には載せない）。 |
| `✕ …` | 削除する列。**［変更］の箱にだけ付ける。** |
| `…` / `ほか（この機能では参照のみ）` | この機能に関係しない列を省いたことを示す。 |

- **載せる列は、その機能が読み書きする列と、PK・FK・一意制約に関わる列だけにする。**  
  全列を載せると、どの列がこの機能に関係するのかが読めなくなる。  
- 監査列（created_at など）は、その機能で意味を持つとき（作成日時を画面に出すなど）だけ載せる。  
- ［新規］の箱では★を付けない（全部が新しいため）。  

## 5. 箱の並べ方

- **左から右へ、土台のマスタ → 業務のデータ → 集計・分析の順に並べる**（プロジェクトに並べ方の決まりがあれば、それに従う）。  
  スキーマ（またはテーブルの役割）ごとに1列（columns）とし、列の中は上ほど土台のマスタ、下ほど末端のトランザクションにする。  
- グループごとに区分見出しを付ける（fontSize 14、太字、#546E7A）。  
  例：「商品（catalog）」「注文（shop）」。  
- 1つのグループの箱が多く、1列では縦に長くなりすぎるときは、そのグループを2列に分けてよい（2列目の見出しは省く）。  
- 箱が少なく、上下の段で見せたほうが読みやすいときは、段（rows）に分けて並べてもよい。  
  そのときも、上の段から土台のマスタ → 業務のデータ → 集計・分析の順にする。  
- どちらの並べ方でも、出来上がりを必ず画像で確かめる。  
- 廃止するテーブルは、図の下部の帯「削除予定のテーブル」にまとめ、線を引かない。  
- 注記は、箱の下にまとめて置く。  

## 6. 線

**線は、親（参照される側）から子（FKを持つ側）へ引く。**  
親の側が「1」、子の側が「0以上の多」の記号になる。  

| 種類 | 線 | 記号 | ラベル |
| --- | --- | --- | --- |
| 外部キー | 灰（#5A6470）の実線 | 1 → 0..多 | 必要なときだけ（「評価者」「依頼者」などの役割、`ON DELETE CASCADE` など） |
| 外部キー＋一意制約（1対0..1） | 実線 | 1 → 0か1 | `1:0..1（UNIQUE）`。DDLの外部キー＋一意制約は、子の行が無いこともあるので、ふつうはこれを使う。 |
| 1対1（子が必ずある） | 実線 | 1 → 1 | `1:1（UNIQUE）`。業務上、親を作るときに子も必ず作る場合だけ使う。 |
| 値だけを持つ関係（FKなし） | 点線 | 1 → 0..多 | `値のみ保持` |
| 簡略化した関係 | 点線 | 1 → 0..多 | 実際の関係を書く（例：`簡略化。実際は注文明細経由の複合FK`） |

- 線は直角に折れる形（orthogonal）で、角を丸める。  
- **読み取りだけでFKの無い関係には、線を引かない。**  
  かわりに注記「値を読むだけでFKの無い関係」に一覧で書く。  
  線が無いことを「関係が無い」と読まれないためである。  
- 線が箱の上を横切らないようにする。  
  生成スクリプトは、箱を障害物として、曲がる回数が少なくほかの線と重ならない最短の経路を探す（`scripts/router.py`）。  

## 7. 注記

注記の種類と色は次のとおり。  
見出し（太字）を1行目に書き、2行目から本文を書く。  
本文の箇条書きは `・` で始める。  

| 種類 | 色 | 書くこと | 要否 |
| --- | --- | --- | --- |
| point（要点） | 橙（#FFF3E0 / #FB8C00） | 現行DDLからの変更点、DBの制約で表せない決まりごと、処理フロー図との違い（訂正）、スナップショットの持ち方など設計の要点 | 変更があれば書く |
| readonly（読み取りのみ） | 青（#F3F7FB / #90CAF9）、文字は濃い灰（#37474F） | 値を読むだけでFKの無い関係の一覧 | 該当があれば必ず書く |
| scope（載せていないもの） | 青（#F3F7FB / #90CAF9）、文字は青（#1565C0） | この図に載せていないテーブルと、載せない理由 | **必ず書く** |
| key（読み方の前提） | 黄（#FFFDE7 / #FBC02D） | 図全体を読む前に知っておいてほしいこと（区分の特定のしかたなど） | 必要なときだけ |
| tbd（確認事項） | 赤い破線の枠（#FFEBEE / #C62828） | まだ決まっていないこと。見出しは「T.B.D　〇〇に確認」とし、何を確認したいのかを箇条書きにする | 決まっていないことがあれば書く |

- point の注記の書き方の例：「判定した時点の区分名を保存し、後から設定が変わっても過去の表示は変えない」のような、テーブルの持ち方に関する補足。  
- T.B.D の枠は、処理フロー図の T.B.D と同じ書式にする（処理フロー図が無いときは、この書式のままでよい）。  
  AIが書いた枠には、末尾に「※ この T.B.D はAIの自動生成です。…」の定型文を付ける（生成スクリプトが自動で付ける。人が書いた枠は `ai: false` で外す）。  
  **処理フロー図と違い、決まったら枠ごと消してよい**（ER図は今のテーブル構成だけを示すため）。  
  決まった内容は、図の中身（箱・列・線）か point の注記に反映する。  
- 「この図に載せていないもの」には、**処理フロー図などに出てくるのにこの図に無いテーブル**と、**関係しそうに見えるのに使わないテーブル**を、理由と一緒に書く。  
  テーブルではないもの（オブジェクトストレージ・キュー）は、処理フロー図を参照するよう書く。  
- 処理フロー図とこの図で食い違いがあるときは、point の注記「<処理フロー図の名前>（<ページ>）との差異（訂正）」に、どちらが正しいかを書く。  
- **決めた日・確認した日を書かない。**  
  主題・説明・区分見出し・注記・線のラベル・箱・変更点の表のどこにも、「（YYYY-MM-DD 決定）」「（YYYY/MM/DD）」「M月D日に合意」のような日付を書かない。  
  ER図は、いつ決めたかを示す図ではないからである。  
  いつ決めたかは、変更箇所一覧・課題管理票・処理フロー図の T.B.D の回答に残る。  
- 生成スクリプトと検査スクリプトは、図の全セルを同じ関数（`styles.py` の `find_dated_decision`）で調べ、次のものを見つけるとエラーにする。  
  - 年・月・日のそろった日付（`YYYY-MM-DD`・`YYYY/MM/DD`・`YYYY.MM.DD`・`YYYY年M月D日` など）。後ろの語に関係なく、すべて拾う。  
  - 年の無い「M月D日」のうち、後ろ8文字以内に「決定・決め・決ま・合意・了承・承認」が続くもの。  
- ただし、すぐ後ろに「時点」が続く日付は、基準日として書ける（例：変更点の表の「（YYYY-MM-DD 時点）」。8）。  
  年の無い「M月D日」の決まりごとや期限（「毎年4月1日に区分を変える」「12月31日までに確認する」）も書ける。  

## 8. 変更点の表（最後のページ）

| 列 | 書くこと |
| --- | --- |
| ファイル / テーブル | DDLのファイル名と、`スキーマ.物理名`。新規テーブルはファイル名を空けてよい。 |
| 区分 | 変更・新規・廃止・変更なし・対象外。行の塗りは箱の色と同じにする。 |
| 変更内容 | 何を足す・消す・直すか。**理由も1文で添える。** |

表の上に、基準にしたDDLの範囲（例：「対象は DDL フォルダの現行ファイルである（YYYY-MM-DD 時点）。」）を書く。  
DDL が無いプロジェクトでは、基準にした設計書を書く。  

同じテーブルでも、ページによって区分が違ってよい（例：注文の参照のページでは［変更］、CSV出力のページではその変更に関係しないので変更なし）。  
表の区分は、そのテーブルを変えるページの区分に合わせる。  

## 9. DDLとの関係

DDL がある場合（検査に `--ddl-dir` を渡す場合）の決まりである。  

- 「変更なし」「変更」「廃止」の箱は、現行DDLにあるテーブルである。  
  ★の付かない列は、現行DDLにある列である。  
  ✕の列も、現行DDLにある列である。  
- 「新規」の箱は、現行DDLにまだ無いテーブルである。  
- **変更がDDLに反映されたら、図の★・✕・［変更］［新規］［廃止］は役目を終える。**  
  検査スクリプト（`--ddl-dir` 付き）は、追加の反映（★だがDDLにある、新規だがDDLにある）も、
  削除の反映（✕だがDDLに無い、廃止だがDDLに無い）も、警告として知らせる。  
  そのまま残すか（合意の記録として）、変更なしに直すかは、その都度ユーザーと決める。  
- 一方、★も✕も付かない列がDDLに無いことと、変更なし・変更の箱のテーブルがDDLに無いことは、エラーである。  
  物理名の誤りか、★の付け忘れのどちらかだからである。  
- 自分自身を参照する外部キー（例：`shop.category.parent_category_id`）は線にしない。  
  線にすると箱を貫いて描かれるため、point の注記に書く。  
- DDL が無いプロジェクトでは、DDLとの照合はしない（`--ddl-dir` を渡さない）。  
  このとき、列の物理名や★・✕の正しさは、設計書との突き合わせで人が確かめる。  

## 判断が分かれる点と、このスキルでの決め

| 判断が分かれる点 | このスキルでの決め | 理由 |
| --- | --- | --- |
| ページ名 | `①使うテーブル（<主題>）` | どの処理のページかがページ名だけで分かるため。 |
| 「載せていないもの」の色 | 青 | 「読み取りのみ」の青と並べても、文字の色で見分けられるため。 |
| 並べ方 | 左から右（columns）を既定にする | 土台から業務のデータへ、流れの向きに読めるため。 |
| 決まっていないこと | 赤い破線の枠（tbd）で書き、決まったら消す | ER図は今のテーブル構成だけを示すため。 |
| 読み取りのみの注記の文字色 | #37474F | 「載せていないもの」（青）と見分けるため。 |
| ✕の付いた列のある箱の色 | ✕・★は［変更］の箱にだけ付ける | 箱の色と中身が食い違うと、変更があるのかどうか読み手が判断できないため。 |
| 箱の幅と見出しの帯 | 箱に `overflow=fill` を付ける | 幅を詰めなくても、帯と区切り線が右端まで届くようにするため。 |
| 区分見出しと線の重なり | 見出しを線より手前に描き、白い背景を付ける | 見出しの文字が読めなくならないようにするため。 |
| 区分見出しの有無 | 付ける（`groups` の `label`。付けないこともできる） | どのスキーマの箱かが、色の無い箱でも分かるため。 |
| 説明の決まり文句の位置 | 説明の最後の行 | 図ごとの説明（並べ方・前提）を先に読ませ、記号の読み方は凡例と並べて後に置くため。 |
| 1対1の線の記号 | 2種類を使い分ける（`zero_to_one` と `one_to_one`） | DDLの外部キー＋一意制約は「0か1件」であり、「1」だと子が必ずあると読めてしまうため。 |
| ★の意味 | 追加は `★ …`、変更は `★ …（変更：…）` か `★ … ← 今回変更` | 追加か変更かで、DDLとの照らし合わせ方が違うため（追加は DDL に無いはず、変更は DDL にあるはず）。 |
