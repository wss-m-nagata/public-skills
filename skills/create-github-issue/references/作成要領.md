# 作成要領：Issue の書き方、進捗コメント、チェックの整理

Issue の本文の書き方と、作成後の進捗コメント・チェックの整理・引き継ぎの書き方である。  
ひな形は [ひな形.md](ひな形.md) にある。  
Issue フォームの項目（`get_issue_template_fields.py <種別>` の `fields`）が、本文の骨格になる。  
フォームに無い節（作業項目・受け入れ条件・決定事項・未決事項）は、手書きの節として、フォームの項目の後ろに足す。  

## 1. 作る前に読むもの

設定の「読むもの」の表にある場所を、作る前に読む。  
既定は、次の3つである。  

| 読むもの | 何を取るか |
|---|---|
| 親 Issue | 親 Issue の番号、子 Issue の分け方、すでに決まっていること |
| `AGENTS.md` | Issue・ブランチ・コミットに関する決まり、書き方の決まり |
| 既存の同種の Issue | 書き方・構成の見本。同じ構成にそろえる |
| 設定の「読むもの」に足した場所 | 設定に書いた「何を取るか」 |

- 読めないものがあるときは、作業を止めて、ユーザーに伝える。  
- 設定の「追加の項目」に書いてあることは、本文を書くときに、必ず確かめる。  

## 2. 各節の書き方

| 節 | 書き方 |
|---|---|
| 背景・目的 | なぜ必要か、何をするかを書く。親 Issue があれば、その番号を書く |
| 対象 | 何が対象か（機能・画面・ファイル・文書など）を書く。置き場所があれば、パスまで書く |
| 更新・追加内容 | 何をどう変えるか、何を足すかを書く。表で示せるものは表にする |
| 決定事項 | 決まったことを、日付を付けて書く。理由が要るものは、1〜2文で添える |
| 未決事項 | まだ決まっていないことだけを、書く。決まったら、決定事項へ移して、未決事項から消す |
| 作業項目 | 手書きの節（フォームに無いとき）。チェックボックスで書き、作業の分類ごとにまとめる |
| 受け入れ条件 | 終わったかを確かめられる形で、条件を書く。作業項目のうち、確かめられるものを使う |
| 補足・関連 | 親 Issue、関連する Issue、読んだ資料の場所。<br/>最後に、作成したセッションを「作成したセッション: Claude Code `<ID>`（`claude --resume <ID>` で開ける）」の形で書く。ID は、環境変数 `CLAUDE_CODE_SESSION_ID` から取る。別の AI が、背景や不明点をそのセッションのログで確かめられるようにするためである。Claude Code 以外で作るときは書かない |

- 種別（bug・feature・docs など）によって、使わない節がある。  
  テンプレートに無い節は、必要なときだけ足す。  
- 未決事項は、決まっていないことだけを書く。  
  推測で決めた内容を、決定事項に書かない。  

## 3. 作業項目

### 3.1. 分け方

作業の分類（例：方針の決定・調整、実装・試験、文書、報告）ごとに、チェックボックスでまとめる。  
作業の順に並べる。  

```markdown
**<分類名>**

- [ ] <作業>
```

### 3.2. 入れる項目の考え方

- 終わったかを、根拠で確かめられる粒度で書く（ファイルがある、テストが通る、など）。  
- Issue の担当でない作業は、書かない。  
  ほかの担当に頼む作業は、「<担当>に依頼する」とだけ書く。  
- 決まっていないことは、作業項目にせず、未決事項に書く。  

## 4. 書き方の決まり

- 文体は、プロジェクトの決まり（`AGENTS.md`）に従う。決まりが無ければ、です・ます調で書き、1文ごとに改行する。  
- ファイル名は省略しない。シート名・セル・行まで書けるときは書く。  
- ID だけで書かず、名称を添える。例：<名称>（<ID>）。  
- 日付は `YYYY-MM-DD` で書く。  
- 「今」「最近」などの相対的な言い方は、日付を添える。  
- ラベルは、設定の「ラベルの扱い」に従う（既定は、指定しない）。  

## 5. 親 Issue とのつなぎ方

子 Issue は、本文に「親 Issue：#<番号>」を書いたうえで、GitHub のサブ Issue として紐づける。  

1. 子 Issue の内部 ID（`id`。Issue の番号とは別の値）を取る。  
   `gh api repos/<owner>/<repo>/issues/<子 Issue の番号> --jq .id`
2. 親 Issue に、サブ Issue として追加する。  
   `gh api -X POST repos/<owner>/<repo>/issues/<親 Issue の番号>/sub_issues -F sub_issue_id=<1. で取った値>`
3. 紐づいたことを確かめる。  
   `gh api repos/<owner>/<repo>/issues/<親 Issue の番号>/sub_issues --jq '.[].number'`

## 6. 進捗コメントと、チェックの整理

### 6.1. 進捗コメントを書くタイミング

- ユーザーが「コミットする」と言ったとき、または「コミットメッセージをください」と言ったときに書く。  
- それ以外のタイミング（作業の区切りなど）では、書かない。  
- コミットは、ユーザーが行う。  
- 投稿するかどうかは、設定の「進捗コメントの扱い」に従う。  
  既定は、投稿する文面をユーザーに見せ、確認を取ってから投稿する。  

### 6.2. 進捗コメントの書き方

- 見出しは `## <YYYY-MM-DD> の作業（<まとまりの名前>）` とする。  
- 前回の進捗コメントのあとに行ったことを、分類（実装・試験・文書など）ごとに、箇条書きで書く。  
- 何をしたかと、どこに置いたか（ファイル名）を書く。  
- 次にやることや、残っていることがあれば、最後に書く。  
- ユーザーが文面を口述したときは、その言葉のまま書く。  
  言い換えたり、注意書きを足したりしない。  
  正確さに懸念があるときは、投稿前に1行だけ伝える。  
- 投稿は、本文を `.agents/state/create-github-issue/` の一時ファイルに書き、`gh issue comment <番号> --body-file <ファイル>` で行う。  

### 6.3. チェックの整理（できるときに）

進捗コメントを書くときに、Issue 本文のチェックも整理できるなら、一緒に行う。  

- 根拠を確かめた項目だけに、チェックを付ける（コマンドの結果・テストの結果・ファイルの有無など）。  
- 「チェックが付いているものは、終わった作業です（<YYYY-MM-DD>時点）」の日付を、更新する。  
- 途中まで終わった項目は、チェックを付けず、括弧で「どこまで終わったか・何が残っているか」を書く。  
- 作業の途中で増えた作業は、作業項目に足して記録する。  
- 本文は、`gh issue view <番号> --json body --jq .body` で取り、直して `gh issue edit <番号> --body-file <ファイル>` で戻す。  
  本文の改行が CRLF のことがあるため、LF にそろえて直し、元の改行に戻して書く。  
  直す前と後の差分を見て、意図した箇所だけが変わっていることを確かめる。  

### 6.4. 終わったときと、ほかの Issue へ引き継ぐとき

- すべて終わったら、完了のコメントを書く（分類の順に、やったこと・残ったこと・後続へ引き継ぐこと）。  
- この Issue でやり切れないことを、ほかの Issue へ引き継ぐときは、次の両方を行う。  
  - 元の Issue：その項目にチェックを付け、括弧で「残りは #<番号> で対応する」と書く。  
  - 引き継ぎ先の Issue：「#<元の番号> から引き継ぐ宿題」の節を作って内容を書き、作業項目にも足す。  
- 投稿済みのコメントを直すときは、新しく投稿せず、`gh api -X PATCH repos/<owner>/<repo>/issues/comments/<コメント ID> -f body=@<ファイル>` で、同じコメントを編集する。  
- 引き継ぎ元から消す項目（別の Issue で終わっているものなど）は、本文から消す。  
  消す前に、ユーザーに確かめる。  
- Issue のクローズは、ユーザーが行う。  
  クローズの前に、チェックの付いていない項目が残っていないことを確かめる。
