# 設定のための質問（初回だけ）

設定ファイル `.agents/config/create-github-issue/settings.md` が無いときに、1回だけ、この手順を行う。  
結果は、`assets/settings.template.md` の形で保存する。  
次回からは、質問せずに、保存した設定を使う（規約の中身は、毎回、設定に書いた場所から読む）。  

**方針：プロジェクトから読み取れるものは、自分で読んで確定する。聞くのは、読み取れないものだけにする。**  
**既定は、そのプロジェクトのハーネス（`AGENTS.md`、規約・ブランチ規約などの文書、手順書、`.github/ISSUE_TEMPLATE/`、`.github/workflows/`）である。まずハーネスを見に行き、ハーネスと外れている点・ハーネスに無い点だけを聞く。**  
**設定に書くのは、規約の「場所」と、ハーネスに無い決めごとだけである。規約の中身は、写さない。**  

## 手順1　先に読んで確定するもの

質問の前に、次を調べて、設定に書く内容を確定する。  
確定できたものは、質問しない（結果だけを伝える）。  

| 確定するもの | 探す場所の例 |
|---|---|
| 種別の一覧 | `python scripts/get_issue_template_fields.py --list` の出力（`.github/ISSUE_TEMPLATE/` のテンプレート） |
| 種別ごとの、タイトル接頭辞 | テンプレートの `title`、`AGENTS.md`・規約 |
| 種別ごとの、ブランチ接頭辞 | ブランチ・コミットの規約、`AGENTS.md`、`CONTRIBUTING.md`、README。無ければ、`--list` の `suggested_branch_prefix` |
| ブランチ名の形式 | 同上（例：`<接頭辞>#<番号>-<スラッグ>`） |
| 起点ブランチの規則と、既定の起点 | ブランチ・コミットの規約、`AGENTS.md`、`git branch -a`、`.github/workflows/` の対象ブランチ |
| ラベルの付け方 | `.github/workflows/` のラベル付けの定義、テンプレートの `labels`、規約 |
| 作る前に読む文書 | `AGENTS.md`・README に書かれた資料の場所、`docs/` の Issue・ブランチに関する規約 |

- 読んでも見つからなかったものは、「このプロジェクトには無い」として、設定に書く。  
- 読んだ結果が複数ある（規約とテンプレートで接頭辞が違う、など）ときだけ、どれかを聞く。  
- `gh` コマンドが使えるか（`gh auth status`）と、PyYAML が入っているか（`python -c "import yaml"`）も確かめる。  
  使えないときは、導入が要ることを伝える。  

## 手順2　読み取れないときだけ聞くこと

| # | 質問 | 既定（答えが無いとき） |
|---|---|---|
| 1 | 種別ごとのブランチ接頭辞は何か（決まりが文書に無いとき） | bug・fix・不具合を含む種別は `fix/`、それ以外は `feature/` |
| 2 | ブランチを切らない種別はあるか（設計書を別の場所に置くものなど） | なし（すべて切る） |
| 3 | 起点にするブランチの規則は何か（決まりが文書に無いとき） | `^(main\|master\|develop\|development)$` に合うブランチ |
| 4 | 規則に合うブランチが無いときの、既定の起点は何か | 取り込み先の HEAD が指すブランチ |

## 手順3　読むもの（プロジェクト固有のものを聞く）

Issue を作る前に読むものを、設定の「読むもの」の表に書く。  
既定は、次の3つである。  

- 親 Issue（あれば）
- `AGENTS.md`
- 既存の同種の Issue

次のように聞く。  

> Issue を作る前に必ず読む、このプロジェクト固有のものはありますか。
> 例：設計書の置き場、画面や API の仕様書、スケジュール表、規約の文書。
> あれば、場所と「何を取るか」を教えてください。

- 答えは、「読むもの」の表に、1行ずつ足す。  
- そのうえで、**「他に追加が必要な項目はありますか」を必ず聞く。**  

## 手順4　既定を示して、差分だけ聞くこと

次は、既定を示したうえで、「変えたい点はありますか」と1問で聞く。  
変えると答えたものだけを、設定ファイルに書く。  

| 項目 | 既定 |
|---|---|
| 進捗コメントの扱い | 投稿する文面をユーザーに見せ、確認を取ってから投稿する |
| ラベルの扱い | ラベルは指定しない（付与は、別の自動化やユーザーに任せる） |

## 手順5　追加の項目を聞くこと

最後に、必ず、次を聞く。  

> ここまでで足りない項目はありますか。
> このプロジェクトに固有の決まり（例：Issue 本文に必ず書くこと、作成前に必ず確かめること）があれば、教えてください。

- 追加で出たものは、設定ファイルの「追加の項目」に、そのまま書く。  
- 追加の項目は、手順（SKILL.md）の該当する箇所で、必ず読み、従う。  

## 手順6　保存して確認を取る

1. `.agents/config/create-github-issue/settings.md` を作る（ディレクトリが無ければ作る）。  
2. 書いた内容を、ユーザーに見せて、確認を取る。  
   読んで確定した項目は、読んだ場所も添える。  
3. Git に入れるかどうかを、ユーザーに確かめる（チームで共有するため、入れることをお勧めする）。  
4. 作業用ファイルの置き場 `.agents/state/create-github-issue/` は、Git に入れない。  
   `.gitignore` に `.agents/state/` を書くことを、ユーザーに案内する（書くかどうかはユーザーが決める）。
