# create-github-issue

GitHub の Issue の作成から、作業用ブランチの準備、作成後の進捗コメント・チェックの整理・引き継ぎまでを、一貫して行うスキル。  

## 目的

Issue の作成とブランチの作成は、手順を型にしないと、次のようなミスが起きやすい。  

- テンプレートの必須項目が抜けた Issue 本文になる。  
- Issue 番号を含む、決まった形式のブランチ名にならない。  
- 誤ったブランチから、作業ブランチを切ってしまう。  

このスキルは、種別（テンプレート）の選択、内容のヒアリング、起点ブランチの決定、ブランチ名の組み立て、最終確認、実行という流れを型にして、抜け漏れを防ぐ。  

**規約の中身は、設定に写さない。** 設定には、規約・手順書の「場所」と、ハーネスに無い決めごとだけを持つ。  
規約の中身は、毎回、その場所から読む。  

## 前提

- `gh` コマンド（GitHub CLI）が入っていて、認証済みであること。  
- Issue テンプレートが `.github/ISSUE_TEMPLATE/` にあること。  
  このスキルは、テンプレートを作らない（あるものを読んで使う）。  
  無いときは、作業を止めて、先にハーネスの整備（`bootstrap-ai-harness` スキルでの導入など）が要ることを、ユーザーに案内する。  
- `scripts/` の Python スクリプトを動かせること（`get_issue_template_fields.py` は PyYAML が要る。無いときは `pip install pyyaml`）。  

## 0. 設定ファイルを確かめる（毎回、最初に行う）

設定ファイルは `.agents/config/create-github-issue/settings.md`（プロジェクトルート直下）である。  
作業用ファイル（Issue 本文の下書き、一時ファイル）は `.agents/state/create-github-issue/` に置く（使い捨て。Git に入れない）。  
**スキル自身のディレクトリの中には、設定も作業ファイルも作らない。**（スキルを更新すると、上書きされるため）  

| 状態 | すること |
|---|---|
| 設定ファイルが無い | [references/interview.md](references/interview.md) に従う。プロジェクトから読み取れるものは、自分で調べて確定する。読み取れないものだけを質問する。結果は [assets/settings.template.md](assets/settings.template.md) の形で保存し、内容をユーザーに見せて、確認を取る。そのあと、手順1へ進む |
| 設定ファイルがある | 質問せずに、その内容を使う。手順1へ進む |
| 「設定を見直したい」と言われた | interview.md の質問をやり直し、変わった項目だけを、設定ファイルに反映する |

- 設定ファイルは、チームで共有する（Git に入れる）ものである。  
  保存したら、Git に入れるかどうかを、ユーザーに確かめる。  
- `.agents/state/` は Git に入れない。  
  `.gitignore` に `.agents/state/` を書くことを、ユーザーに案内する（書くかどうかはユーザーが決める）。  
- 設定の内容と、実際のプロジェクトが食い違ったとき（テンプレートが無い、ブランチが無い、など）は、自分で直さずに、食い違いをユーザーに伝える。  
- 設定の「追加の項目」に書いてあることは、以降の手順の該当する箇所で、必ず読み、従う。  

## 手順

### 1. 種別（テンプレート）の選択

`python scripts/get_issue_template_fields.py --list` を実行し、テンプレートの一覧（`type`・`name`・`title_prefix`・`suggested_branch_prefix`）を取る。  
ユーザーに、どの種別かを確かめる（会話の内容から明らかなら、聞かずに決めてよい）。  

タイトル接頭辞・ブランチ接頭辞・ブランチを切るかは、次の順で決める。  

1. 設定の「種別の表」に、その種別があれば、それに従う。  
2. 無ければ、プロジェクトのブランチ規約（設定の「読むもの」）に従う。  
3. 規約にも無ければ、スクリプトの出力に従う（タイトル接頭辞は `title_prefix`、ブランチ接頭辞は `suggested_branch_prefix`、ブランチは切る）。  
   `title_prefix` が空のときは、`[<type>] ` を、最終確認でユーザーに見せて決める。  

種別の指定は、`type`（ファイル名）か `name` の完全一致である（部分一致はしない）。  
合うテンプレートが無いときは、スクリプトが使える種別の一覧を出して終わる。  
`.github/ISSUE_TEMPLATE/` に、テンプレートが1つも無いときは、Issue を作らずに止める。  
テンプレートを作ることは、このスキルでは行わず、ハーネスの整備（`bootstrap-ai-harness` スキルでの導入など）が先に要ることを、ユーザーに伝える。  

### 2. 内容のヒアリング

`python scripts/get_issue_template_fields.py <種別>` を実行する。  
種別は、`--list` の `type`（ファイル名）か `name` で指定する。  
出力の `fields`（`id`・`label`・`required`・`options`）を、ヒアリングのチェックリストにする。  
テンプレートを、毎回スクリプトから取るため、テンプレートが変わっても、この手順が古くならない。  

- 必須項目が埋まらないときは、作成の前に、ユーザーに確かめる。  
- 設定の「読むもの」の表にある場所を、作る前に読む。  
  読めないものがあるときは、作業を止めて、ユーザーに伝える。  
- ヒアリングの結果、必要に応じて、ソースコードや既存の Issue も確かめる。  
- 本文は、[references/作成要領.md](references/作成要領.md) の「2. 各節の書き方」に沿って書く。  
  構成は、[references/ひな形.md](references/ひな形.md) を元にする。  
  本文の下書きは、`.agents/state/create-github-issue/` に書く。  

### 3. 起点ブランチの決定

種別の「ブランチを切るか」が「切らない」のときは、この手順と手順4をとばす。  

作業ブランチは、正しい起点から作る。  
誤った起点から切ると、あとで余計な差分を持ち込むため、自動で決め打ちせず、スクリプトの判定結果に従って確かめる。  

```bash
python scripts/resolve_base_branch.py                                   # 設定ファイルの規則で判定する（設定が無ければ、組み込みの既定）
python scripts/resolve_base_branch.py --pattern "<規則>" --default <ブランチ>   # 規則を引数で指定する
```

引数は、`--pattern`（起点にできるブランチ名の規則。正規表現）、`--default`（規則に合うブランチが無いときの既定の起点）、`--remote`（リモート名）、`--settings`（設定ファイルのパス）である。  
決め方は、引数、設定、組み込みの既定の順に優先される。  
ハーネス（ブランチ規約）が設定と食い違うときは、食い違いをユーザーに伝える。  

出力の JSON を読む。  

| 出力 | 扱い |
|---|---|
| `needs_user_confirmation` が `false` | `recommended_base_branch` を、そのまま起点にする（今のブランチが規則に合うときだけ、こうなる） |
| `needs_user_confirmation` が `true` で、`recommended_base_branch` に値がある | その値を提案し、使ってよいか確かめる。`candidate_branches` が複数あるときは、候補も見せる |
| `recommended_base_branch` が `null` で、`candidate_branches` が複数 | `candidate_branches` を選択肢として見せ、ユーザーに選んでもらう（自動で選ばない） |
| `recommended_base_branch` が `null` で、`candidate_branches` が空 | 起点をユーザーに聞く |

`reason` に、判定の理由が入っている。  
ユーザーへの提示に使う。  

### 4. ブランチ名の組み立て

Issue のタイトルと概要から、短い英語の kebab-case のスラッグを作る。  
スラッグは、次の最終確認で、ユーザーに見せる。  
ブランチ名の形式は、設定の「ブランチ名の形式」に従う（既定：`<ブランチ接頭辞>#<番号>-<スラッグ>`）。  
Issue の番号は、Issue を作って初めて決まるため、この時点では、スラッグだけを決める。  

### 5. 最終確認

実行の前に、次をまとめてユーザーに見せ、実行してよいかを確かめる。  

- Issue のタイトル（タイトル接頭辞を付けた形）。  
- Issue の本文。  
- 起点ブランチ（ブランチを切らない種別は不要）。  
- ブランチ名の接頭辞とスラッグ（例：`feature/#<番号は作成後に決まる>-<スラッグ>`。ブランチを切らない種別は不要）。  
- ラベルの扱い（設定の「ラベルの扱い」に従う）。  
- 親 Issue の子 Issue にするときは、親 Issue の番号。  

### 6. 実行

1. 本文を、`.agents/state/create-github-issue/` の一時ファイルに書く。  
   本文は複数行の Markdown で、引用符やバッククォートを含むことがあり、`--body "…"` でコマンドラインに直接書くと、シェルの引用符の解釈でコマンドが壊れるおそれがある。  
   そのため、必ず `--body-file` で渡す。  
2. `gh issue create --title "<タイトル>" --body-file <一時ファイル>` で、Issue を作る。  
   ラベルは、設定の「ラベルの扱い」に従う（既定は、指定しない）。  
3. 出力から、Issue の番号を取る。  
4. ブランチ名を決める（設定の形式に、番号とスラッグを入れる）。  
5. 起点ブランチが、ローカルに無いときは、`git fetch <リモート名> <起点ブランチ>` する。  
   そのうえで、`git checkout -b <新しいブランチ名> <起点ブランチ>`（ローカルに無ければ `<リモート名>/<起点ブランチ>`）で、ローカルのブランチを作る。  
6. **push はしない。** ユーザーが、必要なときに自分で行う。  

- ブランチを切らない種別は、4〜6をとばす。  
- 親 Issue の子 Issue にするときは、Issue を作ったあとに、サブ Issue として紐づける。  
  手順は、[references/作成要領.md](references/作成要領.md) の「5. 親 Issue とのつなぎ方」に従う。  
- 使い終わった一時ファイルは、ユーザーに確かめてから消す。  

## 作成したあと（進捗コメント・チェックの整理・引き継ぎ）

作成したあとも、次のときに、このスキルを使う。  
書き方は、[references/作成要領.md](references/作成要領.md) の「6. 進捗コメントと、チェックの整理」に従う。  

- ユーザーが「コミットする」「コミットメッセージをください」と言ったとき：進捗コメントを書く。  
  投稿するかどうかは、設定の「進捗コメントの扱い」に従う（既定：文面を見せ、確認を取ってから投稿する）。  
  できれば、本文のチェックも整理する。  
- すべて終わったとき：完了のコメントを書く。  
- ほかの Issue へ作業を引き継ぐとき：元の Issue と、引き継ぎ先の Issue の両方に書く。  

## やらないこと

- ラベルの付与（設定の「ラベルの扱い」に決めがあるときを除く）。  
- 作ったブランチの push。  
- ユーザーの最終確認を経ずに、Issue の作成・ブランチの作成を実行すること（Issue の作成は、チームから見える操作で、取り消しにくいため）。  
- 設定の「進捗コメントの扱い」が確認ありのときに、確認を取らずに投稿すること。  
- 規約の中身を、設定に写すこと。  
- 設定ファイルと作業用ファイルを、スキル自身のディレクトリの中に作ること。  
- Issue のクローズ（ユーザーが行う）。
