# E2Eテスト作成規約（webapp）

本ドキュメントは、Webアプリの画面のE2Eテストについて、ファイルの配置、要素の特定方法、待機処理、エビデンスの残し方を定める。  
何を、どこまでテストするかは、[テスト規約.md](テスト規約.md)で定める。

Playwrightの一般的な書き方は、[Playwright公式ドキュメント](https://playwright.dev/docs/best-practices)に従う。  
本規約は、公式ドキュメントと判断が異なる点と、本プロジェクトの運用ルールだけを定める。  
公式ドキュメントと本規約が食い違う場合は、本規約を優先する。

## ファイルの配置

ディレクトリ構成の全体は、[README.md](../../README.md)を参照する。

- E2Eテストは`e2e/tests/`に置く。
- Playwrightの設定ファイルは、`e2e/`の直下に置く。  
  通常の実行用は`playwright.config.ts`、証跡の取得用は`playwright.evidence.config.ts`とする。
- テストが増えて重複が出てきたら、次のディレクトリを作って切り出す。
  - `tests/pages/` … Page Object（画面ごとのLocatorの定義）
  - `tests/fixtures/` … 共通の前提条件
  - `tests/utils/` … 補助の関数
- 中身のないディレクトリは作らない。  
  必要になったときに作る。

## ファイル名・テスト名の付け方

### ファイル名

- E2Eテストのファイルは、`<機能名>.spec.ts`とする（例: `products.spec.ts`）。

### テスト名

- 日本語で書く。  
  チーム内でレポートをそのまま共有し、内容を確認しやすくするためである。
- 「何をしたら、どうなるか」が分かる文にする。

```typescript
test.describe("商品一覧画面", () => {
  test("商品一覧が表示される", async ({ page }) => { /* ... */ });
  test("商品コードで検索すると該当する商品が表示される", async ({ page }) => { /* ... */ });
});
```

`test("test1")`や`test("画面確認")`のような名前は使わない。  
失敗したときにレポートを見ても、何が壊れたのか判断できないためである。

## 画面への到達方法

目的の画面へは、リンクを辿らず、URLで直接移動する。

```typescript
// 良い例：対象の画面へ直接移動する
await page.goto("/products");

// 避ける例：途中の画面の変更で失敗する
await page.goto("/");
await page.getByRole("link", { name: "商品一覧" }).click();
```

**理由**: チーム開発では、担当外のメンバーが画面の文言やレイアウトを変更する。  
経路を辿るテストは、そのたびに巻き込まれて失敗し、原因の切り分けにも時間がかかる。

画面遷移そのものを確かめたい場合は、遷移を確かめる専用のテストを用意する。  
そうすれば、文言の変更で失敗するのは、そのテストだけになる。

### 実行の順番に依存しない

テストは、実行する順番に依存しないように書く。  
前のテストが作ったデータやログイン状態に依存せず、単体でも並列でも通るようにする。

## Locatorの基本方針

### 選び方

改修によって変わりにくく、自動で作られていないものを選ぶ。

これが唯一の判断基準である。  
次の優先順位は、この基準にもとづく目安であり、対象の画面の実態に合わせて選ぶ。

| 優先度 | 対象 | 例 |
| --- | --- | --- |
| 1 | 意図的に付けた固定の識別子 | `page.getByTestId("product-list")`、`page.locator("#main-nav")` |
| 2 | フォーム部品の`name`属性 | `page.locator("input[name=productCode]")` |
| 3 | 役割と表示名 | `page.getByRole("button", { name: "検索" })` |
| 4 | ラベル・プレースホルダ | `page.getByLabel("商品コード")` |
| 5 | 構造的に安定したCSSセレクタ | `page.locator("#products > tbody > tr")` |

この順序は、Playwright公式ドキュメントの推奨と異なる。  
公式ドキュメントは、利用者から見える情報（`getByRole`など）を最優先にしている。

**理由**: 本規約は、他のメンバーの変更で壊れにくいことを優先し、固定の識別子を上位に置く。  
チーム開発では、担当外の文言の変更でテストが失敗する影響の方が大きいためである。

### 画面側に識別子を付ける

テストで操作・確認する要素には、画面の実装で`data-testid`属性を付ける。

**理由**: webappの画面は本プロジェクトで実装するため、テストのための識別子を付けられる。  
識別子があれば、文言やレイアウトを変えても、テストは失敗しない。

- `data-testid`の値は、ケバブケースで、画面の中で一意にする（例: `product-list`、`search-button`）。
- 識別子を変更・削除する場合は、それを使っているテストも同時に直す。

### 使わないもの

| 使わないもの | 例・理由 |
| --- | --- |
| 自動で作られた識別子 | Vuetifyの部品が自動で付ける`id`（`input-v-3`など）や、ビルドで付くハッシュ付きのクラス名など |
| 位置に依存するXPath・CSSセレクタ | `/div[3]/span[2]`、`li:nth-child(4)`など。<br/>DOMに1階層追加されただけで失敗するためである |
| 見た目の調整のためのクラス名 | Vuetifyのユーティリティクラス（`ma-2`、`text-h6`など）のように、見た目の調整のたびに変わるもの |

CSSセレクタ・XPathそのものは禁止しない。  
構造的に変わらないと判断できる場合は使ってよい。

### 骨格と要素を組み合わせる

安定した識別子で範囲を絞り、その中の要素を役割で取得する。

```typescript
// 良い例：識別子で骨格を押さえ、その中の要素を役割で取得する
await page.getByTestId("main-nav").getByRole("link", { name: "商品一覧" }).click();

// 避ける例：たまたま1件目が当たっているだけ
await page.getByRole("link").first().click();
```

こうすると、他の画面のレイアウトやクラス名の変更では失敗せず、ナビゲーション自体の仕様が変わったときだけ失敗する。

### `id`を使うときの確認事項

- ページの中で一意であること。  
  重複していると、意図しない要素を掴むためである。
- 自動で作られた値でないこと。

### 文言の一致条件

`getByRole`の`name`、`getByText`、`getByLabel`は、指定しない場合は部分一致になる。

`exact: true`を指定する。  
部分一致は、画面に似た文言が増えたときに、別の要素を掴むか、複数一致でエラーになるためである。

件数や日付など、文言の一部が変わる場合は、正規表現を使う。

```typescript
// 「商品一覧（12件）」のように件数が変わる場合
await page.getByRole("heading", { name: /^商品一覧/ });
```

### クラス名や属性そのものを確かめたい場合

要素の特定には使わず、アサーションで確かめる。

**理由**: 特定に使うと、クラスが変わったときに「要素が見つからない」という分かりにくい失敗になるためである。

```typescript
// 良い例：特定は安定した手段で行い、クラスの有無はアサーションで確かめる
const alert = page.getByTestId("form-error");
await expect(alert).toBeVisible();
await expect(alert).toHaveClass(/is-error/);
```

クラス名は実装の詳細である。  
`aria-invalid`やエラーメッセージの表示など、利用者から見える結果を確かめる方が壊れにくい。

## 待機処理の方針

Playwrightは、要素が表示され操作できるようになるまで、自動で待つ。  
そのため、多くの場合は待機処理を書く必要がない。

ただし、自動で待つのは「その要素が操作できるようになるまで」であり、「画面全体が落ち着くまで」ではない。  
独自のローディング表示やアニメーション、非同期のDOMの差し替えがある画面では、待機処理が必要になる。

待機が必要な場合は、次の順で選ぶ。

| 順 | 手段 | 位置づけ |
| --- | --- | --- |
| 1 | アサーションで待つ（`expect(...).toBeVisible()`など） | 最優先 |
| 2 | 条件を指定して待つ（`waitForURL`、`toBeHidden`、`waitForResponse`） | 状態を特定できる場合 |
| 3 | 固定の秒数で待つ（`waitForTimeout`） | 最終手段 |

### 固定の秒数の待機

`page.waitForTimeout()`は、1と2で解決できない場合に限り、最終手段として使う。

**理由**: 実行する環境の速度で結果が変わり、テストが不安定になる。  
また、無駄な待ち時間が積み上がり、テスト全体が遅くなる。

使う場合は、なぜ必要かをコメントで残す。

```typescript
// 【暫定】ツリーの展開アニメーションの完了を判定できる要素がないため、固定の待機とする。
// 完了時に目印となるクラスや属性が付いたら、条件を指定した待機へ置き換えること。
await page.waitForTimeout(500);
```

コメントを残す理由は2つある。

- 後から条件を指定した待機へ置き換えられるようにするため。  
  判断の根拠が残らないと、誰も触れなくなる。
- 固定の待機が必要な箇所は、画面側に状態を判別する手段がないことを示すため。  
  記録が残れば、画面側の改善につながる。

## エビデンスの書き方

E2Eテストの実行結果は、レポートをエビデンスとして扱う。

レポートだけを見て「何を前提に、どう操作し、何を期待したか」が分かるようにする。  
テストコードを読まないと分からない状態にはしない。

### 記載する3要素

| 要素 | 使う機能 | レポートでの表示 |
| --- | --- | --- |
| 前提 | `annotation` | テスト名の下に「種別：説明」で表示される |
| 操作 | `test.step("操作N：〜")` | ステップの一覧として表示される |
| 期待結果 | `test.step("期待結果：〜")` と`expect` | ステップの一覧として表示される。<br/>失敗したステップは赤く表示される |

### 書き方

```typescript
import { expect, test } from "@playwright/test";

test.describe("商品一覧画面", () => {
  test(
    "商品コードで検索すると該当する商品が表示される",
    {
      annotation: [
        { type: "前提", description: "テスト専用のユーザーでログインしていること" },
        { type: "前提", description: "商品データが登録されていること" },
      ],
    },
    async ({ page }) => {
      await test.step("操作1：商品一覧画面（/products）を開く", async (step) => {
        await page.goto("/products");
        await step.attach(step.titlePath.at(-1)!, {
          body: await page.screenshot({ fullPage: true }),
          contentType: "image/png",
        });
      });

      await test.step("操作2：商品コードに「P001」を入力して「検索」をクリックする", async (step) => {
        await page.getByTestId("product-code").fill("P001");
        await page.getByTestId("search-button").click();
        await step.attach(step.titlePath.at(-1)!, {
          body: await page.screenshot({ fullPage: true }),
          contentType: "image/png",
        });
      });

      await test.step("期待結果：該当する商品の一覧が表示される", async () => {
        await expect(page.getByTestId("product-results")).toBeVisible();
      });
    },
  );
});
```

### レポートでの見え方

テスト名をクリックすると、詳細のパネルが開く。  
書いた内容は、パネルの中で次のように振り分けられる。

```text
商品コードで検索すると該当する商品が表示される      ✓ 1.2s

  Annotations
    前提: テスト専用のユーザーでログインしていること / 商品データが登録されていること

  Attachments
    操作1：商品一覧画面（/products）を開く
    ［画像］
    操作2：商品コードに「P001」を入力して「検索」をクリックする
    ［画像］

  Steps
    ▸ 操作1：商品一覧画面（/products）を開く                          0.3s
    ▸ 操作2：商品コードに「P001」を入力して「検索」をクリックする      0.5s
    ▸ 期待結果：該当する商品の一覧が表示される                          0.2s
```

成功したテストでもステップは残る。  
スクリーンショットの設定とは関係なく、エビデンスとして機能する。

### 画面の記録

レポートを人が見て正しさを判断できるように、画面のスクリーンショットを添付する。

`test.step`のコールバックが受け取る`step`を使い、`step.attach()`で添付する。  
添付名（第1引数）には、そのステップ名をそのまま使う。

**理由**: 添付した画像は、ステップの中ではなく`Attachments`の欄にまとめて表示され、添付名だけが画像を見分ける手がかりになる。  
`step.titlePath`の末尾がステップ名になるため、これを使えばステップ名を二重に書かずに済み、ステップ名を変えても添付名が自動で追従する。

```typescript
await test.step("操作1：商品一覧画面（/products）を開く", async (step) => {
  await page.goto("/products");
  await step.attach(step.titlePath.at(-1)!, {
    body: await page.screenshot({ fullPage: true }),
    contentType: "image/png",
  });
});
```

`"画面"`のような固定の文言は、添付名に使わない。  
操作が2つ以上あると、レポートでどちらの画像か区別できなくなるためである。

撮影するのは、次のときである。

- 画面が切り替わる操作の直後（`page.goto()`、画面遷移を伴うクリックなど）。
- ポップアップやモーダルが表示されたとき。
- エラーメッセージが表示されたとき。
- 期待結果を確かめたあと。

次の場合は撮影しない。

- 入力の途中など、画面の状態が変わらない操作。
- 同じ画面を続けて撮ることになる場合。

**理由**: すべてのステップで撮ると、レポートが重くなり、確認する側の負担も増える。  
画面の状態が変わった瞬間だけを残す。

### ルール

- 前提は、すべてのテストに1つ以上書く。
  - 前提が特にない場合も、テストを始めるときの状態を書く。
  - `type`は`前提`で統一する。  
    `_`で始まる種別名は、レポートに表示されないため使わない。
  - 件数は2件程度までにする。  
    同じ種別の注釈は1行に連結されるため、3件以上あると読みにくくなる。
- 操作は、`操作1：`から連番にする。
  - 1ステップを1操作とし、複数の操作を1ステップにまとめない。
  - 実際の画面の文言（ボタン名・リンク名）をステップ名に含める。
- 期待結果は`期待結果：`で始め、`expect`を必ず含める。
  - 期待結果が複数ある場合は、ステップを分ける。
- `expect`を`test.step`の外に書かない。  
  レポートに現れず、何を確かめたのかが残らないためである。
- ステップ名は日本語で書く。
- 画面が切り替わったステップでは、スクリーンショットを添付する。
- 添付名は、`step.attach(step.titlePath.at(-1)!, ...)`と書き、ステップ名と一致させる。

## 証跡の保管

テストを実行したら、レポートを証跡として残す。  
通常の実行の出力先は、実行のたびに上書きされるためである。

生成AIにテストを作成・実行させた場合も、証跡の出力までを一連の作業として実施する。

### 取得の単位

証跡は、テストファイルの単位で取得する。

**理由**: 全件をまとめて実行すると、1つのレポートに複数の機能の結果が混ざり、どの機能の証跡かを特定できなくなるためである。

### 置き場所

置き場所は、`e2e/evidence/`とする。

```text
evidence/
└── <テストファイル名>/            … 拡張子を除いたファイル名（products.spec.ts → products）
    └── <テスト実施日>/             … YYYYMMDD形式（例: 20260928）
        ├── index.html
        └── attachments/           … スクリーンショット
```

日付には、テストを実施した日を入れる。  
同じテストの証跡は、リリース前の確認や修正後の再確認などで複数回できるため、どの時点の結果かを特定できるようにする。

`evidence/`、`monocart-report/`、`test-results/`は`.gitignore`に追加し、リポジトリにはコミットしない。  
画像を含むため容量が大きく、リポジトリを圧迫するためである。

### 取得のコマンド

証跡の取得手順を実装するときは、テストファイルを1つ指定して取得できるようにする。
次は、対応するnpmスクリプトを設定した場合の例である。

```powershell
npm run test:e2e:evidence -- tests/products.spec.ts
```

- 出力先のディレクトリ名と日付は、指定したテストファイルと実行日から自動で決まるようにする。
- テストファイルを指定しなかった場合と、2つ以上指定した場合は、エラーにする。
- 同じ日の再実行で証跡を上書きする設定では、既存の証跡が消える。  
  残しておきたい証跡がある場合は、ディレクトリ名を変えて退避する。
- 証跡は、`index.html`だけでは完結しない。  
  スクリーンショットは同じ階層の`attachments/`に出力され、相対パスで参照されるため、保管・共有するときはディレクトリごと扱う。

## 実行方法

次は`e2e/`に対応するnpmスクリプトとテストファイルを用意した場合の例である。
スクリプトを導入するまでは、利用可能なコマンドを確認し、未実施の検証を報告する。

| 目的 | コマンド |
| --- | --- |
| 通常の実行（ブラウザを表示しない） | `npm run test:e2e` |
| ブラウザを表示して実行する | `npm run test:e2e:headed` |
| UI Mode（調査・開発のとき） | `npm run test:e2e:ui` |
| レポートを表示する | `npm run test:e2e:report` |
| 証跡を取得する | `npm run test:e2e:evidence -- tests/products.spec.ts` |
| ファイルを指定して実行する | `npx playwright test tests/products.spec.ts` |
| テスト名で絞り込んで実行する | `npx playwright test -g "商品一覧"` |

- テストコードを書いている間は、UI Modeを使う。
- コミットする前に、全件を実行して、すべて通ることを確認する。

## 生成AIにテストコードを作らせるとき

- 本規約を、生成AIへの入力として渡す。
- あわせて、次の情報を伝える。
  - 対象の画面のURL（またはパス）。
  - 操作の手順と期待結果を、文章で1〜3シナリオ分。
  - 対象の画面のHTMLの構造（見出しやリンクの文言、`id`や`data-testid`が分かるもの）。
- 生成AIが作ったコードは、必ず次を確認する。
  - `waitForTimeout`が理由のコメントなしに入っていないか。
  - 自動で作られた識別子や、位置に依存するセレクタを使っていないか。
  - 前提・操作・期待結果が、`annotation`と`test.step`で書かれているか。
  - 添付名がステップ名と一致しており、どのステップの画像か特定できるか。
  - 確かめたい内容を実際に確かめているか（表示されるだけで満足していないか）。
