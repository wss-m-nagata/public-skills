# API実装方針

Pythonで作るwebappのAPIについて、内部の処理と部品の置き方を定める。  
呼び出し元から見た共通の約束は[API共通仕様.md](../40_spec/API共通仕様.md)、APIごとの入出力は各サービスのAPI仕様で定める。

DB、SQL、リポジトリ、トランザクションに関する規則は、それらを利用するサービスに適用する。
DBを利用しないサービスでは、入力検証・処理の分担・エラー処理など、該当する規則を適用する。

## 処理の分担

| 層 | 責務 |
| --- | --- |
| 入口 | メソッドとパスから処理を選び、DB接続とトランザクション、例外の応答への変換を管理する |
| 機能層 | 入力を検証し、要求に対する業務上の判断を行い、結果をAPIの応答に変換する |
| リポジトリ | 指定された条件でSQLを実行し、取得・更新したデータを扱う |
| DTO | リポジトリが受け取る条件や返すデータの形を表す |
| 共通処理 | DB接続など、サービス内の複数の処理で使う部品を提供する |

機能層がHTTPの要求と業務の判断を扱い、リポジトリがDBの読み書きを扱う。  
この分担により、機能の判断をDBに接続せず確認でき、SQLの確認と分けられる。

- 入口には業務の処理やSQLを書かない。
- 機能層にはSQLやDB接続情報の取得を書かない。
- リポジトリにはHTTPステータスや応答の項目名、呼び出し元の権限の判断を書かない。
- 認証・認可の方式は[アーキテクチャ.md](アーキテクチャ.md)に従う。

## 配置

サービスの`src/`に、入口、`functions/`、`repository/`、`core/`を置く。  
入口はLambdaとAPI Gatewayに関わる処理を置き、機能層はAPIごと、リポジトリは主体となるテーブルまたはビューごとに分ける。  
複数のテーブルを結合するSQLは、結果の1件が対応する主体のリポジトリに置く。  
この配置により、APIとデータの変更時に確認する範囲を特定できる。

- DTOはリポジトリに対応する`repository/dto/`に置く。
- サービス内の共通処理は`core/`に置き、同じ処理を各機能に書き写さない。
- 他サービスを呼び出す処理は、呼び出し先ごとのクライアントにまとめる。  
  接続先や電文の組み立てを機能層に散在させないためである。

## 入力の検証

機能層はAPI仕様に定めた必須項目、型、形式、長さ、範囲と業務上の制約を確認する。  
不正な値をそのままSQLに渡したり、既定値で吸収したりせず、API仕様に定めたエラーを返す。

- 省略を許す項目の既定値は、API仕様に定める。
- ソート列などSQLの識別子に使う値は、あらかじめ決めた選択肢と照合する。
- 外部の連携先の応答など、仕様上値の揺れがあり得る場合は、その範囲を明示して扱う。

## リポジトリとDTO

リポジトリの関数は取得に`fetch_`・`find_`、件数に`count_`、存在確認に`exists_`、登録・更新・削除に`insert`・`update_`・`delete`を使い、対象や更新内容が分かる名前にする。  
複数件はDTOのリスト、1件はDTOまたは存在しないことを示す`None`、件数と存在確認はそれぞれ整数と真偽値で返す。

- DTOはPython標準の`dataclass`を使い、項目ごとに意味をコメントで示す。
- SQLの結果とDTOの名前が異なるときは、SQLの列に別名を付けて対応させる。
- DTOからAPIの応答形式への変換は機能層で行う。  
  DBの列名や結合方法が変わっても、外部のAPI契約を独立して管理できるためである。

## SQL

- SQLはリポジトリに置き、予約語と結合の種類を明示し、列と条件を読み取れる形に整える。
- 値はDBドライバーのパラメータとして渡し、文字列結合や書式展開で埋め込まない。  
  不正な入力がSQLとして解釈されることを防ぐためである。
- テーブル名、スキーマ名、並べ替えの列などの識別子は固定値または検証済みの値だけを使用する。
- 検索条件を組み立てるとき、条件式はリポジトリ内に定めたものだけを使い、入力値はパラメータで渡す。
- ページングする場合は、並び順の最後に一意なキーを加える。  
  同じ値の行がページ間で重複したり抜けたりすることを防ぐためである。
- 絞り込み、結合、並び替えに必要なインデックスを確認する。  
  テーブルの定義変更やインデックスの追加が必要な場合は、テーブルを管理する担当者と対応を調整する。

## DB接続とトランザクション

- 接続情報はサービスの定める安全な取得方法を使い、ソースコードに接続先の秘密情報を書かない。
- DBを使う処理は入口が接続を用意し、機能層を通してリポジトリに渡す。  
  一つの要求で行う複数の操作を同じ接続とトランザクションで扱えるためである。
- 更新を伴う一連の処理はひとつのトランザクションで実行し、成功時にコミット、失敗時にロールバックする。
- 参照だけの処理は読み取り専用の接続を使い、不要な長時間のトランザクションを避ける。
- 接続やカーソルは正常時・異常時のどちらも解放する。

## エラーとログ

- 入力や業務上のエラーは、API仕様のステータスと利用者向けの文言で返す。
- APIが返すエラーの本文は[API共通仕様.md](../40_spec/API共通仕様.md)の`error_code`、`message`、`detail`を使う。  
  `error_code`にメッセージIDを入れ、`message`にはIDを含めず利用者向けの文言を入れる。
- 利用者向けの文言は、何が起きたかと、操作者にできる対処があればその対処を示す。  
  APIの項目名ではなく、画面の項目名を使う。
- 想定外のエラーは詳細をログに残し、応答には一般的な文言を返す。  
  接続情報や例外の内部情報を利用者に表示しないためである。
- トークンやパスワードなどの秘密情報は、ログとテストの証跡に出力しない。

## テスト

機能層はリポジトリなどの依存先をモックにして確認し、SQLはテスト専用DBで確認する。  
仕様書、テストコードとレポートの扱いは[テスト規約.md](テスト規約.md)に従う。
