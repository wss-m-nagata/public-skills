# テスト規約（webapp）

本ドキュメントは、Webアプリについて、何を、どのツールで、どこまでテストするかを定める。  
画面のE2Eテストの書き方は、[E2Eテスト作成規約.md](E2Eテスト作成規約.md)で定める。

DBやSQLに関する試験の規則は、それらを利用する機能に適用する。

## 基本方針

webappのバックエンドは、画面のためのAPI（BFF）である。  
そのため、画面のE2Eテストを中心に確認し、APIごとの単体テストで内部処理を確認する。  
PlaywrightによるAPIテストは任意とし、複雑な機能など画面から確認しにくい場合に実施する。

| 対象 | テスト方法 | ツール | 成果物 |
| --- | --- | --- | --- |
| 画面 | E2Eテスト（自動） | Playwright | テストコード、Playwrightのレポート |
| API | APIのテスト（自動・任意） | Playwright（`APIRequestContext`） | テストコード、Playwrightのレポート |
| Lambdaの中の処理 | API単位の単体テスト（自動） | 本体の言語の単体テストのツール（Pythonならpytest） | 仕様書、テストコード、レポート |
| フロントエンドの部品 | 対象外（レビューで確認する） | なし | なし |

**理由**: 画面のE2Eテストは、利用者の操作に沿って、フロントエンドとバックエンドをまとめて確かめられる。  
単体テストは、画面から網羅しにくい処理やSQLを独立して確認するために用いる。

テストは、開発者のローカル環境で実行する。

## 成果物の置き場所

テストコードは、テストする対象と同じ場所に置く。

**理由**: 資料やインフラと同じく、サービスを切り出すときに、テストもコードと一緒に移せるようにするためである。  
画面のE2Eテストは複数のサービスをまたぐため、リポジトリ直下に置く。

| テスト | 置き場所 |
| --- | --- |
| 画面のE2Eテスト | `e2e/tests/` |
| APIのテスト | `backend/<サービス>/tests/api/` |
| Lambdaの中の処理の単体テスト | `backend/<サービス>/tests/unit/` |

ディレクトリ構成の全体は、[README.md](../../README.md)を参照する。

- APIのテストのコードは、`tests/api/`に置く。  
  Playwrightの設定（`playwright.config.ts`など）と依存関係（`package.json`）は、サービスの直下で管理し、`tests/api/`には置かない。  
  サービスの`package.json`を1つにする理由は、[アーキテクチャ.md](アーキテクチャ.md)の「サービスのディレクトリの形」を参照する。
- Playwrightのバージョンは、すべての`package.json`で固定し、同じものにそろえる。  
  バージョンを上げるときは、すべてを同時に上げる。
- 設定ファイルの重複は、3つ目のサービスを追加するときに、共通の部品として切り出すかを判断する。

## 画面のテスト（E2Eテスト）

画面のE2Eテストは、Playwrightでブラウザを操作して実施する。  
書き方は、[E2Eテスト作成規約.md](E2Eテスト作成規約.md)に従う。

### 必須のテスト観点

- 画面設計に書かれた操作ができること。
- 操作の結果が、画面設計に書かれた期待どおりであること。
- 権限のない機能が、画面に表示されないこと。

## APIのテスト

APIのテストは、Playwrightの`APIRequestContext`を使い、HTTPでAPIを呼んで実施する。

### 対象とするケース

APIのテストは任意とする。  
複雑な機能など、画面から確認しにくい場合に実施し、正常系も確認できる。  
次のケースも必要に応じて対象にする。

- 権限のない利用者が呼んだときに、拒否されること。
- webapp以外のアプリのトークンで呼んだときに、拒否されること。
- 不正な入力（必須項目の欠落、型や桁の誤りなど）を送ったときに、エラーが返ること。

### 必須のテスト観点

- HTTPステータスが期待どおりであること。
- レスポンスの本文が、API仕様に書かれた期待どおりであること。

### 書き方

[E2Eテスト作成規約.md](E2Eテスト作成規約.md)の次の節に従い、APIのテストに合わせて読み替える。

| 節 | APIのテストでの読み替え |
| --- | --- |
| 「ファイル名・テスト名の付け方」 | ファイル名は`<API名>.spec.ts`とする |
| 「エビデンスの書き方」 | スクリーンショットの代わりに、送ったリクエストと受け取ったレスポンスを添付する |
| 「証跡の保管」 | 置き場所は`backend/<サービス>/evidence/`とする |
| 「実行方法」 | コマンドはサービスの直下で実行し、`test:e2e`を`test:api`と読み替える（例: `npm run test:api`） |

APIのテストでは、プロジェクトで用意した場合、`tests/api/support/steps.ts`の前提条件・操作手順・期待結果・後片付けの部品を使う。  
リクエストとレスポンスの記録には、プロジェクトで用意した場合、`tests/api/support/evidence.ts`の`callApi`を使う。  
結果を確かめる呼び出しは期待結果のステップ内で行い、期待する値をレポートに記載する。

## Lambdaの中の処理のテスト（単体テスト）

APIの実装が完成したら、API単位の単体テスト仕様書を作り、そのケースに沿ってテストコードを作る。  
特に次の処理を確認する。

- 分岐が多い判定処理（例: 商品の価格帯ごとの判定）。
- データの変換の仕様が複雑な処理。
- 誤った結果になったときの影響が大きい処理（例: マスターデータを更新する処理の入力チェック）。

**理由**: 分岐の多い処理は、画面やAPIからすべてのパターンを確かめるのが難しい。  
関数を直接呼ぶ単体テストなら、パターンごとの入力と期待結果を短く書ける。

- テストファイルは`backend/<サービス>/tests/unit/`に置き、名前はテストのツールの慣習に従う（pytestなら`test_<対象>.py`）。
- テスト名（関数名）は、何を確かめるかが分かる名前にする（例: `test_価格が範囲外ならエラーになる`）。
- 機能層の入力検証・判定はリポジトリなどの依存先をモックにして確認し、SQLの絞り込み・結合・並び順はテスト専用DBで確認する。
- DBの試験データは共通・APIごと・ケースごとに分け、ケースに必要な条件をテストから読み取れるようにする。  
  共有データや他のケースが作ったデータに依存しない。
- 仕様書とケース一覧JSONはサービスの`docs/40_spec/unit-test/`に置く。  
  クラス単体のケースに`<ファイル名>::<クラス名>::<関数名>`または`<ファイル名>::<関数名>`を記載し、結果と対応させる。  
  Excelとケース一覧JSONを管理し、Excelの生成元となる作業用JSONはコミットしない。
- リクエスト単体のシートは画面E2Eで確認するため、対応不要としてグレーアウトする。  
  任意のAPIテストを作る場合も、仕様書の重複作成は求めない。
- 単体テストのレポートは`tests/output/report/unit/<実行日>/`に出力する。  
  テスト結果と仕様書のケースとの突き合わせを別々に判定する。  
  仕様書にあるテストの不足はNG、仕様書にないテストは警告とする。
- DBを使うテストは`TEST_DATABASE_URL`で指定したテスト専用DBに接続し、テスト後にロールバックする。
- レポートをコミットせず、実行後はフルパスを示してレビューを依頼する。

## エビデンス

- 画面のE2EテストとAPIのテストは、Playwrightのレポートをエビデンスとして扱う。  
  レポートの書き方と保管の方法は、[E2Eテスト作成規約.md](E2Eテスト作成規約.md)の「エビデンスの書き方」と「証跡の保管」に従う。
- エビデンスは、リポジトリにコミットしない。

## ログイン

テストでのログインは、テスト専用のユーザーで行い、人が代わりにログインしない。  
多要素認証を使う場合は、テスト専用ユーザーの認証に必要なコードを、登録時の秘密の値からテストのプログラムで作る。

**理由**: 人がログインを代わりに行うと、テストを自動で最後まで実行できなくなる。  
多要素認証を含むログインを自動化すると、試験用ユーザーでも認証を省略せずに試験できる。

- テスト専用のユーザーのパスワードと秘密の値は、環境変数で渡し、リポジトリにコミットしない。
- ログインはテスト全体で1回だけ行い、ログインした状態を保存して、各テストで使い回す。

## テストデータとテストの接続先

前提データはテスト側で用意し、足りない場合はスキップせず失敗させる。  
テストで作ったデータは失敗時にも後片付けし、他のテストや既存データに影響させない。  
SQLでテストデータを準備する場合は、データごとのフォルダに置き、番号付きファイルを親から子の順に実行する。  
`delete.sql`には試験で作る行に限った削除処理を置き、前回の残りと試験終了後のデータを片付ける。  
データ読み込み用の共通処理を設ける場合は、接続先とトランザクションの実装を呼び出し側から渡す。
