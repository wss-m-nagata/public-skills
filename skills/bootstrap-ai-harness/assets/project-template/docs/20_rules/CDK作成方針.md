# CDK作成方針

管理基盤は`infra/foundation/`、共通インフラは`infra/shared/`に置き、それぞれの直下に`cdk.json`、`bin/`、`lib/`を置く。
スタック名は[AWSリソース命名規則](AWSリソース命名規則.md)、リソースの分担は[アーキテクチャ](アーキテクチャ.md)に従う。

## サービスごとにCDKアプリを持つ

サービス専用のインフラは、CDKアプリを1つにまとめず、サービスごとに1つのCDKアプリとして持つ。  
CDKの設定（`cdk.json`）はサービスの直下に置き、CDKのコードは`backend/<サービス>/infra/cdk/`に置く。

**理由**: 資料と同じく「説明・定義する対象と同じ場所に置く」という原則に合わせるためである。  
コード・インフラ・資料がサービスの下にそろうため、サービスを切り出すときはディレクトリを1つ移すだけで済む。  
また、CDKアプリが分かれていることで、スタック間でpropsによる値の受け渡し（後述のExportの固定化の原因）が構造的に起きなくなる。

CDKアプリを複数持つことで起きる問題には、次のように対応する。

| 問題 | 対応 |
| --- | --- |
| CDKのバージョンのずれ | [CDKコーディング規約](CDKコーディング規約.md)に従う。 |
| 共通の書き方（スタック名の付け方、タグ、Lambdaの共通設定など）の重複 | 共通の書き方は、各サービスの中に書く。<br/>3つ目のサービスを追加するときに、共通の部品として切り出すかを判断する。<br/>サービスが2つまでの段階で共通化すると、何を共通にすべきかが分からないまま部品を作ることになるためである。 |

## スタック間の値の受け渡し

独立してデプロイするスタック間の共有値はSSMパラメータストアを使う。
CloudFormationのExportとImportValueを使うと、参照しているスタックがある間は値を変更・削除できない。
Lambda 関数 URLでは、各サービスがCloudFrontのKeyValueStoreに転送先を登録する。
API Gatewayでは、各サービスがAPIのURLをSSMに登録し、共有インフラが転送先を更新する。

## GitHub Actions用のIAMロール

デプロイ対象と環境の組ごとにIAMロールとGitHub Environmentを分け、信頼ポリシーで利用可能なリポジトリとEnvironmentを制限する。
GitHub Actions自身が利用するロールの変更方法と、既存のOIDCプロバイダーの有無は、対象環境の管理方針に従って定める。
GitHub Actionsが利用するロールを含むスタックは、管理者が別の権限で管理する。
ワークフロー自身がそのロールを変更すると、権限変更の失敗によってワークフローから復旧できなくなるおそれがあるためである。

## VPCとLambdaのパッケージ形式

VPC、サブネット、セキュリティグループの参照は対象のネットワーク方針に従う。
Lambdaはzip形式を基本とする。
サービスのソース、必要な共有ソース、ロックファイルで固定した実行時依存だけを含める。
コンテナイメージを選ぶ場合も、テストや実行に不要な開発用依存を除く。

## 初回デプロイの依存関係

GitHub Actionsでデプロイする場合は、管理者が最初に管理基盤を用意する。
IP制限を採用する場合は、必要なWAFを利用側より先にデプロイする。
Cognitoの招待メールに画面URLを載せる場合は、入口を認証より先に用意する。

- Lambda 関数 URLは、管理基盤、CloudFront用WAF（採用時）、入口、認証（採用時）、サービスと画面の順に進める。サービスと画面は依存する共通スタックがそろえば並行できる。
- API Gatewayは、管理基盤、WAF（採用時）、画面用の入口、認証（採用時）、サービスのAPI、入口へのAPI転送先の追加、画面配信の順に進める。入口の初回作成では、未作成のサービスのAPIを参照しない。

実行場所とコマンドは、対象環境のデプロイ手順に記載する。
