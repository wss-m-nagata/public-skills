# リポジトリ規約

本ドキュメントは、本リポジトリにおける作業の流れ・ドキュメント運用・課題管理・ブランチ運用・ツール利用に関するルールを定める。

## 生成AIと人の作業の流れ

生成AIを使って変更するときは、次の流れを基本とする。

| 順番 | 作業 | 行う人 |
| --- | --- | --- |
| 1 | 修正する | 生成AI |
| 2 | 変更の内容を確認する | 人 |
| 3 | 必要があれば調整する | 人（生成AIに直させてもよい） |
| 4 | コミットする | 人 |

コミット、プッシュ、Pull Requestのマージは、人が行い、生成AIは行わない。

**理由**: 人が変更の内容を確かめないまま、生成AIの修正がリポジトリの履歴に残ることを防ぐためである。  
コミットを人が行うことで、どの変更を誰が確かめて取り込んだかが、履歴から分かるようになる。

## 言語・出力ルール

- すべての応答・ドキュメントは日本語で記載する。
- 文は「。」で終わるごとに改行する。
- 箇条書きの説明文も、句点ごとに改行する。
- 見出しが体言止めの場合は「。」は不要とする。

## ドキュメント運用ルール

### ファイル種別

- すべてのファイルは、目的に応じて次のいずれかの種別に属する。
- ファイルを作成・修正する前に、そのファイルの種別を確認し、種別ごとのルールに従う。

| 種別 | 目的 | 本文に書くもの | 本文に書かないもの | 改版履歴 |
| --- | --- | --- | --- | --- |
| 規約 | 決まったルールと定義を示す | 決まったルールと定義、理由（後述） | 経緯、背景、時点を表す表現、未決定の事項 | 持つ |
| 仕様書 | 決まった「何をするか」を示す | 外から見た振る舞い（入力、出力、表示項目、APIの入出力など） | 経緯、背景、時点を表す表現、未決定の事項 | 持つ |
| 設計書 | 決まった「どう実現するか」を示す | 内部の構造と処理、理由（後述） | 経緯、背景、時点を表す表現、未決定の事項、採らなかった案との比較 | 持つ |
| 手順書 | 作業の進め方を示す | 前提条件、手順、結果の確認方法 | 経緯、背景、未決定の事項 | 持たない |
| 案内 | 入り口として全体像を示す | 目的、全体像、各資料へのリンク | 経緯、背景、他の資料と重なる詳しい説明 | 持たない |
| タスク | 進み具合を管理する | 目的、背景、進み具合、いつ何が決まったか | 決まった内容の詳しい説明（規約・仕様書・設計書に書き、リンクで参照する） | 持たない |
| 課題管理 | 未決定の事項と、その結論を管理する | 課題、状態、決まった日付と結論 | 議論の過程 | 持たない |
| ソースコード | 動作を実装する | 今の動作を説明するコメント | 経緯、背景 | 持つ |
| AI向け指示 | 生成AIが作業するときの前提とルールを示す（`AGENTS.md`、`CLAUDE.md`、`SKILL.md`、`.claude/agents/` 配下のファイル） | AIが従うルールと作業の前提。<br/>理由は、AIがルールを正しく当てはめるのに必要な場合だけ1文で書く | 経緯、背景、時点を表す表現、未決定の事項、人向けの資料と重なる詳しい説明 | 持たない |

- 決まったことを示す種別（規約、仕様書、設計書、手順書、案内、ソースコード）では、経緯は改版履歴にだけ書き、本文には書かない。  
  本文では、「現在」「この時点では」のような時点を表す表現を使わない。
- 未決定の事項は、課題管理にだけ書く。  
  規約、仕様書、設計書、手順書、案内には、未決定の事項やTODOを書かない。
- 未決定のために書けない節がある場合は、見出しを残し、未決定であることと、管理するGitHub Issueへのリンクだけを書く。  
  見出しを残すのは、書き忘れではなく未決定であることを、読み手が判断できるようにするためである。
- タスクと課題管理は、本リポジトリには置かない（「課題管理」を参照）。

### AI向け指示の扱い

- AI向け指示は、作業のたびに生成AIに読み込まれるため、短く保つ。  
  内容が増えるほど、生成AIが作業に使える情報の量（コンテキスト）が減るためである。
- AI向け指示の変更の記録は、改版履歴ではなく、Gitのコミットの履歴で追う。
- `SKILL.md` と `.claude/agents/` 配下のファイルは、先頭にYAMLの設定を書く必要がある。  
  設定より前にコメントを置くと、設定が正しく読み込まれなくなる。
- 本規約とリポジトリ直下の `AGENTS.md` には、同じルールを重ねて書いている。  
  `AGENTS.md` は作業のたびに読み込まれるため、参照先を読みに行かなくてもルールが守られるようにするためである。  
  どちらかのルールを変更する場合は、同じコミットでもう一方も変更し、内容が食い違わないようにする。

### 理由の書き方（規約・設計書）

- 規約と設計書では、ルールや構造だけでは「なぜそうするのか」が読み手に伝わらない場合に、理由を書く。
- 理由は、初めて読む人が理解し、判断できるように書く。
- 「どんな問題を避けるのか」または「何を実現するのか」を具体的に書く。
- 短くすることを目的にして、理由を曖昧にしない。

### 相対表現と日付（タスク・課題管理）

- タスクと課題管理では、決まったことに必ず日付を書く。
- 「現在」「最近」などの相対的な表現を使う場合は、日付を併記する。
- 課題管理では、議論の過程を残さず、「日付: 決まったこと」の形で結論だけを書く。
- 日付は `YYYY/MM/DD` 形式、または `YYYY-MM-DD` 形式で統一する。

### 段落と改行

- 同一段落内で改行したい場合は、行末に半角スペース2つ、または `<br/>` を使用する。
- 段落を分ける場合は、空行を1行挿入する。

### docs 配下のディレクトリ命名規則

- `docs/` 配下のディレクトリは、`10_`、`20_`、`30_` のように10刻みで採番する。
- `01_`、`02_` のような1刻みの採番は行わない。
- 理由は、後からディレクトリを追加する際に、採番の隙間を利用して挿入できるようにするためである。

### TODO の表記（タスク・課題管理）

- タスクと課題管理では、未対応・未確定の項目を、赤字太字で `TODO:` と明記する。
- 記載例: `<span style="color:red;"><strong>TODO:</strong></span> ...`

### 改版履歴の記載（Markdown ファイル）

- 改版履歴を持つ種別（「ファイル種別」を参照）の Markdown ファイル（`.md`）を新規作成、または修正する場合は、ファイル冒頭に改版履歴を記載する。
- 改版履歴を持たない種別のファイルには、改版履歴を記載しない。
- 改版履歴は、プレビュー時に表示されないよう、HTMLコメント（`<!-- -->`）で囲む。
- 大項目は1つの目的（新規作成、大きな追記など）を表す。
- 小項目は、同じ大項目内で発生した細かい修正・レビュー対応を、大項目の直下に `  - ` を付けて記載する。
- 小項目の対応日が大項目と異なる場合は、小項目側にも日付を記載する。
- 小項目の対応日が大項目と同じ場合は、日付を省略してよい。

## 課題管理

- 本リポジトリでは、課題管理をリポジトリ内では行わない。
- 課題管理と、作業の進み具合の管理は、GitHub Issueで行う。
- 理由は、解決した課題をリポジトリから削除する手間をなくし、削除し忘れた課題が資料として残るのを防ぐためである。  
  Issueは閉じれば一覧から消え、経緯はIssueの中に残る。

### Issueテンプレート

- Issueを作成する際は、`.github/ISSUE_TEMPLATE/` のテンプレートから、内容に合うものを選ぶ。

| テンプレート | 用途 |
| --- | --- |
| バグ報告 (bug) | 不具合の報告 |
| ドキュメント (docs) | `docs/` 配下のドキュメントの追加・更新 |
| 機能追加 (feature) | 新機能の追加・機能改善 |
| インフラ (infra) | インフラ（CDK）構成の変更・対応 |

- 関連する資料は、リポジトリ内のファイルパスまたはURLで記載する。

## ブランチ運用

- 開発メンバーのGit熟練度を考慮し、本リポジトリは `main` ブランチのみで開発を進めることを基本とする。
- ただし、ブランチを作成する場合は、以下のルールに従う。

### Issueとブランチの紐づけ

- ブランチを作成するかどうかは任意とする。
- ブランチを作成する場合は、何を目的に作られたブランチかを分かりやすくするため、GitHub Issueを起票し、Issueとブランチを1対1で紐づけることを推奨する。

### ブランチ命名規約

- ブランチは `main` から直接作成する。
- 種別・命名形式は以下の通りとする。

| 種別 | 用途 | 命名形式 | 例 |
| --- | --- | --- | --- |
| `feature` | 新機能の追加 | `feature/#{Issue番号}-{内容（kebab-case）}` | `feature/#2-add-catalog` |
| `fix` | 既存コード・既存ドキュメントの不具合・誤りの修正 | `fix/#{Issue番号}-{内容（kebab-case）}` | `fix/#1-scope-consistency` |
| `docs` | 不具合修正を伴わない、ドキュメントのみの新規追加・整備 | `docs/#{Issue番号}-{内容（kebab-case）}` | `docs/#1-steering-docs` |

- 生成AI関連の作業（Claude Codeスキルの追加など）は、ドキュメントではなく機能追加にあたるため `feature` に分類する。
- Issue番号には `#` を付ける（例: `#31`）。
  **理由**: Issueの番号であることをブランチ名から識別できるため。
- ブランチ名に `#` を含むため、シェルで指定するときは、引用符で囲む（例: `git switch -c "feature/#123-add-search"`）。
  **理由**: 引用符で囲まないと、`#` 以降がコメントとして扱われ、意図しない名前のブランチが作られるため。
- ブランチの内容を `main` へ反映する際は、Pull Requestを作成する。

### コミットメッセージ規約

- コミットメッセージには、Conventional Commits のような type/scope プレフィックス（例: `feat(auth): ...`）を付けない。
- 「内容 + Issue番号」のみを記載する。
- 例: `アンケート回答フォームを追加 (#123)`。

## ファイル・文字コードルール

- 文字コードは UTF-8（BOM なし）を基本とする。
- 改行コードは LF に統一する。
- `tmp/` はコミット対象外の一時資料置き場であり、自由に作成・利用してよい。
