# Webアプリのアーキテクチャ

## 対象と責務

{{アプリの目的、対象範囲、利用者と外部システム}}

フロントエンドはNuxt・Vue・VuetifyのSPAとし、画面からバックエンドAPIを呼び出す。
バックエンドは`backend/<サービス名>/`の単位で分け、各サービスの責務、仕様、テスト、専用インフラをそのサービスに置く。
独立した変更とリリースを可能にするため、サービス間で共通のソースディレクトリを持たず、必要な共通処理は各サービスで保持するか、バージョン付きパッケージとして利用する。
サービス本体の言語は各サービスで定め、Pythonを標準案とする。

### リソースの名前

AWSのリソース名は[AWSリソース命名規則.md](AWSリソース命名規則.md)に従う。

### 共有インフラとサービス専用インフラの分け方

画面配信用S3・CloudFrontなど、サービスをまたぐリソースは共有インフラに置く。
Lambda・API Gatewayなどサービスの変更とともにデプロイするリソースは、そのサービスのインフラに置く。
サービス専用のリソースを共有側に置くと、サービス単位の変更でも共有インフラを変更する必要が生じるためである。

### GitHub Actions用のIAMロール

デプロイ対象と環境の組ごとにIAMロールとGitHub Environmentを分け、信頼ポリシーで利用可能なリポジトリとEnvironmentを制限する。
GitHub Actions自身が利用するロールの変更方法と、既存のOIDCプロバイダーの有無は、対象環境の管理方針に従って定める。

### Lambdaのパッケージ形式

コンテナイメージ形式を採用する場合、実行に不要なテストや依存ディレクトリをイメージに含めない。
実際のパッケージ形式はサービスの設計で定める。

### デプロイの順番と実行場所

サービスのAPIを共有インフラが参照する場合は、参照先を先に用意してから共有側を更新する。
画面の配信とキャッシュ更新は、対応するAPIと共有インフラの準備を確認して行う。
実行場所・権限・承認方法は対象環境の運用手順で定める。

## 共通の構成方針

### サービスのディレクトリの形

- サービスの直下を、Node.jsのプロジェクトとする。  
  サービスの直下の`package.json`には、そのサービスで使うNode.jsの依存関係をまとめる（CDK、APIのテストのPlaywright、本体をTypeScriptで書く場合は本体の依存関係）。
- 本体をNode.js以外の言語で書く場合は、その言語の設定ファイル（Pythonなら`pyproject.toml`）も、サービスの直下に置く。
- サービスの中の下位のディレクトリには、`package.json`を置かない。

**理由**: 本体の言語を変えても、ディレクトリとファイルの置き場所を変えずに済むようにするためである。  
置き場所が変わらなければ、CDKのLambdaの定義や、GitHub Actionsの対象ディレクトリの指定を直さずに済む。  
また、Node.jsのプロジェクトの中に、ワークスペースとして登録していない別のNode.jsのプロジェクトを置くと、親の設定が子に効いたり、子が親の依存関係を意図せず使えたりする。  
`package.json`をサービスに1つだけにすることで、この問題を避ける。

### サービスの中の設計

サービスの中だけで決めてよいこと（本体の言語、`src/`の中の分け方、そのサービスのインフラの構成など）は、各サービスの`backend/<サービス>/docs/20_rules/アーキテクチャ.md`で定める。  
ただし、本ドキュメントで定めるサービス共通の約束（サービスのディレクトリの形、APIのパス、共有インフラからの値の受け取り方など）には従う。

本体の言語は、Webアプリ全体では定めず、サービスごとに決める。

**理由**: 各サービスは、外から見える約束を守る限り、中身を個別に変えてよい。  
サービスの中の設計をサービスの資料に置くことで、中身の変更の影響と、その資料の更新を、そのサービスの中に閉じ込められる。

### サービス間の共通処理

`backend/`配下には、サービス間で共有するソースのディレクトリを置かない。

**理由**: 共有するソースのディレクトリがあると、そこを変更するたびに、全サービスのテストとデプロイが必要になる。  
その結果、サービス同士が切り離せなくなり、サービス単位で分ける目的と逆になる。  
ログ出力などの基盤処理は、AWS Lambda Powertoolsなどの外部ライブラリで足りる。

共通化したい処理がある場合は、次のどちらかで対応する。

- 各サービスが同じ処理をそれぞれ持つ（重複を許す）。
- バージョン付きのパッケージとして配布し、各サービスが利用するバージョンを自分で選べるようにする。

### サービス名の付け方

- サービスのディレクトリは、ケバブケースで名付け、`-service`は付けない（例: `catalog`）。
- サービスの中のパッケージやモジュールは、本体の言語の慣習に従って名付ける（例: Pythonならスネークケースの`products`）。
- サービス名には、そのサービスに何を入れるかが分かる名前を付ける。  
  `management`のように意味が広い名前は、関係のない機能が入り込む原因になるため使わない。


### サービスごとにCDKアプリを持つ

サービス専用のインフラは、CDKアプリを1つにまとめず、サービスごとに1つのCDKアプリとして持つ。  
CDKの設定（`cdk.json`）はサービスの直下に置き、CDKのコードは`backend/<サービス>/infra/cdk/`に置く。

**理由**: 資料と同じく「説明・定義する対象と同じ場所に置く」という原則に合わせるためである。  
コード・インフラ・資料がサービスの下にそろうため、サービスを切り出すときはディレクトリを1つ移すだけで済む。  
また、CDKアプリが分かれていることで、スタック間でpropsによる値の受け渡し（後述のExportの固定化の原因）が構造的に起きなくなる。

CDKアプリを複数持つことで起きる問題には、次のように対応する。

| 問題 | 対応 |
| --- | --- |
| CDKのバージョンのずれ | すべての`package.json`で`aws-cdk-lib`と`aws-cdk`のバージョンを固定し、同じものにそろえる。<br/>バージョンを上げるときは、すべてのCDKアプリを同時に上げる。 |
| 共通の書き方（スタック名の付け方、タグ、Lambdaの共通設定など）の重複 | 共通の書き方は、各サービスの中に書く。<br/>3つ目のサービスを追加するときに、共通の部品として切り出すかを判断する。<br/>サービスが2つまでの段階で共通化すると、何を共通にすべきかが分からないまま部品を作ることになるためである。 |

### スタック間の値の渡し方

スタック間で受け渡す値は、SSMパラメータストアに書き込み、使う側がそこから読み込む。  
CloudFormationのExport／ImportValueは使わない。

| 値 | 書き込む側 | 読み込む側 |
| --- | --- | --- |
| API GatewayのURL | 各サービス | 共有インフラ（CloudFrontの転送先に使う） |

**理由**: Export／ImportValueで値を渡すと、読み込み側のスタックが1つでも残っている間は、Export側の値を変更・削除できなくなるためである。


## 資料の配置

- 全体の規約、API共通仕様、要件、共有インフラ設計は`docs/`に置く。
- 画面固有の規約・画面設計は`nuxt/docs/`に置く。
- API仕様、専用インフラ設計、サービスの運用と内部設計は`backend/<サービス名>/docs/`に置く。
- 画面E2Eは`e2e/`に、単体・APIテストは各サービスに置く。
- アプリ全体のテスト方針は[テスト規約](テスト規約.md)に従う。
