## 機能とサービスの分け方

### 1つのWebアプリの中で機能を分ける

フロントエンドはNuxt・Vue・VuetifyのSPAとし、画面からバックエンドAPIを呼び出す。
共通レイアウトや認証の重複を避けるため、関連する機能は1つのWebアプリ内で分ける。
利用者の範囲、開発チーム、リリース周期、ドメインが異なる場合は、アプリを分ける必要性を検討する。

### バックエンドはサービス単位で分ける

バックエンドは`backend/<サービス名>/`の単位で分け、各サービスの責務、仕様、テスト、専用インフラをそのサービスに置く。
独立した変更とリリースを可能にするため、サービス間で共通のソースディレクトリを持たず、必要な共通処理は各サービスで保持するか、バージョン付きパッケージとして利用する。
サービス本体の言語は各サービスで定め、Pythonを標準案とする。

### 共有インフラとサービス専用インフラの分け方

画面配信用S3・CloudFrontなど、サービスをまたぐリソースは共有インフラに置く。
Lambda・API Gatewayなどサービスの変更とともにデプロイするリソースは、そのサービスのインフラに置く。
サービス専用のリソースを共有側に置くと、サービス単位の変更でも共有インフラを変更する必要が生じるためである。
共有リソースを特定のサービスに持たせると、他のサービスがそのサービスに依存し、切り出しや削除が難しくなる。

| リソース | 置き場所 |
| --- | --- |
| 画面配信用のS3とCloudFront | `infra/shared/` |
| CloudFront用のWAF | `infra/shared/`のus-east-1のスタック |
| API Gateway用のWAF | `infra/shared/`のWAFのスタック |
| GitHub Actions用のIAMロール | `infra/foundation/` |
| Lambda、API Gateway、サービス用のIAMロール、API Gateway用のWAFとステージの関連付け | `backend/<サービス名>/infra/cdk/` |

### 画面とAPIの転送（Lambda 関数 URL）

CloudFrontは画面をS3に、`/<サービス名>/*`を該当サービスのLambda関数URLに転送する。
サービスはデプロイ時に転送先をCloudFrontのKeyValueStoreに登録する。
APIの応答はキャッシュせず、関数URLにはIAM認証を設定する。
CloudFrontはOACで署名し、関数URL側は対象のディストリビューションからの呼び出しを許可する。
サービス側で利用者のトークンを検証する場合は、OACの署名に使うAuthorizationと別に利用者トークンを渡す契約を定める。

### 画面とAPIの転送（API Gateway）

CloudFrontから画面とAPIを同一オリジンで公開し、パスで転送先を分ける。
`/<サービス名>/*`をそのサービスのAPI Gatewayへ、それ以外を画面配信用のS3へ転送する。
API Gatewayへの転送では、転送先のパス（オリジンのパス）にステージ名を設定し、APIのパスの先頭をサービス名にする。
CloudFrontの割り当てドメインまたは独自ドメインは対象環境の決定に従う。

**理由**: 画面とAPIを同じオリジンにすると、ブラウザーからの同一オリジン通信ではCORSの設定が不要になり、事前の確認の通信（プリフライト）も起きない。
サービス追加時は、対象サービスのAPIへの転送先を共有インフラに追加する。

### APIの転送の設定（API Gateway）

APIへ転送するビヘイビアは、キャッシュを使わない（キャッシュポリシー`CachingDisabled`）。
リクエストは、Hostヘッダーを除いて、API Gatewayへ渡す（オリジンリクエストポリシー`AllViewerExceptHostHeader`）。
`Authorization`ヘッダー、クエリ文字列、Cookieも、この設定でAPIに渡る。

**理由**: APIの応答をキャッシュすると、ある利用者への応答が、別の利用者に返るおそれがある。
Hostヘッダーを渡すと、API Gatewayが要求を受け付けない。

### 画面のURLの振り分け

画面へ転送するビヘイビア（既定のビヘイビア）にCloudFront Functionsを付け、拡張子の無いパスを`/index.html`に書き換える。
CloudFront全体のエラーページの設定（403・404のときに`/index.html`を返す設定）は使わない。

**理由**: エラーページの設定はディストリビューション全体にかかる。
使うと、APIの403・404の応答まで`/index.html`に置き換わり、画面がエラーの内容を受け取れなくなる。

### IP制限

CloudFrontにWAFのWebACL（スコープ`CLOUDFRONT`）を付け、許可したIPアドレス以外からのアクセスを断る。
画面とAPIはどちらもCloudFrontを通るため、このWebACLで両方にIP制限がかかる。
許可するIPアドレスは、規約に書かず、インフラの設定に置く。
CloudFront用のWAFはus-east-1に作る決まりのため、us-east-1にも共有インフラのスタックを置き、us-east-1でもcdk bootstrapを行う。

### API Gatewayへの直接のアクセスを防ぐ

CloudFrontは、API Gatewayへ転送するときに、秘密の値を入れたヘッダー（カスタムヘッダー）を付ける。
API GatewayのステージにWAFのWebACL（スコープ`REGIONAL`）を付け、このヘッダーが無い要求と、値が違う要求を断る。
API Gateway用のWebACLは、共有インフラのWAFのスタックに1つ置き、各サービスのステージに関連付ける。
WAFを付けられるよう、API GatewayはREST APIを使う（HTTP APIにはWAFを付けられない）。
秘密の値は、規約とソースコードに書かない。

**理由**: API GatewayのURLは公開されており、CloudFrontを通らずに直接呼べる。
直接呼ばれると、CloudFrontのIP制限がかからない。

## デプロイ（GitHub Actions）

### ワークフローの書き方

ワークフローはリポジトリ直下の`.github/workflows/`に置き、デプロイ単位と変更対象に分ける。
リソース定義はCDKアプリに置き、ワークフローは必要なコマンドを呼び出す。
デプロイするスタックを明示し、意図しないスタックを一括更新しない。
共通の認証手順は再利用し、権限と環境の組を明確にする。

## 共通の構成方針

### サービスのディレクトリの形

- サービスの直下を、Node.jsのプロジェクトとする。  
  サービスの直下の`package.json`には、そのサービスで使うNode.jsの依存関係をまとめる（CDK、APIのテストのPlaywright、本体をTypeScriptで書く場合は本体の依存関係）。
- 本体をNode.js以外の言語で書く場合は、その言語の設定ファイル（Pythonなら`pyproject.toml`）も、サービスの直下に置く。
- サービスの中の下位のディレクトリには、`package.json`を置かない。

**理由**: 本体の言語を変えても、ディレクトリとファイルの置き場所を変えずに済むようにするためである。  
置き場所が変わらなければ、CDKのLambdaの定義や、GitHub Actionsの対象ディレクトリの指定を直さずに済む。  
また、Node.jsのプロジェクトの中に、ワークスペースとして登録していない別のNode.jsのプロジェクトを置くと、親の設定が子に効いたり、子が親の依存関係を意図せず使えたりする。  
`package.json`をサービスに1つだけにすることで、この問題を避ける。

### サービスの中の設計

サービスの中だけで決めてよいこと（本体の言語、`src/`の中の分け方、そのサービスのインフラの構成など）は、各サービスの`backend/<サービス>/docs/20_rules/アーキテクチャ.md`で定める。  
ただし、本ドキュメントで定めるサービス共通の約束（サービスのディレクトリの形、APIのパス、共有インフラからの値の受け取り方など）には従う。

本体の言語は、Webアプリ全体では定めず、サービスごとに決める。

**理由**: 各サービスは、外から見える約束を守る限り、中身を個別に変えてよい。  
サービスの中の設計をサービスの資料に置くことで、中身の変更の影響と、その資料の更新を、そのサービスの中に閉じ込められる。

### サービス間の共通処理

`backend/`配下には、サービス間で共有するソースのディレクトリを置かない。

**理由**: 共有するソースのディレクトリがあると、そこを変更するたびに、全サービスのテストとデプロイが必要になる。  
その結果、サービス同士が切り離せなくなり、サービス単位で分ける目的と逆になる。  
ログ出力などの基盤処理は、AWS Lambda Powertoolsなどの外部ライブラリで足りる。

共通化したい処理がある場合は、次のどちらかで対応する。

- 各サービスが同じ処理をそれぞれ持つ（重複を許す）。
- バージョン付きのパッケージとして配布し、各サービスが利用するバージョンを自分で選べるようにする。

### サービス名の付け方

- サービスのディレクトリは、ケバブケースで名付け、`-service`は付けない（例: `catalog`）。
- サービスの中のパッケージやモジュールは、本体の言語の慣習に従って名付ける（例: Pythonならスネークケースの`products`）。
- サービス名には、そのサービスに何を入れるかが分かる名前を付ける。  
  `management`のように意味が広い名前は、関係のない機能が入り込む原因になるため使わない。


## 資料の配置

- 全体の規約、API共通仕様、要件、共有インフラ設計は`docs/`に置く。
- 画面固有の規約・画面設計は`nuxt/docs/`に置く。
- API仕様、専用インフラ設計、サービスの運用と内部設計は`backend/<サービス名>/docs/`に置く。
- 画面E2Eは`e2e/`に、単体・APIテストは各サービスに置く。
- アプリ全体のテスト方針は[テスト規約](テスト規約.md)に従う。
