# Node.jsコーディング規約（webapp）

本ドキュメントは、``配下のNode.js（TypeScript、Vue）のコードの書き方と、Nodeのバージョン、パッケージの追加の決まりを定める。  
画面の構成と方針（ファイルの置き場所、部品の分け方、メッセージの管理など）は、[フロントエンド実装方針.md](../../nuxt/docs/20_rules/フロントエンド実装方針.md)で定める。

`> [AI]`で始まる引用は、AIが従う指示と、AIに伝える前提である。人は、読み飛ばしてよい（書き方は、[screen-design-rules/README.md](../../nuxt/docs/20_rules/screen-design-rules/README.md)の「`[AI]`」の記載に従う）。

## Vueのファイルの書き方

### ファイルの中の順番

1つのファイルの中は、次の順番で書く。

1. `<script setup lang="ts">`
2. `<template>`
3. `<style scoped>`（必要な場合だけ）

**理由**: 順番がそろっていると、どのファイルでも、処理・画面・見た目の場所をすぐに見つけられる。

## 名前の付け方

| 対象 | 付け方 | 例 |
| --- | --- | --- |
| 共通の部品のファイル | パスカルケースで、先頭に`App`と分類名を付ける | `components/app/feedback/AppFeedbackConfirmDialog.vue` |
| 共通の部品の分類のディレクトリ | 小文字の英単語 | `components/app/feedback/` |
| 機能の部品のファイル | パスカルケースで、先頭に機能名を付ける | `components/products/ProductTree.vue` |
| 機能のディレクトリ | ケバブケース | `components/products/` |
| ページのファイル | ケバブケース（URLになるため） | `pages/products.vue` |
| composableのファイルと関数 | キャメルケースで、先頭に`use`を付ける | `useProduct.ts`、`useProduct()` |
| utilsのファイルと関数 | キャメルケース | `buildProductList.ts`、`buildProductList()` |
| 型 | パスカルケース | `Product`、`ProductResult` |
| `data-testid` | ケバブケース | [E2Eテスト作成規約.md](E2Eテスト作成規約.md)の「画面側に識別子を付ける」に従う |

**理由**: 部品のファイル名を、置いたディレクトリ名で始めると、ファイル名と同じ名前で、部品を使える（`<AppFeedbackConfirmDialog />`）。

> [AI]
> - Nuxtは、部品が置かれたディレクトリの名前を、部品の名前の先頭に付ける。ファイル名を、ディレクトリ名のパスカルケースで始めれば、重複が除かれる。始めなければ、`<AppFeedbackAppConfirmDialog />`のように、長い名前になる。

## CSS

- 画面全体で共通のCSSは、`assets/css/`に置き、`nuxt.config.ts`の`css`に登録する。
- 1つの部品やページだけに効かせるCSSは、そのファイルの`<style scoped>`に書く。
- 色は、値（`#1C5D99`など）を直接書かず、Vuetifyのテーマに定義した名前（`primary`など）で指定する。

**理由**: 色の値を画面ごとに書くと、色を変えるときに、すべての画面を直すことになる。  
テーマの名前で指定しておけば、テーマの定義を1か所直すだけで済む。

## TypeScript

- `any`は使わない。  
  型が分からない外部のデータは、`unknown`で受け取り、中身を確かめてから使う。
- インデントは、半角スペース2つとする。
## Nodeのバージョン

- webapp配下でNodeを使うもの（画面、CDK、バックエンドのテストなど）は、同じ系統のNodeを使う。系統は、24とする。
- Nodeの保証期限（EOL）の約半年前に、次のLTSの系統に上げる。

**理由**: 画面、CDK、CIで、Nodeのバージョンが違うと、同じコードが、環境によって、動いたり動かなかったりするため。  
保証期限が切れたNodeは、セキュリティの修正を受けられなくなるため、期限の前に、上げる時間を取る。

> [AI]
> - 使うバージョンは、`package.json`の`engines`で指定する（例: `">=24.22.1 <25"`）。
> - CI（GitHub Actions）の`setup-node`は、`node-version`に系統（例: `'24'`）を指定し、`check-latest: true`を付ける。`check-latest: true`がないと、CIの実行環境に入っている古い版が使われ、セキュリティの更新を取り込めないため。

## パッケージの追加

- パッケージは、バージョンを固定して追加する（`pnpm add -E <名前>@<バージョン>`）。
- インストール時のスクリプトが承認待ちになり、`ERR_PNPM_IGNORED_BUILDS`のエラーになった場合は、`nuxt/pnpm-workspace.yaml`の`allowBuilds`に、パッケージごとに、`true`（実行する）か、`false`（実行しない）を書く。
- 値は、そのスクリプトが、動作に必要かで決める。必要でなければ`false`にする。決めた理由は、`pnpm-workspace.yaml`のコメントに書く。

**理由**: pnpmは、依存パッケージのインストール時のスクリプトを、承認制にしている。  
承認が決まっていないと、インストールがエラーになり、CIや、ほかの開発者の環境でも、同じように止まる。  
動作に必要でないスクリプトを許可しないのは、パッケージの更新で、スクリプトの中身が変わっても、実行され続けるのを避けるためである。

> [AI]
> - 判断を促す仮の文（`set this to true or false`）のままで、`pnpm-workspace.yaml`をコミットしない。

## コードの検査（ESLint）

- コードの検査には、ESLintを使う。`nuxt/`で`pnpm lint`を実行する（自動で直せるものは`pnpm lint:fix`）。
- コードを変更したら、設定済みのlintコマンドで、指摘が0件であることを確認する。
- 指摘は、コードを直して解消する。ルールを無効にする（`eslint-disable`、設定でオフにする）場合は、その理由を、コメントに書く。
- CIで画面をデプロイする場合は、デプロイ前にlintを実行し、指摘があれば失敗とする。
- VS Codeでは、ESLintの拡張機能を入れると、指摘が書いた場所に表示される。

**理由**: メッセージのキーの打ち間違いのように、型チェックでは見つからない誤りを、実行する前に見つけるため。  
CIでも検査すれば、検査を忘れたコードが、デプロイされるのを防げる。  
ルールを無効にした理由を残すのは、あとから読む人が、意図した例外か、見落としかを、区別できるようにするため。

> [AI]
> - ESLintの設定と利用可能なコマンドはプロジェクトの実装を確認する。
> - メッセージのキーの検査は、`i18n/locales/ja.json`を読む。このプラグインは、JSON、JSON5、YAMLだけを読めるため、アプリの文言は`ja.json`に書き、`ja.ts`には書かない。
> - コードを変更したら、`pnpm lint`と`pnpm typecheck`を実行し、どちらも指摘が0件であることを確認してから、完了を報告する。
