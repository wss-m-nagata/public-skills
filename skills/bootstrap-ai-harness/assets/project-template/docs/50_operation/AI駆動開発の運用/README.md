# AI駆動開発の運用

このプロジェクトのAI駆動開発の運用（誰が何をして、人がどこで確認・判断するか）の入口である。  
処理フロー、AIが守る決まり、利用ツール、図は、[運用フロー.md](運用フロー.md)にある。

## 目的

AIと人が、同じ理解で作業を進めるために、作業の分担と、人の確認・判断の場所を定める。

## スタンス

- 仕様・設計書は、AI用と人用に分けない。  
  AIも人も、同じものを見る。  
- 要件定義と画面設計は、人が作る。  
  それをもとに、AIが設計書とプログラムの案を作る。  
- 人が、案を確認・判断する。  
  AIは、人の確認なしに先へ進まない。  
- 開発者は、ハーネス（AIが守る決まり）・スキル（AIの作業手順）・運用の整備に注力する。  
- 成果物の品質（レビュー）と、運用の品質にこだわる。  

## 用語

| 用語 | 意味 |
|---|---|
| チケット | 作業の記録帳。GitHub Issue のこと |
| 正式版 | 設計書の正式な置き場所（{{設計書の正式版の置き場所}}）にある版 |
| 取り込み | PR（変更の提出）を経て、本体に反映すること |
| スキル | AIの作業手順書 |
| ハーネス | AIが守る決まり |
| MCP / MCPツール | AIが外部のサービスの情報を取得・操作するための接続の仕組み |

## 役割

| No | 役割 | 内部／外部 | 担当すること |
|---|---|---|---|
| 1 | 要件定義・画面設計の担当 | どちらもあり | 要件定義書・画面詳細設計書を作る |
| 2 | 開発担当者 | 内部 | AIに依頼し、AIがつくったものを確認・判断する。チケットの作成、取り込み、正式版への反映を行う |
| 3 | レビュー担当者 | 外部 | 設計書をレビューして、合意する |
| 4 | 生成AI | — | 資料を読み、設計書・プログラム・テストなどの案をつくる。作業の記録を残す |

- 1人が、複数の役割を兼ねる場合がある。  

## スキル

スキルは、`.claude/skills/` に置く。  
スキルは、プロジェクトの決まり（ハーネス）を先に読み、読み取れないものだけを質問して、回答を `.agents/config/<スキル名>/settings.md` に保存する。

| 作業 | スキルのID | 使う工程 | 使う場面 |
|---|---|---|---|
| チケットの作成・更新 | `create-github-issue` | 設計、開発・テスト | 設計用・実装用のチケット（GitHub Issue）を作るとき。進捗・完了の記録にも使う |
| 処理フロー図の作成 | `process-flow-diagram` | 設計 | 画面・処理・テーブルの関係を、1枚の図にまとめるとき |
| API仕様書・テーブル定義書の作成、単体テスト仕様書の作成（バックエンド） | `nablarch-basic-design-excel` | 設計、開発・テスト | API仕様書・テーブル定義書を作るとき。実装が終わったあとに、単体テスト仕様書を作るとき |
| ER図の作成 | `feature-er-diagram-drawio` | 設計 | 機能ごとに、使うテーブルと、変更点を、ER図にまとめるとき |
| 設計書の修正手順（変更箇所一覧・確認資料の作成を含む） | `design-doc-revision` | 設計、開発・テスト | 設計書を作る・直すとき。変更箇所一覧と確認資料を作り、レビュー用の場所に置く・正式版に反映するための手順書を作る |
| 画面設計規約の作成 | `generate-screen-design-rules` | 設計（画面） | 画面設計規約（デザインの原則、画面の共通ルール）を、作る・更新するとき |
| 設計書・単体テスト仕様書の作成（画面） | `nablarch-frontend-design-excel` | 設計（画面）、テスト（画面） | 画面側（SPA）の設計書と単体テスト仕様書を、作る・更新するとき |
| 自動試験の作成 | `playwright-best-practices` | 開発・テスト | API・ブラウザの自動試験を書く・直すとき |
| プッシュ前の確認 | `pre-push-check` | 開発・テスト | プッシュする前に、全テスト・AIレビュー・規約チェックを流し、結果を報告するとき |

## ハーネス

ハーネスは、AIが守る決まりである。

### ハーネスの種類

| 種類 | 何を伝えるか |
|---|---|
| 指示書 | AIが、毎回最初に読む決まり |
| 規約 | コードや資料の作り方（コーディング、アーキテクチャ、テスト、命名、画面設計など） |
| 仕様 | 作るものの内容、用語 |
| 手順書 | 作業を進める順番（インストール、テストの進め方、この運用など） |
| チケットのフォーマット | チケットに、何を、どう書くか（Issueのひな形、ラベル） |
| 自動で動く仕組み | 決まりを、機械的に守らせる・確かめる（フック、承認なしで許可する操作、GitHub Actions） |

### リポジトリの中の配置

| 場所 | 内容 | 種類 |
|---|---|---|
| `AGENTS.md`、`CLAUDE.md` | AIへの共通の指示書。`CLAUDE.md` は、`AGENTS.md` を読み込む入口 | 指示書 |
| `README.md`、`docs/README.md` | リポジトリと資料の入口 | 指示書 |
| `.github/ISSUE_TEMPLATE/` | チケット（Issue）のひな形（バグ報告、ドキュメント、機能追加、インフラ） | チケットのフォーマット |
| `.github/workflows/`、`.github/claude/` | GitHub上で自動で動く処理（PRのAIレビュー、Issueの自動ラベル付けなど）。GitHub Actionsを設定した場合に置く | 自動で動く仕組み |
| `.claude/skills/` | スキル | — |
| `.claude/settings.json`、`.claude/hooks/` | 承認なしで許可する操作、保存時の整形のフック。おすすめの設定を使う場合に置く | 自動で動く仕組み |
| `.agents/config/` | スキルの設定（チームで共有する） | — |
| `docs/` | アプリ全体の資料。`10_installation/`（インストール手順）、`20_rules/`（規約）、`30_glossary/`（用語集）、`40_spec/`（仕様）、`50_operation/`（手順書） | 手順書・規約・仕様 |
| `backend/<サービス>/docs/` | サービスごとの資料 | 規約・仕様・手順書 |
| `nuxt/docs/` | 画面側の資料。規約（CSS、フロントエンド実装方針、画面設計規約）、設計、テストの進め方 | 規約・仕様・手順書 |

## 情報の置き場所

| 置き場所 | 入っているもの |
|---|---|
| リポジトリ | ソースコード、ハーネスの資料、スキル、変更履歴。テスト結果とAIレビューの結果は、PR に載せる |
| GitHub | 作業の記録（チケット）、PRのAIレビュー、開発環境への反映 |
| {{設計書の正式版の置き場所}} | 設計書の正式版（正）と、設計書を作り・直すための作業場 |

- チケットは、履歴として残るが、正式な成果物ではない。  
  成果物は、{{設計書の正式版の置き場所}}とリポジトリに置く。  
- 設計書の正は、{{設計書の正式版の置き場所}}の正式版である。  
  実装と設計書が食い違ったときは、設計書に従う。  
  設計を変える場合は、別の作業として直す。
