# おすすめの設定（任意）

Claude Codeの設定（承認なしで許可する操作、保存時の整形のフック）を、対象プロジェクトに反映する手順である。
任意の機能であり、入力シートで「する」とされた項目だけ、反映する。

ひな形は `assets/optional/recommended-settings/` にある。
`assets/project-template/` には入れていない。
そのため、「しない」場合に、ファイルが配置されることはない。

## 0. 入力シートの値を、設定ファイルに保存する（セットアップの最初に行う）

する・しないは、入力シートの「ハーネスの設定」シートの値（既定値を当てた値）を使い、利用者に質問しない。

| 項目 | 入力シートの項目のID |
| --- | --- |
| 承認なしの許可・確認・禁止（`permissions`） | `harness.permissions` |
| 保存時の整形のフック（`formatter-hooks`） | `harness.formatter_hooks` |
| アプリのルート | `harness.app_root` |

値は、設定ファイル `.agents/config/bootstrap-ai-harness/settings.md`（プロジェクトルート直下）に保存する。
ひな形は、`assets/optional/recommended-settings/settings.template.md` にある。

| 状態 | すること |
| --- | --- |
| 設定ファイルが無い | ひな形から作り、入力シートの値を書く |
| 設定ファイルがあり、入力シートの値と違う | 入力シートの値で直す（入力の正本は入力シートである） |
| 項目が「する」で、まだ反映していない | 2. 以降を行う |
| 入力シートが無い作業で、設定ファイルの値がある | 設定ファイルの値に従い、聞かない |
| 入力シートが無い作業で、設定ファイルの値が「未確認」 | 1. の説明をして尋ね、回答を保存する |

- 設定ファイルは、チームで共有する（Gitに入れる）ものである。`.gitignore` に入れない。
  保存したら、Gitに入れるかどうかを、利用者に確かめる。
- 作業用ファイルを置く `.agents/state/` は、Gitに入れない（`.gitignore` に `/.agents/state/` を書く）。

## 1. 尋ねるとき

入力シートが無い作業で、設定ファイルの値が「未確認」のときだけ、次のとおり尋ねる。

> おすすめの設定を、使いますか。
> - **承認なしの許可・確認・禁止**：Gitの状態の確認や、型チェックなどは、承認なしで実行できるようにします。コミットは、実行のたびに確認し、プッシュとマージは、禁止します。AIが、承認の確認で、何度も止まるのを減らし、人が行うべき操作を、AIが実行してしまうのを防ぎます。
> - **保存時の整形のフック**：AIがファイルを編集するたびに、自動で整形します（TypeScript、Vue、JSONはPrettier、PythonはBlack）。コードの書き方がそろい、レビューで、書き方の違いによる差分が、混ざらなくなります。

回答を、設定ファイルの表に書く（「しない」も、書く）。

## 2. 承認なしの許可・確認・禁止（`permissions`）

`.claude/settings.json` の `permissions` に、次を統合する。

| 区分 | 操作 |
| --- | --- |
| 承認なしで許可 | Gitの参照（`status`、`diff`、`log`）、GitHubの参照（Issue、PR、ラベル、Actionsの実行結果）、型チェック、コードの検査、単体テスト（`pnpm typecheck`、`pnpm lint`、`uv run pytest`、レポートを出す `uv run python tests/unit_report.py`） |
| 実行のたびに確認 | `git commit` |
| 禁止 | `git push`、`gh pr merge` |

- 規則は、`assets/optional/recommended-settings/permissions.json` にある。
  プロジェクトのコマンドに合わせて、書き換える（例：パッケージマネージャーが違うときは、`pnpm` を直す。単体テストのレポートを出すコマンドの名前が違うときは、`tests/unit_report.py` を直す）。
- 既存の規則は、変更も削除もしない。足りない規則だけを足す。
- 禁止は、書き方を変えた実行（例：`git -C . push`）を、止められない。
  確実に止めたいときは、`.claude/settings.json` の規則ではなく、GitHub側の設定で、制限する。

## 3. 保存時の整形のフック（`formatter-hooks`）

AIがファイルを編集した直後に、拡張子に応じて、整形ツールを実行する。

| ツール | 対象の拡張子 | 補足 |
| --- | --- | --- |
| Prettier | `.ts`、`.vue`、`.mjs`、`.js`、`.json` | `nuxt/` 配下は、先にESLintの自動修正を行う |
| Black | `.py` | ファイルから上に辿った、最初の `pyproject.toml` のサービスで、`uv run black` を実行する |

- 拡張子の絞り込みは、`.claude/settings.json` の `if`（`Edit(*.ts)` など）で行う。
  `if` には、1つのパターンしか書けず、`|` や `{ts,vue}` は使えない。
  ツール（`Edit`、`Write`）と拡張子の組み合わせごとに、別のフックを書く。
- 生成物と依存（`node_modules`、`.nuxt`、`.output`、`dist`、`cdk.out`、`.venv`）は、整形しない。
- `.prettierignore` で、ロックファイル、`docs`、Markdownも、除外する。
  Markdownを除外するのは、行末の半角スペース2つによる改行など、文書の規約を崩さないためである。
  `docs` を除外するのは、設計書の生成元のJSONなど、資料を、整形で書き換えないためである。
- `.prettierrc` の既定は、`semi: false`、`singleQuote: true`、`tabWidth: 2`、`printWidth: 100` である。
  プロジェクトの規約に合わせて、決める。

### 3.1. ひな形を写して、設定に統合する

対象プロジェクトのルートで、次を実行する。
最初は、確認だけ（dry-run）になる。

```powershell
python <スキル>/scripts/recommended-settings/apply_recommended_settings.py --items permissions,formatter-hooks
```

- `--items` には、入力シートで「する」とされた項目を、カンマ区切りで指定する。
- アプリがリポジトリの直下でなく、サブディレクトリにあるときは、`--app-dir <ディレクトリ名>` を付ける。
  設定ファイルの「アプリのルート」に書いた値を使う。
- 出力で、写す先と、`settings.json` への追加を確認してから、`--apply` を付けて、もう一度実行する。
- 同名のファイルが既にあるときは、上書きせず、スキップして、同一か、内容が異なるかを表示する。
  内容が異なるときは、既存のファイルと統合する。
- `.claude/settings.json` は、上書きしない。足りない規則とフックだけを足す。
- 修正履歴の担当者は、`--author "<会社の略称><氏名>"` で、人が指定した値だけが入る。
  AIは、人の名前を推測して指定しない。分からないときは、利用者に尋ねる。

### 3.2. 整形ツールを導入する（人が行う）

スクリプトは、ツールの導入を行わない。次を、利用者が行う。

```powershell
# Prettier（アプリのルートの nuxt で実行）
cd <アプリのルート>/nuxt
pnpm add -D -E prettier eslint-config-prettier

# Black（Pythonのサービスごとに実行）
cd <アプリのルート>/backend/<サービス>
uv add --dev black
```

- Prettierは、`-E` で、バージョンを固定する（プロジェクトのパッケージの追加の規約に合わせる）。
- ESLintの設定（`eslint.config.mjs`）の最後に、`eslint-config-prettier` を追加する。
  ESLintと、Prettierが、同じ箇所を、逆向きに直し合うことを、避けるためである。
- Blackは、PCのPythonには入れず、サービスの開発用の依存に入れる。
  バージョンを固定し、`uv sync` で、誰の環境にも、同じものが入るようにするためである。
- `pyproject.toml` に `black` がないサービスでは、フックは、整形せず、警告だけを出す。
- サービスを追加したときは、そのサービスにも、Blackを追加する。

### 3.3. 既存のコードを、先に、一括整形する

フックを有効にする前に、既存のコードを、一括で整形し、**別のコミット**にする。
整形していないコードに、フックが動くと、AIが編集していない部分の差分が、混ざるためである。

- 整形の対象と、影響の大きさは、`--check`（変更しない）で、先に確かめる。
- 整形のあとに、型チェック、コードの検査、テストが、成功することを確認する。
- 整形だけのコミットとして、差分を確認する。

### 3.4. 規約に、整形の決まりを追記する

整形のフックを使うときは、規約に、整形の決まりを追記する。
ひな形は、`assets/optional/recommended-settings/rules/` にある。

| ひな形 | 追記先 |
| --- | --- |
| `node-formatting.md` | `docs/20_rules/Node.jsコーディング規約.md`（節として、末尾に足す） |
| `python-formatting.md` | `docs/20_rules/Pythonコーディング規約.md`（節として、末尾に足す） |

- 追記先の規約の修正履歴に、1行を足す（担当者は、人が指定した値だけを書く）。
- ひな形は、プロジェクトの実際の設定（`.prettierrc` の値、Blackの設定、フックの対象）に合わせて、直してから追記する。
- 整形のフックを使わないときは、追記しない。規約に、整形ツールの記述を、残さない。
- `AGENTS.md` には、整形の記述を足さない。フックが、AIの行動に関係なく、整形するためである。
- Pythonの規約は、整形以外の決まり（インデント、命名、docstringなど）を、プロジェクトの方針に合わせて、別に決める。

### 3.5. 有効にする

- Claude Codeを、再起動する。設定の変更は、再起動後に、有効になる。
- 確認用に、整形が必要な内容のファイルを、AIに編集させ、整形されることを確かめる。
  構文エラーのファイルでは、フックが、AIにエラーを伝えることも、確かめる。

## 4. 完了の報告

次を報告する。

- 入力シートの値（する、しない）と、設定ファイルの保存先。
- 写したファイルと、`settings.json` に足した内容。
- 利用者の対応が要るもの（ツールの導入、一括整形のコミット、再起動、修正履歴の担当者）。
- 確認できたことと、確認できていないこと（`if` の動作は、再起動して編集するまで、確認できない）。
