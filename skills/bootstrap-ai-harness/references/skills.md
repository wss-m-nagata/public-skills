# 必須スキルの導入と使用

## 標準で導入するスキル

| 区分 | スキル | 用途 | 実行するタイミング |
| --- | --- | --- | --- |
| 設計書・図 | `generate-screen-design-rules` | DADSを主、Carbonを補完として、具体値と部品の状態を含む画面設計規約を作る。 | 初期構築時と規約の更新時。 |
| 設計書・図 | `process-flow-diagram` | 画面、バックエンド処理、テーブルやファイルの関係を処理フロー図に整理する。 | 機能の洗い出し、見積もり、設計の前段階。 |
| 設計書・図 | `nablarch-frontend-design-excel` | 画面一覧・画面遷移・画面機能設計・画面単体テスト仕様などをExcelの様式で作る。 | 対象と内容が決まり、設計書を作成・更新するとき。 |
| 設計書・図 | `nablarch-basic-design-excel` | API、機能、外部インタフェース、テーブルなどのバックエンド設計書や単体テスト仕様をExcelの様式で作る。 | 対象と内容が決まり、設計書を作成・更新するとき。 |
| 汎用版 | `create-github-issue` | チケット（GitHub Issue）の作成、作業ブランチの準備、進捗の記録。 | 設計・開発の作業を始めるとき。 |
| 汎用版 | `design-doc-revision` | 設計書の修正、変更箇所一覧と確認資料の作成、レビュー用の場所への配置・正式版への反映のスクリプトの作成。 | 設計書を作る・直すとき。 |
| 汎用版 | `feature-er-diagram-drawio` | 処理フロー図の機能ごとに、使うテーブルと変更点をER図にまとめる。 | DBを使う機能の設計。 |
| 汎用版 | `pre-push-check` | 全テスト・AIレビュー・規約チェックを流し、結果を報告する。 | プッシュする前。 |
| 外部 | `playwright-best-practices` | API・ブラウザの自動試験を書く・直す。 | 開発環境での試験。 |

- 各スキルを使う工程は、`docs/50_operation/AI駆動開発の運用/運用フロー.md` の「使用スキル」に従う。
- 明示されたプロジェクト方針により不要なものがあれば、理由を示して除外する。
- `design-standards` は、画面規約で必要に応じて用いる任意の補完スキルであり、必須ではない。
- 汎用版の4つは、初回の使用時に、プロジェクトのハーネスを読み、読み取れないものだけを質問して、回答を `.agents/config/<スキル名>/settings.md` に保存する。
  このスキルでは、その設定ファイルを作らない。

## 導入

1. 公開スキルのリポジトリを確かめる。
   入力シートの「公開スキルのリポジトリ」（`harness.skills_repo`）を使い、`.agents/config/bootstrap-ai-harness/settings.md` の「公開スキルのリポジトリ」に保存する。
   入力シートが無い作業（スキルの追加だけなど）では、設定ファイルの値を使う。
2. 新規プロジェクトのGitリポジトリのルートで、導入済みのスキル（`.claude/skills/`）を確かめ、不足するスキルだけを、AIが次のコマンドで導入する。

   ```powershell
   # 公開スキル（区分が「設計書・図」「汎用版」のもの）
   npx skills add <公開スキルのリポジトリ> --skill <スキル名> --agent claude-code

   # 外部のスキル
   npx skills add currents-dev/playwright-best-practices-skill --skill playwright-best-practices --agent claude-code
   ```

   `nablarch-frontend-design-excel`は、利用可能なものを使う前提とし、同名スキルを無条件で再導入しない。
   Codexでも使用する場合は、`--agent claude-code` を `--agent codex` に置き換えて実行する。
   それぞれの配置先、正本と同期方法を定める。
3. 各コマンドの終了結果と導入先の `SKILL.md`、付属資料を確認する。
   各スキルの`SKILL.md`が参照するテンプレート・資料・実行ファイルがそろっていることを確認する。
   中断された導入ではディレクトリや `SKILL.md` が存在しても一部しか展開されていない場合があるため、導入成功と扱わず復旧する。
   公開版に目的のスキルがない場合や取得に失敗した場合は、導入済みと扱わず、スキル名とエラーを報告する。
   利用可能な版や公開が確認されるまで、そのスキルを必要とする作業は実施しない。
   導入先に同名スキルがある場合は強制上書きせず、内容と版の差を確認して既存の利用方針に合わせる。
   再配布条件と、Python、openpyxl、Excel等の必要な実行環境を各スキルの指示に従って確認する。
   環境の不足は報告し、未承認のインストールを行わない。
4. `.gitignore` を確かめる。
   スキルの作業用ファイルを置く `.agents/state/` は、Gitに入れないため、`.gitignore` に `/.agents/state/` があることを確かめ、無ければ足す。
   スキルの設定を置く `.agents/config/` は、チームで共有するため、`.gitignore` に入れない。
   `.agents/` 全体を除外する記述があれば、利用者に伝える。
5. スキル名、配置先、実行する作業、参照する規約を新規プロジェクトのAI向け指示に追記する。
   対象AIが実際にその配置を読み込めることを確認し、認識に再読み込みが必要な場合は利用者に伝える。

## 画面規約の初期生成

1. 簡略版の画面規約を先に配置せず、出力先を`nuxt/docs/20_rules/screen-design-rules/`、部品ライブラリをVuetify、画面URL規約を`docs/20_rules/URL命名規則.md`として、導入したスキルの初回生成手順を実行する。
   Nuxt・VueのSPA、画面実装方針の置き場所 `nuxt/docs/20_rules/フロントエンド実装方針.md`、画面設計の置き場所 `nuxt/docs/60_design/`、DADS優先・Carbon補完も決定済みの前提として渡す。
   ユーザーが別の方針を決めていない場合、Vuetifyの部品を基本として規約との対応を実現方式に整理する。
   ボタンやフォームの具体的な表示・状態・属性は、生成スキルの資料と採用するVuetifyの版を確認し、規約・実現方式に分けて書く。
   実装コードをまだ作っていない場合は、設定ファイルや共通部品を実装済みと記載しない。
2. 入力シートの「画面」シートの値（既定値を当てた値）と、「画面とメニュー」シートの一覧を、決定済みの情報として渡す。
   生成スキルが確認を求める事項のうち、入力シートにあるものは、利用者に聞き直さず、入力シートの値を使う。
   入力シートに無い事項（表示密度、操作上の例外など）は、推測を確定事項として記載せず、未決定事項として報告する。
   ブランドカラー（`screen.brand_color`）は、次のとおりに扱う。
   - 「濃い緑」のように言葉で書かれたときは、その色合いの16進数の案を作る。
   - 白い背景に対して、文字のコントラスト比が4.5:1に届かないときは、同じ色合いで濃さを変えた案を作る。
   - 「指定なし」のときは、DADSの既定の青を使う。
   - 案を作ったときは、元の値と案を、利用者の確認待ちとして報告する。
   メニューの階層とURL（`screen.menu_url`）の値で、URL命名規則と画面規約を作り、「画面とメニュー」シートのメニューの階層と照合する。
   照合して合わない画面があるときは、URL命名規則と画面規約を矛盾したまま確定せず、合わない画面を報告する。
3. 導入したスキルの`SKILL.md`に従って管理情報の整理と検証を実施し、生成物のリンクやプロジェクト固有設定、未決定事項を確認する。
   形式検査の成功だけでは、規約の具体化、Vuetifyとの対応、ユーザー判断の完了を意味しない。
   同スキルのモック確認手順に従い、実際のメニューや対象画面に基づく確認用モックを作り、ブラウザーで値と操作を確認する。
   付属のレイアウト例は参考素材であり、プロジェクトの規約を反映済みの確認用モックとして扱わない。
   少なくとも文字サイズ、ボタンの表示サイズと操作できる領域、余白、色、フォーカスを測定し、規約との差異を修正してから利用者に見せる。
   画面規約の確定には、モックを利用者に見せて判断を受け、指摘を反映する。
   モックの確認を待つ間も、ほかの環境づくりは止めずに進める。
   モックの未確認項目や利用者の判断待ちは、形式検査の結果と分けて、利用者の確認待ちとして報告する。
   未決定事項が残る場合は完成と扱わず、管理先とともに報告する。

## 設計書の作成

機能の洗い出しや見積もりでは `process-flow-diagram` に従って処理フロー図を作成・更新する。
図の出力先とプロジェクト固有ルールは、同スキルの手順と対象プロジェクトの資料配置に従う。
画面設計は`nablarch-frontend-design-excel`を使い、`nuxt/docs/60_design/`へプロジェクトの採番と配置に従って作成する。
バックエンドのAPI一覧と外部インタフェース設計書は`nablarch-basic-design-excel`で作成し、各サービスの`docs/40_spec/api-spec/`に正本として置く。
全APIに共通する入出力・エラーの決まりは、アプリ全体の`docs/40_spec/API共通仕様.md`に置く。個別APIの契約はExcelに記載し、別のMarkdownを正本として作らない。
テーブルを使うサービスでは、同スキルでテーブル一覧とテーブル定義書を作成し、各サービスの`docs/40_spec/table-definition/`に正本として置く。
機能ごとの主要処理フローは`process-flow-diagram`を使い、`docs/40_spec/detailed-design/<機能名>/`に置く。DBを使う機能では、同じ機能のディレクトリにER図を置く。
機能別の一覧や図からサービスのAPI仕様・テーブル定義の正本を参照し、個別仕様書の複製を別の正本として管理しない。
DBを使わないサービスではテーブル一覧、テーブル定義とER図を作成しない。
スキルに付属する生成・検証手順と対象成果物の確認を実施する。
機能やDB仕様が未決定の段階で、実在する仕様や完成済みの設計書を捏造しない。
