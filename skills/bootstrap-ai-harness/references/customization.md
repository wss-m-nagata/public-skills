# プロジェクト固有情報の反映

次をユーザーの指示と既存資料から確認し、決定済みの内容を正本へ反映する。
確認済みの項目は繰り返し質問しない。

入力シートは `.agents/state/bootstrap-ai-harness/project-intake.md` に作業用として置く。
対象プロジェクトのGit管理から入力シートを除外し、既存の `.gitignore` がある場合は設定を統合する。
既存シートは上書きせず、確認結果を更新する。
利用できない場合は対象プロジェクト内の書き込み可能な作業用領域を使い、パスを報告する。
確定事項は表の正本へ反映し、入力シートには参照先を残す。
共通ルールは適用し、標準案は採用可否を確認する。固有情報は選択肢または自由入力で尋ねる。
DBと外部連携は利用の有無を先に確認し、使わない場合は詳細を聞かない。
DBを使わない場合は、DB接続・SQL・DBテストを必須とする記述を対象外とし、アーキテクチャのDB責任分界欄にはDBを使用しない旨を記す。
具体的には全体・サービスのアーキテクチャ、API実装方針、テスト規約を確認し、入口のDB接続、リポジトリとDTO、SQL、トランザクション、DB専用テストの記述を対象に応じて削除または書き換える。
全体アーキテクチャのローカル動作確認にあるテスト用DBの前提と、テスト規約のSQLによるデータ準備・削除も確認する。
「リポジトリ」はGitリポジトリを指す場合もあるため、DBアクセス層を指す記述と区別して調整する。
各資料の相互参照と、DBを前提としない入力検証・エラー処理・単体テストは保持する。
標準案を変更した場合は、関連するAI向け指示と人向け規約を両方更新する。
たとえば人がコミットする標準案を変更するときは、`AGENTS.md`とリポジトリ規約の作業の流れ、担当者の表、禁止事項とその理由を照合し、ユーザーが許可した範囲だけを反映する。
コミット、プッシュ、マージは別々の操作として扱い、一つの許可を他の操作への許可と解釈しない。
入力シートで「未確認」「未決定」の標準案を、採用済みとして出力しない。
サービスのアーキテクチャにあるPython・uv・pytestの記述も標準案として確認し、採用しない場合は決定内容に合わせて変更する。
既存の明示的な方針とユーザーの回答を優先し、標準案と異なる場合は該当する資料の記述を統一する。
画面とAPIを同一オリジンで公開する標準案を変更する場合は、全体アーキテクチャ、API共通仕様、フロントエンド実装方針とURL命名規則を照合し、接続方式と責任分担を一致させる。
GitHub Actionsを使わない場合は、全体アーキテクチャのIAMロールとワークフローの説明を採用するデプロイ方法に合わせる。
未決定の項目は、テンプレートの既定文や空欄を決定済みの規約として残さず、プロジェクトの未決定事項の管理方法に従う。
未決定は推測せず記録し、決定済みの部分を進める。
パスワード、トークン、秘密鍵や接続文字列を入力シートに記載しない。

| 確認項目 | 反映先 |
| --- | --- |
| プロジェクト名、アプリの目的、利用者、対象範囲 | `README.md`、`AGENTS.md`、必要な要件資料。 |
| サービスの責務、Python採用の有無、サービス間の境界 | `docs/20_rules/アーキテクチャ.md`、各サービスの設計。 |
| DBの所有者、DDLやマイグレーションの責任、参照先 | 全体とサービスのアーキテクチャ、必要な運用手順。 |
| 認証・認可、環境、デプロイと外部操作の権限 | アーキテクチャと実際の運用手順。 |
| 画面とAPIの公開方式、ドメイン、パス | 全体アーキテクチャ、API共通仕様、フロントエンド実装方針、URL命名規則。 |
| AWS識別名、環境名、リージョン、サービス略称 | AWSリソース命名規則の各要素とサービスの略称一覧。秘密情報を記載しない。 |
| 業務用語と略語 | `docs/30_glossary/用語集.md`。 |
| メニュー階層と画面URL | `docs/20_rules/URL命名規則.md`と各画面設計。 |
| AIと人のレビュー・Git運用、課題管理先 | リポジトリ規約と必要なAI指示。 |
| 使用ツールと必要なスキル | AI向け指示、スキル配置と同期方針。 |
| 実行可能なセットアップ、ローカル確認、テスト | 実装・環境を確認後に対象別の手順書。 |
| テスト環境とAPI接続先、共有データの準備・削除 | `docs/20_rules/テスト規約.md`と実際の環境の手順書。 |

人向け規約を正本とし、AI向け指示には作業に必要な要約とリンクを記載する。
共通部品名やコマンドは、実在を確認するか、設計上の要求であることを明示する。
未決定事項は合意した課題管理先で管理し、ユーザーから権限を与えられていない外部サービスへの登録はしない。
未決定の節は対象プロジェクトの文書規約に従い扱い、管理先がなければ完了報告に残す。

スキルの採用時は対象作業、出典、ライセンス、依存と付属ファイルを確認する。
複数ツールでスキルを複製する場合は正本、同期方法、双方の検証方法を定める。
