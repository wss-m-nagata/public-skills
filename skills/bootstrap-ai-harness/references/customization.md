# プロジェクト固有情報の反映

入力シート（Excel）の値を、`scripts/project-intake/read_intake.py`で読み、対象プロジェクトの正本へ反映する。
入力シートにある項目は、利用者に質問しない。
項目ごとの意味、既定値、反映先は、[記入要領](intake-guide.md)に従う。

## 反映の記録

反映の記録は `.agents/state/bootstrap-ai-harness/project-intake.md` に作業用として置く（ひな形は[assets/project-intake.md](../assets/project-intake.md)）。
対象プロジェクトのGit管理から反映の記録を除外し、既存の `.gitignore` がある場合は設定を統合する。
既存の記録は上書きせず、追記して更新する。
利用できない場合は対象プロジェクト内の書き込み可能な作業用領域を使い、パスを報告する。
確定事項は記入要領の反映先へ反映し、記録には反映先へのリンクを残す。
パスワード、トークン、秘密鍵や接続文字列を記録に記載しない。

## 値の状態ごとの扱い

| 状態 | 扱い |
| --- | --- |
| 記入 | 記入された値を反映する。標準案と異なる値なら、次の「標準案と異なる値の調整」に従う |
| 既定値 | 既定値（テンプレートの標準案）を、決定済みとして反映する |
| 未決定 | 推測で埋めない。記入要領の説明にある「未定・不明のとき」の扱いに従い、反映の記録の「未決定の項目」に書く |

- 未決定の節を規約・仕様・設計に出力する場合は、節の見出しを残し、未決定である旨と実在する管理先へのリンクだけを記載する。
  テンプレートの既定文や空欄を、決定済みの規約として残さない。
- 管理先がなくリンクできない場合は、その節を完成済みの資料として出力せず、反映の記録と結果報告に残す。
  未確認のIssue番号を作らない。
- 「未定」「不明」のときに、人がAWSなどで確かめる必要がある項目（2要素認証、既存のVPC、OIDCプロバイダー、cdk bootstrap）は、確かめ方を案内する。
  AWSへの接続、リソースの作成は、人が行う。

## 項目ごとの注意

### データベース

アプリはデータベースを使う前提で作る。
DBの接続、SQL、トランザクション、DB専用のテストの記述は、テンプレートのとおり残す。

使うデータベース（`app.database`）が未定のときは、次のとおりにする。

- 開発者のPCで動かすDBを使い、開発者のPCでだけ動作確認できる形で、インストール手順とローカル動作確認手順を書く。
- 全体とサービスのアーキテクチャの`{{DBの責任分界}}`と、AWSの環境のDBに関わる記述（接続先、作成と管理の責任）は、未決定として扱う。
- AWSの環境での動作確認は、DBが決まってから行う旨を、反映の記録の「未決定の項目」に書く。

「リポジトリ」はGitリポジトリを指す場合もあるため、DBアクセス層を指す記述と区別して扱う。

### 認証・認可

既定値は、Amazon Cognitoでパスワードとワンタイムパスワード（認証アプリ）の2要素認証を行い、利用者は開発者が登録・削除し、権限は分けない、である。
`app.login`、`app.user_registration`、`app.roles`の値を、全体アーキテクチャの`{{認証と環境の方針}}`にまとめて書く。
権限を分ける値が記入されたときは、権限の種類と、各権限で使える機能の決め方を書く。

### 画面とAPIの公開、IP制限

既定値は、CloudFrontで画面とAPIを同じドメインにまとめ、パスの先頭（サービス名）でサービスごとのAPIに振り分ける、である。
APIの公開方式、転送の設定、AWS構成図は[インフラ設計の適用](infra-design.md)に従う。
「画面のURLの振り分け」は両方式に共通する。
IP制限（`infra.ip_restriction`）の既定値は「かける」とする。
「かけない」の場合は、IP制限の記述とAWSリソース命名規則のうち、採用しないWAFリソースの行を取り除く。
Lambda 関数 URLを採用する場合は、IP制限の有無にかかわらずOACでCloudFrontからの呼び出しを許可する。
許可するIPアドレス（`infra.allowed_ips`）と既存のVPCのID（`infra.vpc_id`）は、資料に書かない。
インフラのコードを作るときに、入力シートから読んで設定に使う。

### GitHub ActionsとOIDCプロバイダー、cdk bootstrap

OIDCプロバイダーとcdk bootstrapは、AWSアカウントの管理者が、AWSアカウント（cdk bootstrapはリージョンも）ごとに1回だけ行う作業である。
「あり」「済み」なら、既存のものを使う方針で書く。
「なし」「まだ」なら、作り方の手順を、デプロイ手順の「新しい環境の構築」に書く。
IP制限をかける場合、cdk bootstrapは使うリージョンに加えて、us-east-1（CloudFront用のWAFを作るリージョン）でも要る。

## 標準案と異なる値の調整

標準案と異なる値が記入されたときは、関連するAI向け指示と人向け規約を両方更新する。

- 人とAIの役割（`dev.roles`）を変える場合は、`AGENTS.md`とリポジトリ規約の作業の流れ、担当者の表、禁止事項とその理由を照合し、記入された範囲だけを反映する。
  コミット、プッシュ、マージは別々の操作として扱い、一つの許可を他の操作への許可と解釈しない。
- サービスの言語と依存管理（`app.service_stack`）がPython・uv・pytest以外の場合は、サービスのアーキテクチャと`backend/<サービス名>/AGENTS.md`の技術スタックを、記入された内容に合わせて変更する。
- 画面とAPIの公開方式（`app.publishing`）を変える場合は、全体アーキテクチャ、API共通仕様、フロントエンド実装方針とURL命名規則を照合し、接続方式と責任分担を一致させる。
- デプロイの方法（`infra.deploy`）がGitHub Actions以外の場合は、全体アーキテクチャのIAMロールとワークフローの説明を、記入された方法に合わせる。
- 課題管理（`dev.issue_tracker`）がGitHub Issues以外の場合は、Issueテンプレートや文言を運用に合わせて変更する。
- 設計書の正式版の置き場所（`dev.design_doc_master`）が「リポジトリ」の場合は、運用フローの「正式版への反映」を、リポジトリでの取り込みに読み替えて書き直す。

既存の明示的な方針がある場合は、入力シートの値と照合し、食い違うときは利用者に確認する。

## 正本と参照

人向け規約を正本とし、AI向け指示には作業に必要な要約とリンクを記載する。
共通部品名やコマンドは、実在を確認するか、設計上の要求であることを明示する。
未決定事項は入力シートの課題管理先で管理し、利用者から権限を与えられていない外部サービスへの登録はしない。

スキルの採用時は対象作業、出典、ライセンス、依存と付属ファイルを確認する。
複数ツールでスキルを複製する場合は正本、同期方法、双方の検証方法を定める。
