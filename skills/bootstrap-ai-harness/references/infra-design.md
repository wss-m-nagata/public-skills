# インフラ設計の適用

入力シートの `infra.api_origin` の解決値を使用する。
旧シートで項目がない場合と空欄の場合の既定値は Lambda 関数 URL である。
作成した設計書の配置先は `docs/40_spec/basic-design/AWSインフラ設計書.drawio` とする。
既存の設計書がある場合は、採用済みの設計と照合して統合する。

| APIの公開方式 | コピー元 |
| --- | --- |
| Lambda 関数 URL | [lambda-function-url.drawio](../assets/infra-design/lambda-function-url.drawio) |
| API Gateway | [api-gateway.drawio](../assets/infra-design/api-gateway.drawio) |

1. 図の AWS 構成、スタック構成、コスト基準、認証フローの4ページを入力シートに合わせる。
   DBやVPCを使わない場合は対応する箱、線、費用項目を削除する。
   VPCを使う場合は作成か参照か、DBを使う場合はその所有者と接続境界を明記する。
   IP制限をしない場合は、WAFの箱、接続、費用項目と、WAFだけが理由で必要なリージョンを削除する。
   認証フローは採用した認証方式に差し替える。
   GitHub Actionsを使わない場合は、採用したデプロイ方式に合わせて管理基盤と実行者を描き直す。
2. アーキテクチャ、CDK作成方針、デプロイ手順に、同じ方式と条件を反映する。
   Lambda 関数 URLでは、CloudFrontのOACからIAM認証付き関数URLへ転送し、対象ディストリビューションに呼び出しを限定する。
   サービスのデプロイで転送先をCloudFrontのKeyValueStoreへ登録する。
   API Gatewayでは、共有側がサービスのREST API URLを読み、入口の転送先を更新する。
   IP制限ありの場合は、REST API用WAFでもCloudFront経由の要求を検査する。
   初回の順序はCDK作成方針に従い、アーキテクチャ、CDK作成方針、AWSリソース命名規則から選択していない方式の節や行を取り除く。
   スタック名の例はAWSリソース命名規則と揃える。
3. 実際のCDKアプリやワークフローがある場合は、スタック名、実行コマンド、自動デプロイの条件を確認して、手順のひな形を完成させる。
   未整備の場合は、入力の反映記録に不足内容を残す。
   資料案内から構成図と完成した手順書を参照できるようにする。
4. 全ページを開き、ラベルの欠け、矢印の接続、選択した構成とデプロイ順序を照合する。
   本文と図のラベルおよびXMLに、元プロジェクトの名称、URL、アカウント、サービス名、接続先、ローカルパスが残っていないことを確認する。
