# GitHub Actionsの設定（任意）

GitHub上で動く自動化（PRのAIレビュー、Issueの自動ラベル付け、デプロイ前のテスト）を、対象プロジェクトに設定する手順である。
任意の機能であり、利用者が「設定する」と答えたときだけ行う。
「設定しない」と答えたときは、この手順を行わず、入力シートの該当行を「対象外」にする。

ひな形は `assets/optional/github-actions/` にある。
`assets/project-template/` には入れていない。
そのため、「設定しない」場合に、ファイルが配置されることはない。

## 1. 質問する

次のとおり、尋ねる。

> GitHub Actionsを設定しますか。
> 設定すると、GitHubに反映したときに、次のことが自動でできるようになります。
> - Claude Codeによる、PRの自動レビュー（PRを作ると、AIがレビューのコメントを付ける）
> - GitHubでIssueを管理する場合の、課題の自動分類（Issueを起票すると、Claudeが種別や優先度のラベルを付ける）
> - デプロイ前のテスト（テストが1つでも失敗したら、デプロイしない）
>
> 設定する場合は、使うものを選んでください。

「する」と答えたら、次の前提を伝えて、了解を得る。

| 前提 | 内容 |
| --- | --- |
| 認証情報 | Claude Code Actionを使うため、リポジトリのシークレット `CLAUDE_CODE_OAUTH_TOKEN` の登録が要る。登録は人が行う |
| 費用 | PRの作成とIssueの起票のたびに、AIが動き、費用がかかる |
| 動く条件 | Issueの自動ラベル付けは、リポジトリの標準のブランチに反映されてから動く。ブランチの上では、動作確認できない |
| 起票者の権限 | Issueの自動ラベル付けは、書き込み権限のない人が起票した場合は動かない（ジョブは失敗し、ラベルは付かない） |

入力シートの「GitHub Actionsの設定（任意）」に、選んだ機能と、前提の了解を記録する。
回答は、`.agents/config/bootstrap-ai-harness/settings.md` にも保存する（「しない」も、記録する）。以後は、聞き直さない。

## 1.1. Claude Code Actionの導入手順は、公式を見る

GitHubアプリの導入、認証情報の登録、`anthropics/claude-code-action` の設定方法は、変更されることがある。
このスキルには、操作手順を書かない。
「設定する」と答えたときは、Claude Codeの公式ドキュメント（GitHub Actionsの項）で、その時点の最新の手順を確認し、従う。
公式の手順と、ひな形の記述が食い違うときは、公式を優先し、食い違いを利用者に報告する。
認証情報の登録など、GitHubへの変更は、利用者が行う。

## 2. ひな形を写す

選ばれた機能のひな形を、スクリプトで、対象プロジェクトの正しい場所へ写す。
置き先の対応は、スクリプトが持つ。手作業で写さない。

対象プロジェクトのルートで、次を実行する。
最初は、確認だけ（dry-run）になる。

```powershell
python <スキル>/scripts/github-actions/install_github_actions.py --features review,labeling
```

- `--features` には、選ばれた機能を、カンマ区切りで指定する。
  `review`（PRのAIレビュー）、`labeling`（Issueの自動ラベル付け）が使える。
  デプロイ前のテストは、ひな形がないため、指定しない（4. を参照）。
- 出力で、写す先を確認してから、`--apply` を付けて、もう一度実行する。
- 同名のファイルが既にあるときは、上書きせず、スキップして、同一か、内容が異なるかを表示する。
  内容が異なるときは、既存のファイルと統合する。
- 修正履歴の担当者は、`--author "<会社の略称><氏名>"` で、人が指定した値だけが入る。
  指定しなかったときは、`<会社の略称><氏名>` が残り、スクリプトが一覧を表示する。
  AIは、人の名前を推測して指定しない。分からないときは、利用者に尋ねる。
- Gitのステージは、スクリプトの中では行わない。

写されるファイル（`assets/optional/github-actions/` から）は、次のとおりである。

| 機能 | ひな形 | 置き先 |
| --- | --- | --- |
| `review` | `workflows/claude-code-review.yml` | `.github/workflows/` |
| `review` | `claude/code-review-focus.md` | `.github/claude/` |
| `labeling` | `workflows/issue-triage.yml` | `.github/workflows/` |
| `labeling` | `commands/label-issue.md` | `.claude/commands/` |
| `labeling` | `scripts/gh.sh`、`edit-issue-labels.sh`、`stage-executable-scripts.sh` | `scripts/` |
| `labeling` | `labels.json` | `.github/labels.json` |

- `scripts/gh.sh` は、AIが使える `gh` のサブコマンドを、参照系に限定する。
  `scripts/edit-issue-labels.sh` は、存在するラベルだけを付ける。
  どちらも、プロジェクト固有の記述を持たないため、変更しない。

### 2.1. PRのAIレビューの重点を決める

`review` を選んだときは、レビューの重点を、プロジェクトに合わせて決める。
重点は、`.github/claude/code-review-focus.md` に書く。
ワークフローが、`--append-system-prompt-file` で、このファイルを読ませる。
GitHub Actionsのレビューだけに適用され、`CLAUDE.md` には、書かない。

**理由**: `CLAUDE.md` は、AIがプロジェクトで作業するたびに読み込まれる。
レビュー専用の指示を書くと、通常の作業にも、影響するためである。

ひな形の重点は、次のとおりである。

| 確認すること | 内容 |
| --- | --- |
| 規約への準拠 | AI向け指示と規約に、明確に違反している箇所 |
| 水平展開の漏れ | 変更が原因で生じる、同じ修正の直し漏れ。差分の外のファイルも調べる |
| 文書間の整合 | 変更した文書と、参照し合う文書との、記述の食い違い |
| リンクの有効性 | プロジェクト内へのリンクの、リンク先の存在 |
| 純粋な不具合 | 構文エラー、明らかな誤動作 |

- 要件や設計書が、リポジトリの外（ファイルサーバーなど）にあるときは、仕様の正しさを、対象外にする。
  AIが、リポジトリの中だけを見て、判断できないためである。
- 規約のパスは、ひな形では、このスキルのテンプレートの構成に合わせている。
  プロジェクトの実際の構成に合わせて、書き換える。
- 重点が、実際に効くかは、次の順で確かめる。
  1. ワークフローと重点のファイルを、標準のブランチ（main など）に反映する。
  2. 反映したあとに、確認用のPRを、別に作る。規約違反と、水平展開の漏れを、わざと1つずつ含める。
  3. レビューで、両方が指摘されることを確かめる。
     指摘されないときは、重点の書き方を具体的にする。それでも弱いときは、水平展開を見る、別のレビューを追加する。

  **理由**: ワークフローのファイルが、標準のブランチと違う内容のPRでは、Claude Code Action が処理を飛ばし、コメントを付けずに成功として終わる。反映と同じPRでは、確かめられないためである。

**使えない方法**: Claudeの Team または Enterprise プランでは、`REVIEW.md` を使う、マネージドの Code Review を使える。
無料プランなど、そのプランがないときは、この手順のAction方式を使う。
プラグインの `/code-review` は、`CLAUDE.md` だけを読み、`REVIEW.md` を読まない。

## 3. Issueの自動ラベル付け

順序を守る。
ラベルを作る前にワークフローを動かすと、ラベルが付かない。
存在しないラベルは、エラーにならず、黙って除外されるため、気づきにくい。

### 3.1. ラベルを決める

プロジェクトの種別と優先度を、利用者と決める。
決めた内容は、2. で写された `.github/labels.json` に書く。
次は、決め方の例である。名前と基準は、プロジェクトに合わせて変える。

| 分類 | ラベルの例 | 説明に書くこと |
| --- | --- | --- |
| 種別 | bug、enhancement、documentation、infra | 何の作業か。Issueひな形（`.github/ISSUE_TEMPLATE/`）の種別と、名前を合わせる |
| 優先度 | P1、P2、P3 | いつまでに対応するか。基準は、プロジェクトのリリースの運用に合わせて決める |

- ラベルの説明は、AIがラベルを選ぶときの判断材料になる。
  AIが迷わないよう、具体的に書く（GitHubの上限は100文字）。
- GitHubの標準ラベル（`enhancement`、`documentation` など）が、決めた種別と意味が重なるときは、利用者に、削除してよいかを確認する。
  重なったまま残すと、AIが、決めたラベルの代わりに、または一緒に、標準ラベルを付けることがある。
  `gh label list` で、既存のラベルを確認し、どれが重なるかを、利用者に示す。
  利用者が了承したラベルだけを、3.2. のあとで削除する。
- Issueひな形の `labels` に書いたラベルが、リポジトリに無いと、起票時に付かない。
  ひな形のラベルも、`labels.json` に入れる。
- `label-issue.md` が、優先度のラベル（P1〜P3）を必ず付ける指示を持つ。
  優先度を使わないときは、この指示を、手作業で外す。

### 3.2. GitHubにラベルを作る（人が行う）

`.github/labels.json` に書いたラベルのうち、足りないものだけを、スクリプトで作る。
既存のラベルは、変更も削除もしない。
最初は、確認だけ（dry-run）になる。

```powershell
python <スキル>/scripts/github-actions/create_missing_labels.py
```

- 出力で、作成予定のラベルと、既存との差異を確認する。
- 問題がなければ、`--apply` を付けて、もう一度実行する。
- GitHubへの変更になるため、`--apply` は、利用者の指示があるときだけ、実行する。
- 色や説明が違う既存のラベルは、差異が表示されるだけで、変更されない。
  変更するときは、`gh label edit` を、人が実行する。

重なる標準ラベルは、利用者が削除を了承したときだけ、次のコマンドで削除する。
削除すると、そのラベルが付いていた既存のIssueとPRからも、ラベルが外れる。
元に戻すには、同じ名前で作り直す必要がある。
了承のないラベルは、削除しない。

```powershell
gh label delete <ラベル名> --yes
```

### 3.3. 実行権限を付けてステージする

Windowsでは、スクリプトの実行権限がGitに記録されない。
権限がないと、GitHub Actions上で実行できない。
コミットの前に、利用者が、次を実行する。

```powershell
bash scripts/stage-executable-scripts.sh
```

出力の先頭が `100755` であることを確認する。
`100644` のときは、実行権限が付いていない。
このスクリプトは、ステージまでを行い、コミットはしない。
`scripts/` に `.sh` を追加したときも、同じ手順を行う。

### 3.4. 反映して、動作確認する

1. 利用者が、コミットして、標準のブランチに反映する。
2. テスト用のIssueを起票する（種別ラベルは、ひな形が付ける形で指定する）。
3. `gh run list --workflow issue-triage.yml` で、実行が `success` で終わることを確認する。
4. `gh issue view <番号> --json labels` で、種別と優先度のラベルが付いたことを確認する。
5. 確認用のIssueは、利用者が閉じる。

付かないときの確認先は、次のとおりである。

| 症状 | 確認すること |
| --- | --- |
| ワークフローが動かない | 標準のブランチに反映されているか。起票者に書き込み権限があるか |
| 動くが、ラベルが付かない | ラベルが、リポジトリに存在するか。ラベルの説明が、判断できる内容か |
| `gh` の認証で失敗する | ワークフローの `env` に `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}` を足す |
| `Permission denied` | 3.3. の実行権限が、`100755` で反映されているか |

## 4. デプロイ前のテスト

ひな形は用意しない。
テストの範囲（どのテストを、CIで流すか）は、対象プロジェクトの環境とテスト規約によって決まるためである。

### 4.1. 構成の考え方

デプロイのワークフローの前に、テストのジョブを置き、1つでも失敗したら、デプロイしない。

- テストのジョブを、デプロイのジョブとは別に定義する。
- デプロイのジョブに `needs: <テストのジョブ>` を書く。
  `needs` を書くと、テストが失敗したときに、デプロイのジョブが実行されない。
- テストを、複数のワークフローから使うときは、再利用ワークフロー（`on: workflow_call`）にする。
- 実行するテストは、対象プロジェクトの構成に合わせる。
  例：型チェック、コードの検査、単体テスト。
  実環境への接続が前提のテストは、認証情報とネットワーク経路を決めるまで、CIには入れない。

### 4.2. 範囲が決まっていないとき

環境が整っておらず、範囲を決められないときは、決まっていないことを、完成した設定として配置しない。
課題管理先に、範囲を決める課題を作り、決まった時点で設定する。

## 5. 完了の報告

次を報告する。

- 選ばれた機能と、設定しなかった機能。
- 配置したファイルと、利用者の対応が要るもの（シークレットの登録、ラベルの作成、実行権限のステージ、コミットと反映）。
- 動作確認の結果（確認できたこと、確認できていないこと）。
- 未決定のもの（デプロイ前のテストの範囲など）と、その管理先。
