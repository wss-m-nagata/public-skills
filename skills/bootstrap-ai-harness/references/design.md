# テンプレートの適用手順

## 対象と構造

`assets/project-template/`はWebアプリをルートとした出力用の基本構成である。
Nuxt・Vue・VuetifyのSPA、API GatewayとLambdaのバックエンド、AWS CDK、Python、Playwrightを基本とする。
サービス本体の言語は現行のWebアプリではサービス単位で決めているため、Pythonを標準案とし、サービスの決定を確認する。

| テンプレート | 展開先と役割 |
| --- | --- |
| `project-template/` | Webアプリ全体のREADME、AI指示、Issueテンプレート、共通の規約・仕様・用語集、フロントエンド規約。 |
| `service-template/` | `backend/<サービス名>/docs/`へサービスごとに配置する設計・仕様・手順のひな形。 |
| 公開スキル | 画面規約と設計書の作成に必要なスキルは[必須スキルの導入](skills.md)に従って公開元から取得する。 |

必要に応じて`docs/40_spec/requirements/`、`table-definition/`、`detailed-design/`、`nuxt/docs/60_design/`、`backend/`、`e2e/`、`infra/`を資料配置の計画として扱う。
サービス別のAPIとテーブルの正本および機能別の処理フロー・ER図は、[必須スキルの導入](skills.md)の配置に従う。
Gitは空ディレクトリを管理しないため、実際の資料やファイルが必要になったときに作成する。
`.claude/skills/`にも必要なスキルを選んで配置し、空のディレクトリだけを作らない。

## 適用と調整

1. アセットのファイル一覧と対象先の既存ファイルを照合する。
   対象先へ変更する前に、上書きされるファイルや矛盾する指示を確認する。
   コーディング規約、API実装方針、画面からのAPI呼び出し方針など、業務や接続先に依存しない規則は、章立て・条件・理由・例を含めて保持する。
   適用時に共通規則を要約して落とさず、固有値と対象外の部分だけを適合させる。
2. テンプレートを対象に適用し、`{{...}}`を対象の決定に基づき置き換える。
   条件に合わない記述は削除または書き換える。
   未確定の情報を埋めるためだけの推測や、既存の指示の削除は行わない。
   未決定の節を規約・仕様・設計に出力する場合は、節の見出しを残し、未決定である旨と実在する管理先へのリンクだけを記載する。
   管理先がなくリンクできない場合は、その節を完成済みの資料として出力せず、入力シートと結果報告に残す。未確認のIssue番号を作らない。
   業務用語が未決定なら、用語集の記入用の表行を削除して見出しと表だけを残す。
   APIの同一オリジンなど、テンプレートの初期方針とプロジェクトの決定が異なる場合は仕様と関連規約を合わせて直す。
3. インストール・運用手順、各サービスの仕様と設計は実在する構成を確かめてから作成する。
   アセットの`*.template.md`は記入ガイドであり、対象の事実を確認してから対応する名前で出力する。
   インストール手順は、技術スタックから定まる共通のツール、導入方法、確認コマンドを保持する。プロジェクトの実装や接続先に依存する部分だけを適合させる。
   設定ファイルがまだない場合も、ツールの準備手順と、ファイルが用意されてから依存関係を導入する条件付きの手順は残す。存在しないファイルや導入済みの環境を事実として書かない。
   出力時はひな形自体の使い方を説明する文章と記入用の未置換行を除き、確定した内容と実際の参照先に置き換える。
   未決定の場合、完成済みの手順書として配置せず、未決定と不足資料を報告する。
4. READMEとAI指示のリンクは実際に生成したファイルだけに向ける。
   課題をGitHub Issues以外で管理する場合、Issueテンプレートや文言を運用に合わせて変更する。
5. Webアプリの構成管理に関する内容は、リポジトリ規約、アーキテクチャ、言語規約にそれぞれ置く。
   独立した構成管理規約は対象プロジェクトに必要と確認された場合に限り追加する。

## 元資料と転用の境界

| 元資料 | 利用する内容 | 変更・除外する内容 |
| --- | --- | --- |
| 直下のAGENTS.md、docs/20_rules/リポジトリ規約.md | 作業分担、文書種別、AI指示、履歴とGit運用。 | データ基盤、DB接続ツールと現在のIssue。 |
| docs/20_rules/コーディング規約.md | Pythonの命名、インデント、docstring。 | データ処理Lambdaの処理方式をAPIへ強制しない。 |
| webapp/docs/20_rules/ | Webアプリ、API、言語、テスト、命名の方針。 | 固有の業務、DB管理者、アカウントと環境、未確定の認証方式。 |
| webapp/nuxt/docs/20_rules/ | Nuxtの構成と画面規約。 | 実在しない共通部品や設定を実装済みと書かない。 |
| docs/30_glossary/用語集.md | 用語と説明の管理方法。 | 現行の業務システム名、Lambda名と組織情報。 |
| webapp/backend/master-maintenance/docs/ | サービスごとの資料構成。 | 組織図API、接続先、シークレット名と具体的なテーブル。 |
