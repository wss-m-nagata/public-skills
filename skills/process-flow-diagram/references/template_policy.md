# 生成スクリプトの運用ルール

処理フロー図は、図1枚ごとに書いた**生成スクリプト**を実行して作る。

生成スクリプトは毎回ゼロから書かず、**雛形**をコピーしてその図専用に書き換える。
雛形は `.agents/state/process-flow-diagram/assets/build_flow_template.py` に置く。

図を描くたびに、次の図でも使える書き方を雛形へ戻して育てていく。
雛形がまだ無い段階では、スキル同梱の**作例** `assets/build_example.py` をコピー元にする。

## 3つのスクリプトの関係

```
作例  assets/build_example.py（スキル同梱。架空の題材。変更しない）
  │
  │ 初回だけ、ここから雛形を起こす
  ↓
雛形  .agents/state/process-flow-diagram/assets/build_flow_template.py
  │                                          ↑
  │ コピーして図専用に書き換える              │ 次の図でも使える書き方を戻す（§4）
  ↓                                          │
生成スクリプト  <作業ディレクトリ>/build_<対象>_flow.py（図1枚ごと。使い捨て）
  │
  │ 実行する
  ↓
.drawio（渡した時点でこちらが正。以後は人とAIが直接直す）
```

| 呼び名 | 実体 | 寿命 |
| --- | --- | --- |
| **作例** | `assets/build_example.py` | スキルに同梱。書き方の見本であり、案件では変更しない |
| **雛形** | `.agents/state/process-flow-diagram/assets/build_flow_template.py` | 案件をまたいで育てる |
| **生成スクリプト** | `<作業ディレクトリ>/build_<対象>_flow.py` | 図1枚を生成したら終わり |

## 生成スクリプトとは何か

雛形から起こして、`.drawio` を**新規に作る**ためのスクリプトである。
図1枚につき1本を書き、実行すると図が丸ごと生成される。

**レイアウトを計算させるための道具**である。

**なぜ道具が必要か。**
処理フロー図は1ページに数十個の箱と線が乗る。
3段構成で、配置の規則がある（`default_rules.md` §2）。
そのため箱を1つ足すと、右隣の箱も、真下の処理も、そこへ伸びる線も、まとめてずれる。
この座標の計算を人が当て直すのは現実的でない。
XML を手で書けば、ID の重複・エスケープ漏れ・座標のずれで壊れる。

**寿命は、図の新規作成を終えるまでである。**
計算が必要なのは、要素を洗い出して並べ直している間だけである。
図を渡したあとに出てくる修正は、たいてい局所的な直しであり、全体の再計算を必要としない。

加えて、人が drawio で箱をつまんで動かしたあとは、正しい位置が「人が見て決めた位置」になる。
それを再現する計算式は無いので、そうなった図は生成スクリプトでは作り直せない。

## 雛形とは何か

**生成スクリプトを書き始めるための型**である。
生成スクリプトから案件固有の内容を抜いて、書き方だけを残したものである。

雛形を置く理由は、生成スクリプトを毎回ゼロから書かないためである。
同じプロジェクトの中では、3段構成・ページ分割・凡例の作り方は毎回同じなので、型にして残す。

**作例をそのまま雛形にはしない。**
作例は `flow()` `screen()` `note()` `callout()` `tbd()` `scope_out()` `small()` を1回ずつ使った基本の一巡であり、
`section()`（1ページを段に分ける見出し）などは入っていない。
雛形は作例から起こしたうえで、そのプロジェクトで実際に使う書き方を足して仕上げる。

## 場面別の早見表

| 場面 | やること |
| --- | --- |
| 新しい図を描き始める | 雛形をコピーして生成スクリプトを起こす → §1 |
| 図を渡して、新規作成の作業を終えた | 生成スクリプトを片付ける → §2 |
| 生成スクリプトに、雛形へ残すべき書き方があった | §3 の基準で選ぶ |
| 雛形に無い書き方を使った | 雛形へ足す → §4 |
| 既定が変わり、雛形が動かなくなった | 雛形を直す → §5 |

## 1. 生成スクリプトは、雛形から起こす

```bash
cp .agents/state/process-flow-diagram/assets/build_flow_template.py \
   <作業ディレクトリ>/build_<対象>_flow.py
```

コピーしたら、第2層（§3）のうち今回使わない行を消し、案件固有の内容を書き入れる。
図を生成したあとの検査と目視は SKILL.md の手順5 に従う。

## 2. 生成スクリプトは、図の新規作成を終えたら削除する

図を生成し、検査と目視の調整（SKILL.md 手順5）を終えて図を渡した時点で削除する。
**人が drawio で触るのを待たない。**

| いつ | 生成スクリプトの扱い |
| --- | --- |
| 生成 → 検査 → 目視の調整をしている間 | 直して再実行してよい |
| 調整を終えて図を渡した | 雛形へ残すものを選び（§3）、削除する |

したがって、生成スクリプトが存在するのは**新規作成の作業中だけ**である。

次の順で片付ける。

1. §3 の基準で、雛形へ残すものがあるかを見る
2. 雛形へ移す
3. 生成スクリプトを削除する

**2 と 3 の間に、雛形が動くことを確かめる（§5）。**
作業ディレクトリが `.gitignore` の対象だと、削除したスクリプトは git から復元できない。

**なぜ削除するか。**
図を渡した時点で正は `.drawio` に移り、再実行すれば以後の手直しと衝突する。
使えないスクリプトが図の隣にあると、後から読んだ人が最新の生成元だと受け取る。
人が触るのを待つと、消す時機が「図が確定したか」という主観に委ねられて決まらない。

生成スクリプトを図に追随させてはいけない理由は SKILL.md の手順7 にある。

## 3. 雛形へ残すものを選ぶ

雛形は2層に分けて書く。
コピーした人が「どこを消せばよいか」を迷わないためである。

### 第1層　骨格 — コピーしてそのまま使う部分

- ページの作り方と、ページ分割の並び（①②③…⑤凡例）
- 3段構成の宣言と `section()` の見出し
- `legend_page()` の呼び出し
- 出力パスと、生成後に `validate_drawio.py` を通すところ

**次の3つがすべて「はい」になるものだけを入れる。**

| 確認 | 「いいえ」になる例 |
| --- | --- |
| 次に描く図でも必ず使うか | ウィザードの多段階表示。その形の画面がある案件だけ |
| コピー先で消さずに残るか | 業務固有の箱が20個あると、次の人が全部消す |
| 案件固有の業務語が入っていないか | 「受注明細を読む」のように業務名を含むもの |

### 第2層　技法カタログ — 使うときだけ参照し、使わなければ消す部分

- `group()` `text()` `scope_out()` `tbd()` `callout()` などの最小の使用例
- 各1〜2行にとどめ、「どういうときに使うか」を1行のコメントで添える

**次の2つがともに「はい」なら入れる。**

- 実案件で一度でも使った書き方か
- 使わない図では、その行を消すだけで済むか

**第1層と条件を分ける理由。**
「1案件だけだから個別対応」と切ると、この書き方は次に必要になったとき再発明することになる。
かといって骨格に入れると、使わない図でも毎回消すことになる。

### 雛形に入れないもの

| 入れないもの | 置く場所 |
| --- | --- |
| 描く対象そのもの（テーブル名、画面名、業務の流れ） | 図（`.drawio`）と `naming.md` |
| 色・列幅・段の高さなどの数値 | 既定（`drawio_builder.py`）。雛形は既定を呼ぶだけにする |
| 判断を伴う規則（戻り線を引く条件など） | `default_rules.md` と `extension_rule.md` |

**数値と規則を雛形に書き写さない。**
既定・プロジェクト固有ルール・雛形の3箇所に同じ内容が散り、既定を直したときに雛形だけが古くなる。
`extension_rule.md` が「既定と同じ内容は書かない」としているのと同じ理由である。
雛形は**規則を守った結果の形**を示すに留める。

## 4. 雛形を更新する

`naming.md` と同じ運用にする。
必要になったときに足し、予測して先に足さない。

| 契機 | 対応 |
| --- | --- |
| 新しい図で、雛形に無い書き方を使った | その書き方を**第2層**へ足す |
| 2案件連続で同じ書き方をした | 第2層から**第1層**へ繰り上げる |
| 既定（`drawio_builder.py`）が変わり、雛形が動かなくなった | 雛形を直す |
| 案件固有の業務内容 | **足さない** |

足したときは、雛形の冒頭の修正履歴に、**何を足したか**と**どの案件で必要になったか**を書く。
後から第1層へ繰り上げるかを判断するのに、案件名が要る。

**第1層への繰り上げに2案件を待つ理由。**
1案件の経験で骨格を決めると、次の案件では「毎回消す部分」に変わることがある。
早すぎる一般化を1回分だけ待つ、という趣旨である。

## 5. 雛形が動くことを確かめる

雛形を更新したときと、生成スクリプトを削除する前に実行する。

```bash
python .agents/state/process-flow-diagram/assets/build_flow_template.py
python .claude/skills/process-flow-diagram/scripts/validate_drawio.py <雛形の出力>.drawio
```

これが通ることを、雛形が使える状態の条件とする。
出力した図は確認用なので、作業ディレクトリへ捨ててよい。

**コメントだけの断片集にしない。**
既定が変わっても誰も気づかず、次に使った人が最初にデバッグから始めることになる。
実行できる形にしておけば、既定の変更で壊れた時点で気づける。
