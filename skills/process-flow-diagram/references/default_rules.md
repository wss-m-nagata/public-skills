# 処理フロー図の既定ルール

プロジェクト固有のルールが無い場合、この内容を既定として使う。
利用者へは「この形で進めます。変えたい点はありますか」と一度だけ確認し、
差分が出たものだけを `extension_rule.md` に書き足す。

毎回ゼロから決めると、図ごとに見た目が変わって読み手が戸惑う。
既定を持つのは、複数の図を並べたときに同じ読み方ができるようにするためである。

## 1. この図の目的と粒度

目的は2つある。

- **作るものの洗い出し**（WBS の作成、作業量の見積もり）
- **関係者の認識合わせ**（他社を含む開発チーム）

この2つから粒度が決まる。基本設計や詳細設計で書くフローより粗い。

| 要素 | 書く | 書かない |
| --- | --- | --- |
| 画面 | 名前・役割・遷移 | 項目、レイアウト |
| 処理 | 何をするかを1〜2行 | インターフェース定義、引数、アルゴリズム |
| テーブル | 名前・読み書きの別 | カラム、型、制約 |
| ファイル | 名前・入出力の別 | レイアウト、文字コード |
| DB以外の保存先 | 名前・読み書きの別 | 設定内容、スキーマ |
| 流れ | 正常系 | 異常系、分岐の網羅 |

右列を書かないことが「粗い」の中身である。
書き始めると設計書になってしまい、見積もりに使うには重すぎて完成しない。

似た図法との違いを押さえておくと、迷ったときの判断基準になる。

| 図法 | 中心に置くもの | この図との違い |
| --- | --- | --- |
| 業務フロー図 | 誰が何をするかの手順 | 処理やテーブルは書かない |
| DFD | 処理とデータストアの関係 | 画面遷移を書かない |
| シーケンス図 | 時系列の呼び出し順 | 基本設計以降の粒度 |

この図は3つの中間で、**画面・処理・データを1枚に載せて「作る対象を数える」**ためのものである。

## 2. レイアウト（3段構成）

**左から右へ読む。** 縦に積むと、操作の数だけ縦に伸びて読み通せなくなる。
横に長くなるのは構わない。

| 段 | 目安のY座標 | 内容 |
| --- | --- | --- |
| 上段 | 140 | 画面。利用者から始めて、遷移の順に横へ並べる |
| 中段 | 330 | 処理。呼び出し元の画面の真下に置く |
| 下段 | 420 | テーブル・ファイル |
| 補足 | 760 | 吹き出し、注記、T.B.D |

### 処理を置く位置

**呼び出し元の画面の真下に置く。** どの画面から呼ばれた処理かが、線を追わなくても位置で分かる。
複数の画面から呼ばれる処理は、それらの中間に置く。

**処理は必ず中段に置き、例外を作らない。** 「この操作は流れを一直線に見せたい」と考えて
処理を画面の段まで上げたくなることがあるが、そうすると「上段は画面、中段は処理」という
規則が崩れ、読み手が段で判断できなくなる。規則が単純なほうが速く読める。
流れの見せ方より、段の規則性を優先する。

### 画面遷移をともなう処理

処理から次の画面へ直接つながない。次の順で描く。

```
画面A ──① 操作──▶ [処理]
  ▲                  │
  └──② 結果を返す────┘
  │
  └──③ 次の画面へ移る──▶ 画面B
```

処理から画面Bへ直接引くと「処理が画面遷移している」ように読める。
実際には処理が値を返し、それを受け取った画面が遷移している。
この違いは、後で実装の分担を決めるときに効いてくる。

②の戻り線は、渡す値が画面Bで使われるときだけ引く（§3「戻り線は、戻る値が〜」を参照）。
値を渡さない単なる遷移なら②は省き、①と③だけを引けばよい。

### 画面の中だけで完結する操作は、画面の右上へ自己ループで描く

処理を呼ばずに画面の中で終わる操作は、その画面から自分自身へ線を引く。
処理の箱を置かないことが「Backend を作らなくてよい」という情報になるため、
線を省いて文章だけで補うより、ループとして見せたほうが伝わる。

```
        ┌─ 条件を変える → 画面内で絞る ─┐
        │                                ▼
   ┌────────────────────┐
   │      一覧画面      │
   └────────────────────┘
        │
        ▼ （処理へ降りる線）
```

**置き場所は画面の右上とする。** どの辺が空いているかは、3段構成で構造的に決まっている。

| 辺 | そこを通るもの | 自己ループを置けるか |
| --- | --- | --- |
| 上 | 原則として何も通らない | **空いている** |
| 下 | 処理へ降りる線。その先にテーブルへの線も続く | 競合する |
| 右 | 次の画面への遷移線 | ふさがっている |
| 左 | 前の画面からの遷移線 | ふさがっている |

自己ループを描くのは一覧画面が多く、一覧画面はほぼ必ず処理を呼ぶ。
つまり**下に置くと、その画面が呼ぶ処理への線とラベルが必ず競合する**。
上がぶつかる相手は段の見出し（`section()`）だけで、見出しはページの左端にあるため、
ループを右寄りにしておけば当たらない。それでも念のため、見出しと画面の間は 60px 以上あける。

`self_loop()` で描く。**`flow()` の始点と終点に同じ画面を渡してはいけない**（エラーになる）。
接続位置（`exit_xy` / `entry_xy`）の指定だけでは drawio の直交ルータが経路を決めきれず、
2点を近づけるとループが潰れて線に見えず、離すと戻り脚が画面の箱を突き抜ける。
`self_loop()` は中継点を置いて経路を固定するので、形が必ず決まる。

何を対象に、なぜ通信が起きないのかは、ループのそばに `small()` で添える。

### ウィザードのような多段階の画面

1つの箱にまとめず、段階ごとに分けて横に並べる。
「どの段階でどの処理が動くか」が分かることが、この図の主目的だからである。

### 1ページを段に分けるときは、見出しで分ける（枠で囲まない）

1ページの中に複数のまとまりを載せるときは、`section()` の見出しを置いて上下に並べる。
枠（`group()`）で囲んで分けてはいけない。

```
1. 画面を開いたとき（初期表示）
   … 画面・処理・テーブルの3段

2. 絞り込みの条件を変えたとき
   … 画面・処理・テーブルの3段
```

枠で分けないのは、この図では囲みがすでに別の意味を持っているからである。
`aws_frame()`（システムの範囲）、`tables()`（読み取り元・書き込み先）、
`scope_out()`（この図では扱わない範囲）と3種類あり、そこへ「段の区切り」の囲みが加わると、
読み手は囲みを見たときに何の囲みか判断できなくなる。見出しなら記号の意味が増えない。

見出しは `1.` `2.` の連番にする。分けた理由が操作の違いでも処理の段階の違いでも、
読み手のやることは「上から順に読み、各段は左から右へ読む」で同じなので、書式は変えない。

**枠を使うのは、段を分けるときではなく、並列するものを対比させるときである。**
たとえば2つの案を比べて見せる場合は、横に並べた双方を枠で囲むと対比が伝わる。

### 幅は惜しまない

要素が詰まって見えたら、ページを横へ広げて間隔を取る。
縦に積んだり文字を小さくしたりするより、横に伸ばすほうが読みやすい。
ページ幅が 3000 を超えても構わない。この図は元々スクロールして読むものである。

### 段の位置はページごとに変えてよい

Y座標の目安は「そろえておくと読みやすい」というだけで、守るべき制約ではない。
処理の箱を2行にしたり、1つの処理から複数の画面へ分岐して画面が縦に並んだりすると、
既定の位置では収まらない。そのときは段を下げる。読みやすさのほうが優先である。

## 3. 線の引き方

| 種類 | 色 | 向き | 用途 |
| --- | --- | --- | --- |
| 流れ | 灰 `#546E7A` | 左→右 | 画面と処理のつながり |
| 読み取り | 青 `#1976D2` | 下→上 | テーブルから処理へ |
| 書き込み | 緑 `#2E7D32` | 上→下 | 処理からテーブルへ |
| 削除 | 赤 `#C62828` | 上→下 | テーブルからの削除 |
| 戻り | 茶の点線 `#8D6E63` | 右→左 | 処理から呼び出し元の画面へ |
| 連鎖削除 | 赤の点線 | — | 外部キーの CASCADE |
| 引き出し線 | 赤の点線・矢印なし | — | 注記がどの図形に対するものかを示す |

読み書きは配置ではなく**矢印の向きと色**で区別する。
3段構成では書き込み先を処理の右に置けない（隣の処理と重なる）ためである。

### 戻り線は、戻る値がその先の流れを決めるときだけ引く

処理を呼べば何かが返るのは当たり前なので、**戻り線は既定では引かない**。
処理名から戻り値が読み取れるものに線を引いても情報は増えず、線の本数だけが増える。

**なぜ省くのか。戻り線を「情報」ではなく「強調」として使うためである。**

この図の目的は、作るものの洗い出しと関係者の認識合わせである。
そこで本当に見てほしいのは、**値が次の処理や次の画面へ渡っている箇所**である。
そこには実装の依存関係があり、作る順序・担当の分担・インターフェースの決めごとが発生する。
図を見てすぐ「ここは繋がっているから、先に決めないと進めない」と分かる必要がある。

ところが処理の数だけ戻り線を引くと、本数が倍になったうえ、
どの線も同じ見た目で並ぶため、**注意して読むべき1本が自明な線に埋もれる**。
自明なものを省くと、残った戻り線がそれだけで「ここは注意して読む箇所」の印になる。
省略は手間を惜しんでいるのではなく、残す線に意味を持たせるための操作である。

この考え方は戻り線に限らない。
線を足すか迷ったときは「この線が無いと読み手が誤解するか」を基準にする。
誤解しないなら、足さないほうが図は読みやすくなる。

| 例 | 引くか | 理由 |
| --- | --- | --- |
| 「カラーマスタの一覧を返す」→ 表示色を返す | 引かない | 処理名で自明 |
| 「シグナルの一覧を返す」→ 一覧の行を返す | 引かない | 処理名で自明 |
| 「下書きを1件作る」→ 採番されたIDを返す | **引く** | そのIDを次の処理が使う |
| 「CSV出力を受け付ける」→ 作業IDを返す | **引く** | 状況確認・ダウンロードで使う |

引くのは次の3つに当てはまるときである。

- 返った値を**別の処理が使う**（採番されたIDなど）
- 返った値を**画面遷移で次の画面へ渡す**。このときはラベルに渡すキーを書く
- 返るものが処理名から読み取れない、または**戻り先が呼び出し元とは別の画面**

参照だけの機能では、戻り線が1本も残らないことがある。
それでも凡例の「戻り」の説明は残しておく。図の間で凡例の読み方をそろえるためである。

### DB以外の保存先も同じ扱いで描く

認証基盤（Cognito）、キュー（SQS）、オブジェクトストレージ（S3）、外部システムなど、
テーブルでもファイルでもない保存先は `stores()` で描く。
形は角丸の箱にして円柱と区別するが、読み書きの線の引き方はテーブルと同じである。
AWS 上のシステムでは頻繁に出てくるので、テーブルだけで済ませようとしない。

### 線はテーブル群の枠につなぐ

個々のテーブルへ引くと本数が増えて読めなくなる。
どのテーブルが対象かは枠の中に並べておけば分かる。

### ラベルの位置

長い線では、既定の中点にラベルが置かれると遠くの図形へ重なる。
`label_pos` を終点寄り（0.8 前後）に指定して、線の行き先の近くに置く。

## 4. 範囲の切り方

### 実装があるものは描く

**「この機能の作成対象ではない」は、描かない理由にならない。**
描かれている画面や処理が実際に呼んでいるものは、誰が作るものであっても描く。
図はありのままを写すものであり、省くと実態と食い違う。

誰が作るかは、名前の後ろの（新規）（既存）（他機能で作る）で示す（§6）。
見積もりから外れることはこれで伝わるので、省く必要がない。

省いてよいのは、次の3つで**流れそのものが図の外へ出る**ときだけである。

| 出ていく先 | 例 |
| --- | --- |
| システムの外 | 利用者の手作業、他社システムでの処理 |
| 前後の工程 | この図が扱う操作の手前・その後にあたる、別の画面での操作 |
| 別の図 | 別に1枚を起こしてある画面へ遷移する |

### 切るときは行き先を書く

図が担当範囲の外へ出るところで、黙って線を切らない。
「どこで整理するのか」を書いた枠を置き、点線でつなぐ。

> **この先はこの図では扱わない**
> 配信の開始・停止・再開と、その後の配信処理は
> 「配信設定」の図で整理する。

読み手が続きを探せるようにするためである。
**行き先の呼び方は、そのプロジェクトで使っているものに合わせる。**
別の図の名前でも、工程の名前でも、作業計画の項目名でもよい。
読み手が次に見るものを特定できることだけが要件である。

実装がまだ無いものを枠で示すときは、**無いのか、別の図で扱うのかを書き分ける**。
読み手が「未実装だから描いていない」と取り違えるためである。

**枠へ線を引くかどうかは、引きやすさで決めてよい。** 線が既存の図形を突き抜けるようなら、
線は引かず、流れの先に枠を置くだけでよい。位置で続きを示せていれば読み手は追える。

## 5. 未確定事項（T.B.D）

仕様が未確定な箇所、実装が要件を満たしていない箇所は、赤い破線の枠で示す。

- 冒頭に **T.B.D　実装者に確認**
- 続けて、**何を確認したいのか**を箇条書きにする。事実と質問を分けて書く
- 対象の処理へ引き出し線（矢印なしの赤い点線）を引く。どこの話か分かるようにする
- **AIが書いたものは、末尾に自動生成である旨を必ず添える**

```
※ この T.B.D はAIの自動生成です。内容は必ずしも正しいとは限りません。
重要な情報は確認するようにしてください。
```

読み手が内容を鵜呑みにしないために必要なので、この一文は省かない。
`drawio_builder.py` の `Page.tbd()` は既定で付ける。

## 6. 名前の付け方

図の中では**和名を使う**。物理名だけでは、実装していない人が読めない。

- テーブル … 和名のみ。物理名との対応は凡例ページの表で示す
- スキーマ … 和名（例：`survey` → アンケート実施スキーマ）
- 画面 … 実際に画面に表示される名前
- 処理 … 「何をするか」を動詞で終える（例：下書きを1件作る）

他システムのテーブルなど、和名だけでは所在が分からないものは
`カラーマスタ（common.color_master）` のようにスキーマ名を添える。

### 名前の後ろの（　）は「この機能で作るか」を示す

画面・処理・テーブルの名前の後ろに付ける（　）は、**見積もりで数える対象を見分けるための印**である。
語彙を3つに固定し、これ以外を使わない。読み手が意味を推測する状態にしないためである。

| 表記 | 意味 | 作業量 |
| --- | --- | --- |
| （新規） | この機能で新しく作る | **数える** |
| （既存） | 他の機能で作成済み。そのまま使う | 数えない |
| 無印 | すでに在るものを、そのまま使う | 数えない |

処理には（新規）か（既存）を必ず付ける。処理の箱は「作る対象の候補」として読まれるため、
無印だと新規なのか流用なのか判断できない。テーブルは無印を既定とし、
新設するものにだけ付ける。

**（　）に書くのは「この機能で作るかどうか」だけである。**
どの機能が作るのか、どのチームが作るのかは書かない。
処理フロー図は役割分担を割り当てる図ではない（§9、2026/09/03 決定）。
以前は「（他機能で作る）」という語もあったが、割り当てを書くことになるため外した
（2026/09/08 ユーザー判断）。

**「（未実装）」とも書かない。** 図は実装があるものを描くので、
処理の箱があるなら実装はあるか、この機能で作るもののどちらかである（§4）。

**まだ無いものに依存していることは、（　）ではなく注記か T.B.D に書く。**
「この経路は◯◯が揃うまで動かない」という事実は見積もりに効くので、
書く価値はある。ただし短い印では伝わらないため、文で書く。

この対応表は `legend_page()` が凡例ページに出すので、図の読み手にも伝わる。

## 7. ページの構成

操作ごとにページを分ける。1枚に詰め込むと、どの線がどの操作のものか分からなくなる。

```
①新規作成・編集
②複製
③（更新など、性格の違う操作）
④削除
⑤凡例・和名対応
```

最後の凡例ページは、記号・線の色・和名対応表・図の範囲をまとめる。
`drawio_builder.legend_page()` で生成できる。

## 8. 成果物

- 形式は `.drawio`。VS Code 拡張（`hediet.vscode-drawio`）でそのまま閲覧できる
- 画像へ変換するとレイアウトが崩れるため、変換は求められたときだけ行う
- 出す前に `validate_drawio.py` で検査し、`preview_drawio.py` で目視する

### 正は `.drawio` であって、生成スクリプトではない

この図は**人とAIが交互に直す**。人は drawio で図を開き、線の取り回しや箱の位置を
その場で整える。その手直しは生成スクリプトには戻ってこない。

したがって、**人が一度でも drawio で保存したら、その時点で `.drawio` が正**になる。
生成スクリプトは初回を組み立てた道具であり、図の履歴ではない。以後は実行しない。

スクリプトを正に保とうとしてはいけない。人が図を触るたびに逆同期の作業が発生し、
レイアウトの微調整まで拾う必要が出て、いずれ必ず破綻する。
「スクリプトは古い」と割り切り、`.drawio` を直接編集するほうが運用に耐える。

既にある図を直す手順は SKILL.md の手順7 にある。

## 9. 見積もりに使うために足すとよいもの

必須ではないが、作業量を見積もる目的で描くなら、次があると図の価値が上がる。

1. **新規と既存の区別** — 新しく作るものが見積もりの対象そのものになる
2. **作業計画の項目との対応** — 図の1要素が計画の1項目に対応する粒度が理想

**誰が作るか（役割分担）は書かない。** この図は「何を作るか」と「データがどう流れるか」を
示すものであり、担当を割り当てる図ではない。担当は作業計画の側で管理する。
図に「別チーム作成」のような注記を足すと、図の目的が2つになって粒度がぶれる。
