# 処理フロー図の作成

画面・Backend の処理・テーブルやファイルの関係を1枚にまとめ、
**何を作る必要があるか**と**データがどう流れるか**を関係者で共有できるようにするスキル。

WBS の作成や見積もりに使うため、基本設計より粗い。
インターフェース定義やカラムまで書くと設計書になってしまい、完成しないまま時間だけが過ぎる。
粒度の線引きは [references/default_rules.md](references/default_rules.md) の §1 にある。

## この図は、人とAIが交互に直す

**新規に描くときと、既にある図を直すときで、進め方が違う。**
既にある図には人の手直しが入っていることがあり、生成スクリプトを実行すると**それが消える**。

まず、どちらなのかを判断する。

| 状況                           | 進め方                                                         |
| ------------------------------ | -------------------------------------------------------------- |
| 図がまだ無い                   | 手順1〜6（新規作成）                                           |
| 図があり、**人が触っていない** | 生成スクリプトを直して再実行してよい                           |
| 図があり、**人が触った**       | [手順7](#手順7既にある図を直す) へ。**スクリプトは実行しない** |

人が触ったかどうかは、`check_untouched()` で分かる。

```bash
python -c "import sys; sys.path.insert(0, r'<スキルのパス>/scripts'); from drawio_builder import check_untouched; print(check_untouched(r'<対象>.drawio'))"
```

戻り値は状態と説明の2つ組で、状態は次の3つ。

| 状態      | 意味                           | 進め方                               |
| --------- | ------------------------------ | ------------------------------------ |
| `clean`   | 前回書き出したときのまま       | 生成スクリプトを直して再実行してよい |
| `touched` | 内容が変わっている＝人が触った | 手順7へ。**スクリプトは実行しない**  |
| `unknown` | 台帳が無く、判断できない       | 手順7へ。**スクリプトは実行しない**  |

判定は SHA-256 のハッシュで行う。  
図と同じ場所の `.drawio-baseline/<ファイル名>.json` に、最後に書き出した内容のハッシュを控えてある。

**`mxfile` の `host` 属性で判断してはいけない。**
Web版 drawio で保存すると生成スクリプトと同じ `app.diagrams.net` になり、区別がつかない。
テキストエディタでの編集はそもそも `host` に出ない。

**この判定は `Diagram.save()` にも入っている。** `clean` 以外は書き込まずに例外で止まる。
うっかり実行しても図は壊れないが、止まってから考えるのではなく、先にこの確認をする。
どうしても上書きする必要があるときだけ `save(path, force=True)` を使う。

## 進め方

### 手順1　プロジェクト固有ルールの有無を確認する

```
.agents/state/process-flow-diagram/rules/
├── extension_rule.md   描き方の固有ルール（既定との差分だけ）
└── naming.md           スキーマ・テーブル・画面・処理の和名対応
```

**あれば** 両方を読み、手順3へ進む。聞くのは「今回はどの操作を描きますか」だけでよい。

**無ければ** 手順2でヒアリングして作る。

**ルールと依頼が食い違うときは、依頼を優先する。** 固有ルールは過去に描いた図の都合で
書かれていることがある。たとえば「As-Is で描く」とあるのに、依頼が未実装の機能だったり、
「この範囲は参照だけ描く」とあるのに、依頼がその範囲そのものだったりする。
そのときはルールに縛られず依頼に応え、**なぜルールと違う描き方をしたのかを図の凡例ページに書く**。
読み手がルールと図を見比べたときに混乱しないようにするためである。
恒久的な変更が必要そうなら、報告でその旨を伝えてルールの更新を促す。

### 手順2　ヒアリングしてルールを作る（初回のみ）

[references/interview.md](references/interview.md) に沿って進める。要点は3つ。

1. **質問する前に、インプットから拾えるものを集める。**
   DDL があればテーブルの物理名は全部拾える。画面のソースがあれば画面一覧も拾える。
   拾えるものを聞くのは相手の時間を使うだけなので、一覧を提示して「和名を教えてください」と聞く。

2. **必ず聞くのは7項目。** インプットの種類、対象範囲、As-Is/To-Be、システム構成、
   スキーマの和名、テーブルの和名、画面の呼び方。
   インプットが要件定義だけなら As-Is/To-Be は聞かない（To-Be しかない）。

3. **見た目は既定を提示して差分だけ聞く。** 1問で済ませる。
   毎回ゼロから決めると図ごとに見た目が変わり、複数の図を並べたときに読み方が揃わない。

聞き終えたら、テンプレートに沿って `extension_rule.md` と `naming.md` を書く。
既定と同じ内容は書かない。既定を直したときに食い違うためである。

### 手順3　図に載せるものを洗い出す

インプットから、この4つを拾う。

| 種別     | 拾うもの                                 | 探す場所の例                             |
| -------- | ---------------------------------------- | ---------------------------------------- |
| 画面     | 名前・遷移・どの処理を呼ぶか             | 画面のソース、画面一覧、要件定義         |
| 処理     | 何をするか・どのテーブルを読み書きするか | ハンドラのソース、API 定義、インフラ定義 |
| テーブル | 名前・読み書きの別                       | DDL、ER図、テーブル定義書                |
| ファイル | 名前・入出力の別                         | バッチのソース、連携仕様書               |

**コードがインプットなら、コードを正とする。** 設計書と食い違うことがあるが、
それ自体が報告に値する情報である。食い違いは T.B.D として図に残す。

**インプットが要件定義だけのときは、根拠のある要素と推測で補った要素を書き分ける。**
要件に API の分け方やテーブル名が書かれていることはまずないため、処理やテーブルは
こちらで仮に切ることになる。そのまま描くと、読み手は決定事項だと受け取ってしまう。

| 出どころ               | 図での示し方                               |
| ---------------------- | ------------------------------------------ |
| 要件に書かれている     | そのまま書く                               |
| 要件から推測して補った | 名前に「（仮称）」を付け、前提を注記に書く |
| 分割の仕方に根拠がない | T.B.D に「この単位で分けてよいか」と書く   |

洗い出した結果は、図を描く前に表の形で利用者へ見せる。
ここで漏れや粒度のずれを直しておくと、図を描き直さずに済む。

ただし**承認を待つ必要はない**。見せたうえでそのまま図の生成へ進む。
図ができてから直すほうが、文字だけの表を見て判断してもらうより早いためである。
サブエージェント実行など利用者へ問いかけられない場面では、仮定を置いて進め、
置いた仮定を報告に列挙する。ここで止まると何も出力されないまま終わってしまう。

### 手順4　図を生成する

[references/builder_api.md](references/builder_api.md) を読み、[scripts/drawio_builder.py](scripts/drawio_builder.py) を使う。

**XML を手で書かない。** 座標のずれ、ID の重複、エスケープ漏れで簡単に壊れる。
生成スクリプトを1つ書き、それを実行して .drawio を作る。
描き直しが何度も発生するので、スクリプトにしておくと座標を1箇所直すだけで済む。

**ただし、人が保存した図に対してスクリプトを実行してはいけない。**
スクリプトは図を丸ごと作り直すため、人の手直しが跡形もなく消える。
実行前に必ず `check_untouched()` で状態を確かめる（冒頭「この図は、人とAIが交互に直す」を参照）。

**作例がある。** [assets/example_process_flow.drawio](assets/example_process_flow.drawio) は、
架空の「お知らせ管理」を題材に、この図で使う描き方（3段構成・戻り線・T.B.D・範囲外の注記・凡例）を
一通り並べたものである。生成に使ったスクリプトは
[assets/build_example.py](assets/build_example.py) にあるので、これを雛形にすると早い。

**箱の高さは書かない。** `note()` `callout()` `tbd()` `scope_out()` `small()` `text()` は、
高さ `h` を省略すると本文と幅から必要な高さを見積もる。
高さを自分で決めると、文字を1行足すたびに数値を当て直すことになる。
見積もりは余る側へ寄せてあるので、余白が少し多くても文字は切れない。

ページは操作ごとに分ける。最後に凡例ページを `legend_page()` で作る。
1ページの中を段に分けるときは `section()` の見出しを置く。枠で囲んで分けてはいけない
（囲みは範囲を示す記号として既に使っているため。既定ルール §2 を参照）。

```
①新規作成・編集
②複製
③（更新など性格の違う操作）
④削除
⑤凡例・和名対応
```

### 手順5　検査して目視する

```bash
python .claude/skills/process-flow-diagram/scripts/validate_drawio.py <出力>.drawio
python .claude/skills/process-flow-diagram/scripts/preview_drawio.py <出力>.drawio --serve
```

検査は、図形の重なり・線のつなぎ先の消失・ページからのはみ出し・文字が箱に入りきらないかを見る。
これらは drawio で開かなくても分かる。

**検査を通しても、線の経路の読みにくさは分からない。** 必ずブラウザで描画して目を通す。
ラベルが別の図形に重なる、線が枠を突き抜ける、といった問題はここでしか気づけない。
drawio が未インストールでも [scripts/preview_drawio.py](scripts/preview_drawio.py) で確認できる。

**見た目の微調整は2巡までにして、残りはユーザーに渡す。**
検査を直して描画し直す、を1巡と数える。
数 px の重なりや、はみ出しの詰めは、drawio 上で図形をつまんで動かすほうが速い。
スクリプトの座標を当て直すと、直した箇所の隣がまた動くので巡回が終わらない。
2巡しても残る崩れは、何がどこで崩れているかを添えて報告し、ユーザーに調整してもらう。
内容（何を描くか）の誤りは対象外で、こちらは残さず直す。

### 手順6　報告する

- 何を描いたか（ページ構成）
- インプットとの食い違いや、実装が要件を満たしていない箇所（T.B.D に書いたもの）
- 判断に迷って既定と変えた点

### 手順7　既にある図を直す

人が触った図は、**`.drawio` が正**である。生成スクリプトは、初回を組み立てた道具にすぎない。
以後はスクリプトを捨て、`.drawio` を直接編集する。

スクリプトを図に追随させようとしてはいけない。人が図を触るたびに同期作業が発生し、
いずれ必ず破綻する。「スクリプトは古い」と割り切るほうが運用に耐える。

**雛形がある。** [assets/edit_existing.py](assets/edit_existing.py) を使う。
控えを取る・競合を確かめる・差分の案内を出す、までを引き受けるので、
呼ぶ側は「何を確かめて、何を変えるか」だけ書けばよい。

```python
import sys
sys.path.insert(0, r"<スキルのパス>/assets")
from edit_existing import edit_drawio, find_cell, label, edge_endpoints

def apply(tree):
    page = tree.getroot().findall("diagram")[1]      # ②シグナル詳細
    cell = find_cell(page, "n20")

    # ---- 前提の検査。想定と違えば、何も変えずに止まる ----
    assert label(cell) == "検知理由（保存先未定）", "中身が想定と違う: %r" % label(cell)
    assert cell.get("id") not in edge_endpoints(page), "削除対象に線がつながっている"

    cell.set("value", "AI提案")
    return ["n20 の中身を 検知理由 → AI提案 に変えた"]

edit_drawio("tmp/処理フロー/処理フロー_xxx.drawio", apply)
```

守ることは4つある。運用の中で、守らなかったときに実際に壊れた点である。

**1. 変更前に控えを取る。** 雛形が自動で取る。

**2. 書き込む直前に、人が保存していないかを確かめる。**

人が drawio を開いたまま作業していることがある。読み込んでから書き込むまでの間に
保存されると、その分が消える。雛形は読み込み時のハッシュを覚えており、
書く直前に取り直して一致しなければ**書き込まずに止まる**。

そのためにも、**読み込みと書き込みは同じスクリプトの中で続けて行う。**
調査のために読んだ結果を、後から別の実行で書き戻してはいけない。

**3. 消す前に前提を検査し、違えば何もせずに止める。**

対象のセルが想定どおりの中身か、線がつながっていないかを `assert` で確かめてから消す。
座標や ID を当てにした書き換えは、人が図をいじると簡単に狙いを外す。
`apply` の中で例外を投げれば、ファイルは1バイトも書き換わらない。

**4. 書いたあと、控えとの差分で変更範囲を確かめる。**

```bash
python .claude/skills/process-flow-diagram/scripts/diff_drawio.py <控え>.drawio <対象>.drawio
```

削除・追加・値・スタイル・線のつなぎ先・座標の別に出る。
**意図した以外の項目が出たら、人の編集と競合している。** その場合は消さずに報告する。

最後は新規作成と同じく `validate_drawio.py` と `preview_drawio.py` を通す。

## この図で守ること

詳細は [references/default_rules.md](references/default_rules.md) にある。特に外せないのは次の5つ。

**左から右へ読む。** 縦に積むと操作の数だけ伸びて読み通せなくなる。横に長くなるのは構わない。

**処理は呼び出し元の画面の真下に置く。** どの画面から呼ばれたかが位置で分かる。

**処理から次の画面へ直接つながない。** 遷移は画面どうしでつなぐ。
直接つなぐと「処理が画面遷移している」ように読めてしまう。
実際には処理が値を返し、それを受け取った画面が遷移している。

**戻り線は、戻る値がその先の流れを決めるときだけ引く。** 処理を呼べば何かが返るのは
当たり前なので、「表示色を取る → 表示色を返す」のように処理名で自明なものには引かない。
引くのは、採番されたIDを次の処理が使う場合や、値を画面遷移で次の画面へ渡す場合である。
参照だけの機能では1本も残らないことがあり、それが正しい。

省くのは、戻り線を**情報ではなく強調として使う**ためである。値が次へ渡る箇所には
実装の依存関係があり、作る順序・分担・インターフェースの決めごとが発生する。
自明な線まで引くと、その1本が同じ見た目の線に埋もれて見つけられなくなる。

**実装があるものは描く。** 「この機能の作成対象ではない」は、描かない理由にならない。
描かれている画面が実際に呼んでいる処理は、誰が作るものであっても描く。
**この機能で作るかどうか**は名前の後ろの（新規）（既存）で示す。
どの機能・どのチームが作るのかは書かない（既定ルール §6・§9 を参照）。

**範囲外は黙って切らない。** 行き先を書いた枠を置く。読み手が続きを探せるようにするためである。
省いてよいのは、システムの外・前後の工程・別の図の3つへ流れが出ていくときだけである
（既定ルール §4 を参照）。

## 未確定事項の書きかた

仕様が未確定な箇所、実装が要件を満たしていない箇所は、図の中に T.B.D として残す。
別の資料に書くと図と離れてしまい、読み手が気づかない。

- 冒頭に **T.B.D　実装者に確認**
- 事実と質問を分けて書く。「現状はこうなっている。これでよいか」の形にすると答えやすい
- 対象の処理へ引き出し線を引く
- **AIが書いたものは、末尾に自動生成である旨を必ず添える**

`Page.tbd()` は最後の一文を自動で付ける。読み手が内容を鵜呑みにしないために必要なので、
`by_ai=False` にするのは人が内容を確認して書き直したときだけにする。
