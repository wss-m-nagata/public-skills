# 記入要領: 共通コンポーネント設計書

## 資料の目的

共通コンポーネント一覧に載せた共通部品1つについて、インタフェース（入力・出力）、使うデータ、エラー、処理の中身を定める。  
実装担当と、単体テスト仕様書(共通コンポーネント)を書く担当が、この設計書だけで作業できる粒度で書く。

### どんなときに作るか

この設計書は、プロジェクトによって要るかどうかが変わる。  
共通コンポーネント一覧に載せた部品のうち、次のいずれかに当てはまるものについて作る。

- 複数の画面から使われ、入力・出力の取り決めを文書で共有したい。
- 処理の中身（分岐、エラー、他の共通部品の呼び出し）が複雑で、実装前に確認したい。
- 単体テストの元になる仕様を、文書で残したい。

見た目だけの小さな部品で、画面側の設計書や設計方針に書けば足りるものは、作らなくてよい。  
1つのコンポーネントIDにつき、1ファイルを作る。

### 読み替え（SPAの場合）

Nablarch の原文は、サーバー側の共通クラスとそのメソッドを前提にしている。  
SPA では、画面部品（Vue・React のコンポーネント）と、共通の関数・composable・フック・ストアを対象にする。  
サーバー描画の場合は、原文のとおり（クラスとメソッド）に書く。

| 欄 | 原文の意味 | SPAでの読み替え |
|---|---|---|
| クラス名 | 実装しているクラス | 実装しているファイル名またはコンポーネント名。 |
| メソッド名 | 処理に対応するメソッド | 呼び出し名。画面部品は`props`・イベントを含む呼び出し形、関数・composable は関数名と引数。 |
| 入出力パラメータ | メソッドの引数と戻り値 | 画面部品は、props・スロット・イベントのペイロード。関数・composable は、引数と戻り値。 |
| I/O | I＝入力、O＝出力 | I＝部品が受け取るもの（props、引数）。O＝部品が返す・通知するもの（イベント、戻り値）。 |
| CRUD一覧 | 処理が使うテーブルへの操作 | 処理が使うデータ（API、ストア、ブラウザのストレージ）への操作。「テーブル名」の欄に、APIの名称（WebサービスAPI一覧のAPI名）やストア名を書く。 |
| エラー種別 | 例外クラス | エラーの扱い方（画面に表示する、例外を投げる、戻り値で返す）。 |

### シートの分け方

テンプレートの見出しは、「処理名」と「メソッド名」が1つずつである。  
そのため、1つのシートに、1つの処理（1つの関数、または1つの画面部品）を書く。

- 画面部品：1コンポーネントにつき1シート。「処理名」には部品の役割（例：確認ダイアログ表示）を書く。
- 関数・composable：公開する関数ごとに1シート。1つのコンポーネントIDが複数の関数を持つときは、同じファイルの中にシートを足す。

## どこに何を書くか（シート『1.  コンポーネント名 』）

シート名は、サンプルでは「1. 〈コンポーネント名〉」の形である。  
シートを足すときは、「2. 〈処理名〉」のように連番を付ける。  
1〜3行目のPJ名・システム名・サブシステム名は、`変更履歴`シートを参照する数式のため、書かない（`記入要領_共通シート.md`を参照）。

グレーの行は、固定の見出しで、書き換えない。  
値を書くのは、白いセルである。

| 位置 | 項目名 | 記入内容 | 記入例（受注管理システム） |
|---|---|---|---|
| 5行目 F5（F5:H5） | コンポーネントID | 共通コンポーネント一覧のID。 | `CM0001` |
| 5行目 M5（M5:U5） | コンポーネント名 | 共通部品の名称。 | 確認ダイアログ |
| 5行目 Z5（Z5:AH5） | 処理名 | 処理の名称。 | 確認ダイアログ表示 |
| 7〜12行目 B7（B7:AH12） | 処理説明（処理概要・注意事項） | 6行目「処理説明」は固定の見出し。**本文は7行目のB7に書く**。B7には、「1.処理概要」「2.注意事項」の見出しが入っているので、見出しごと書き直す（下記）。 | 下記 |
| 13行目 F13（F13:P13） | クラス名 | 実装しているファイル名。 | `ConfirmDialog.vue` |
| 13行目 U13（U13:AH13） | メソッド名 | 呼び出し名。 | `<ConfirmDialog v-model message okLabel @ok @cancel>` |

B7（処理説明）は、セル内改行で次の形に書く。  
本文は6行以内にする（B7:AH12は6行分の高さで、行の高さを自動で広げられないため）。

```
1. 処理概要
　確認メッセージとボタンを持つダイアログを表示し、押されたボタンを親へ通知する。
2. 注意事項
　ダイアログは親が持つ表示フラグで開閉する。閉じる処理は親が行う。
```

### 入出力パラメータ（見出し14行目、列名15行目、データ16〜18行目の3行）

| 列 | 項目名 | 記入内容 | 記入例 |
|---|---|---|---|
| B（B:I結合） | 項目名 | props名、引数名、イベント名、戻り値の名前。 | `message` |
| J（J:K結合） | I/O | プルダウン：`I`、`O`。 | I |
| L（L:N結合） | 型 | 型名。イベントのときは「イベント」。 | `string` |
| O（O:P結合） | 必須 | プルダウン：`○`、`-`。出力（O）は`-`にする。 | ○ |
| Q（Q:AH結合） | 項目説明 | 項目が何かを1文で書く。既定値があれば書く。 | OKボタンの表示文言（省略時は「OK」） |

### CRUD一覧（見出し19行目、列名20行目、データ21〜22行目の2行）

| 列 | 項目名 | 記入内容 | 記入例 |
|---|---|---|---|
| B（B:I結合） | テーブル名 | 処理が使うデータ名（API名、ストア名、ストレージのキー）。 | 受注検索API |
| J〜M | C・R・U・D | プルダウン：`○`、`-`。作成・参照・更新・削除のどれを行うか。 | `-`、`○`、`-`、`-` |
| N（N:AH結合） | 備考 | 補足。無ければ空欄。 | - |

使うデータが無いときは、B21に「（なし）」と書き、J〜Mを`-`にする。

### エラー情報（見出し23行目、列名24行目、データ25行目の1行）

| 列 | 項目名 | 記入内容 | 記入例 |
|---|---|---|---|
| B（B:C結合） | エラー番号 | エラーの通し番号。処理定義の「エラー番号」欄から、この番号で参照する。 | 1 |
| D（D:J結合） | エラー名 | エラーの名称。 | メッセージ未指定 |
| K（K:O結合） | エラー種別 | エラーの扱い方（画面に表示する、例外を投げる、戻り値で返す）。 | 画面表示エラー |
| P（P:R結合） | メッセージID | 画面に出すメッセージのID。メッセージ設計書のIDと一致させる。無ければ`-`。 | `E.ORD.0001` |
| S（S:W結合） | 埋め込み文字列 | メッセージの`{0}`、`{1}`に入れる値。1行に1つ、`{0}：説明`の形で書く。 | `{0}：項目名` |
| X（X:AH結合） | エラー概要 | どういうときに起きるエラーか。 | messageが空のとき。 |

### 処理定義（見出し27行目、データ28〜41行目の14行）

処理の中身を、1行に1文で、段階を追って書く自由記述の欄である。  
見出し行の右側に、他の共通部品を呼ぶとき（Y：共通ｺﾝﾎﾟｰﾈﾝﾄID、AB：共通ｺﾝﾎﾟｰﾈﾝﾄ処理名）と、エラーが起きるとき（AG：エラー番号）の欄がある。

書き方（サンプルに合わせる）：

- 処理のまとまりの見出しを、B列に「1. 〇〇処理」の形で書く。
- そのまとまりの説明を、C列に書く。行の頭に全角スペースを1つ付けて字下げする。
- 分岐や詳細は、D列、E列、F列と、1段ごとに1列ずつ右にずらして書く。
- 1つのセルに、セル内改行を入れて何行も書かない。1行につき1セルに書く。
- 他の共通部品や、使うライブラリの部品を呼ぶ行は、`⇒使用コンポーネント：〇〇`のように書く。
  他の共通部品は、同じ行のY・ABに、そのコンポーネントIDと処理名も書く。
- その行でエラーが起きるときは、AG列にエラー番号（エラー情報の番号）を書く。
- まとまりの間は、1行空ける。

記入例：

```
B: 1. 表示処理
C: 　modelValueがtrueの間、messageを本文にしてダイアログを表示する。   AG: 1
C: 　⇒使用コンポーネント：UIライブラリのダイアログ部品
B: 2. ボタン押下処理
C: 　OKが押されたら、okイベントを通知する。
C: 　キャンセルが押されたら、cancelイベントを通知する。
D: どちらの場合も、modelValueは変更しない（閉じる処理は親が行う）。
```

## 記入時のポイント

- コンポーネントIDと名称は、共通コンポーネント一覧と、表記を完全にそろえる。
  ファイル名の`(共通コンポーネントID)_(共通コンポーネント名)`も、同じ表記にする。
- 画面部品のpropsとイベントは、画面側の設計書（画面項目の定義、画面イベントの設計書）が、その部品をどう呼ぶかと食い違わないようにする。
  食い違いを見つけたら、どちらが正かを確認してから直す。
- 画面に出すメッセージは、メッセージIDで指す。
  文言は、メッセージ設計書（またはバックエンドの設計書）が正で、ここには写さない。
- 型は、APIの項目の型とそろえる。APIの契約はバックエンド側の設計書が正で、ここは参照するだけである。
- 処理定義に、実装の細かな書き方（変数名、ライブラリの内部呼び出し）を書かない。
  何を、どの順に、どの条件で行うかを書く。
- 変更箇所を示すときは、`scripts/mark_changed_cells.py`で、今回変えたセルを赤字にする（`記入要領_共通シート.md`の「版を上げたときの変更箇所の示し方」を参照）。

## 行が足りないとき

3つの表（入出力パラメータ・CRUD一覧・エラー情報）は、下に別の表が続くため、`scripts/insert_rows.py`で行を挿入して増やす。  
処理定義は表の最下部なので、`scripts/extend_table_rows.py`で増やす。

行を挿入すると、それより下の行番号がずれる。  
**下の表から順に**（エラー情報、CRUD一覧、入出力パラメータの順に）増やすと、上の表の行番号がずれず、迷わない。

```bash
# 例：エラーを3行、CRUDを3行、パラメータを5行にする（テンプレートは1行・2行・3行）
# 1) エラー情報：26行目（空き行）の直前に、25行目の書式で2行挿入
python scripts/insert_rows.py <入力xlsx> "<シート名>" 26 2 25 <出力1>
# 2) CRUD一覧：23行目（エラー情報の見出し）の直前に、22行目の書式で1行挿入
python scripts/insert_rows.py <出力1> "<シート名>" 23 1 22 <出力2>
# 3) 入出力パラメータ：19行目（CRUD一覧の見出し）の直前に、18行目の書式で2行挿入
python scripts/insert_rows.py <出力2> "<シート名>" 19 2 18 <出力3>
# 4) 処理定義：全部で5行挿入した（2+1+2）ので、最終データ行は41＋5＝46。6行足す
python scripts/extend_table_rows.py <出力3> "<シート名>" 46 6 B AH <出力4>
```

- 上の例の結果、入出力パラメータは16〜20行、CRUD一覧は23〜25行、エラー情報は28〜30行、処理定義の見出しは32行目になる。
  値を書く前に、見出しの文字（「処理定義」「エラー情報」など）が実際にどの行にあるかを確かめる。
- 行を挿入すると、挿入した行には入力規則（プルダウン）が付かない。
  `I/O`・`必須`・`C/R/U/D`には、プルダウンの選択肢と同じ値（`I`、`O`、`○`、`-`）を書く。
- エラー情報の行は、挿入した行の高さがテンプレートの行と違うことがある（既定の高さより高くなる）。
  見た目に困るときは、Excelで高さを直す。
- 印刷範囲は広がらない。印刷や PDF 化で下の行が切れるときは、Excelの[ページレイアウト]→[印刷範囲]で広げる。
- 行を足すと、`verify_layout.py`は「行数・結合セル・罫線が増えた」と報告する。
  これは意図した変更であり、足した行以外に差分が無いことを確かめる。

## 長い文を書くとき

行の高さは、入出力パラメータ・エラー情報などの結合セルでは自動で広がらない。  
値を書いたあとに、`scripts/fit_row_heights.py`で行の高さを広げる。  
**処理定義の行（見出し以降）には使わない。** 処理定義は、セルから右へ文字があふれて表示される作りで、使うと行が不必要に高くなる。

```bash
# 例：13行目から処理定義の見出しの前の行まで（上の例では31行目まで）
python scripts/fit_row_heights.py <入力xlsx> <出力xlsx> --rows 13-31 --sheet "<シート名>"
python scripts/verify_layout.py <書き込み前のxlsx> <出力xlsx> --allow-row-heights
```

処理説明（7〜12行目）は、複数行にまたがる結合セルのため対象外である。  
6行を超えるときは、本文を短くするか、Excelで7〜12行目の高さを広げる。

## シートの名前と目次

テンプレートのシート名は「1.  コンポーネント名 」（スペースの数に注意）で、目次B7は「1. [コンポーネント名]」である。  
実際の名称に書き換える（`記入要領_共通シート.md`の「1インスタンス＝1シート」型）。

```bash
# 1) シート名を変える
python scripts/rename_sheet.py <フォーマットのxlsx> "1.  コンポーネント名 " "1. 確認ダイアログ" <出力xlsx>
# 2) 処理（シート）を足すとき：シートを複製する（入力規則も複製される）
python scripts/duplicate_sheet.py <入力xlsx> "1. 確認ダイアログ" "2. 通知表示" <出力xlsx>
# 3) 目次に書く（B7、B9…。目次は罫線外のため --allow-outside-border が要る）
python scripts/apply_mapping.py <入力xlsx> <マッピングJSON> <出力xlsx> --allow-outside-border
```

シート名は31文字以内で、`[ ] : * ? / \`を含められない。  
目次は自動では更新されない。

## 値を書き込む手順

```bash
python scripts/apply_mapping.py <入力xlsx> <マッピングJSON> <出力xlsx>
python scripts/verify_layout.py <書き込み前のxlsx> <書き込み後のxlsx>
```

マッピングJSONの例：

```json
{"sheets": {"1. 確認ダイアログ": {
  "F5": "CM0001", "M5": "確認ダイアログ", "Z5": "確認ダイアログ表示",
  "B7": "1. 処理概要\n　…\n2. 注意事項\n　…",
  "F13": "ConfirmDialog.vue", "U13": "<ConfirmDialog v-model message okLabel @ok @cancel>",
  "B16": "message", "J16": "I", "L16": "string", "O16": "○", "Q16": "確認メッセージ"
}}}
```

- 結合セルは、左上のセルを指定して書く。
- 「処理説明」（B6）、「入出力パラメータ」（B14）、「CRUD一覧」（B19）などの見出しは、書き換えない。
- 値を書いたあと、`scripts/export_sheet_preview.py`で見た目を確かめる。
