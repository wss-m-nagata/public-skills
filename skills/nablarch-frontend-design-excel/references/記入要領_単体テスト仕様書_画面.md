# 記入要領: 単体テスト仕様書(画面)

## 資料の目的

1つの取引（1つの機能。例：受注の一覧から登録・変更まで）について、画面の単体テストで**何を・どの観点で・どこまで**確かめるかを一覧にする。  
**取引1つにつき1ファイル**作成する（ファイル名の `(取引ID)_(取引名)` を実際の値に置き換える）。

このスキルは、フロントエンドが SPA（Vue・React などのシングルページアプリ）の場合を主な対象とする。  
テンプレートの見出し・列・観点は、Nablarch 標準のまま変えない。  
変えるのは、「何を書くか」の解釈だけである（下の「SPA での読み替え」）。  
サーバーで画面を作る方式（JSP など）の場合は、読み替えずに、Nablarch の原文のとおりに書く。

テスト仕様のシートには、テスト観点カタログの観点が、あらかじめ1行ずつ並んでいる。  
カタログは「一般的なテスト観点」であり、その機能固有の決まり（設計書に書かれた個別の業務要件）を確かめる観点は、カタログに無いことがある。  
次の3段階で埋める。

1. **その機能にある分類（大項目〜詳細）を整理し、無い分類の行はシートから消す。**  
   例：ファイルのアップロードが無い画面では「ファイル取込」の行を消す。一覧を表示するだけの画面では、入力チェックの行を消す。  
   消した分類は、仕様書には残さない。
2. **設計書の記述を順に見て、それぞれを確かめる観点を当てる。当てはまる観点がカタログに無ければ、追加観点として足す。**  
   見る設計書は、システム機能設計書（画面項目定義・画面イベント一覧・入力チェック・表示ルールなど）、画面遷移図、画面一覧、共通コンポーネント設計書など。  
   特に、権限・状態による表示や操作の違いのような業務の決まりは、カタログの観点だけでは抜けやすい。  
   例：「一般ユーザーには、削除ボタンを表示しない」「締め処理済みの受注は、編集画面を開けない」。
3. **残した分類の観点ごとに、「テストケースを書く」か「対象外理由を書く」かのどちらかを必ず埋める。**  
   どちらも空の観点が残っていなければ、その機能にある観点の抜けが無い（全量を確かめた）と言える。  
   対象外の行は灰色にし、テストする行（白）と見分けられるようにする。

## シートの種類と使い分け

単体テストは、テストする範囲で3つに分かれる（Nablarch システム開発ガイドのサンプルプロジェクトの単体テスト標準）。  
仕様書は、取引1つにつき1つ作り、次の表で「作る」になっているシートを入れる。

| テストの範囲 | シート（作成後のシート名） | このスキルでの読み替え | 作る条件 |
|---|---|---|---|
| モジュール単位 | `<テストターゲット名>_クラス単体` | 画面を構成する部品の単体。コンポーネント、composable、ストア、入力チェックの関数など | ロジックが複雑なものだけ作る（0個以上） |
| 画面・リクエスト単位 | `<リクエストID>_リクエスト単体` | 画面イベント単位のテスト。リクエストIDは、画面イベントID（ボタン押下、初期表示、API 呼び出しなど）と読む | **必ず作る**（1個以上。画面イベントの数だけ作る） |
| 取引単位 | `取引単体` | 取引（機能）単位のテスト。画面遷移をまたぐ一連の操作 | リクエスト単体が2個以上ある取引のときに作る（1個だけ） |

- `build_unit_test_spec.py` は、次の組み合わせをエラーにする。
  - リクエスト単体が1つも無い。
  - 取引単体が2つ以上ある。
  - 取引単体があるのに、リクエスト単体が1つしか無い（画面遷移をまたぐ操作が無いため）。
  - 同じシート名が2つある。
- リクエスト単体が2つ以上あるのに取引単体が無いときは、エラーにせず、警告を出す。  
  取引単体を作るかどうかは、テストの範囲で決める。
  - ユーザーが、テストの範囲を、特定の画面イベントに限定したとき（例：2つのイベントだけ）は、取引単体を作らなくてよい。このときの警告は、無視してよい。
  - テストの範囲を限定しなかったときは、取引単体を作る（単体テスト標準では、画面の取引は取引単体を作る）。
  - 作った・作らなかった理由は、最後の報告に書く。
- 使わない種類のシートは残さない（`build_unit_test_spec.py` は、定義に無い種類のシートを消す）。
- クラス単体のシートは、テスト対象の部品の数だけ作る。
- クラス単体で確かめず、リクエスト単体で確かめる観点は、クラス単体のシートで「リクエスト単体テストで確認するため対象外」とする。  
  逆に、クラス単体で確かめる観点は、リクエスト単体のシートで「クラス単体テストで確認するため対象外」とする。
- シート名は31文字以内。`[ ] : * ? / \` は使えない。
- 実行するテストの道具（Vitest・Jest・Playwright・Cypress など）は、限定しない。  
  部品の単体は単体テストの道具、画面イベントと取引は、コンポーネントテストやブラウザ操作のテストの道具で確かめることが多い。

## 見出し（5〜8行目）

「<項目名>：<値>」の形で、ラベルと同じセルに書く（例：`機能名：受注管理`）。

| 項目 | 書く内容 | 書けるシート |
|---|---|---|
| 機能名 | システム機能一覧の機能名 | 全シート |
| 取引名 | 取引の名前（ファイル名と同じ） | 全シート |
| テストターゲット名 | クラス単体：テスト対象の部品名（例：`useOrderForm`、`OrderStore`）。リクエスト単体：画面イベントを受ける画面（ページ）のコンポーネント名（例：`OrderCreatePage`） | クラス単体・リクエスト単体 |
| リクエストID | 画面イベントのID。画面イベント一覧のIDを書く | リクエスト単体のみ |

PJ名（1行目）・サブシステム名（4行目）・作成者・作成日・更新者・更新日は、`変更履歴` シートから自動で表示される数式なので、書かない（`build_unit_test_spec.py` が数式を入れる）。

## 表の列

クラス単体・リクエスト単体のシートの列は、次のとおり。

| 列 | 書き方 |
|---|---|
| ケースNo | 数式で自動で振られる（「詳細-観点-テスト内容」の連番）。**書かない** |
| 大項目・中項目・小項目・詳細・観点 | テスト観点カタログのまま。**書き換えない**。カタログに無い観点は「追加観点」として行を足す（下記） |
| 対象外理由 | その観点をテストしない理由。テストケースを書く観点では空欄。対象外の行は、観点から右を灰色にする |
| 対応設計書・対応箇所 | その確認の根拠になる設計書と、その中の箇所（節・シート・項目）。例：`システム機能設計書`／`画面イベント一覧 ORD0101` |
| テスト内容 | 何をするか。前提条件があるときは、**先頭に `【前提】…` と書き、改行してから操作を書く** |
| 想定結果 | 何が起きれば合格か。観測できる形で書く（表示された文言・ボタンの状態・遷移先のルート・呼ばれた API とその内容・ストアの値など） |
| テストデータシート名・データNo | 試験で作るデータがあるときに書く。シート名には `試験データ`、データNoには、そのケースが使うデータのまとまりの番号（`D01` など）を書く。使わなければ空欄（書き方は、下の「試験データのシート」） |
| 実施者・実施日・実施結果・確認者・確認日 | 実施の記録。実施結果は `OK` / `NG` から選ぶ |

- このテンプレートには、テストコードの列が無い。  
  テストコードの場所（例：`orderForm.spec.ts > 受注者名が空だとエラー`）を残すときは、定義ファイルのケースに `テストコード` を書く。  
  `build_unit_test_spec.py` が、テスト内容の末尾に `【テストコード】…` として書く。
- 対象外理由の列は、テンプレートでは折りたたまれている（グループ化されている）。  
  `build_unit_test_spec.py` は、観点ごとの「テストした」か「対象外にした理由」かが見えるように、展開して出力する。

取引単体のシートの列は、観点の列が違う。

| 列 | 書き方 |
|---|---|
| ケースNo. | 数式で自動で振られる（「確認観点2-確認観点3-テスト内容」の連番）。**書かない** |
| 区分・確認観点1・確認観点2・確認観点3 | テスト観点カタログのまま。**書き換えない**。確認観点3は、確認観点2が「異常取引」「その他のイベント」「取引の連続実行」のときだけ埋まっている |
| 対象外理由・対応設計書・対応箇所・テスト内容・想定結果・テストデータシート名・データNo・実施者〜確認日 | クラス単体・リクエスト単体と同じ |

- 取引単体の「対応設計書」には、画面遷移図とシステム機能設計書を、`(a)画面遷移図` `(b)システム機能設計書` のように並べて書く方法がある（公式の記入例）。  
  「対応箇所」には、それぞれの中の箇所を、同じ記号で書く。

### 1つの観点に、テストケースが複数あるとき

観点の行の下に行を足し、2件目以降のケースを書く（ケースNoの3つ目が `1-1-1`、`1-1-2` … と増える）。  
足した行の分類・観点の列は空欄にする。

### 対象外理由の書き方

「なぜこの観点でテストしなくてよいか」が、読んだ人に分かるように書く。

- 機能が無い：`ファイルのアップロードが無いため対象外`
- ほかのテストで確かめる：`クラス単体テストで確認するため対象外`
- 画面ではなく、バックエンドで確かめる：`データベースはバックエンドのテストで確認するため対象外`
- ほかの活動で確かめる：`UI標準のレビューで確認するため対象外`

観点の取捨選択の考え方（Nablarch システム開発ガイド「テスト項目の検討」）：
- プロジェクトに関係しない観点（その機能が無いもの）は外す。
- 残った観点も、「そのテストでバグが見つかる見込みが低い」「レビューや次の工程のテストで見つかる」「バグがあっても影響が軽い」ものは、理由を書いて外してよい。

### 追加観点（カタログに無い、プロジェクト独自の観点）

設計書の記述に当てはまる観点がカタログに無いとき（上の「資料の目的」の2）に足す。  
カタログの観点の行の後ろに行を足し、観点の列に書く。  
カタログに無い大項目を足すときも、残した分類のどれかの観点の後ろに置く（`after` で指定する）。  
新しい詳細（または小項目・中項目・大項目）として始めるときは、その列にも書く。  
取引単体では、確認観点2・確認観点3（必要なら区分・確認観点1）に書く。  
足した行も、カタログの観点と同じく、テストケースか対象外理由のどちらかを埋める。

## 観点Noと分類の決め方

### 観点Noの数え方

定義ファイルの `観点` の `No` と `追加観点` の `after` には、**空のテンプレートでの観点No**を書く。  
観点Noは「1つ目-2つ目」の形で、次のとおり数える。

- 1つ目は、詳細の列に値がある行ごとに1つ増える。  
  テンプレートでは、同じ詳細が続く行の詳細の列は空欄なので、増えない。  
  値が「-」の行も、値がある行として数える。  
  小項目が変わる行で詳細が「-」でも、新しい行に値があるので、1つ増える。
- 2つ目は、詳細の中で、観点の列が空でない行ごとに1つ増える。詳細が変わると、1に戻る。
- 分類（大項目・中項目・小項目）が変わっても、1つ目は連続して増える。分類ごとに1から数え直さない。

数え間違えを避けるため、数式を読んで自分で番号を振らず、次のコマンドで一覧を出す。

```bash
python scripts/build_unit_test_spec.py <テンプレート> --list-catalog [--filter <分類の前方一致>] [--sheet-template クラス単体|リクエスト単体|取引単体]
```

- 出力は、1観点1行の `観点No  [分類]  観点の文言` である。
- `--filter` は、分類の前方一致で、「/」でつなぐ（例：`--filter 画面表示/表示結果`）。
- `--sheet-template` の省略時は、リクエスト単体（取引単体の観点Noは `--sheet-template 取引単体` で出す。取引単体は、1つ目が確認観点2、2つ目が確認観点3の数え方になる）。
- 一覧の観点Noは、組み立ての処理と同じ関数で数えている。  
  定義ファイルには、この一覧の観点Noを、そのまま書く。

### 分類の前方一致の考え方

`分類` に書いた分類は、**前方一致**で観点を残す。  
指定した分類の下にある観点が、すべて残る。

- `["画面表示", "表示結果", "画面表示データ"]` と書くと、小項目が「画面表示データ」の観点が、詳細が「-」のものも「編集仕様」のものも、すべて残る。
- 1つの詳細だけを残したいときは、詳細まで書く（例：`["画面表示", "表示結果", "画面表示データ", "-"]`）。
- 大項目だけ（`["画面表示"]`）を書くと、大項目の下の観点がすべて残る。

残った観点は、すべて、テストケースか対象外理由を書く。  
範囲を絞るときは、次の手順で進める。

1. `--list-catalog --filter <分類>` で、その分類を書いたときに残る観点を、先に見る。
2. 残したくない観点が含まれるときは、分類を細かく書き直すか、`対象外` にまとめて理由を書く。
3. 組み立てて、未記入の観点のエラーが出たら、エラーに出る分類と観点の文言を見て、2に戻る。

### まとめて対象外にする書き方

`対象外` は、`分類` に書いた分類のうち、まとめて対象外にするものを、分類（前方一致）と理由で書く。

```json
"対象外": [
  {"分類": ["画面表示", "表示結果", "画面表示データ", "編集仕様"], "理由": "取得した値の編集が無いため対象外"}
]
```

- `観点` に個別に書いた観点は、`対象外` より優先される（まとめて対象外にした中の一部だけ、テストケースを書ける）。
- 分類の前方一致の範囲は、`分類` と同じである。

### 未記入の観点のエラー

テストケースも対象外理由も無い観点が残っていると、組み立てはエラーになる。  
エラーには、観点No・分類（大項目〜）・観点の文言が、1観点1行で出る。  
分類を見て、どの `分類` の指定から残った観点かを確かめる。

## SPA での読み替え

観点カタログの観点は、増減しない。  
SPA で意味が変わる観点は、次のように読み替えて、テストケースか対象外理由を書く。  
「Nablarch の原文」は、サーバーで画面を作る方式での意味である。

### 用語

| Nablarch の用語 | SPA での読み替え |
|---|---|
| 取引 | 1つの機能（ユースケース）。1取引に複数の画面（ルート）がある |
| 画面ID | 画面（ルート／ページ）のID |
| リクエストID | 画面イベントのID（ボタン押下、初期表示、API 呼び出しなど） |
| Action、フォワード先 | 画面イベントごとの処理（ストアの更新、画面遷移、API 呼び出し） |
| セッション | ストア（状態管理）、ルートのパラメータ、ブラウザのストレージ |
| サーバー側の入力チェック | クライアント側の入力チェックと、API が返すエラーの表示 |
| 画面とAPIの入出力 | 画面項目と、API の項目の対応。API の契約は、バックエンドの設計書が正で、フロントエンドは参照する |

### 大項目ごとの読み替え

| 大項目（中項目） | Nablarch の原文の意味 | SPA での読み替え |
|---|---|---|
| バリデーション（単項目・相関） | サーバーで行う入力チェック（Form の検証メソッド） | クライアント側の入力チェック。「エラーとなる」は、検証の関数がエラーを返すこと、画面にエラーメッセージが表示されること、API が呼ばれないことのどれかで書く。検証の関数はクラス単体、画面での入力からエラー表示までは、リクエスト単体で確かめる |
| バリデーション（DBとの相関バリデーション） | DB を引いて行う検証（重複・存在チェックなど） | API が返す重複・存在のエラー（409・422 など）を受けた画面の動き。API の応答は、モックなどで作る。検証そのものは、バックエンドの仕様書で確かめる |
| DB操作・DB制御 | SQL の条件・実行結果、更新順序、排他制御、コミット、ロールバック | 画面は DB を直接操作しないため、**原則「データベースはバックエンドのテストで確認するため対象外」**とする。API 経由のデータは、「画面表示」（取得結果の表示）と「送信処理」（リクエストの内容）で確かめる。排他制御は、API が排他エラーを返したときの画面の動き（メッセージ・入力値の保持）に読み替える。ブラウザのストレージ（IndexedDB・localStorage など）にデータを持つ画面では、その読み書きに読み替えて、この観点を使う |
| ファイル取込 | サーバーに取り込むファイルの検証と取込結果 | ブラウザで選んだファイルの検証（サイズ・形式・件数・文字コード）と、API への送信結果の表示。取り込んだ後の処理は、バックエンドで確かめる |
| ファイル出力 | サーバーが出力するファイルの内容 | ブラウザで作る、またはダウンロードするファイルの内容（ファイル名・文字コード・改行・並び順・レイアウト）。サーバーが作るファイルの内容は、バックエンドで確かめる |
| ファイル操作 | サーバー上のファイルの削除・移動・コピー | ブラウザでは行わないため、対象外 |
| メール処理 | サーバーからのメール送信 | ブラウザでは送信しないため、原則対象外（メールのリンクは「画面操作」で確かめる） |
| 受信処理 | 外部システムからの電文の受信 | API のレスポンスの取り込み。電文の桁数・レコード件数は、レスポンスの項目の長さ・配列の件数に読み替える。マルチレイアウトの観点は、該当しなければ対象外 |
| 送信処理 | 外部システムへの電文の送信 | 画面からの API 呼び出し。電文の編集は、リクエストの URL・メソッド・ヘッダ・ボディ・クエリの組み立てに、タイムアウトやその他のエラーは、通信エラー時の画面の動きに読み替える |
| ログ出力 | ログファイルの格納先・名前・権限、ログの編集 | ブラウザのコンソール出力、エラーの報告（エラー情報の送信）。ログファイルの格納先・権限などの観点は対象外 |
| 画面表示 | 画面の見た目・表示データ | そのまま。画面はルート（ページ）とコンポーネントの描画に、画面の幅・高さはビューポートに、JavaScript エラーはコンソールエラーと未処理の例外が出ないことに、スタイルシートは CSS・テーマに読み替える。「タイムアウトした場合」は、API の応答待ちの打ち切りと、ログイン状態の期限切れの両方を考える |
| 画面操作（イベント実行結果） | ボタン・入力部品の動き | そのまま。「二度押し防止」は、API が二度呼ばれないことで書く |
| 画面操作（遷移結果） | URL・フォワード・ブラウザの動き | 画面遷移は、ルーターによる遷移とルートのパスで書く。別ウィンドウは、別タブ・ダイアログで書く。「戻る」は、ブラウザ履歴の戻るで書く。URL 直接アクセスは、ルートの直接指定とリロード（ルートガード・認可を含む）で書く |
| 画面操作（HTTPステータス） | 画面遷移の結果の HTTP ステータス | SPA では、画面遷移で HTTP ステータスは返らない。API のステータス（401・403・404・500 など）に応じた画面の動き（ログイン画面へ戻る・エラー表示など）に読み替える。ステータスに応じた動きが無ければ、対象外 |
| 画面操作（ブラウザキャッシュ） | ブラウザのキャッシュ保持 | 戻ったときの画面の状態の保持（ストアの値・コンポーネントの保持）と、API 応答のキャッシュ |
| データベースアクセス（二重サブミット防止） | DB の二重更新が起きないこと | 更新 API が二重に呼ばれないこと（ボタンの二度押し・戻って再実行・リロード）。DB が二重に更新されないことは、バックエンドで確かめる |

### 設計書の記載の読み替え

- 観点の中の「[システム機能設計書の記載通り]」「[UI標準の記載通り]」「[画面遷移図の記載通り]」は、その設計書の、確認する箇所を、対応設計書・対応箇所の列に書く。
- 「セッション」「フォワード」など、サーバー描画の言葉がテスト内容・想定結果に必要なときは、上の用語の表のとおり、ストア・ルートの遷移などで書く。
- サーバー描画の画面（JSP など）の場合は、読み替えずに、原文のとおりに書く。

## 取引単体の書き方

取引単体は、画面遷移をまたぐ一連の操作を確かめる。  
区分は「取引実行確認」、確認観点1は「画面遷移パターン」である。  
確認観点2・確認観点3は、次のとおりに読む。

| 確認観点2（確認観点3） | 書く内容 |
|---|---|
| 正常取引 | 取引の入口から完了までの、画面遷移とデータの引き継ぎ。例：一覧→登録→確認→完了→一覧。入力した内容が、次の画面に表示される |
| 戻るイベント | 各画面の「戻る」ボタン（画面内のボタン・ブラウザの戻る）の遷移先 |
| 検索結果0件 | 検索結果が0件のときの画面（空表示・メッセージ）と、その後の遷移。0件で画面が表示されないときは、対象外理由に書く |
| サブウィンドウ連携 | ダイアログ・別タブなどで開く画面との値の受け渡し |
| 異常取引（精査エラー） | 入力チェックのエラー後、入力を直して取引を続けられること |
| 異常取引（検索結果上限超過エラー） | 検索結果が上限を超えたときの画面の動き |
| 異常取引（排他制御エラー） | API が排他エラーを返したときの画面の動き |
| 異常取引（その他エラー） | 通信エラー・権限エラー・API のエラー応答など、その他のエラーのときの画面の動き |
| その他のイベント（ページング処理、ソート処理 など） | 一覧のページ切り替え・並び替えなどを挟んだ遷移 |
| 取引の連続実行（異常取引→正常取引 など） | エラーの後に、同じ取引を続けて行い、入力項目やストアの値が正しく復元・初期化されること |

- 「テスト内容」には、画面遷移を `A画面→[ボタン名]→B画面` の形で書くと、読みやすい。
- 取引単体のケースは、複数の画面イベントにまたがる。画面イベント1つで確かめられることは、リクエスト単体に書き、ここには書かない。

## 試験データのシート

リクエスト単体・取引単体の試験で、データを作る必要があるときは、**別のファイルに分けず、同じ仕様書の末尾に「試験データ」のシートを足して書く**（Excel だけで、試験の前提が確認できるようにするため）。  
画面の試験では、画面に表示するための API の応答（モックの応答）と、ストアの初期値が、試験データにあたる。

- **ケースの前提・テスト内容には、データの中身を並べない。** 「試験データを使う。」のように書き、中身は、データNoで、このシートに任せる。
- **データは、API の応答やストアごとに、項目名と、実際に入れる値で書く。** 「主な値」のような概要では、仕様書を見て、試験できることが確認できないため。
  - 項目が多いものは、試験に関係しない項目を割愛してよい。割愛したことは、表の上の注記に書く。
  - 日時のように、実行のたびに変わる値は、「試験の実行時の1日前」のように、相対的に書く。
- **共通データ（試験では作らず、環境に入っている前提のデータ）は、「入っている前提のレコード」で書く。**
- **個別データ（試験で作り、終わったら消すデータ）には、データNoと、そのデータを使うケースを書く。**
- シートの形は、`scripts/add_test_data_sheet.py` で作る。  
  定義の書式は、スクリプト冒頭の説明を参照する。  
  このスクリプトは、データベースのテーブルを前提にした書式（テーブル名・カラム名）で書く。  
  API の応答やストアを書くときは、テーブル名の欄に、API のパスやストアの名前を書き、カラム名の欄に、項目名を書く。

## 作り方（ローカル実行）

手で行を足すと、ケースNoの数式・罫線・入力規則・印刷範囲がずれるため、`scripts/build_unit_test_spec.py` で組み立てる。

1. テスト項目を、定義ファイル（JSON）に書く。書き方は `build_unit_test_spec.py` の冒頭の説明を参照する。
   - `分類` に、その機能にある分類を書く（クラス単体・リクエスト単体は大項目〜詳細、取引単体は区分・確認観点1・確認観点2）。書いていない分類の行は、シートから消える。
   - 設計書の記述を順に見て、確かめる観点を当てる。カタログに無いものは `追加観点` に書く。
   - 観点は、空のテンプレートでのケースNoの前2つ（クラス単体・リクエスト単体は「詳細-観点」、取引単体は「確認観点2-確認観点3」。例：`3-2`）で指定する。観点Noは、`--list-catalog` で出した一覧のものを、そのまま書く（組み立てた後のケースNoは、消した行の分だけ詰まる）。
   - 残した分類のうち、まとめて対象外にするものは、`対象外` に分類と理由を書く。
   - 表紙・変更履歴の内容（PJ名・システム名・サブシステム名・会社名・部門名・変更履歴）は `document` に書く。
   - 前提条件は `前提` に書くと、テスト内容の先頭に `【前提】…` として入る。
2. 組み立てる。
   ```bash
   python scripts/build_unit_test_spec.py "assets/templates/フォーマット/単体テスト仕様書(画面)_(取引ID)_(取引名).xlsx" <定義json> <出力パス> --cases-json <ケース一覧json>
   ```
   どちらも埋まっていない観点が残っていると、その観点の番号を挙げてエラーになる（書きかけの確認だけなら `--allow-unaddressed`）。  
   表紙・変更履歴も、このスクリプトが書く（このテンプレートに『目次』シートは無い）。
3. `export_sheet_preview.py` でテスト仕様のシートをPDFにし、行の高さ・折り返し・罫線・ケースNoを目で確かめる。  
   PDFをReadツールで開けない（`pdftoppm`が無い）ときは、PyMuPDFでPNGにして開く。

### 検証

組み立てたファイルは、`verify_layout.py` の対象外である（シート構成が変わり、ケースNoの配列数式も誤検知になるため）。  
次の4点を確かめて、完了とする。

1. `build_unit_test_spec.py` の終了コードが 0 であること（観点の抜け・組み合わせの誤りはエラーで止まる）。
2. 標準エラー出力に警告が出ていないこと。出ているときは、内容を確かめ、無視してよい理由があれば、報告に書く。
3. `--cases-json` の出力で、ケースNo・分類・観点・テスト内容・想定結果が、意図どおりであること。
4. `export_sheet_preview.py` で、行の高さ・折り返し・罫線・ケースNo・印刷範囲を、目で確かめること。

### 版を上げるとき（変更箇所を赤字にする）

既存の仕様書の版を上げるときは、その版で変えた箇所だけを赤字にし、前の版の赤字は残さない。  
定義ファイル（JSON）の、変えたケース・観点に `"changed"` を付けて、組み立て直す。  
組み立て直すので、前の版の赤字は消え、今の版で `"changed"` を付けた箇所だけが赤字になる（前の版の `"changed"` は消す）。

| 付ける場所 | 指定 | 赤字になるセル |
|---|---|---|
| ケース（`cases` の1件） | `true` | そのケースの、値のある列の全部（対応設計書・対応箇所・テスト内容・想定結果など） |
| ケース | 列名のリスト（例：`["想定結果"]`） | 指定した列だけ（`テストコード` は、テスト内容の列になる） |
| 追加観点・対象外理由の記入 | `true` | 分類と観点（対象外理由の記入は、対象外理由）の全部 |
| 追加観点・対象外理由の記入 | 列名のリスト（例：`["観点"]`） | 指定した列だけ |

- 1つでも付けると、表紙の版数も赤字になる。
- 変更履歴にも、新しい版の行を足す（`document` の `変更履歴`）。
- 新しい観点を足すときは、既存のケースNoがずれないよう、追加観点の並びの最後に足す。

`--cases-json` には、組み立てた結果の全行（ケースNo・分類・観点・テスト内容・想定結果など）が出る。  
openpyxlで書いたファイルにはケースNo（数式）の計算結果が入らないため、ケースNoを確かめたり、ほかの仕組み（テストのレポートなど）で使ったりするときは、こちらを使う。

## 仮定で進めるとき

ユーザーに質問できず、試験データやメッセージの文言などを仮に置いて進めるときは、次のとおりにする。

- 仮置きしたケースの前提・想定結果に、`（仮）` と書く。
- 最後の報告に、仮置きした箇所の一覧（シート名・ケースNo・仮置きした内容）を書く。

## 記入時のポイント

- ケースNo（A列）は数式なので、書かない。
- 大項目〜観点（取引単体は区分〜確認観点3）の文言は、書き換えない。
- 対象外理由は、「なぜテストしなくてよいか」が分かる文で書く。「対象外」だけは書かない。
- 実施結果は、`OK` / `NG` のプルダウンから選ぶ。
- ケースNoの計算には、Excel の `LET` 関数を使っている。Microsoft 365 または Excel 2021 以降で開く。
- テンプレートの列・シート構成は、変えない。
