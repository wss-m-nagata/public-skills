# 記入要領: 単体テスト仕様書(共通コンポーネント)

## 資料の目的

画面をまたいで使う共通コンポーネント（共通の UI 部品、composable、ストア、入力チェック・値の整形の関数、API を呼ぶ共通の関数など）について、単体テストで**何を・どの観点で・どこまで**確かめるかを一覧にする。  
**共通コンポーネント1つにつき1ファイル**作成する（ファイル名の `(共通コンポーネントID)_(共通コンポーネント名)` を実際の値に置き換える）。

テンプレートの見出し・列・観点は、Nablarch 標準のまま変えない。  
変えるのは、「何を書くか」の解釈だけである（下の「SPA での読み替え」）。  
サーバーで画面を作る方式の場合は、読み替えずに、Nablarch の原文のとおりに書く。

テスト仕様のシートには、テスト観点カタログの観点が、あらかじめ1行ずつ並んでいる。  
カタログは「一般的なテスト観点」であり、その部品固有の決まり（共通コンポーネント設計書に書かれた個別の仕様）を確かめる観点は、カタログに無いことがある。  
次の3段階で埋める。

1. **その部品にある分類（大項目〜詳細）を整理し、無い分類の行はシートから消す。**  
   例：金額を整形する関数には、ファイル・メール・ログの行は要らない。  
   消した分類は、仕様書には残さない。
2. **共通コンポーネント設計書の記述を順に見て、それぞれを確かめる観点を当てる。当てはまる観点がカタログに無ければ、追加観点として足す。**  
   見る設計書は、共通コンポーネント設計書（入力・出力・処理詳細・エラー）と、共通コンポーネント一覧である。  
   例：「0円未満は、赤字で表示する」「通信エラーのとき、3回まで再試行する」。
3. **残した分類の観点ごとに、「テストケースを書く」か「対象外理由を書く」かのどちらかを必ず埋める。**  
   どちらも空の観点が残っていなければ、その部品にある観点の抜けが無い（全量を確かめた）と言える。  
   対象外の行は灰色にし、テストする行（白）と見分けられるようにする。

## シートの構成

シートは、次のとおり。

| シート | 内容 |
|---|---|
| 表紙 | 表紙。`build_unit_test_spec.py` が書く |
| 変更履歴 | 変更履歴。`build_unit_test_spec.py` が書く |
| `<テストターゲット名>_クラス単体` | テスト対象の部品の単体テスト。部品の数だけシートを作る |

- 共通コンポーネントの単体テスト仕様書には、クラス単体のシートだけを作る。  
  リクエスト単体・取引単体のシートは無く、`build_unit_test_spec.py` は、定義に書くとエラーにする。
- 1つの共通コンポーネントが複数の部品（関数・コンポーネント）から成るときは、部品ごとにクラス単体のシートを作る。
- シート名は31文字以内。`[ ] : * ? / \` は使えない。
- 実行するテストの道具（Vitest・Jest など）は、限定しない。

## 見出し（5〜7行目）

「<項目名>：<値>」の形で、ラベルと同じセルに書く（例：`機能名：金額表示`）。

| 項目 | 書く内容 |
|---|---|
| 機能名 | 共通コンポーネント一覧の機能名（共通コンポーネント名） |
| 取引名 | 共通コンポーネントは取引に属さないため、`-` と書く（公式の記入例のとおり） |
| テストターゲット名 | テスト対象の部品名（関数名・コンポーネント名・ストア名など。例：`formatCurrency`） |

PJ名（1行目）・サブシステム名（4行目）・作成者・作成日・更新者・更新日は、`変更履歴` シートから自動で表示される数式なので、書かない（`build_unit_test_spec.py` が数式を入れる）。

## 表の列

| 列 | 書き方 |
|---|---|
| ケースNo | 数式で自動で振られる（「詳細-観点-テスト内容」の連番）。**書かない** |
| 大項目・中項目・小項目・詳細・観点 | テスト観点カタログのまま。**書き換えない**。カタログに無い観点は「追加観点」として行を足す（下記） |
| 対象外理由 | その観点をテストしない理由。テストケースを書く観点では空欄。対象外の行は、観点から右を灰色にする |
| 対応設計書・対応箇所 | その確認の根拠になる設計書と、その中の箇所。例：`共通コンポーネント設計書`／`処理詳細` |
| テスト内容 | 何をするか。前提条件があるときは、**先頭に `【前提】…` と書き、改行してから操作を書く**。呼ぶ関数と、渡す値を、具体的に書く |
| 想定結果 | 何が起きれば合格か。観測できる形で書く（返り値・投げられた例外・描画された内容・ストアの値・呼ばれた API など） |
| テストデータシート名・データNo | 試験で作るデータがあるときに書く。シート名には `試験データ`、データNoには、そのケースが使うデータのまとまりの番号（`D01` など）を書く。使わなければ空欄 |
| 実施者・実施日・実施結果・確認者・確認日 | 実施の記録。実施結果は `OK` / `NG` から選ぶ |

- このテンプレートには、テストコードの列が無い。  
  テストコードの場所（例：`formatCurrency.spec.ts > 最大桁を整形できる`）を残すときは、定義ファイルのケースに `テストコード` を書く。  
  `build_unit_test_spec.py` が、テスト内容の末尾に `【テストコード】…` として書く。
- 対象外理由の列は、テンプレートでは折りたたまれている（グループ化されている）。  
  `build_unit_test_spec.py` は、観点ごとの「テストした」か「対象外にした理由」かが見えるように、展開して出力する。

### 1つの観点に、テストケースが複数あるとき

観点の行の下に行を足し、2件目以降のケースを書く（ケースNoの3つ目が `1-1-1`、`1-1-2` … と増える）。  
足した行の分類・観点の列は空欄にする。

### 対象外理由の書き方

「なぜこの観点でテストしなくてよいか」が、読んだ人に分かるように書く。

- 機能が無い：`日付を扱わないため対象外`
- 共通コンポーネントの責務ではない：`共通コンポーネントでは対象外`（公式の記入例）。使う側の画面の単体テストで確かめることを、一言添えるとよい
- ほかのテストで確かめる：`使う側の画面のリクエスト単体テストで確認するため対象外`

観点の取捨選択の考え方（Nablarch システム開発ガイド「テスト項目の検討」）：
- プロジェクトに関係しない観点（その機能が無いもの）は外す。
- 残った観点も、「そのテストでバグが見つかる見込みが低い」「レビューや次の工程のテストで見つかる」「バグがあっても影響が軽い」ものは、理由を書いて外してよい。

### 追加観点（カタログに無い、部品独自の観点）

設計書の記述に当てはまる観点がカタログに無いとき（上の「資料の目的」の2）に足す。  
カタログの観点の行の後ろに行を足し、観点の列に書く。  
新しい詳細（または小項目・中項目・大項目）として始めるときは、その列にも書く。  
足した行も、カタログの観点と同じく、テストケースか対象外理由のどちらかを埋める。

## 観点Noと分類の決め方

### 観点Noの数え方

定義ファイルの `観点` の `No` と `追加観点` の `after` には、**空のテンプレートでの観点No**を書く。  
観点Noは「1つ目-2つ目」の形で、次のとおり数える。

- 1つ目は、詳細の列に値がある行ごとに1つ増える。  
  テンプレートでは、同じ詳細が続く行の詳細の列は空欄なので、増えない。  
  値が「-」の行も、値がある行として数える。  
  小項目が変わる行で詳細が「-」でも、新しい行に値があるので、1つ増える。
- 2つ目は、詳細の中で、観点の列が空でない行ごとに1つ増える。詳細が変わると、1に戻る。
- 分類（大項目・中項目・小項目）が変わっても、1つ目は連続して増える。分類ごとに1から数え直さない。

数え間違えを避けるため、数式を読んで自分で番号を振らず、次のコマンドで一覧を出す。

```bash
python scripts/build_unit_test_spec.py <テンプレート> --list-catalog [--filter <分類の前方一致>] [--sheet-template クラス単体|リクエスト単体|取引単体]
```

- 出力は、1観点1行の `観点No  [分類]  観点の文言` である。
- `--filter` は、分類の前方一致で、「/」でつなぐ（例：`--filter 画面表示/表示結果`）。
- `--sheet-template` の省略時は、クラス単体（共通コンポーネントのシートは、クラス単体だけである）。
- 一覧の観点Noは、組み立ての処理と同じ関数で数えている。  
  定義ファイルには、この一覧の観点Noを、そのまま書く。

### 分類の前方一致の考え方

`分類` に書いた分類は、**前方一致**で観点を残す。  
指定した分類の下にある観点が、すべて残る。

- `["画面表示", "表示結果", "画面表示データ"]` と書くと、小項目が「画面表示データ」の観点が、詳細が「-」のものも「編集仕様」のものも、すべて残る。
- 1つの詳細だけを残したいときは、詳細まで書く（例：`["画面表示", "表示結果", "画面表示データ", "-"]`）。
- 大項目だけ（`["画面表示"]`）を書くと、大項目の下の観点がすべて残る。

残った観点は、すべて、テストケースか対象外理由を書く。  
範囲を絞るときは、次の手順で進める。

1. `--list-catalog --filter <分類>` で、その分類を書いたときに残る観点を、先に見る。
2. 残したくない観点が含まれるときは、分類を細かく書き直すか、`対象外` にまとめて理由を書く。
3. 組み立てて、未記入の観点のエラーが出たら、エラーに出る分類と観点の文言を見て、2に戻る。

### まとめて対象外にする書き方

`対象外` は、`分類` に書いた分類のうち、まとめて対象外にするものを、分類（前方一致）と理由で書く。

```json
"対象外": [
  {"分類": ["画面表示", "表示結果", "画面表示データ", "編集仕様"], "理由": "取得した値の編集が無いため対象外"}
]
```

- `観点` に個別に書いた観点は、`対象外` より優先される（まとめて対象外にした中の一部だけ、テストケースを書ける）。
- 分類の前方一致の範囲は、`分類` と同じである。

### 未記入の観点のエラー

テストケースも対象外理由も無い観点が残っていると、組み立てはエラーになる。  
エラーには、観点No・分類（大項目〜）・観点の文言が、1観点1行で出る。  
分類を見て、どの `分類` の指定から残った観点かを確かめる。

## SPA での読み替え

観点カタログの観点は、増減しない。  
共通コンポーネントのクラス単体のシートで使うことが多い分類は、次のとおり読み替える。  
「Nablarch の原文」は、サーバーで画面を作る方式での意味である。  
画面の単体テスト仕様書の読み替えの全体は、`記入要領_単体テスト仕様書_画面.md` の「SPA での読み替え」を参照する。

| 大項目 | Nablarch の原文の意味 | 共通コンポーネントでの読み替え |
|---|---|---|
| バリデーション | サーバーで行う入力チェック | クライアント側の入力チェックの共通関数（必須・文字数・数値・日付・メールアドレス・相関チェックなど）。「エラーとなる」は、関数がエラーを返す（または例外を投げる）ことで書く |
| DB操作・DB制御 | SQL の条件・実行結果、排他制御、ロールバック | 共通コンポーネントは DB を直接操作しないため、原則対象外。ブラウザのストレージを読み書きする部品では、その読み書きに読み替える |
| ファイル取込・ファイル出力・ファイル操作 | サーバーのファイルの取込・出力・操作 | ブラウザで選んだファイルの検証、ブラウザで作るファイルの内容。値の整形（桁数・編集仕様）を行う部品は、「出力内容（編集仕様・桁数）」を、整形した値の確認に読み替えて使う |
| メール処理 | サーバーからのメール送信 | 対象外 |
| 受信処理・送信処理 | 外部システムとの電文の受信・送信 | API を呼ぶ共通部品の、リクエストの組み立て（送信）と、レスポンスの取り込み（受信）。タイムアウト・通信エラー時の動き（再試行・エラー表示）も、ここで確かめる |
| ログ出力 | ログファイルの格納先・権限、ログの編集 | コンソール出力・エラー報告の編集。ログファイルの格納先・権限などの観点は対象外 |

- 観点の中の「[共通コンポーネント設計書の記載通り]」は、その設計書の、確認する箇所を、対応設計書・対応箇所の列に書く。
- サーバー描画の場合は、読み替えずに、原文のとおりに書く。

## 作り方（ローカル実行）

手で行を足すと、ケースNoの数式・罫線・入力規則・印刷範囲がずれるため、`scripts/build_unit_test_spec.py` で組み立てる。

1. テスト項目を、定義ファイル（JSON）に書く。書き方は `build_unit_test_spec.py` の冒頭の説明を参照する。
   - 見出しの `取引名` には `-` を書く。
   - 部品ごとに、`template` が `クラス単体` のシートを定義し、`name` に部品名を書く（シート名は `<name>_クラス単体` になる）。
   - `分類` に、その部品にある分類（大項目〜詳細）を書く。書いていない分類の行は、シートから消える。
   - 観点は、空のテンプレートでのケースNoの前2つ（「詳細-観点」。例：`4-2`）で指定する。観点Noは、`--list-catalog` で出した一覧のものを、そのまま書く（組み立てた後のケースNoは、消した行の分だけ詰まる）。
   - 残した分類のうち、まとめて対象外にするものは、`対象外` に分類と理由を書く。
   - 表紙・変更履歴の内容は `document` に書く。
2. 組み立てる。
   ```bash
   python scripts/build_unit_test_spec.py "assets/templates/フォーマット/単体テスト仕様書(共通コンポーネント)_(共通コンポーネントID)_(共通コンポーネント名).xlsx" <定義json> <出力パス> --cases-json <ケース一覧json>
   ```
   どちらも埋まっていない観点が残っていると、その観点の番号を挙げてエラーになる（書きかけの確認だけなら `--allow-unaddressed`）。  
   表紙・変更履歴も、このスクリプトが書く（このテンプレートに『目次』シートは無い）。
3. `export_sheet_preview.py` でテスト仕様のシートをPDFにし、行の高さ・折り返し・罫線・ケースNoを目で確かめる。  
   PDFをReadツールで開けない（`pdftoppm`が無い）ときは、PyMuPDFでPNGにして開く。

### 検証

組み立てたファイルは、`verify_layout.py` の対象外である（シート構成が変わり、ケースNoの配列数式も誤検知になるため）。  
次の4点を確かめて、完了とする。

1. `build_unit_test_spec.py` の終了コードが 0 であること（観点の抜け・組み合わせの誤りはエラーで止まる）。
2. 標準エラー出力に警告が出ていないこと。出ているときは、内容を確かめ、無視してよい理由があれば、報告に書く。
3. `--cases-json` の出力で、ケースNo・分類・観点・テスト内容・想定結果が、意図どおりであること。
4. `export_sheet_preview.py` で、行の高さ・折り返し・罫線・ケースNo・印刷範囲を、目で確かめること。

### 版を上げるとき（変更箇所を赤字にする）

既存の仕様書の版を上げるときは、その版で変えた箇所だけを赤字にし、前の版の赤字は残さない。  
定義ファイル（JSON）の、変えたケース・観点に `"changed"` を付けて、組み立て直す。  
組み立て直すので、前の版の赤字は消え、今の版で `"changed"` を付けた箇所だけが赤字になる（前の版の `"changed"` は消す）。

| 付ける場所 | 指定 | 赤字になるセル |
|---|---|---|
| ケース（`cases` の1件） | `true` | そのケースの、値のある列の全部（対応設計書・対応箇所・テスト内容・想定結果など） |
| ケース | 列名のリスト（例：`["想定結果"]`） | 指定した列だけ（`テストコード` は、テスト内容の列になる） |
| 追加観点・対象外理由の記入 | `true` | 分類と観点（対象外理由の記入は、対象外理由）の全部 |
| 追加観点・対象外理由の記入 | 列名のリスト（例：`["観点"]`） | 指定した列だけ |

- 1つでも付けると、表紙の版数も赤字になる。
- 変更履歴にも、新しい版の行を足す（`document` の `変更履歴`）。
- 新しい観点を足すときは、既存のケースNoがずれないよう、追加観点の並びの最後に足す。

`--cases-json` には、組み立てた結果の全行（ケースNo・分類・観点・テスト内容・想定結果など）が出る。  
openpyxlで書いたファイルにはケースNo（数式）の計算結果が入らないため、ケースNoを確かめたり、ほかの仕組み（テストのレポートなど）で使ったりするときは、こちらを使う。

## 仮定で進めるとき

ユーザーに質問できず、試験データやメッセージの文言などを仮に置いて進めるときは、次のとおりにする。

- 仮置きしたケースの前提・想定結果に、`（仮）` と書く。
- 最後の報告に、仮置きした箇所の一覧（シート名・ケースNo・仮置きした内容）を書く。

## 記入時のポイント

- ケースNo（A列）は数式なので、書かない。
- 大項目〜観点の文言は、書き換えない。
- 対象外理由は、「なぜテストしなくてよいか」が分かる文で書く。「対象外」だけは書かない。
- 実施結果は、`OK` / `NG` のプルダウンから選ぶ。
- ケースNoの計算には、Excel の `LET` 関数を使っている。Microsoft 365 または Excel 2021 以降で開く。
- テンプレートの列・シート構成は、変えない。
- 共通コンポーネント設計書の「処理詳細」の分岐は、1分岐につき1ケース以上を書く。
