# 記入要領: 共通コンポーネント一覧

## 資料の目的

複数の画面で使う共通の部品を一覧にし、コンポーネントIDを採番する。  
ここで採番したコンポーネントIDが、共通コンポーネント設計書（1コンポーネント＝1ファイル）のキーになる。

### どんなときに作るか

この設計書は、プロジェクトによって要るかどうかが変わる。  
次のいずれかに当てはまるときに作る。

- 複数の画面・機能で使う共通の部品（ボタン、入力欄、ダイアログ、一覧表など）が、一定数ある。
- 共通の関数・composable・ストアを、複数の画面の設計書から参照させたい。
- 共通部品の重複開発を避けるため、何があるかを一覧で見られるようにしたい。

共通の部品がほとんど無い、または UI ライブラリの標準部品だけで足りるときは、作らなくてよい。  
一覧に載せたコンポーネントは、共通コンポーネント設計書を作る対象になる。

### 読み替え（SPAの場合）

Nablarch の原文の「共通コンポーネント」は、サーバー側の共通クラス（業務共通の処理を持つクラスとそのメソッド）である。  
SPA では、次のものを共通コンポーネントとして扱う。  
サーバー描画の場合は、原文のとおり（共通クラスとメソッド）に書く。

- 画面部品：Vue コンポーネント、React コンポーネント（確認ダイアログ、検索条件欄、共通の一覧表など）。
- 共通の関数：複数の画面から呼ぶ関数（日付の整形、入力チェックなど）。
- composable・フック・ストア：状態や処理を共有する仕組み（API呼び出しの共通処理、ログイン状態など）。

| 欄 | 原文の意味 | SPAでの読み替え |
|---|---|---|
| コンポーネントID | 共通コンポーネントのID | 共通部品のID。 |
| コンポーネント名 | コンポーネントの名称 | 共通部品の名称（日本語）。 |
| クラス名 | 実装しているクラス名 | 実装しているファイル名またはコンポーネント名（`ConfirmDialog.vue`、`useApiClient.ts`）。 |
| 処理名 | コンポーネントの処理名 | 部品・関数が行う処理の名称（日本語）。 |
| メソッド名 | 処理に対応するメソッド名 | 呼び出し名。画面部品は`<ConfirmDialog>`、関数・composable は`useApiClient()`。props・イベント・引数の詳細は、共通コンポーネント設計書に書く。 |
| 処理概要 | 処理の概要 | 処理の概要。 |

## どこに何を書くか

シートは、共通の範囲ごとに分かれている。

| シート | 載せるもの |
|---|---|
| 1. システム内共通 | システム全体（複数のサブシステムや機能）で使う共通部品。例：アプリ全体の共通ダイアログ、API呼び出しの共通処理。 |
| 2. サブシステム内共通 | 1つのサブシステムの中の、複数の機能で使う共通部品。サブシステムを分けないプロジェクトでは、記入しない。 |
| 3.1. 機能名(機能ID) | 1つの機能の中の、複数の画面で使う共通部品。機能ごとにシートを作る。 |

共通部品がどの範囲で使われるかで、載せるシートを決める。  
範囲が広がったら（機能共通から、システム内共通へ）、シートを移し、コンポーネントIDは変えない。

1〜3行目のPJ名・システム名・サブシステム名は、`変更履歴`シートを参照する数式のため、書かない（`記入要領_共通シート.md`を参照）。

### シート『1. システム内共通』『2. サブシステム内共通』（見出しは7行目、データは8〜38行目の31行）

| 列 | 項目名 | 記入内容 | 記入例（受注管理システム） |
|---|---|---|---|
| C | No. | 通し番号（コンポーネントごと）。 | 1, 2 |
| D（D:G結合） | コンポーネントID | プロジェクトで定めた採番ルールに沿ったID。共通コンポーネント設計書のファイル名と一致させる。 | `CM0001` |
| H（H:K結合） | コンポーネント名 | 共通部品の名称。 | 確認ダイアログ |
| L（L:O結合） | クラス名 | 実装しているファイル名。 | `ConfirmDialog.vue` |
| P（P:T結合） | 処理名 | 部品・関数の処理名。 | 確認ダイアログ表示 |
| U（U:AA結合） | メソッド名 | 呼び出し名。 | `<ConfirmDialog>` |
| AB（AB:AH結合） | 処理概要 | 処理の概要を、「〜する。」で1〜2文。 | 確認メッセージとボタンを持つダイアログを表示し、押されたボタンを親へ通知する。 |

### シート『3.1. 機能名(機能ID)』（見出しは8行目、データは9〜38行目の30行）

列の位置が、1つ右にずれている。  
6行目のC6には、見出し「3.1. ［機能名］(［機能ID］)」が入っている。実際の機能名と機能IDに書き換える。

| 列 | 項目名 | 記入内容 |
|---|---|---|
| D | No. | 通し番号（コンポーネントごと）。 |
| E（E:H結合） | コンポーネントID | 同上。 |
| I（I:L結合） | コンポーネント名 | 同上。 |
| M（M:P結合） | クラス名 | 同上。 |
| Q（Q:U結合） | 処理名 | 同上。 |
| V（V:AB結合） | メソッド名 | 同上。 |
| AC（AC:AH結合） | 処理概要 | 同上。 |

### 1つのコンポーネントに複数の処理があるとき

1つのコンポーネントに処理が複数ある（関数を複数公開する、など）ときは、処理ごとに1行を使う。  
コンポーネントID・コンポーネント名・クラス名・No.は、最初の行にだけ書き、2行目以降は空欄にする。  
処理名・メソッド名・処理概要は、行ごとに書く。  
サンプルでは、コンポーネントの列を縦に結合しているが、テンプレートは行ごとに結合した作りである。結合し直さず、最初の行にだけ書く。

## 機能共通のシートを追加する（1機能＝1シート）

機能ごとに、`3.x. 機能名(機能ID)`のシートを足す。  
手順は次のとおりで、`記入要領_共通シート.md`の「1インスタンス＝1シート」型にあたる。

```bash
# 1) 最初の機能：テンプレートのシート名を、実際の名称に変える（括弧は半角、「3.1.」の後ろに空白1つ）
python scripts/rename_sheet.py <フォーマットのxlsx> "3.1.  機能名 ( 機能ID )" "3.1. 受注管理(ORD)" <出力xlsx>
# 2) 2つ目以降：シートを複製する（入力規則・結合セルも複製される）
python scripts/duplicate_sheet.py <入力xlsx> "3.1. 受注管理(ORD)" "3.2. 顧客管理(CST)" <出力xlsx>
# 3) 各シートのC6と、目次に名称を書く（目次は罫線外のため --allow-outside-border が要る）
python scripts/apply_mapping.py <入力xlsx> <マッピングJSON> <出力xlsx> --allow-outside-border
```

- 目次のC12に3.1、C13に3.2…と、機能の数だけ書く。目次は自動では更新されない。
- シート名は31文字以内で、`[ ] : * ? / \`を含められない。
- 3.1のテンプレートの表は、複製しても空のまま複製される（値は複製されない）。

## 記入時のポイント

- コンポーネントIDの採番ルールを、最初に決める（例：範囲を表す英字＋連番）。
- 1つのコンポーネントIDは、共通コンポーネント設計書の1ファイルに対応する。
  ここで確定したIDと名称は、共通コンポーネント設計書のファイル名・コンポーネントID欄、単体テスト仕様書(共通コンポーネント)のファイル名、画面側の設計書で共通部品を指すときの表記と、完全にそろえる。
- 画面ごとに作る部品（1つの画面でしか使わないもの）は載せない。
  2つ以上の画面から使うものだけを載せる。
- UI ライブラリが提供する標準部品（ボタン、入力欄など）は、そのまま使うなら載せない。
  共通の既定値や見た目を付けて包んだ部品は、載せる。
- 処理概要には、部品が行うことだけを書く。
  どの画面から使うかは、画面側の設計書に書く（部品の側に書くと、画面が増えるたびに直すことになる）。

## 行が足りないとき

シート1・2は31行、3.xは30行までしか書けない。  
超えるときは、`scripts/extend_table_rows.py`で、最終データ行の書式を下へ複製する（行の挿入はしない）。  
表の下には何も無いため、この方法が使える。  
シートごとに、別々に実行する。

```bash
# シート1・2: 最終データ行は38、対象列はC〜AH。10行足す
python scripts/extend_table_rows.py <入力xlsx> "1. システム内共通" 38 10 C AH <出力xlsx>
# シート3.x: 最終データ行は38、対象列はD〜AH
python scripts/extend_table_rows.py <入力xlsx> "3.1. 受注管理(ORD)" 38 10 D AH <出力xlsx>
```

- 増やした行には、値は入らない。値は`apply_mapping.py`で書く。
- 行を足すと、`verify_layout.py`は「行数・結合セル・罫線が増えた」と報告する。
  これは意図した変更であり、足した行以外に差分が無いことを確かめる。
- 印刷範囲は広がらない。印刷や PDF 化で下の行が切れるときは、Excelの[ページレイアウト]→[印刷範囲]で広げる。

## 長い文を書くとき

データ行の高さは既定のままで、処理概要が1行を超えると、2行目以降が隠れる。  
値を書いたあとに、`scripts/fit_row_heights.py`で、行の高さを広げる。

```bash
python scripts/fit_row_heights.py <入力xlsx> <出力xlsx> --rows 8-20 --sheet "1. システム内共通"
python scripts/verify_layout.py <書き込み前のxlsx> <出力xlsx> --allow-row-heights
```

## 値を書き込む手順

```bash
python scripts/apply_mapping.py <フォーマットのxlsx または 前の手順の出力> <マッピングJSON> <出力xlsx>
python scripts/verify_layout.py <書き込み前のxlsx> <書き込み後のxlsx>
```

マッピングJSONの例：

```json
{"sheets": {"1. システム内共通": {"C8": 1, "D8": "CM0001", "H8": "確認ダイアログ", "L8": "ConfirmDialog.vue", "P8": "確認ダイアログ表示", "U8": "<ConfirmDialog>", "AB8": "確認メッセージとボタンを持つダイアログを表示し、押されたボタンを親へ通知する。"}}}
```

- 結合セルは、左上のセル（D・H・L・P・U・AB。3.xでは E・I・M・Q・V・AC）を指定して書く。
- 値を書いたあと、`scripts/export_sheet_preview.py`で見た目を確かめる。
