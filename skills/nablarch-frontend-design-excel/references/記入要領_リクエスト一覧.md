# 記入要領: リクエスト一覧

## 資料の目的

Nablarch では、画面から送られる処理依頼（リクエスト）にリクエストIDを振り、その一覧を持つ。  
このスキルでは、SPA の画面から起きる「画面イベント」（初期表示、検索ボタン押下、確定ボタン押下、API 呼び出しなど）に、画面イベントIDを振る台帳として読み替える（読み替え）。  
サーバー描画の画面の場合は、原文のとおりに、リクエストIDとリクエスト名を書く。

この資料は、必要に応じて作る設計書である。  
機能設計書（システム機能設計書(画面)）の画面イベント一覧だけで、イベントの洗い出しと採番が足りるプロジェクトでは、この資料は作らなくてよい。  
次のような場合に作る。
- 複数の機能にまたがって、画面イベントIDの重複や漏れを確認したい。
- テスト仕様書や課題管理で、画面イベントIDだけを横断して引きたい。
- バックエンドの API 一覧と、画面イベントの対応を、機能単位で見渡したい。

## どこに何を書くか（シート『1』）

見出し行は7行目、データ行は8行目から35行目までの28行である。  
1〜3行目は、『変更履歴』シートの値を参照する数式なので、このシートには書かない。

| 位置 | 項目名 | 読み替え | 記入内容 | 記入例 |
|---|---|---|---|---|
| C列 | No. | なし | 通し番号。 | 1, 2, 3 |
| D〜F列（結合） | 機能ID | なし | 機能のID。機能の最初の行にだけ書き、同じ機能の2行目以降は空欄にする。 | `11AA` |
| G〜K列（結合） | 機能名 | なし | 機能の名称。 | 受注管理 |
| L〜N列（結合） | リクエストID | 画面イベントID | 画面イベントのID。採番規則はプロジェクトで決める（原文は、プロジェクトで定めたリクエストIDの採番規則）。 | `E11AA0101` |
| O〜U列（結合） | リクエスト名 | 画面イベント名 | 「画面名：イベント名」の形で書く。 | 受注一覧照会：初期表示 |
| V〜AH列（結合） | 説明 | なし | そのイベントで何をするか（ストアの更新、API 呼び出し、画面遷移）を、1文で書く。 | 受注一覧照会画面の初期表示で、受注の一覧を取得して表示する。 |

## 記入時のポイント

- 画面イベントIDの採番規則は、プロジェクトで先に決めておく。決め方の例を示す。
  - 例1：イベントを表す英字1桁（`E`）＋機能ID（4桁）＋画面の連番（2桁）＋イベントの連番（2桁）。
  - 例2：画面IDの後ろにイベントの連番を付ける（`W11AA0101-01`）。
  - どちらの例でも、機能設計書の画面イベントIDと完全に一致させる。
- 画面イベントとして数えるのは、画面の外へ作用するもの（API の呼び出し、画面遷移、ストアの更新）に限る。  
  入力欄の見た目だけが変わる動作は、数えない。
- 「リクエスト名」は、画面名と、そのイベントの動作（初期表示、検索、確認、登録など）を並べて書く。
- 1つの画面イベントが複数の API を呼ぶ場合も、画面イベントは1行にする。  
  呼ぶ API の一覧は、機能設計書に書く。
- 機能ID・機能名・画面名は、画面一覧と表記を完全に一致させる。
- 機能ごとにイベントを続けて並べる。機能が変わる行で、機能ID・機能名を書く。

## 行が足りないとき

テンプレートの記入可能行は28行である。  
超えるときは、最終データ行（35行目）の書式を下へ複製して、行を増やす。

    python scripts/extend_table_rows.py <元xlsx> 1 35 <追加する行数> C AH <出力xlsx>

- 引数の意味は、画面一覧の記入要領と同じである。
- 実行後は、`scripts/verify_layout.py` で構造が壊れていないことを確認する。

## 参照ファイル

- 空テンプレート：`assets/templates/フォーマット/リクエスト一覧_(サブシステムID)_(サブシステム名).xlsx`
- Nablarch標準サンプル：`assets/templates/サンプル/リクエスト一覧_サンプル.xlsx`
- 構造情報：`references/構造メモ_リクエスト一覧.md`
- 行の増やし方：`scripts/extend_table_rows.py`
