# 記入要領: 画面共通部品設計書

## 資料の目的

画面の共通部品1つについて、**その部品を使う人が、使い方を分かる**ように示す。
部品の配置先、名前、分類は対象プロジェクトの決まりに従う。
課題の管理や、実装の作業メモには使わない。

**この様式は、Nablarch には無い。**
Nablarch の「共通コンポーネント設計書」は、バックエンドのクラス（メソッド、CRUD、エラー）向けで、画面部品の表示、状態、公開する関数を書くには合わなかった。
そのため、構成は独自（本体7シート）にし、書式（表紙、変更履歴、ヘッダー帯、フォント、罫線、灰色の見出し、印刷設定）は、Nablarch の共通コンポーネント設計書を引き継いでいる。
Nablarch の「共通コンポーネント設計書」とは別の設計書として扱う。

### どんなときに作るか

画面の共通部品を、新しく作ったときと、仕様を変えたときに作る。
1つの部品につき、1ファイルを作る。
部品の一覧（台帳）は、この設計書の対象外である。

## 書き方の原則

### 設計書だけで、使い方が分かるように書く

他の資料（規約など）への依存を避ける。
理由は、次の2つである。

- 規約の表現が変わると、部品の仕様が変わっていなくても、設計書を直す必要が出る。
- 読む人が、意味を知るために、規約を開かないといけなくなる。

具体的には、次のように書く。

- 「規約どおりに」「規約に従う」とだけ書いて、内容の説明を省略しない。
  形、色、大きさ、キーの割り当てなど、規約の内容に当たる部分は、設計書に具体的に書く。
- 規約の名前や場所を、参考として示すのは、よい。
  ただし、リンクは補足にとどめ、内容の説明は、設計書の側に書く。
- 具体的な値（色、キーなど）が、規約と設計書で二重になるのは、許容する。
  設計書は、その時点の部品の仕様を示すもので、規約が変わったときは、部品の改修とあわせて直す。

### 目的は、使う人にとっての価値で書く

「この部品を使うと、何が得られるか」を書く。
作る側の都合（実装を1か所にする、など）は、書かない。

- よくない例: 「ボタンの見た目と動きを、規約どおりに、1か所で実装する。」
- よい例: 「ボタンの見た目と動きを、アプリ全体で統一するための共通部品として提供する。」

### 未決定の事項や課題は書かない

この設計書は、決まった内容を、使う人に示す資料である。
未決定の事項、確認中の事項、課題は、GitHub Issue で管理する。
特記事項にも、使うときの注意（制約、例外）だけを書く。

## 構成（本体7シート）

シートは、左から次の順に並ぶ。
表紙、変更履歴は、他の Nablarch の設計書と同じである。
「目次」シートは、置かない（Nablarch の単体テスト仕様書にも、目次シートが無いため）。

| シート | 書く内容 |
|---|---|
| 表紙 | 部品の設計書であることを示す表紙。 |
| 変更履歴 | 版数、変更日、変更内容。 |
| 1. 概要 | 基本情報、提供機能、特記事項、設計上の留意事項。 |
| 2. 画面レイアウト | 表示パターンごとの表示イメージ（画像を貼る枠）と、構成要素の一覧。 |
| 3. 状態 | 状態属性、代表的な組合せ、状態遷移。 |
| 4. 入力属性 | 部品の入力属性とイベントを区別して書く。 |
| 5. オブジェクト定義 | 入力属性で使うオブジェクトの構成を、種類ごとに同じシートに書く。 |
| 6. 関数定義 | 公開関数の名前、引数、戻り値と説明を書く。ない場合もシートを残す。 |
| 7. 関数詳細 | 関数定義だけでは説明が足りない関数を書く。ない場合もシートを残す。 |

節の見出し（「1. 基本情報」など）は、B列に置く。
内容（表など）は、C列から始める。
理由は、見出しを選んだ状態で `Ctrl＋↑↓` を押すと、見出しだけを順に移動できるようにするためである。
この配置は、変えない。

## シート『1. 概要』

| 節 | 内容 |
|---|---|
| 1. 基本情報 | 部品ID（コンポーネント名）、部品名、プロジェクトで定めた分類、目的、概要、利用条件、対象外。 |
| 2. 提供機能 | 機能ID（`F-01`）、機能名、内容、利用する関数（引数、イベント、関数の名前）、備考。 |
| 3. 特記事項 | No.、分類、対象、内容、理由・補足、関連する状態・関数。使うときの注意（制約、例外）だけを書く。 |
| 4. 設計上の留意事項 | この部品に固有の留意事項。 |

- 部品IDは、ファイル名の部品IDと一致させる。
- 「関連する状態・関数」には、『3. 状態』の属性IDや関連する公開関数名を書く。

## シート『2. 画面レイアウト』

- 表示が異なる代表的なパターンを、1つずつ「レイアウト例：<パターン名>」として書く。
  画面全体のイメージは不要である。
- 各パターンの表示イメージの枠は、既定で14行とする。
  画像の文字や部品が小さく読みにくいときは、必要な範囲で最大30行まで広げる。
  1行は12pt、30行は360ptであり、これを超えない。
  30行でも読めないときは画像の撮影範囲やパターンの分割を見直す。
  組み立てスクリプトは、2つ目以降の表示例の手前に改ページを入れる。
- 画像上で構成要素を赤枠で囲み、対応する要素IDを記載する。
  赤枠とIDは、画像に描き込まず、Excelで編集可能な図形とテキストボックスとして配置する。
  構成要素一覧のIDと画像上のIDは一致させる。
- 複数のレイアウト例で同じ要素を示す場合、先の例で対応を示せる要素は後の例で赤枠とIDを省略する。
  後の例で初めて現れる要素や、表示・配置の違いを示す必要がある要素には赤枠とIDを付ける。
- 撮影時はアニメーションの完了を待ち、画像と赤枠の座標を同じ表示状態で取得する。
  画像の切り出し範囲を原点に座標を換算し、拡大縮小と余白を含めて対応を確認する。
- 最後に「構成要素一覧」を書く。
  要素ID（`E-01`）、名称、表示内容、表示条件、操作・イベント、関連状態、関連関数、備考。

## シート『3. 状態』

- 「1. 状態属性」は、互いに独立した状態の軸ごとに書く。
  属性ID（`ST-01`）、状態属性、値、意味、表示・操作への影響、関連関数、備考。
  同じ属性の値は、同じ属性IDで、複数の行に書く。
- 「2. 代表的な組合せと表示イメージの対応」は、表示や動作が異なる組合せだけを書く。
  「状態の組合せ」は、「ST-01=enabled、ST-02=指定なし」のように、属性IDと値で書く。
- 「3. 状態遷移」は、操作の結果が誤解されやすい箇所だけを書く。

## シート『4. 入力属性』

- 入力属性の名前、型、必須、既定値と説明を書く。
- オブジェクトやその配列を受け取る場合は型と対応する「5. オブジェクト定義」の名前を示す。
- イベントは入力属性と別の表に、イベント名、引数と説明を書く。

## シート『5. オブジェクト定義』

- オブジェクトの種類ごとに入力属性名を含む見出しと表を、同じシートに追加する。
- 表は属性名、データ型、必須、既定値と説明を書く。
- 設定例は概要に書き、このシートには重複して書かない。

## シート『6. 関数定義』と『7. 関数詳細』

- 公開関数の名前、引数、戻り値と説明を「6. 関数定義」に書く。
- 部品の利用に必要な外部の共通関数がある場合は、部品自身の公開関数と区別して「利用する関連関数」の表に書く。
- 利用者がイベント処理などから呼び出す必要のある既存の関数も、提供元を示して関数定義に書く。
  画面側が任意に作成するイベント処理の例は、部品が提供する関数として扱わない。
- 複雑な判定や処理順序など、一覧だけでは説明が足りない関数を「7. 関数詳細」に書く。
- 部品内部の処理順序を設計上明確にする必要がある場合も「7. 関数詳細」に書き、内部処理であることを明示する。内部処理を公開関数として「6. 関数定義」に載せない。
- 公開関数や詳細がない場合もシートを残し、「該当なし。」とする。
- 見出しは、「関数ID　関数名」の形式で、B列に書く（例：`M-02　onShortcut(event)`）。
- 見出しの下に、概要、引数、戻り値、事前条件、処理仕様、状態への影響、エラー・例外を書く。
- 関数ごとにシートを増やさない。同じシートに、ブロックを足す。

### 入力属性・イベント・関数の区別

| 分類 | 設計書に書くもの | 例 |
|---|---|---|
| 入力属性 | 画面から部品へ渡す値と型。 | `items`、`loading`。 |
| イベント | 部品から画面へ通知する名前と通知値。 | `update:modelValue`、`cancel`。 |
| 公開関数 | 部品が公開し、画面が呼び出せる関数。 | 入力欄の `validate()`。 |
| 利用する関連関数 | 部品の外にあり、部品を使うため画面から呼ぶ既存の共通関数。 | `useNotify()` が返す `notify(text)`。 |

例えば `@cancel="onCancel"` は、部品の `cancel` イベントを受けて画面側で定義した `onCancel` を実行する指定である。
`cancel` はイベントの表に書き、`onCancel` はページの利用例で示す。
`onCancel` を部品の公開関数や既存の共通関数として記載しない。
画面側のイベント処理から既存の `notify(text)` などを呼ぶ場合は、その既存関数を「利用する関連関数」に記載する。
`v-model` の更新イベントも、イベント名と値を記載し、利用例で `v-model` との対応を示す。

## 表紙と変更履歴

共通の決まり（`記入要領_共通シート.md`）に従う。
PJ名、システム名、サブシステム名は、「変更履歴」シートの E1・E2・E3 にだけ書く。
成果物名は、`画面共通部品設計書` で固定である。

## 書き方のコメント

各シートの列タイトル、ラベル、節の見出しには、書き方を示すセルコメントが付いている。
コメントは、削除しない。
テンプレートからコメントの文言を変えるときは、`scripts/build_ui_component_design.py` の `COMMENTS` を直して、テンプレートを作り直す。

## 作り方

`scripts/build_ui_component_design.py` で、定義 JSON から作る。
行の追加や、セルの結合を、手で行わない（見出しの配置、行の高さ、枠線がずれるため）。

```bash
# 内容を入れて、1つの部品の設計書を作る
python -X utf8 scripts/build_ui_component_design.py <出力xlsx> --content <定義json>
# 架空のボタンの記入例を作る。JSON の形の見本にもなる
python -X utf8 scripts/build_ui_component_design.py <出力xlsx> --example
# 見出しだけの空のテンプレートを作る（assets/templates/フォーマット/ の再作成に使う）
python -X utf8 scripts/build_ui_component_design.py <出力xlsx>
```

### 定義 JSON の形

形は、`--example` の内容と同じである。
`scripts/build_ui_component_design.py` の `_example()` を見本にする。
記入例は架空の仕様であり、対象システムにそのまま適用しない。

| キー | 内容 |
|---|---|
| `meta` | 表紙と変更履歴に入れる値。`project`、`system`、`subsystem`、`version`、`date`（`YYYY-MM-DD`）、`author`、`company`、`department`。 |
| `overview` | `id`、`name`、`category`、`purpose`、`summary`、`conditions`、`out_of_scope`、`features`、`notes`、`remarks`、`usage`（Vueページの利用例）。 |
| `layout` | `patterns`（例の名前の文字列、または`{"title":"名前","height_rows":30}`の配列）、`elements`（行の配列）。`height_rows`は14〜30の整数、省略時14。 |
| `state` | `attributes`、`patterns`、`transitions`（それぞれ行の配列）。 |
| `interface` | `props`（属性名・型・必須・既定値・説明）、`events`（イベント名・引数・説明）の行配列。 |
| `objects` | `name`、`prop`、`fields`（属性名・型・必須・既定値・説明の行配列）を持つオブジェクトの配列。 |
| `public_functions` | 関数名・引数・戻り値・説明の行配列。 |
| `related_functions` | 必要な場合に指定する、部品外の共通関数の関数名・引数・戻り値・説明の行配列。 |
| `details` | ブロックの配列。各ブロックは、`title`（「関数ID　関数名」）と、`values`（項目名→内容）。 |

- 表の行は、列の順に並べた文字列の配列である。
  列の順は、各シートの表の見出しの順と同じである。
- 複数行にしたいセルは、`\n` で改行する。
- 材料が無い項目は、仮の値を置かず、空の文字列にする。
  会社名、部門名が無いときは、空にして、角括弧のプレースホルダーを消す。
- `meta.history` に `version`、`date`、`kind`、`sections`、`description`、`author` の配列を記載すると、変更履歴を再生成できる。
  表紙の `meta.version` は、最後の履歴の版数と一致させる。
  複数行の変更箇所・変更内容に合わせて行高を調整する。

### 画像と要素IDの配置

Playwrightで操作したページから取得する場合は、`scripts/capture_ui_layout.mjs` の `captureUiLayout` を使える。
画面の操作・認証・表示内容は呼び出し側で準備し、画像の切り出し対象と、その内部にある要素のCSSセレクターを指定する。
画面のアニメーションと遷移を一時的に止め、撮影直前と直後の位置が変わった場合はエラーにする。
画像とJSONは同じフォルダの未作成のファイル名を指定し、出力されたJSONを `annotate_ui_layout.py` に渡す。

```js
import { captureUiLayout } from './capture_ui_layout.mjs'
await captureUiLayout(page, {
  root: '[data-testid="confirm-dialog"]',
  elements: [{ id: 'E-01', selector: 'h2' }],
  frameCell: 'C8',
  imagePath: 'work/dialog.png',
  definitionPath: 'work/dialog.json',
})
```

`page` は、呼び出し側で作成し、対象画面へ移動済みの Playwright の Page である。
複数画像を一つの設計書に載せる場合は、それぞれの出力JSONの `layouts` 配列を一つの定義にまとめる。
要素が撮影対象の範囲外の場合や、セレクターが複数要素に一致する場合は実行を中止する。

作成・編集した設計書の画像以外の加工を終え、表示枠の左上セルと画像を確認する。
WindowsのExcel、pywin32、Pillowを用いて、次の定義JSONから画像と編集可能な図形を配置する。
画像のパスはJSONからの相対パス、座標は画像の左上を原点とした0〜1の相対値とする。
要素IDは構成要素一覧に存在するものを指定する。

画像をExcelに埋め込んで管理する場合は、設計内容と画像配置のJSONを保存し、画像の重複保存は不要である。
次回の更新では、画像入りの既存設計書から、配置JSONの枠セルに対応する画像を一時フォルダへ取り出す。
同じフォルダへ配置JSONも複製されるため、そのJSONを注釈処理に渡す。
各枠に画像がちょうど１枚あることを確認し、画像がない場合や複数ある場合は停止する。

```powershell
python -X utf8 scripts/extract_ui_layout_images.py 既存設計書.xlsx 画像配置.json 一時出力フォルダ
python -X utf8 scripts/annotate_ui_layout.py 画像をまだ含まない設計書.xlsx 一時出力フォルダ/画像配置.json 出力.xlsx
```

Excelそのものが画像の保存元になるため、再生成前に既存設計書を保持する。
画像を更新した場合は、Excelと配置JSONの整合を確認してから保存する。

```json
{"layouts":[{"frame_cell":"C8","image":"button.png","min_scale":0.8,
  "elements":[{"id":"E-01","x":0.1,"y":0.2,"width":0.5,"height":0.4}]}]}
```

```powershell
python -X utf8 scripts/annotate_ui_layout.py 入力.xlsx 定義.json 出力.xlsx
```

`min_scale`は画像の96dpi換算サイズに対する許容する最小の縮小率で、既定は0.8である。
要素IDの表示が画像内の文字に重なる場合は、`label_x`、`label_y`に画像左上を原点とした0〜1の相対座標を指定して、ID表示位置を調整できる。
範囲外の座標、存在しないID、14〜30行・360ptを超える枠、既存図形との重なり、指定より大きな縮小はエラーとする。
画像が読めなければ枠を広げ、画像の範囲や分割を見直す。
出力は新規ファイルとし、同じ枠にすでに画像・図形がある場合はExcelで確認する。
この処理の後にopenpyxlで保存すると、Excel図形が失われる可能性があるため、図形の追加は最後に行う。
画像・赤枠・IDの対応、枠からのはみ出し、文字の可読性と印刷時の改ページをExcelのプレビューで確認する。

複数の部品を同じ作業で更新する場合は、画像配置のジョブをJSONにまとめて `scripts/batch_annotate_ui_layout.py` を使うと、Excelを一度だけ起動して順番に作業版を作成できる。
各 `source`、`definition`、`output` はジョブ一覧JSONからの相対パスであり、出力は元ファイルと異なる未作成ファイルにする。

```json
{"jobs":[{"source":"button/base.xlsx","definition":"button/画像配置.json","output":"button/review.xlsx"},{"source":"link/base.xlsx","definition":"link/画像配置.json","output":"link/review.xlsx"}]}
```

```powershell
python -X utf8 scripts/batch_annotate_ui_layout.py ジョブ一覧.json
```

入力の記録と元ファイルの差分確認は部品ごとに行い、生成された作業版もそれぞれ確認してから反映する。
途中で失敗した場合は後続ジョブを実行せず、それまでに作られた作業版は残す。
既存の設計書を拡張する場合は、元ファイルの記録・変更履歴・他の結合や画像の保持を確認し、無理に行を挿入せずExcelで直接編集する。

## 仕上げの確認

すべての本体シートの列幅を統一し、目盛線を非表示にする。
保存時は表紙を選択し、A1が表示・選択された状態にする。

1. スクリプトが、終了コード 0 で終わっていること。
2. `scripts/preview_sheet.py <xlsx> <出力フォルダ> <シート名> ...` で、シートを PNG にして、目で見ること。
   文字が切れていないか、枠が崩れていないかを見る。
   `verify_layout.py` は、このテンプレートには使わない（シートを作り替えるため、差分が必ず出る）。
