# 記入要領: コード設計書

## 資料の目的

選択肢の値と名称（区分値、ステータス、種別など）を、1か所で管理するための資料。  
コードIDごとに、コード値、画面に表示する名称、略称、並び順、画面ごとに出し分ける選択肢のパターンを定める。

### どんなときに作るか

この設計書は、プロジェクトによって要るかどうかが変わる。  
次のいずれかに当てはまるときに作る。

- 画面の選択肢（プルダウン、ラジオボタン、状態表示など）の値と表示名を、画面側で持つ。
- バックエンド（API）の区分値と、画面に出す表示ラベルの対応を、関係者で共有したい。
- 同じ区分を複数の画面で使い、表示名や並び順をそろえたい。

次のときは、作らなくてよい。

- 選択肢の一覧と表示名を、すべてAPIが返す（画面側は受け取った名称をそのまま表示する）。
- 区分が少なく、画面項目の定義に値と名称を書けば足りる。

### 読み替え（SPAの場合）

Nablarch の原文は、サーバー側のコード管理（コードテーブル、コードのリスト取得）を前提にしている。  
SPA（Vue・React などのシングルページアプリ）では、次のように読み替える。  
サーバー描画の場合は、原文のとおりに書く。

| 欄 | 原文の意味 | SPAでの読み替え |
|---|---|---|
| コードID | コードの識別ID | 区分の識別ID。画面の選択肢の定数名・型名と対応づけられるIDにする。 |
| コード値 | DBに保存するコード値 | APIの項目が持つ区分値。値はバックエンドの設計書が正で、ここはそれを写す。 |
| 名称 | コード値の名称 | 画面に表示するラベル。 |
| パターン1〜20 | コードのリストの取得パターン | 画面ごと・選択肢ごとの表示パターン。1＝その選択肢に出す、0＝出さない。 |

## どこに何を書くか（シート『ja』『en』）

シートは言語ごとに分かれている（`ja`＝日本語、`en`＝英語）。  
2つのシートの構造は同じで、`ja`にだけ「パターン1〜20」の列がある。  
1〜3行目のPJ名・システム名・サブシステム名は、`変更履歴`シートを参照する数式のため、書かない（`記入要領_共通シート.md`を参照）。

見出しは11行目、データは12行目から（`ja`は12〜41行目の30行、`en`は12〜38行目の27行）。  
7行目と9行目は凡例で、背景色の意味を示す。

- オレンジ色（C7）：言語ごとに変えてよい項目。ソート順、名称、略称、オプション名称1〜10。
- グレー（C9）：言語によらない共通の項目。コードID、コード名称、説明、コード値、パターン1〜20。

| 列（ja） | 項目名 | 記入内容 | 記入例（受注管理システム） |
|---|---|---|---|
| C | No. | 通し番号。コード値の行ごとに1ずつ増やす。 | 1, 2, 3 |
| D（D:E結合） | コードID | プロジェクトで定めた採番ルールに沿ったコードID。コードの最初の行にだけ書く。 | `C0000001` |
| F（F:I結合） | コード名称 | コード（区分）の名称。最初の行にだけ書く。 | 受注ステータス |
| J（J:O結合） | 説明 | コードが何を表すかを1文で書く。最初の行にだけ書く。 | 受注の進み具合を表す。 |
| P | コード値 | 区分の値。文字列で書く（`00`のように先頭の0がある値を保つため）。 | `10`, `20`, `30` |
| Q | ソート順 | 画面に並べる順（昇順）。 | 1, 2, 3 |
| R（R:T結合） | 名称 | コード値に対応する、画面に出す名称。 | 受付済み |
| U（U:V結合） | 略称 | 名称が長く、一覧などの狭い欄に入らないときの短い名称。省略可。 | 受付 |
| W〜AZ（3列ずつ結合） | オプション名称1〜10 | 名称・略称のほかに出したい名称。省略可。 | 検索条件用の表示名など |
| BA〜BT（1列ずつ） | パターン1〜20（`ja`のみ） | 選択肢のパターンごとに、そのコード値を出すなら`1`、出さないなら`0`。省略可。 | 1, 0 |

### 1つのコードに複数の値があるとき

1つのコード（例：受注ステータス）にコード値が3つあれば、3行を使う。  
コードID・コード名称・説明は、最初の行にだけ書き、2行目以降は空欄にする（テンプレートはコードごとに結合しておらず、1行1値の作りである）。  
No.は、コード値の行ごとに連番にする。

次のコードは、前のコードの最後の行の、次の行から書く。

## 記入時のポイント

- コード値は、APIの設計書（Webサービス・外部インタフェースの設計書）が定める区分値と**一字一句そろえる**。
  APIの契約が正で、フロントエンド側で別の値を作らない。
- `ja`と`en`の、グレーの項目（コードID・コード名称・説明・コード値）は、同じ内容を書く。
  言語ごとに変えてよいのは、オレンジの項目（ソート順・名称・略称・オプション名称）だけである。
- 多言語対応をしないプロジェクトは、`en`のシートを記入しない（残すか消すかは`記入要領_共通シート.md`の「多言語シート型テンプレート」に従う）。
- パターンの番号が何を指すか（どの画面のどの選択肢か）を書く欄は、この設計書に無い。
  パターンを使うときは、画面側の設計書（画面項目の定義など）の選択肢の欄に、パターン番号を書いて対応づける。
- コード値と名称は、画面項目の定義・画面イベントの設計書・メッセージ設計書から参照できるように、表記を完全にそろえる。
- 列の追加・削除はしない（構造が崩れる）。

## 行が足りないとき

`ja`は30行、`en`は27行までしか書けない。  
超えるときは、`scripts/extend_table_rows.py`で、最終データ行の書式を下へ複製する（行の挿入はしない）。  
表の下には何も無いため、この方法が使える。  
言語ごとに、別々に実行する。

```bash
# ja: 最終データ行は41、対象列はC〜BT（パターン20まで）。10行足す
python scripts/extend_table_rows.py <入力xlsx> ja 41 10 C BT <出力xlsx>
# en: 最終データ行は38、対象列はC〜AZ。10行足す
python scripts/extend_table_rows.py <入力xlsx> en 38 10 C AZ <出力xlsx>
```

- 増やした行には、値は入らない。値は`apply_mapping.py`で書く。
- 行を足すと、`verify_layout.py`は「行数・結合セル・罫線が増えた」と報告する。
  これは意図した変更であり、足した行以外に差分が無いことを確かめる。
- 印刷範囲は広がらない。印刷や PDF 化で下の行が切れるときは、Excelの[ページレイアウト]→[印刷範囲]で広げる。

## 値を書き込む手順

```bash
# 1) 変更履歴シートにPJ名等を書く（初回）。2) ja・en に値を書く。マッピングJSONの例:
#    {"sheets": {"ja": {"C12": 1, "D12": "C0000001", "F12": "受注ステータス", ...}}}
python scripts/apply_mapping.py <フォーマットのxlsx または 前の手順の出力> <マッピングJSON> <出力xlsx>
python scripts/verify_layout.py <書き込み前のxlsx> <書き込み後のxlsx>
```

- 結合セルは、左上のセル（D・F・J・R・U・W…）を指定して書く。
- 値を書いたあと、`scripts/export_sheet_preview.py`で見た目を確かめる。
