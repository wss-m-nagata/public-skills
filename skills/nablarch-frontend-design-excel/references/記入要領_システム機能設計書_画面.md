# 記入要領: システム機能設計書(画面)

## 資料の目的

1つの機能（取引）について、画面の構成・画面項目・画面とAPIの入出力・画面イベントごとの処理までを定義する。  
**取引（機能）1つにつき1ファイル**を作る。  
1つの取引には、複数の画面（ルート）がある。  
**画面1つにつき、1シート**（`2. 画面ID(画面名)`）を作る。  
ファイル名の`(取引ID)_(取引名)`の部分は、実際の値に置き換える。

このスキルは、フロントエンドがSPA（Vue・Nuxt・Reactなどのシングルページアプリ）の場合を主な対象にする。  
Nablarchの原文は、サーバーで画面を作る方式（JSP・Action・リクエストID・セッション）を前提にしている。  
そこで、様式（見出し・列・シート構成）は変えずに、「何を書くか」をSPAに読み替える。  
読み替えが要る欄には、**読み替え**と明記し、Nablarchの原文の意味も添える。  
**サーバー描画の画面（JSPなど）の場合は、原文のとおりに書く**（読み替えない）。

| Nablarchの用語 | このスキルでの読み替え |
|---|---|
| 取引 | 1つの機能（ユースケース。例：一覧から詳細、編集まで）。1取引に複数の画面がある |
| 画面ID | 画面（ルート・ページ）のID |
| リクエストID・処理依頼 | 画面イベント（初期表示・ボタン押下・API呼び出しなど） |
| Action・フォワード先 | 画面イベントごとの処理（ストア更新・画面遷移・API呼び出し） |
| セッション | ストア（状態管理）・ルートのパラメータ・ブラウザのストレージ |
| サーバー側の入力チェック | クライアント側の入力チェックと、APIが返すエラーの表示 |
| 画面とAPIの入出力 | 画面項目と、APIの項目の対応 |

**APIの契約（リクエスト・レスポンスの項目名・型・桁・必須）は、バックエンド側の設計書（WebサービスAPI一覧・外部インタフェース設計書）が正である。**  
この設計書では、APIの項目を二重に定義しない。  
APIの項目は、「APIの名称.項目名」の形で**名前で参照するだけ**にする。  
型・桁・必須などを写すと、バックエンド側の変更に追従できなくなる。

## シート構成

| シート | 内容 | 件数 |
|---|---|---|
| 表紙 | 表紙 | 1 |
| 変更履歴 | 変更履歴 | 1 |
| 目次 | 目次。画面のシート名・章番号に合わせる | 1 |
| `1.1. 取引概要` | 取引ID・取引名・取引概要・想定利用ユーザ | 1 |
| `2. 画面ID(画面名)` | 画面の定義。シート名は`2. ORD0101(受注一覧画面)`のように画面ごとに変える。章番号は、2・3・4…と画面の順に振る | 画面の数 |
| データ | プルダウンの選択肢。**書き換えない** | 1 |

- `1.1. 取引概要`のシート名は固定で、変えない。
- 画面のシートは、`build_screen_function_design.py`が複製・改名し、シート内の章番号（`2.1.`など）も振り直す。
- シート名は、31文字以内で、`[ ] : * ? / \`を含めない。長いときは、定義の`sheet_name`で短い名前を指定する。

## シート『1.1. 取引概要』

| 位置 | 項目名 | 記入内容 | 記入例 |
|---|---|---|---|
| G8 | 取引ID | この機能固有のID。ラベル（C8）は固定 | `ORD01` |
| G9 | 取引名 | 機能の名称 | 受注の照会 |
| G10〜G29 | 取引概要 | 1文（または一まとまり）を1行（1セル）に書く。長い文は、列幅に合わせて自動で次の行に続ける | 受注の登録内容を確認するときに、本機能を利用する。 |
| G30〜G34 | 想定利用ユーザ | 1行に1つ | 受注担当者 |

- ラベル（C列）は固定で、書き換えない。
- 取引概要・想定利用ユーザの行が足りないときは、スクリプトが罫線・結合を保ったまま行を広げる。
- 取引概要は、機能が何をするかを書く。画面の操作手順や項目の説明は、画面のシートに書く。
- 空行を入れたいときは、定義の`overview`に空文字（`""`）を入れる。

## シート『2. 画面ID(画面名)』

ここから先は、画面1つの仕様を書く。  
見出し（`2.1.`〜`2.6.`）は固定で、**章番号だけ**シートごとに変わる（3番目のシートなら`3.1.`〜`3.6.`）。  
各節の位置は、未編集のテンプレートでの目安である。  
行を広げると、下の節は下へずれる。

### 2.1. 画面レイアウト

画面のスクリーンショットや、レイアウトを示す画像を貼る。  
**図形は作れないため、画像を貼る。**

- 画像は、定義の`layouts`に書く。1画面に複数の画像を貼れる（初期表示・入力エラー表示など）。
- 画像のパスは、定義JSONのあるフォルダからの相対パスで書く。
- 画像は、枠に収まる大きさ（D列から右、32行分の高さまで）に縮めて貼る。拡大はしない。
- 画像の上に、見出しを1行書ける（`caption`）。
- 2枚目以降の画像は、新しいページから始める。枠に収まらなければ、行を広げる。
- 画像のパスを省略すると、枠の左上に「（画像未添付）」の文字を入れ、警告を出す。
- **画像が無いときの対応**：ユーザーに、画面の画像（スクリーンショットやワイヤーフレーム）の用意を依頼する。
  報告には、「2.1 画面レイアウトは未添付」と書く。
  画像ができたら、定義の`layouts`にパスを足して、組み立て直す。
- 画像の中に、領域名（2.2・2.3の「領域名」と同じ名前）と、必要なら項目の番号を書き込んでおく。
  シートの上には図形を描けないため、画像の側で領域を示す。
- 画像は、画面の状態（初期表示・エラー表示・ダイアログなど）が分かる粒度で用意する。

### 2.2. 一覧表示

**一覧（テーブル・リスト）のある領域**を書く。  
見出し：`No. / 領域名 / ページング有無 / ソート条件 / 備考`

| 列 | 記入内容 | 記入例 |
|---|---|---|
| No. | 連番（自動） | 1 |
| 領域名 | 2.1の画像・2.3の領域名と同じ名前 | 受注検索結果 |
| ページング有無 | プルダウン：`有` `無` | 有 |
| ソート条件 | 初期の並び順。ユーザーが並び替えられる場合は、その旨を備考に書く | 受注日の降順 |
| 備考 | 1ページの件数など、この画面だけの決まり。無ければ`-` | 1ページ10件 |

- **読み替え**：ページングは、画面側（クライアント）で分けるか、APIがページ単位で返すかを、備考に書く。
- 一覧のある領域が無い画面は、`list_areas`を空にする。`-`を書いた1行になる。
- 検索結果の上限件数・1ページの件数が、システム共通の決まりなら、個々の設計書には書かず、共通の決まりに任せる（原文のコメント）。

### 2.3. 画面項目定義

画面に表示する項目・入力する項目を、領域ごとに定義する。  
見出し：`No. / 表示情報（画面項目名・画面項目種別・情報取得元・編集仕様・初期値・必須）/ ドメイン名 / 画面項目名（物理）`  
定義の順は、**Tabキーで移動する順**にする。

領域ごとに、「領域名：○○」の行（オレンジ）を置き、その下に項目を並べる。  
項目は、領域の中で連番を振る（領域をまたいで通し番号になる）。  
1つの項目が複数の入力欄に分かれる場合（郵便番号の上3桁・下4桁など）は、続きの行に`"cont": true`を付ける。続きの行には番号を振らない。

| 列 | 記入内容 | 記入例 |
|---|---|---|
| 画面項目名 | 画面に表示する項目の名称 | 顧客名 |
| 画面項目種別 | プルダウン。`-` `label` `text` `text(disable)` `textarea` `radio` `checkbox` `select(pulldown)` `select(multiple)` `password` `file` | text |
| 情報取得元 | 表示する値の出どころ。**APIの項目は「APIの名称.項目名」で参照する**（項目の型・桁は書かない）。入力項目で取得元が無いときは`-` | 受注検索API.orders[].orderNo |
| 編集仕様 | 値をそのまま表示せずに加工・検査する場合に書く（下記） | ＜入力チェック＞<br/>全角50文字以内 |
| 初期値 | 画面を開いたときの値。ストアに初期値があるときは、その値 | `-` |
| 必須 | プルダウン：`○`（必須）`-`（必須でない） | ○ |
| ドメイン名 | 入力チェックの型（ドメイン）の名前。**同じドメインの項目には、同じドメイン名を書く**（例：受注日（開始）と受注日（終了）は、どちらも`日付`）。ドメインの定義書が無いときは、項目名をそのまま書き、同じドメインの項目は同じ名前にそろえる。入力チェックの無い表示項目は`-` | 日付 |
| 画面項目名（物理） | コンポーネントの入力モデルのキー・フィールド名（内部設計情報） | searchForm.customerName |

**編集仕様の書き方（読み替え）**

Nablarchの原文では、編集仕様は「表示変換」（取得元の値を加工して表示する決まり）を書く欄である。  
SPAでは、次の3種類を、見出し付きで分けて書く。  
種類ごとに、行頭に見出しを置き、セル内改行で1項目1行に書く。

| 見出し | 書く内容 |
|---|---|
| ＜表示変換＞ | 表示用の加工。日付の書式、件数の文言、コード値から名称への変換、プルダウンの並び順など |
| ＜入力チェック＞ | クライアント側で行う、この項目に固有の検査。ドメイン・必須で表せないもの（桁数・形式・他の項目との関係） |
| ＜表示条件＞ | 項目の表示・非表示・入力不可の条件（権限・状態による切り替え） |

- **編集仕様は、該当する種類の見出しだけを書く。** 3種類すべての見出しを並べない（サンプルも、該当する種類だけを書いている）。
- **3種類のどれにも該当しないときは、`-`を1つだけ書く。** 種類ごとの`-`は書かない。
- スクリプトは、定義の`edit`をそのままセルへ書く。省略すると`-`を書く。見出しを補わず、`-`を足しもしない。
  行の高さは、セル内改行の行数に合わせて自動で広がる。
- 編集仕様以外の欄は、該当しないとき空欄にせず`-`を書く。まだ決まっていない欄は、`T.B.D（後ほど記載）`と書く。
- 初期値は、radio・checkbox・select の場合、初期の選択状態を書く（原文のコメント）。
- 取得元と表示の桁数が違う場合も、編集仕様に書く（原文のコメント）。
- コード値のプルダウンは、コード値の取得元（APIの名称・コード種別）を、編集仕様に書く。
- ボタン・リンクは、画面項目としては定義しない。イベントの発生元として、2.5の発生タイミングに書く（Nablarchの様式と同じ）。
- 画面項目種別に無い種類（calendar・hiddenなど）を使うと、スクリプトは警告を出す。選択肢のどれに当たるかを決めるか、データシートの選択肢を、設計書の持ち主が増やす。

### 2.4. 入出力一覧

この画面が**受け取る・渡すもの**をすべて書く。  
見出し：`No. / 入出力名 / 種別 / I/O / DBアクセス種別（C R U D ﾛｯｸ対象）/ 備考`

| 列 | 記入内容 | 記入例 |
|---|---|---|
| 入出力名 | 画面が呼ぶAPIの電文（要求・応答）、または読み書きするストアなどの名称 | 受注検索API 応答 |
| 種別 | プルダウン：`-` `テーブル` `電文` `I/Fファイル` `帳票` `電子メール` | 電文 |
| I/O | プルダウン：`I` `O` | I |
| DBアクセス種別 | 各列に`○`または`-` | `-` |
| 備考 | 補足。無ければ`-` | 検索結果を受け取る |

**読み替え**

- 入出力名は、**API単位ではなく電文単位**で書く。要求電文と応答電文を、別の行にする。
- **I/O**：`I`は、画面が受け取るもの（APIの応答、ストアから読む値）。`O`は、画面が渡すもの（APIの要求、ストアへ書く値）。
- 種別：APIの電文は`電文`にする。ストア・ブラウザのストレージ・ルートのパラメータは、種別の選択肢に無いため`-`にし、備考に何かを書く（例：ストア searchCondition）。
- DBアクセス種別：フロントエンドは、DBに直接アクセスしない。すべて`-`にする（APIの先のDBアクセスは、バックエンド側の設計書に書く）。
- 画面が呼ぶ共通部品が、内部で使うAPI・ストアは書かない（共通コンポーネント設計書に書く。原文の決まり）。
- バリデーションのために呼ぶAPIも書く（原文の決まり）。
- APIの項目は書かない。API単位の名称（APIの一覧にある名称）で参照する。

### 2.5. 画面イベント一覧

この画面で起こりうるイベントを書く。  
見出し：`No. / 画面イベント名 / 発生タイミング / 画面イベント概要 / 正常時遷移先画面 / サーバ通信有無`

| 列 | 記入内容 | 記入例 |
|---|---|---|
| 画面イベント名 | イベントの名称。2.6の見出し（`○○イベント`）になる | 一覧検索 |
| 発生タイミング | 起こる契機 | 「検索」ボタン押下 |
| 画面イベント概要 | どんな処理が動き、どの画面へ移るかの概要。処理の詳細は2.6に書く | 入力された検索条件に合致する受注を検索する。 |
| 正常時遷移先画面 | 正常に終わったときの遷移先。遷移しなければ`-` | 受注一覧画面(結果表示) |
| サーバ通信有無 | プルダウン：`あり(同期)` `あり(非同期)` `なし` | あり(非同期) |

- イベントには、初期表示・ボタン押下・リンク押下・特定のキー押下・入力値の変更などを書く（原文のコメント）。
- 異常時の遷移先は、画面ごとには書かない。共通のUI標準に任せる（原文のコメント）。
- **読み替え**：`サーバ通信有無`は、次の意味で選ぶ。

| 選択肢 | Nablarchの原文の意味 | SPAでの読み替え |
|---|---|---|
| あり(同期) | 画面遷移を伴う通信 | ブラウザがページ全体を読み直す通信（外部サイトへのリダイレクト、ファイルのダウンロード遷移など） |
| あり(非同期) | Ajaxによる通信 | fetch・XHRによるAPI呼び出し（SPAの通常のAPI呼び出し） |
| なし | JavaScriptによる処理（通信なし） | クライアント側の入力チェック・ストア更新・ルート遷移だけで終わる処理 |

- API呼び出しを伴うイベントは、成功後に画面を遷移する場合でも`あり(非同期)`にする。遷移の有無は、正常時遷移先画面に書く。

### 2.6. 画面イベント詳細

2.5で定義したイベントごとに、処理を処理の順に書く。  
見出しは、`2.6.1. ○○イベント`の形で、イベントの数だけ作る（スクリプトが作る）。

**書き方（読み替え）**

Nablarchの原文は、イベントごとに次の3つを書く。  
(1) バリデーション処理　(2) 検索・登録・更新・削除処理　(3) 表示処理  
SPAでは、次のように読み替える。

| 原文 | SPAでの読み替え | 書く内容 |
|---|---|---|
| (1) バリデーション処理 | (1) 入力チェック | クライアント側で行うチェック。チェックごとに、メッセージIDと、エラー時にチェックを続けるかを書く |
| (2) 検索・登録・更新・削除処理 | (2) API呼び出し | 呼ぶAPIの名称、要求の各項目に**何を設定するか**（画面項目・ストア）、応答のエラーの扱い |
| (3) 表示処理 | (3) 状態更新・表示処理 | 応答を受けたあとの、ストア更新・画面項目への反映・画面遷移・メッセージ表示。0件・上限超過など、場合分けも書く |

- イベントに処理が無い（遷移するだけなど）場合は、処理を1〜2行の文で書く。他のイベント・他の画面の処理と同じなら、その節・画面を参照する形で書く。
- **要求の項目は、APIの項目名（バックエンド側の設計書の名称）で書く。** 項目の型・桁・必須は、ここに書かない。
- 文章だけでは誤解されるおそれがある仕様は、表や数式で分かりやすく書く（原文のコメント）。
- 画面とAPIの間で値を詰め替える場合（複数の入力欄を1つの項目にまとめるなど）は、表で対応を書く。

**記入の形**

イベントの詳細は、定義の`detail`に、次のブロックを並べて書く。

| ブロック | 書く場所 | 内容 |
|---|---|---|
| `h1` | E列 | `(1) 入力チェック`のような大見出し |
| `h2` | F列 | `(a) 単項目チェック`のような中見出し |
| `h3` | G列 | 小見出し |
| `text` | 既定はF列（`indent`で字下げを変える） | 文。長い文は、列幅に合わせて次の行に続く。先頭が「・」「※」の文は、続きを字下げする |
| `table` | 既定はF列（`indent`で変える） | 罫線付きの表。`preset`か`columns`で列を決める |

- 1つの`text`に、1文（または一まとまり）を書く。段落をまとめて1つにしない。
- 表の書式は、2.4の表から借りる。表の下に空行が1行入る。
- 表は、そのステップで**何を伝えるか**で列を決める。次の`preset`は、内容が当てはまるときだけ使う時短用である。

| preset | 列 |
|---|---|
| validation | No. / チェック名 / チェック内容 / メッセージID / 埋め込み文字列 / 後続チェックの続行判定 |
| parameter | パラメータ / 設定値 |
| api_error | HTTPステータス / エラーコード / メッセージID / 画面の動作 |

- `columns`を使うときは、列を`{"title": "…", "span": 列数}`で書く。`span`を省略すると、`No.`は1列、残りは残りの幅を等分する。
- 表の列数の合計は、シートの幅（AH列まで）を超えない。超えるとエラーになる。
- イベントに`detail`が無いときは、`-`を1行書く。

### 画面引継ぎ項目（内部設計情報）

2.6の下に、`【内部設計情報】 画面引継ぎ項目`がある。  
この節は印刷しない（印刷範囲の外）。  
イベントごとに、`（1） ○○イベント`の見出しと表がある。  
画面イベントのあとの画面へ**渡す・受け取る値**を書く。

見出し：`No. / 項目情報（引継ぎ項目名・格納先・設定値・項目説明）/ 備考`

| 列 | 記入内容 | 記入例 |
|---|---|---|
| 項目グループ | プレフィックスをつける単位で、項目をまとめる。グループ名は、内容を推測しやすい名前にする | 検索条件 |
| プレフィックス | グループに付けるキーの接頭辞（ストアのモジュール名・クエリのキーの接頭辞など）。無ければ`-` | order |
| 引継ぎ項目名 | 引き継ぐ値の名称 | 顧客名 |
| 格納先 | **読み替え**：リクエストスコープなどではなく、値を渡す手段を書く | ルートのクエリ |
| 設定値 | 設定する値。前の画面から継続して引き継ぐだけなら、書かなくてよい | 検索条件の入力内容 |
| 項目説明 | 何のための値か | 戻ってきたときの再検索に使う |
| 備考 | 補足。無ければ`-` | `-` |

- **読み替え（格納先）**：`ルートのパラメータ`（パス）・`ルートのクエリ`・`ストア`・`ブラウザのストレージ`のうち、実際に使うものを書く。この列にプルダウンは無い。
- 引き継ぐ値が無いイベントは、グループ・項目に`-`を書いた1行になる。

## 目次・表紙・変更履歴

表紙・変更履歴・目次は、`記入要領_共通シート.md`に従う。  
`build_screen_function_design.py`は、次を書く。

- 変更履歴：E1（PJ名）・E2（システム名）・E3（サブシステム名）、S1（成果物名の欄。`システム機能設計書(画面)`と、`取引ID/取引名`）、8行目以降の履歴。
- 表紙：J12（PJ名）・J16（サブシステム名）・J19（版数）・J28（会社名）・J30（部門名）。
- 目次：画面の数だけ、`N. 画面ID(画面名)`と`N.1.〜N.6.`を並べる。`1.1. 画面取引概要`の行は固定で、書き換えない。

履歴の行を定義しないときは、「新規作成」の1行だけを書く。  
履歴の行を定義するときは、`where`・`what`に、セル内改行で1行ずつ書く（書き方は`記入要領_共通シート.md`）。

## 組み立て（build_screen_function_design.py）

定義（JSON）から、1回で組み立てる。  
行の複製・挿入・削除、シートの複製、目次の同期、入力規則のかけ直し、行の高さ、画像の貼り付けまで行う。

```bash
python scripts/build_screen_function_design.py \
  "assets/templates/フォーマット/システム機能設計書(画面)_(取引ID)_(取引名).xlsx" \
  定義.json 出力.xlsx
```

- 元ファイルは、**必ず`フォーマット/`のテンプレート**を指定する。サンプルは、人が編集した図形が残っているため、元ファイルにしない。
- 定義に誤り（必須項目の不足・表の列数の不一致・画像が無い・シート名が不正）があると、出力を作らずに誤りの一覧を表示して終わる。
- プルダウンの選択肢に無い値は、警告として表示する（書き込みは止めない）。`-`は、該当しないことを表すため警告しない。
- 変更箇所を赤字にするときは、行・ブロックに`"changed": true`を付ける。前の版で付けた`changed`は、定義から外す。
- 定義の書式は、スクリプト冒頭の説明を参照する。

### 検証

**この出力には、`verify_layout.py`を使わない。**  
シートの複製・改名、行の増減、目次の書き換え、入力規則の範囲の変更があるため、テンプレートと比べると必ずNGになる。  
代わりに、次の3つで確かめる。

1. スクリプトの終了コードが0であること。
2. 表示された警告を、すべて確かめること（プルダウンに無い値・画像未添付など）。
3. `export_sheet_preview.py`で各シートをPDFにして目視すること（長文が隠れない・画像が枠に収まる・節が重ならない）。

比べる必要が出たときは、`verify_layout.diff_sheet`で、シートごとに比べる。  
**想定される差分**は、次のとおり。

- 画面のシート名の変更、シートの追加（複製）、目次の文字。
- 2.2〜2.5・画面項目定義の行数の増減による、結合セル・罫線・行の高さ・入力規則の範囲の変化。
- 2.6と画面引継ぎ項目の、行の位置・結合セルの変化。
- 行の高さが広がった行、赤字（`changed`）のセル、変更履歴のS1の折り返し。

**これ以外の差分は異常である。**  
例：表紙・データシートの変化、ラベル・見出しの文字や背景色の変化、図形（表紙の機密区分）の消失。

## 記入時のポイント

- 見出し・列・シート構成は、変えない。変えるのは「何を書くか」だけである。
- グレーの欄・ラベルは固定で、書き換えない。
- 該当しない欄は、空欄にせず`-`を書く。決まっていない欄は、`T.B.D（後ほど記載）`と書く。
- **APIの項目を二重に定義しない。** APIの項目名で参照する。型・桁・必須は、バックエンド側の設計書にだけ書く。
- 2.4の入出力名は、バックエンド側のWebサービスAPI一覧・外部インタフェース設計書にある名称と合わせる。
- 2.3の情報取得元・2.6のAPI呼び出しの項目名は、外部インタフェース設計書の項目名と完全に一致させる。
- 2.5のイベント名・正常時遷移先画面は、2.6の見出し・画面遷移図の画面名と合わせる。
- 2.2の領域名・2.3の領域名・2.1の画像に書いた領域名は、同じ名前にする。
- 2.6の処理は、2.5の画面イベント概要と矛盾しないようにする。概要は一言、詳細は2.6に書く。
- 画面引継ぎ項目は、遷移元の「渡す値」と、遷移先の「受け取る値」を合わせる。
- シートの行番号・セル座標は、未編集のテンプレートでの目安である。行を広げると、下の内容はずれる。書き込む前に、実際のセルを確かめる。
