# Nablarch フロントエンド設計書Excel 作成・更新スキル

Python 3、openpyxl 3.1系、Pillowが必要。画面遷移図にはGraphviz（dot）、画像へのExcel図形の追加とプレビューにはWindows・Microsoft Excel・pywin32、PNGへのプレビューにはPyMuPDFが必要。
開始前に使用するPythonで依存ライブラリとExcelの利用可否を確認し、不足を報告する。
作業フォルダに書き込めない場合は実行環境の権限を確認し、許可された作業先を使う。

## 目的

フロントエンドの設計書を、独自の書式ではなく、Nablarch開発標準のフォーマットに沿って標準化して作成・維持することを支援する。
フォーマットが逸脱すると、他のプロジェクトとの一貫性や、レビューのしやすさが損なわれる。

この目的には、次の2つが両方とも要る。

1. **書くべき内容を正しく確定すること** — 誰に何を確認し、どの資料を読むか（「内容を確定する」）。
2. **確定した内容を、標準フォーマットを壊さずにExcelへ反映すること** — 結合セル・数式・プルダウンを保ったまま書き込む（「ローカル実行の手順」）。

## このスキルが対象とする範囲

### 必須の4点

| 設計書 | 粒度 | 役割 | 組み立てスクリプト |
|---|---|---|---|
| 画面一覧 | サブシステム | 画面ID・画面名を定義し、画面IDを採番する。 | `apply_mapping.py`（行が足りないときは `extend_table_rows.py`） |
| 画面遷移図 | サブシステム（機能ごとに1シート） | 機能ごとの画面遷移を定義する。 | `build_screen_flow.py` |
| システム機能設計書(画面) | 取引（1シート＝1画面） | 画面レイアウト、画面項目定義、入出力、画面イベントを定義する。 | `build_screen_function_design.py` |
| 単体テスト仕様書(画面) | 取引 | 画面の単体テストを、観点ごとに定義する。 | `build_unit_test_spec.py` |

### 必要に応じて作る設計書

プロジェクトの方針によって、要るかどうかが変わる。
各記入要領の冒頭に、「どんなときに作るか」を書いている。

| 設計書 | どんなときに作るか |
|---|---|
| リクエスト一覧 | 画面イベントのIDを、一覧で採番・管理したいとき。 |
| コード設計書 | 画面の選択肢・区分値・表示ラベルを、1か所で管理したいとき。 |
| メッセージ設計書 | 画面に出すメッセージを、画面側で管理するとき（バックエンドから受け取るなら要らない）。 |
| 共通コンポーネント一覧 | 複数の画面で使う共通部品（画面部品・関数・composable・ストア）を、一覧で管理するとき。 |
| 共通コンポーネント設計書 | 共通部品ごとの、インタフェース（props・イベント・戻り値）と処理を定義するとき。 |
| 単体テスト仕様書(共通コンポーネント) | 共通部品の単体テストを、観点ごとに定義するとき（`build_unit_test_spec.py`）。 |

### Nablarch に無い独自様式

| 設計書 | どんなときに作るか |
|---|---|
| 画面共通部品設計書 | 画面の共通部品について、使う人が使い方を分かるように示すとき。部品の配置・命名・分類は対象プロジェクトの決まりに従う。 |

- Nablarch の共通コンポーネント設計書は、バックエンドのクラス向けの様式で、画面部品の表示、状態、公開する関数を書くには合わない。
  そのため、構成（概要、画面レイアウト、状態、入力属性、オブジェクト定義、関数定義、関数詳細）は独自にし、書式（表紙、変更履歴、ヘッダー帯、フォント、罫線、見出しの配色、印刷設定）は、Nablarch から引き継いでいる。
- 1部品につき1ファイルである。組み立ては、`build_ui_component_design.py`（定義 JSON から作る）で行い、手で行や結合を変えない。
- 書き方は、`references/記入要領_画面共通部品設計書.md` を読む。
  特に、「設計書の中で完結して書く（規約などへの参照で済ませない）」「目的は使う人の価値で書く」「未決定の事項や課題は書かない」を守る。
- 画像枠は14行を基本とし、可読性のため最大30行（1行12pt、計360pt）まで広げる。
  画像上の構成要素はExcelの赤枠と要素IDで示し、記入要領の手順と`annotate_ui_layout.py`で検証する。
  複数の設計書では `batch_annotate_ui_layout.py` でExcelの起動を共有できるが、元ファイルと各成果物の確認は省略しない。
  `app.vue`などの画面基盤にも、対象の構成と宣言する情報を使う人に示すため、この様式を使ってよい。

### 対象外

- バックエンド（API・テーブル・バッチ）の設計書は、`nablarch-basic-design-excel` を使う。
- 帳票設計、メール設計、ジョブフロー設計は、対象外。
- 画面が呼ぶ API の契約（項目・型・エラー）は、バックエンド側の設計書（WebサービスAPI一覧・外部インタフェース設計書）が正である。
  フロントエンドの設計書は、API の項目を二重に定義せず、項目名で参照する。
  Nablarch の設計書一覧にも、「画面アプリケーションは、インタフェース設計とシステム機能設計を1つの設計書に書く」とある。

## SPA（シングルページアプリ）への読み替え

Nablarch の画面設計は、サーバーで画面を作る方式（JSP、Action、リクエストID、セッション）を前提にしている。
このスキルは、主な対象を SPA とし、**テンプレートの見出し・列・シート構成は変えずに、書く内容の解釈だけ**を読み替える。
様式を保つことが、このスキルの目的だからである。

| Nablarch の用語 | このスキルでの読み替え |
|---|---|
| 取引 | 1つの機能（ユースケース。例：一覧から詳細、編集まで）。1取引に複数の画面（ルート）がある。 |
| 画面ID | 画面（ルート／ページ）のID。 |
| リクエストID・処理依頼 | 画面イベントのID（ボタン押下、初期表示、API 呼び出しなど）。 |
| Action・フォワード先 | 画面イベントごとの処理（ストア更新、画面遷移、API 呼び出し）。 |
| セッション | ストア（状態管理）、ルートのパラメータ、ブラウザのストレージ。 |
| サーバー側の入力チェック | クライアント側の入力チェックと、サーバー（API）が返すエラーの表示。 |
| 画面とAPIの入出力 | 画面項目と、API の項目の対応。 |
| DBアクセス（CRUD） | フロントエンドは、テーブルを直接使わない。API・ストアへの操作として読む。 |

- 各記入要領に、節ごとの「読み替え」と、Nablarch の原文の意味を書いている。
- サーバーで画面を作る方式（JSP など）の場合は、原文のとおりに書く。
- 読み替えで迷った欄は、仮の値で埋めず、ユーザーに確認する。

## 設計書の作成順序と、入力にする資料

作成の順序は、前の設計書が、次の設計書の入力（IDの元）になる。

1. 画面一覧（画面IDを決める）
2. 画面遷移図（画面IDと、遷移のきっかけを使う）
3. システム機能設計書(画面)（画面ID・画面イベントを使う）
4. 共通コンポーネント一覧・設計書、コード設計書、メッセージ設計書（機能設計書から参照される）
5. 単体テスト仕様書（機能設計書の画面項目・画面イベントから、観点とケースを起こす）

材料にするもの（ユーザーが持っているものから、読み込む）：
- 画面の詳細設計（画面ごとの項目、操作、表示条件、エラー）、ワイヤーフレーム、デザイン、スクリーンショット。
- バックエンドの API 設計書（API の項目の名前、エラー）。
- 既存のソースコード（ルート、コンポーネント、ストア、入力チェック）。
- 要件定義書（機能の範囲、権限）。

## 内容を確定する（ユーザーとのやり取り）

Excel に書き込む前に、必ずここを済ませる。
飛ばして、仮の値や推測でセルを埋めると、フォーマットは守れていても、内容として誤った設計書になる。

1. **対象範囲を確認する**：必須の4点と、必要に応じて作る設計書のうち、今回作るもの。
   画面（取引）の範囲も確認する。一度にすべてを作ろうとせず、対象を決めてから着手する。
2. **前提を確認する**：フロントエンドの方式（SPA か、サーバーで画面を作るか）。
   SPA の場合は、フレームワーク、状態管理、入力チェックの方式、メッセージの管理の方式（画面側か、API か）。
3. **材料を取り込む**：上の「入力にする資料」を読み、記入要領が求める項目に対応づける。
   資料に無い項目は、次の手順で質問する。
4. **記入要領と照らして、内容を確定する**：記入要領と構造メモ、`記入要領_共通シート.md` を読み、何を書くかを決める。
   不明点・矛盾（IDの揺れ、画面項目と API 項目の食い違い）は、仮の値を置かず、その場で質問する。
5. **確定した内容をユーザーに提示する**：次のものは、書き込む前に確認を得る。
   - 後続の設計書に波及するID（画面ID、取引ID、画面イベントID、共通コンポーネントID）。
   - 分量の多い内容（画面項目定義、画面イベント詳細、テストケース）。
   1シート（1画面）分をまとめて確定してから、次に進めばよい。

### ユーザーに質問できないとき

確認の相手がいない場面（自動実行など）では、次の順で、仮定を置いて進める。

1. **ユーザーの指定が最優先**：依頼に書かれた名前・ID（サブシステム名、画面ID、取引名など）は、記入要領の例より優先する。
   記入要領の例の名前は、例にすぎない。
2. **IDの採番は、記入要領の既定案**：画面ID、機能ID、画面設計書IDなどは、各記入要領の「決めていないときの既定案」に従う。
3. **材料に無い内容は、仮置きと分かる形にする**：画面項目、API の項目名、メッセージの文言、エラーコードなどは、記入要領の「T.B.D（後ほど記載）」の表記か、「（仮）」を付けて書く。
   推測を、確定した内容のように書かない。
4. **最後の報告に、置いた仮定の一覧を書く**：何を、なぜ、そう置いたか。ユーザーが確認すべき点がどれか。
5. 表紙の部門名など、材料が全く無い欄は、ダミーを入れず、空にする（角括弧のプレースホルダーは消す）。

## ローカル実行の手順

前段の「内容を確定する」が済んでいることが前提である。
入力ファイルは、新規に作るときは `assets/templates/フォーマット/` のテンプレートを、既存の設計書を直すときは、その設計書を使う。

**⚠️一連の処理の「元ファイル」には、必ず `フォーマット/` のテンプレート、またはそこから始まる自分の出力ファイルを使う。**
`サンプル/` と `原本/` は、読むだけにする。
サンプルは、人が編集した図形が残っており、元ファイルにすると、表紙が二重に表示される。

**出力先は、原則としてプロジェクトのルート直下の `.agents/state/nablarch-frontend-design-excel/` の下に、作業ごとのフォルダ `<YYYYMMDD>_<件名>/` を作って置く。**
実行環境の書き込み権限で使えない場合は、許可された作業領域に同名の作業フォルダを作り、場所を報告する。
フォルダの直下にファイルを溜めない。
途中のファイルが溜まると、古い版を元ファイルに使う事故が起きる。
作業が終わったら、`scripts/cleanup_state.py` で、古い作業フォルダを片付ける（既定は一覧の表示だけで、`--delete` を付けたときだけ消す。消す前に、成果物が上がっていることを、ユーザーに確かめる）。

**Windows では、Python に `-X utf8` を付けて実行する**（日本語のシート名・見出しの文字化けを防ぐ。`python -X utf8 scripts/...`。環境変数 `PYTHONIOENCODING=utf-8` でもよい）。

**既存の設計書を直すときは、元にした設計書が、作業中に人に直されていないかを確かめる**（`record` の元は、手元のコピーと、共有場所にある現行版の両方）。
`scripts/track_sources.py` で、作業の開始時に元のファイルを記録し（`record`）、書き出す前に比べる（`check`）。
違いが出たら、作業を止め、変更箇所をユーザーに伝える。
新しく作るとき（`フォーマット/` から作るとき）は、元のテンプレートが変わらないことを確かめるだけでよく、省略してもよい。
`record` は、作業フォルダの下に `sources/` と `sources.json` を作る（比べる基準の写しで、成果物ではない）。

```bash
python scripts/track_sources.py record <作業フォルダ> <元にしたファイル> [...]
python scripts/track_sources.py check <作業フォルダ> [<ファイル> ...]
```

### 設計書ごとの組み立て

次の3つの設計書は、構造が複雑なため、専用のスクリプトで、定義 JSON から一括で組み立てる。
手でマッピングを組むと、行の挿入や複製で、結合セル・行高・入力規則・印刷範囲がずれる。
JSON の書式は、各スクリプトの冒頭の説明と、各記入要領にある。
`build_unit_test_spec.py` は、`--list-catalog` で、空のテンプレートの観点の一覧（観点No・分類）を先に見られる。

```bash
# 画面遷移図（Graphviz で画像を作って貼る。凡例の図形は残す）
python scripts/build_screen_flow.py <フォーマットのテンプレート> <定義json> <出力xlsx> [--dot-out <dotソースの出力フォルダ>]

# システム機能設計書(画面)（画面ごとのシート複製、表の行数の調整、目次の同期、画像の貼り付け、表紙・変更履歴の記入）
python scripts/build_screen_function_design.py <フォーマットのテンプレート> <定義json> <出力xlsx>

# 単体テスト仕様書（画面・共通コンポーネント）。観点の抜けを検出する。
python scripts/build_unit_test_spec.py <フォーマットのテンプレート> <定義json> <出力xlsx> [--cases-json <ケース一覧の出力先>]
```

- 画面遷移図は、Graphviz が自動で配置するため、手描きのような配置にはならない。
  画面が多い（10を超える）と、縮小で文字が小さくなるので、機能を分けることを、ユーザーに提案する。
- システム機能設計書(画面)の画面レイアウトは、画像（スクリーンショットなど）を貼る。
  画像が無いときは、枠を空けて警告する。
- 単体テスト仕様書は、観点ごとに、テストケースか対象外理由のどちらかを埋める。
  埋めていない観点があると、エラーで止まる（書きかけの確認には `--allow-unaddressed`）。

### それ以外の設計書（画面一覧・リクエスト一覧・コード設計書・メッセージ設計書・共通コンポーネント一覧/設計書）

次の順に処理する。

1. **（必要なとき）シートを複製する**：`scripts/duplicate_sheet.py <元xlsx> <複製元シート名> <新シート名> <出力> --before-sheet <シート名>`。
2. **（必要なとき）シートの名前を変える**：`scripts/rename_sheet.py <元xlsx> <現在の名前> <新しい名前> <出力>`。
   手でシート名を書き換えない。
3. **（必要なとき）行を増やす**：表の下が空き領域なら `scripts/extend_table_rows.py`、下に別の表や節があるなら `scripts/insert_rows.py`（結合セル・行高・入力規則をずらす）。
   ブロックごとの複製は `scripts/insert_row_block.py`。
   **`表紙`・`変更履歴`・`目次`のシートには使わない。**
4. **値を反映する**：確定した内容を、「シート名 → セル座標 → 値」のマッピング JSON にまとめ、`scripts/apply_mapping.py <元> <マッピングJSON> <出力>` で反映する。
   - PJ名・システム名・サブシステム名は、`変更履歴` シートの E1・E2・E3 にだけ書く（他のシートは、これを参照する数式で、上書きすると壊れる）。
   - 表紙の J12・J16・J28・J30 は、静的テキストで、罫線の外にあるため、本文とは別の呼び出しで、`--allow-outside-border` を付けて書く。
   - 変更履歴の担当者（AF列）を埋める（埋めないと、全シートの「作成」「変更」欄が空欄のままになる）。
   - 変更履歴に行を足す前に、`scripts/normalize_change_history.py` で、結合と書式をそろえる。
5. **行の高さを合わせる**：結合セルの長文は、Excel が行の高さを自動で広げない。
   変更履歴は `scripts/fit_change_history_rows.py`、本文は `scripts/fit_row_heights.py` を使う。
6. **構造を検証する**：`scripts/verify_layout.py <直前の入力> <最終の出力>`。
   `OK` が出るまで、完了として報告しない。
   行の高さを変えたときは `--allow-history-row-heights` と `--allow-row-heights` を、赤字の前後には `--allow-font-colors` を付ける。
   **次の組み立てスクリプトの出力には、`verify_layout.py` を使わない。**
   シートを複製・削除し、表の行数を変えるため、テンプレートとの比較は、必ず差分が出る（誤検知を含む）。
   代わりに、次の3点で確かめる。
   - スクリプトが、終了コード 0 で終わっている。
   - 出た警告を読み、意図したものか（画像が無い、プルダウンに無い値、縮小が大きい、など）を確かめている。
   - 見た目を確認している（次の7）。
7. **見た目を確認する**：`scripts/preview_sheet.py <xlsx> <出力フォルダ> <シート名> [<シート名> ...]` で、シートを PNG にし、Read ツールで開いて目で見る（Windows と Excel が要る）。
   画像や長文を入れたとき、組み立てスクリプトで作ったときは、必ず行う。
   長文が隠れていないか、画像が枠に収まり他の節と重なっていないか、行を増やした後の罫線が切れていないか、を見る。

### 版を上げるときは、今回変えたセルだけを赤字にする

既存の設計書の版を上げるときは、前の版の赤字をすべて黒に戻してから（`scripts/mark_changed_cells.py <xlsx> --reset-all --output <出力>`）、値を書き、検証したあとに、今回変えたセル（表紙の版数 J19 を含む）を赤字にする（`scripts/mark_changed_cells.py <xlsx> <シート名> <セル座標...> --output <出力>`）。
変更履歴の行は、赤字にしない。
変更履歴の書き方（セル内改行で1行ずつ、行の高さを合わせる）は、`記入要領_共通シート.md` にある。
初版だけを作るときは、同じファイルの「シート『変更履歴』」の初版の行（座標の表）だけを読めばよい。

## 判断に迷ったら

- 記入要領に無い項目・列が出たとき：仮の値を置かず、`scripts/extract_structure.py <xlsx> <出力md>` で構造を見直し、必要なら記入要領を直してから進める。
- 読み替えで迷ったとき：Nablarch の原文の意味と、SPA での読み替えの両方を、ユーザーに示して、どちらで書くかを確認する。
- スクリプトで読み書きできない要素（数式、チェックボックス、条件付き書式、図形）に当たったとき：無理に openpyxl で直さず、ユーザーに「Excel で直接確認・編集が要る」と伝える。
- `verify_layout.py` が「図形が失われたシート」を報告したとき：`scripts/restore_shapes.py <元> <加工後> <出力>` で復元する。
