# ドキュメントの書き方

このスキルは、ドキュメントを「どの種別として、何を書くか」の方針を定める。
改版履歴の書式、対応者の書き方、言語、改行などのプロジェクト固有の決まりは、そのプロジェクトの規約に従う。
このスキルは、それを定めない。

## 進め方

1. ファイルの種別を決める。
   目的で決め、迷ったら「種別の判定」を使う。
2. 「種別表」の、その種別の行を確認する。
3. 「共通ルール」と、種別に応じた節（README・AGENTS.md）に従って書く。
4. 「点検」の問いで見直す。

## 種別の判定

- 決まった「何をするか」を、外から見た形で示す → 仕様書。
- 決まった「どう実現するか」を、内部の構造と処理で示す → 設計書。
- 守るべき決まりや定義を示す → 規約。
- 作業の進め方（前提・手順・確認）を示す → 手順書。
- 入り口として全体像と他資料への案内を示す → 案内。
  README.md はここに入る。
- 進み具合を管理する → タスク。
- 未決定の事項とその結論を管理する → 課題管理。
- 生成AIに作業の前提とルールを渡す → AI向け指示。
- 動作を実装する → ソースコード。

1つのファイルに複数の目的を混ぜない。
混ざっていたら、種別ごとに、ファイルを分ける。

## 種別表

| 種別 | 目的 | 本文に書くもの | 本文に書かないもの | 改版履歴 |
| --- | --- | --- | --- | --- |
| 規約 | 決まったルールと定義を示す | 決まったルールと定義、理由 | 経緯、背景、時点を表す表現、未決定の事項 | 持つ |
| 仕様書 | 決まった「何をするか」を示す | 外から見た振る舞い（入力、出力、表示項目、APIの入出力など） | 経緯、背景、時点を表す表現、未決定の事項 | 持つ |
| 設計書 | 決まった「どう実現するか」を示す | 内部の構造と処理、理由 | 経緯、背景、時点を表す表現、未決定の事項、採らなかった案との比較 | 持つ |
| 手順書 | 作業の進め方を示す | 前提条件、手順、結果の確認方法 | 経緯、背景、未決定の事項 | 持たない |
| 案内 | 入り口として全体像を示す | 目的、全体像、各資料へのリンク | 経緯、背景、他の資料と重なる詳しい説明 | 持たない |
| タスク | 進み具合を管理する | 目的、背景、進み具合、いつ何が決まったか | 決まった内容の詳しい説明（規約・仕様書・設計書に書き、リンクで参照する） | 持たない |
| 課題管理 | 未決定の事項と、その結論を管理する | 課題、状態、決まった日付と結論 | 議論の過程 | 持たない |
| ソースコード | 動作を実装する | 今の動作を説明するコメント | 経緯、背景 | 持つ |
| AI向け指示 | 生成AIが作業するときの前提とルールを示す（`AGENTS.md`、`CLAUDE.md`、`SKILL.md`、`.claude/agents/` 配下のファイル） | AIが従うルールと作業の前提。理由は、AIがルールを正しく当てはめるのに必要な場合だけ1文で書く | 経緯、背景、時点を表す表現、未決定の事項、人向けの資料と重なる詳しい説明 | 持たない |

## 共通ルール

### 経緯・時点・未決定の事項

- 決まったことを示す種別（規約、仕様書、設計書、手順書、案内、ソースコード）では、経緯は改版履歴にだけ書き、本文には書かない。
  本文では、「現在」「この時点では」のような時点を表す表現を使わない。
  理由は、本文に経緯や時点が混ざると、どれが今の決定か読み手に分からなくなり、書いた時点から古くなるためである。
- 未決定の事項は、課題管理にだけ書く。
  規約、仕様書、設計書、手順書、案内には、未決定の事項や TODO を書かない。
- 未決定のために書けない節がある場合は、見出しを残し、未決定であることと、管理する場所（GitHub Issue など）へのリンクだけを書く。
  見出しを残すのは、書き忘れではなく未決定であることを、読み手が判断できるようにするためである。

### 理由の書き方（規約・設計書）

- ルールや構造だけでは「なぜそうするのか」が読み手に伝わらない場合に、理由を書く。
- 初めて読む人が理解し、判断できるように書く。
- 「どんな問題を避けるのか」または「何を実現するのか」を具体的に書く。
- 短くすることを目的にして、理由を曖昧にしない。

### 手順の書き方（手順書、作業の手順を含む AI向け指示）

- 手順として表せることは、番号付きの手順で書く。
  1つの番号には、1つの動作を書く（何を、どこで、どうするか）。
- 手順で表せることを、「〜してはならない」「〜に留意する」「〜に注意する」の形に省略しない。
  読み手が、代わりに何をすればよいか分からず、迷うためである。
  避けたいことがあるときは、それを避けられる手順（どうするか）に書き換え、避ける理由を手順の理由として添える。
  手順で表せないこと（判断の基準など）や、手順を行った結果を確かめる観点は、この形で書いてよい。
  例：×「ワークフローを変えたPRで確認しない」→ ○「1. ワークフローを main に反映する。2. 反映したあとに、確認用のPRを別に作る。」
- 手順で行う動作を、「補足」「注意」「※」として、手順の外に書かない。
  手順の中の、行う順番の位置に、番号付きの手順として入れる。
  手順の外にあると、読み手が、どの時点で行うのかを判断できず、行い忘れるためである。
- 条件によって動作が変わるときは、「〜の場合は、〜する」と、条件と動作を対にして書く。
- 各手順の後、または最後に、結果の確かめ方（何が見えれば成功か）を書く。

### 日付と TODO（タスク・課題管理）

- 決まったことには、必ず日付を書く。
  日付の形式は、プロジェクトの決まりに従う。
  （決まりが無ければ `YYYY/MM/DD`）
- 「現在」「最近」などの相対的な表現を使う場合は、日付を併記する。
- 課題管理では、議論の過程を残さず、「日付: 決まったこと」の形で結論だけを書く。
- 未対応・未確定の項目は、他の文と見分けがつく形で `TODO:` と明記する。
  書式は、プロジェクトの決まりに従う。
  （決まりが無ければ、太字の `**TODO:**`）

### AI向け指示

- 作業のたびに生成AIに読み込まれるので、短く保つ。
  内容が増えるほど、生成AIが作業に使える情報の量が減るためである。
- 変更の記録は、改版履歴ではなく、Git の履歴で追う。
- `SKILL.md` と `.claude/agents/` 配下のファイルは、先頭に YAML の設定を書く。
  設定より前にコメントを置くと、設定が正しく読み込まれなくなる。
- 必ず守らせたいことは、文ではなく、仕組み（フック・権限・CI など）で担保する。
  「重要」「絶対」などの強調語で、守らせようとしない。

### 共通の基本

- **コードを読めば分かることは、書かない。**
  書くのは、コードから分からないこと（決まり・環境・手順・理由）だけにする。
- 資料に無い決まりや事実を、推測で足さない。
  分からないことは、確認事項として挙げる。
- 同じことを、複数の文書に書かない。
  片方に書き、もう片方は、そこへ案内する。
- 詳しい決まりが別にあるときは、写さず、リンクにするのを基本とする。
  写すと、元が変わったときに、ずれる。
  ただし、エージェントが守らなかった決まりは、案内にせず、AGENTS.md に直接書く。
  （「AGENTS.md の書き方」の「守られなかったとき」）
- 開発が進むたびに直す記述（状況、個別名の列挙）を、決まったことを示す文書に入れない。
  直し忘れで古くなり、読み手が文書全体を信用しなくなる。

## README.md（案内）の書き方

README.md の読み手は、人間の開発者（初めて来た人を含む）である。

### 書くこと

- **概要**：何のためのものか、何を扱うか。
  最初に書く。
- **始め方**：前提（言語・ツール）、セットアップ、実行、テストの手順。
- **体系**：構成の型（どんな種類のものを、どこに置くか）。
- **環境情報**：環境変数、接続先、デプロイの方式。
  環境変数の一覧に正本（`.env.example` など）があるときは、名前を列挙せず、その場所を案内する。
  値の入手先や環境ごとの違いなど、正本から分からないことだけを書く。
- **相談先・担当**：変わりやすいときは、名簿などへ案内する。
- **案内**：詳しい決まりや設計書の場所。
  リンクは、相対リンクにする。

始めて使うのに必要な情報だけを書く。
長くなる詳細は、別の文書に置いて、案内する。

### 書かないこと

- 個別のコード・ファイル・部品の一覧と説明。
- 開発の状況。
  （「まだ〜がない」「現在は〜だけ対応」）
- 規約の写し。
- 経緯。

### ディレクトリ構成の書き方

- ツリーにして、ディレクトリの横に、概要を書く。
- ツリーには、個別の名前の代わりに、`<番号>_<内容>/` のように、名前の決まり（型）を書く。
- ファイルは、体系に関わるもの（設定ファイルなど）だけを書く。
  コードのファイルは、列挙しない。
- 表は、使い分けが分かりにくいところだけに使う。

### 親子の README

- 子の README は、親の README に書くと複雑になるときだけ作る。
- 子を作るときは、親は案内だけ、子が詳細を持つ。
- 詳細が規約にすでに書いてあるなら、子の README は、要約ではなく、規約への案内にする。

## AGENTS.md（AI向け指示）の書き方

AGENTS.md の読み手は、AI エージェントである。

### 書くこと

- **実行するコマンド**：ビルド・テスト・整形など。
  オプションまで書き、早い位置に置く。
  README にあるコマンドは繰り返さず、README へ案内する。
- **守る規約**：具体的で、検証できる文にする。
  規約の本文は規約に置き、AGENTS.md には、どの作業のときに、どの規約を読むかを書く。
  規約と同じ文を、AGENTS.md に書き写さないのが基本である。
  規約が変わると、ずれる。
  例外は、エージェントが守らなかった決まりである。
  「〇〇の規約を見る」という案内では、読まれず、守られない。
  AGENTS.md に、「必ず〜する」と、決まりそのものを直接書く。
- **規約・文書への案内は、ファイル名と、見出しの名前で書く。**
  章の番号は、文書の構成が変わるとずれる。
  番号を書くときは、書く前に、実際の見出しを確かめる。
  案内先の文書に、その決まりが書いてあるかも、確かめる。
  無ければ、先に案内先の文書に書く。
- **境界**：常にやること／先に確認すること／絶対にやらないこと、を分けて書く。
- **コードから分からない注意点**：読む順番、よくある間違い、環境の癖。
- サブディレクトリの AGENTS.md は、上位と重複しない、そのディレクトリ固有の内容だけを書く。

### 上位と下位に分けるとき（間違えやすい点）

全体で決めるものは上位、そのディレクトリ固有のものは下位に書く。
この分け方は、エージェントも知っている。
間違えやすいのは、次の点である。

| 間違い | 正しい扱い |
| --- | --- |
| 念のため、同じ決まりを、上位と下位の両方に書く | どちらか一方にだけ書く。全体で守らせるものは上位、そのディレクトリだけのものは下位 |
| 全体で守らせたい決まりを、下位に書く（下位は、そのディレクトリで作業するときにしか効かない） | 上位に書く |
| 下位固有の内容を、上位に書く（全員の作業で、毎回、注意を使う） | 下位に書く |
| 守られなかったとき、その場所に近い下位に足す。または、「〇〇の文書を見る」という案内を足す | 「保ち方」の「守られなかったとき」で、上位か下位かを決め、決まりそのものを直接書く |

### 書かないこと

- フォルダ・ファイルの配置と役割の説明、概要・体系の説明。
  （README にあるなら、案内する）
- 開発の状況、個別の作業の経緯。

### 保ち方

- 目安は、1ファイル 200行未満。
  長い手順や、一部のコードにだけ関係する内容は、スキル、サブディレクトリの AGENTS.md、規約へ移す。
- **守られなかったとき。**
  決まりが文書にあっても、守られないことがある。
  そのときは、次の順に考える。
  1. その決まりは、全体で守らせたいものか、特定のディレクトリ固有のものか。
     全体なら上位の AGENTS.md に、固有なら、そのディレクトリの AGENTS.md に書く。
     （同じことを、両方に書かない）
  2. 「〇〇の文書を見る」という案内にしない。
     「必ず〜する」「〜してはいけない」と、決まりそのものを直接書く。
     詳しい手順や根拠は、文書に置き、案内を添える。
  3. 案内先の文書に、その決まりが無ければ、文書にも書く。
  4. 文だけで足りないときは、仕組み（フック・権限・CI など）で担保できないかを考える。
- 上位の AGENTS.md と矛盾させない。
  階層にある複数の AGENTS.md は、近いものが優先されるツールと、全部が足し合わされるツールがある。
- 最初は小さく始め、エージェントが間違えたときに、その間違いを防ぐ1行を足す。
  効かなくなったもの、古くなったものは、削る。
- AGENTS.md だけを管理する。
  別名のファイルが必要なツールを使うときだけ、AGENTS.md を取り込む形にする。

## 点検

次の問いで点検する。

1. 種別は正しいか。
   種別が混ざっていないか。
2. 「本文に書かないもの」に当たる記述（経緯、時点表現、未決定の事項）が、本文に入っていないか。
3. 開発が進むたびに直す記述（状況、個別名、ファイルの列挙）が、入っていないか。
4. コードを読めば分かることを、書いていないか。
5. 存在しない名前（フォルダ・ファイル・部品）を書いていないか。
6. 規約や設計書の内容を、写していないか。
7. 規約・設計書の理由は、初めて読む人に、何を避け、何を実現するかが伝わるか。
8. README と AGENTS.md で、同じことを書いていないか。
   （特に、コマンド）
9. 子の README は、本当に必要か。
   AGENTS.md は、具体的で検証できる文か。
   長すぎないか。
   上位と矛盾していないか。
10. 改版履歴を持つ種別に、プロジェクトの書式で改版履歴があるか。
    持たない種別に、改版履歴を書いていないか。
11. リンク先は存在するか。
12. 上位と下位に、同じ決まりを書いていないか。
    全体で守らせる決まりが下位に、下位固有の内容が上位に、入っていないか。
13. 案内先の文書に、その決まりは、実際に書いてあるか。
    案内に書いた見出しは、実在するか。
14. 規約と同じ文を写している箇所は、守られなかった決まりを、直接書いたものか。
    （そうでなければ、案内にする）
15. 手順として表せることが、手順として書かれているか。
    手順で表せる動作が、「〜してはならない」「〜に留意する」の形や、「補足」「注意」として、手順の外に省略されていないか。

点検の結果は、**箇所・理由・案**の表で報告する。
点検だけを頼まれたときは、直さない。

### 頼まれた範囲の外にも、同じ問題があるとき（水平展開）

頼まれた範囲の外に、同じ問題を見つけたときは、見つけたことを報告する。
直すのは、ユーザーの同意を得てからにする。

- 範囲外の箇所は、「箇所・理由・案」の表にまとめる。
- 同意は、**3件ずつ**取る。
  似た問題は1件にまとめ、1回の確認で、3件を超えて聞かない。
  件数が多いときは、同意を得た3件を直したあとで、次の3件を聞く。
- 同意が得られた箇所だけを直す。
  得られなかった箇所は、直さず、報告だけに残す。
