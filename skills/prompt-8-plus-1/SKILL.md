# Prompt 8+1

目的と実行結果から課題を診断し、8+1の公式に沿ってプロンプトを設計または改善する。
詳細は [references/prompt-8-plus-1.md](references/prompt-8-plus-1.md) を読む。

## Workflow

1. ユーザーの目的、入力、想定読者、出力先、制約、成功条件を整理する。
不足があり、合理的に補えない場合だけ確認する。
既存プロンプトの改善では、対象の利用場面と修正範囲を確認する。
異なる利用場面で共通化された記述は、その場面で取得できる情報と実際の処理に合うか点検する。
2. 既存プロンプトの改善では、利用可能な実行時の入力・プロンプト・出力と、後続処理の結果を突き合わせる。
[問題の診断と結果の検証](references/prompt-8-plus-1.md#問題の診断と結果の検証)に従い、観測された問題と原因の仮説を分ける。
指示不足と決めつけず、入力、ツール、設定、実装、後続処理の問題も切り分ける。
実行記録がない場合は、文面から分かる課題と実行しなければ分からない課題を区別して進める。
3. 参照資料の8項目を順に検討する。
項目が不要な場合は、プロンプトを冗長にしないため省略する。
各項目を、対象・行動・判断基準・出力の観点で具体化する。
曖昧な名詞や弱い動詞を、対象と操作が分かる表現へ置き換える。
追記を既定の解決策にせず、削除、置き換え、矛盾の解消、前後工程との役割整理から適切な方法を選ぶ。
各変更がどの問題をどう改善するか説明できない場合は、要求を増やさない。
4. 出力形式と出力フォーマットを分ける。
形式では必須項目、空値、制約を定義し、フォーマットでは最小の有効例を示す。
5. 追加指示を最後に検討する。
禁止事項、優先順位、不確実性の扱い、根拠提示、ツール利用条件など、品質または安全性に必要なものだけを追加する。
既存の該当箇所を書き直して解決できる問題は、末尾への注意書き追加で重複させない。
6. [実行するAIへの指示としての点検](references/prompt-8-plus-1.md#実行するaiへの指示としての点検)を行い、各記述がAIの行動・判断・出力・入力の解釈に必要か確認する。
作成依頼者向けの説明はプロンプト外へ移し、完成したプロンプトをMarkdownで提示する。
ユーザーが段階的な検討を求めた場合は、次の項目へ進む前に合意を得る。
7. 修正内容に応じて、形式の整合性と目的達成の両方を検証する。
実行できる場合は代表的な入力で変更前後を比較し、改善と副作用を確認する。
実行権限・費用・環境の制約がある場合は、未検証事項と確認方法を示し、文面の修正だけで効果を断定しない。

## Output Rules

- ユーザー指定の見出し名、用語、データモデルを優先する。
- 入力の説明には意味と判断での用途を記載する。解釈に影響する取得元・時点・取得条件・確認範囲・欠損の意味も必要に応じて示し、限定的な参考情報を確定・網羅的な情報として扱わせない。
- 入力の制約や禁止事項だけで説明を終えず、何の判断にどう使うための情報かを明示する。取得経緯が不明な場合は、説明を補うために推測しない。
- 判断基準を変える依頼か、結果の説明を充実させる依頼かを区別する。
  説明の改善では、既存の出力項目に何を根拠として記載するかを定義し、採否条件を無断で追加しない。
- 事実、推論、不確実性の区別が必要な用途では、出力先の既存フィールドに収まる表現を設計する。
- JSONやスキーマを使う場合は、プロンプトの必須項目、空値の扱い、例がスキーマと矛盾しないことを確認する。
- 件数の上限・目標・必須件数と、探索範囲・終了条件を区別する。出力件数だけで探索の十分さや品質を判定せず、件数を埋めるために根拠の薄い結果を増やさない。
- Web検索を指示する場合は、検索目的、利用条件、保存または出力すべき参照情報を明記する。
- 追加の要求がない限り、不要な役割設定、重複した制約、長い説明を増やさない。
