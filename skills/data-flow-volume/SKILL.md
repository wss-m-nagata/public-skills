# DFD・データ量の見積もり

処理フロー・DB設計・インターフェース設計の結果を材料に、
**データがどこから入り、どこへ出ていき、どれくらい溜まり、いつ消えるか**を1冊のExcelにまとめるスキル。

## このスキルが担う工程

| 順番 | 工程 | このスキルとの関係 |
| ---- | ---- | ---- |
| 1 | 業務処理フローを決め、何を作るかを洗い出す | 材料として読む |
| 2 | DB設計・インターフェース設計・画面設計をする | 材料として読む |
| 3 | **1.・2.の結果から、データの流れと量を見積もる** | **このスキル** |

このスキルは設計をしない。
設計書に無いことが見つかったら、自分で埋めずに「打合せで決めたいこと」に回す。
見積もりの役目は、設計がデータの規模と寿命を踏まえているかを関係者と確かめることであり、
見積もる側が勝手に埋めると、その確認の機会がなくなるためである。

## 読み手を前提にする

読み手は管理者や他社の担当者で、長い文章は読まれない。
Markdownや文章の報告ではなく、**図と表のExcel**にする。
1枚目（DFDシート）の要点の欄と図を見ただけで、規模と流れが分かるようにする。
詳しい根拠は2枚目以降に回し、疑問を持った人が自分で確かめられるようにする。

## 成果物

データ定義（YAML）1つから、スクリプトで次の2つを生成する。

- `<対象>_データ量・DFD.xlsx`：以下の4シート
  | シート | 中身 |
  | ---- | ---- |
  | DFD | 要点の数字を横に並べた欄、凡例、DFDの図 |
  | テーブル別データ量 | テーブルごとの、データが入るきっかけ・使われる画面・1回あたり/1年あたりの件数・更新・保持・削除のきっかけ |
  | 前提 | 見積もりの前提と、その出典 |
  | 打合せで決めたいこと | 論点、案、決まらないと何に影響するか |
- `<対象>_DFD.png`：DFDの図（Excelに貼るもの）

**内容はYAMLが正であり、Excelを直接編集しない。**
Excelは人が直接直すことがあるので、そのときは手順7で取り込む。
取り込まずに作り直すと、人が直した内容が黙って消えてしまう。

## 進め方

### 手順1　担当範囲を決める

最初に、**自分が見積もる範囲（どのサブシステム・スキーマのテーブルか）**をユーザーに確かめる。
複数の組織やチームで開発していると、テーブルごとに担当が分かれていることが多い。
範囲外のテーブルまで見積もると、他の担当者の領分に踏み込むうえ、確かめようのない数字が混ざる。
範囲外のシステムや画面は、DFDでは「データの出どころ」「表示・出力先」の側に置き、件数は数えない。

プロジェクトに固有ルールの置き場所の決まり（例：`.agents/state/data-flow-volume/rules/`）があれば、先にそこを読む。
資料の置き場所・共通の前提・画面名の一覧が書かれていれば、聞き直さずに済む。
一度確かめたことは、そこへ書き残しておくと次回に使える。

### 手順2　材料を集める

| 知りたいこと | 主な資料 |
| ---- | ---- |
| データが作られるきっかけ | 処理フロー図、処理の設計書 |
| 対象のテーブル、1件の大きさ | テーブル定義書 |
| 登録される画面・表示される画面・CSV、表示件数、ボタンを押せる人 | 画面設計書、インターフェース設計書 |
| 頻度、保持期間、性能要件 | 要件定義書 |
| 業務側の要望（保管の希望、使い方） | 要件整理の資料、打合せの記録、レビューの記録 |
| 資料に無い数字（対象人数など） | ユーザーに聞く |

**1つの値について、要件定義書だけでなく、業務側の要望やレビューの記録も当たる。**
要件定義書は合意した最低限を書くことが多く、業務側はそれより長い保管や別の使い方を望んでいることがある。
資料によって値が違うときは、どちらかに決めず、差を「打合せで決めたいこと」に出す。

### 手順3　件数を見積もる

- 件数は「人数×頻度」のように前提から計算する。前提の無い数字は置かない。
  根拠の無い数字は、打合せの場で一度疑われると資料全体が信用されなくなる。
- **利用の頻度（誰が・いつ・何回使うか）は、システムの作りから推測しない。業務側に確かめる。**
  たとえば「CSV出力ボタンがある」ことから「依頼のたびに出力される」とは決められない。
  業務側は「締めのあとに月1回だけ取る」と決めていることがある。
- 数えられないもの（運用が決まっていない評価ボタンなど）は、「最大○件」と根拠のある上限で書き、運用が未定であることを添える。
  「押された分」「依頼の回数分」のような書き方では、規模が読み取れない。
- 画面に関わる件数は、利用者が実際に目にする仕様（画面設計書の表示件数など）から取る。
  インターフェースが受け付ける上限の値とは別物なので、取り違えない。

### 手順4　データ定義（YAML）を書く

`assets/template/data_flow_volume.yaml` を成果物のフォルダへコピーし、書き換える。
各項目の書き方は、テンプレートのコメントにある。
図の座標は人が調整する前提で、YAMLに持たせる。
自動で配置する仕組み（mermaid等）は、要素が増えると並び順を制御できず読みにくくなるため使わない。

### 手順5　生成して目視する

```
python ./skills/data-flow-volume/scripts/build_data_flow_volume.py build <データ定義.yaml>
python ./skills/data-flow-volume/scripts/build_data_flow_volume.py preview <生成したExcel> <PDFの出力フォルダ>
```

スクリプトのパスは、このスキルを置いた場所に合わせて読み替える。
PNGを開いて、線の交差や文言の重なりが無いかを確かめる。
PDFを開いて、はみ出しや印刷時のページ分かれが無いかを確かめる。
行の高さは文字量から自動で決まるので、手で調整しない。
preview はExcelかLibreOfficeが要るので、どちらも無ければPNGの確認だけ行い、その旨を報告する。

### 手順6　見直す

渡す前に、読み手の立場で次を確かめる。

- 要点の欄の数字と、図・表の数字が一致しているか（要点で「3テーブル」と書いたら、図にも3つ出てくるか）。
- 要点の見出しだけで、何を数えた数字かが分かるか。
- 意味を持たせた色・形のすべてに、そのそばで凡例が付いているか（「色と凡例」を参照）。
- 各テーブルについて、作成・更新・保持・削除のどこかが空いていないか。空いているなら、それは論点である。

### 手順7　Excelが直接編集されたら取り込む

YAMLから作り直したExcelと、編集されたExcelを比べる。

```
python ./skills/data-flow-volume/scripts/build_data_flow_volume.py diff <作り直したExcel> <編集されたExcel>
```

出てきた差分をYAMLへ反映し、もう一度 build して、diff の差が無くなったことを確かめる。

### 手順8　報告する

修正を報告するときは、**どこを直したかを場所で書く**。
diff の結果（シート名!セル番地）をもとに、「シート・場所／修正前／修正後」の表にする。
図は「② 保存する の処理」「判定結果 の円柱」「○○→○○ の矢印の文言」のように、要素の名前で示す。
「○○を直しました」だけでは、読み手は直した場所を探すところから始めることになる。

## 図（DFD）で守ること

- **純粋なDFDにする。** どこから取得してどこへ出力するかだけを描く。
  処理の手順や分岐は処理フロー図の役目であり、DFDに入れると流れと量が読み取りにくくなる。
- **データは左から右へ流す。** 列は「データの出どころ → 処理 → テーブル → 表示・出力の処理 → 表示・出力先」とする。
  出力の依頼のような「要求」の線は描かない。データの流れではないうえ、右から左の線が増えて読みにくくなるためである。
  画面からの入力（評価の登録など）や、設定を読む破線のように、データの流れとして必要な右から左の線は例外として残してよい。
- **画面は画面ID付きの名前で1画面ずつ描く。** 複数の画面を1つの枠にまとめない。
  読み手は実物の画面を思い浮かべて図を読むので、どの画面か特定できないと流れを追えない。
  利用者の役割名は、画面を特定するのに役立つときだけ書く。
- **ファイルなどの出力は、どの画面で受け取るかまで描く。** 出力が宙に浮いていると、誰がどこで使うのかが伝わらない。

## 色と凡例

- **色や形に意味を持たせたら、それを使っている場所のすぐそばに凡例を置く。**
  凡例が無いと、読み手は色の意味を推測するしかない。
  凡例を別のシートにまとめると、読み手は今見ているシートしか見ないので気づかれない。
- スクリプトは、次の凡例を自動で作る。
  - DFDの図：図の上端に、図で実際に使っている形（画面・処理・テーブルなど）と線の種類だけを、色の見本つきで並べる。
    使っていない種類まで載せると、読み手がそれを図の中で探してしまうためである。
    説明の文言を変えたいときは、YAMLの `legend_labels` で上書きする。
  - 表：行を分類ごとに塗り分けたとき（`category_fill`）と合計行があるときに、表のすぐ上へ色の見本つきで並べる。
- 見出しの青や要点の欄の緑のような、意味を持たない飾りの色は凡例に載せない。
  載せると、飾りにも意味があるのかと読み手を迷わせる。
- 新しく色で意味を表したくなったら、凡例を作る仕組みも一緒に足す。凡例の無い色は使わない。

## 表で守ること

- **決まっていないことは「TODO」と書かない。** 見積もった側の作業が残っているように見えるためである。
  「打合せで決めたいこと」シートに、論点・案・決まらないと何に影響するか、の3列で書く。
  案は、要件や設計に根拠があるものだけにする。根拠が無ければ「ご意向を伺いたい」とする。
  問いだけを並べるより、案と影響を添えたほうが、打合せの場で決まりやすい。
- **出典は省略しない。** ファイルのフルパス（ファイルサーバーならUNCパス）、シート名、行番号・項番まで書く。
  「これは本当か」と思った人が、自分で元の資料を開いて確かめられるようにするためである。
  ファイルの無いものは「○○ヒアリング（○○ミーティングでの回答）」「氏名の見込み（YYYY-MM-DD時点）」のように、誰から出た情報かが分かる書き方にする。
