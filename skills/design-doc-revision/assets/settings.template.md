# design-doc-revision の設定

このファイルは、`design-doc-revision` スキルが読む設定である。  
初回に、プロジェクトから読み取った内容と、質問の回答を保存したもので、以後の実行では、質問せずに、これを使う。  
**規約・運用手順の中身は、書かない。** 設計書の置き方や手順を決めた文書の「場所」だけを書く（中身は、実行のたびに、その場所から読む）。  
内容を変えたいときは、「設定を見直したい」と伝えるか、このファイルを直接直す。  

記入日：<YYYY-MM-DD>  

## 場所と名前（スクリプトが読む）

スクリプトは、次の表の「項目」と「値」を読む。  
項目の名前は、変えない。  
値の前後のバッククォートは、読むときに取り除かれる。  
`<…>` のままの値があると、スクリプトは止まる（未記入のため）。  

| 項目 | 値 |
|---|---|
| 設計書のルート | `<例：<共有フォルダ>\<設計書のルート>>` |
| 正本の場所 | `<例：<正本のフォルダ>（設計書のルートからの相対パス）>` |
| レビュー用の置き場の場所 | `<例：<レビュー用のフォルダ>（設計書のルートからの相対パス。案件ごとのフォルダの親）>` |
| 手元の作業フォルダ | `.agents/state/design-doc-revision` |
| 取得の記録ファイル名 | `取得の記録.json` |
| 構造を保つフォルダ | `なし` |
| レビュー担当者の呼び名 | `外部のレビュー担当者` |

- 「手元の作業フォルダ」は、プロジェクトルートからの相対パスである。案件ごとに、その下に `<案件名>/` を作り、これを案件の作業フォルダとする。作業フォルダの中は、レビュー用の置き場の `<案件名>` フォルダと、同じ構成（同じ相対位置）にする。  
- 「構造を保つフォルダ」は、正本の直下のフォルダ名を、カンマ区切りで書く。ここに書いたフォルダの下は、作業フォルダでも同じ構成で置く。それ以外は、作業フォルダの直下に、ファイル名だけで置く。`なし` のときは、すべて同じ構成で置く。  
- 手元の作業フォルダは、使い捨てである。Git に入れない（`.gitignore` に `/.agents/state/design-doc-revision` を書く）。  

## 段階（区分）ごとの対応（任意）

設計書の置き場が、段階（区分）ごとに分かれていて、区分によって、レビュー用の置き場と反映先が変わるときだけ書く。  
区分を使わないとき（反映先が1つのとき）は、「なし」と書く。  

`<なし>`  

| 区分 | レビュー用の置き場の親フォルダ（設計書のルートからの相対パス） | 合意後の反映先（設計書のルートからの相対パス） | 備考 |
|---|---|---|---|
| `<例：区分A>` | `<例：<レビュー用フォルダ>/<区分Aのフォルダ>>` | `<例：<正本のフォルダ>、<区分Aの正本のフォルダ>>` | `<例：どのファイルをどちらへ反映するか>` |

- 区分があるときは、仕様 JSON に `server_root`（置き場の親フォルダ）と、反映の各件の `root`（反映先）を書く。  

## 設計書の種類ごとの使うスキル

設計書を直す作業は、種類ごとに、次のスキルに任せる。  
別のものを使うときは、この表を直す。  

| 設計書の種類 | 使うスキル |
|---|---|
| Excel の設計書（版を上げる・変更履歴・赤字の決まりを含む） | `nablarch-basic-design-excel`（`scripts/revise_workbook.py`） |
| 処理フロー図（`.drawio`） | `process-flow-diagram` |
| 機能別 ER 図 | `feature-er-diagram-drawio` |

## 読む文書（ハーネス）

設計書の置き方、レビューの進め方、書き方を決めた、プロジェクトの文書の場所である。  
**中身は写さない。** 実行のたびに、場所から読む。  
「前回読んだ時点の最終更新」は、実行のたびに、スキルが書き戻す。  

| 文書 | 場所 | 前回読んだ時点の最終更新 |
|---|---|---|
| `<例：共通の指示書>` | `<例：AGENTS.md>` | `<例：a1b2c3d（YYYY-MM-DD）>` |
| `<例：設計書の置き方・運用の文書>` | `<例：<ファイルサーバー側の README のパス>>` | `<例：更新日時>` |

## 設計書を直したあとの進め方

設計書を直したあとの、実装・試験などの進め方を決めた、ハーネスの手順書の場所を書く。  
報告のときに、その手順を読んで、ユーザーに案内する。  

`<既定：なし（案内しない）>`  

## 変更履歴に必ず書く記載

運用で決まった記載（例：対応した区分を示す語）が、変更履歴に要るときだけ書く。  
改版では、仕様 JSON（`revise_workbook.py`）の `history.summary` の頭に書く。  
新規の版では、電文定義 JSON の `history_summary` に書く。  
後から足すと、全ファイルの再生成が要るため、最初に書く。  

`<既定：なし>`
