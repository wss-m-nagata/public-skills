# design-doc-revision

共有の場所（ファイルサーバーなど）の設計書を直す作業は、毎回、同じ流れになる。  
このスキルは、その流れと、繰り返し作る資料（変更箇所一覧・確認資料・アップロードのスクリプト）の作り方をまとめたものである。  

流れは、次のとおり。  
修正対象の確認 → 作業フォルダ作成 → 正本から取得（読み取りのみ）→ 設計書を直す → 変更箇所一覧を作る → 確認資料を作る → 上げる・反映するスクリプトを作る → 見た目と整合の確認 → 報告。  

**場所・名前・運用の決まりは、スキルに書かない。** 設定ファイルに持つ。  
**運用手順の中身は、設定に写さない。** 設定には、手順書の「場所」だけを持ち、中身は、毎回、その場所から読む。  

## 守ること

- **ファイルサーバーのファイルは、直接直さない。** 読み取って手元に写し、手元で直す。サーバーへ上げるのは、ユーザーである（このスキルが作るスクリプトを、ユーザーが実行する）。  
  - サーバーを書き換える操作は、取り消しにくく、他の人の作業と衝突しうるため。  
- 設計書の正は、正本である。レビュー用の置き場は、レビューのための置き場で、正ではない。  
- 作業の前後で、サーバーの版が変わっていないかを確かめる（取得時の SHA-256 を記録し、反映スクリプトが突き合わせる）。  
- **サーバーの共有文書（README・設計書など）を直すときは、サーバーの現在の版を土台にする。** 取得した時点の手元の写しが古いと、そのまま上げたときに、他の人の更新が消える。書き込む直前に、サーバーの版が、土台にした版と同じことを、ハッシュ値でもう一度確かめる。更新前の版は、バックアップとして残す。  
- 変更履歴に、運用で決まった記載が要るとき（設定の「変更履歴に必ず書く記載」）は、改版では、仕様JSONの `history.summary` の頭に書く。新規の版は、外部インタフェース設計書なら電文定義JSONの `history_summary` に書く。後から足すと、全ファイルの再生成が要る。  
- **変更箇所一覧と確認資料（手順5・6）を作るまで、ユーザーにも、ほかの人にも、レビュー・確認を依頼しない。**  
  設計書だけを直した段階で、「直しました。確認してください」と報告しない。手順5・6まで進めてから、手順9で報告する。  
  - レビューする人は、何が変わったか（変更箇所一覧）と、何を判断するか（確認資料）を、この2つの資料で把握するため。  
  - 確認資料は、設定の「確認資料の要否の基準」に従う。既定では、相手に判断・対応してもらうこと（要確認の行）が1つも無いときだけ、作らなくてよい。変更箇所一覧は、必ず作る。  
- レビュー担当者への連絡（チャットなど）は、ユーザーの明示の指示があるときだけ行う。文面を作るときは、`references/message.md` に従う（資料に書いてあることは、メッセージに書き写さず、資料を見てもらう）。  
- 作業が終わったら、した内容と、確認してほしい点を報告する。  
- **スクリプト（アップロード・反映）は、作るだけで、実行しない。** 実行は、ユーザーが行う（ドライラン → 確認 → 実行）。  
- ファイルサーバーの中は、取得のために**読む**だけにする。実在の場所への書き込みは、行わない。  

## 0. 設定ファイルを確かめる（毎回、最初に行う）

設定ファイルは `.agents/config/design-doc-revision/settings.md`（プロジェクトルート直下）である。  
**スキル自身のディレクトリの中には、設定も作業ファイルも作らない。**（スキルを更新すると、上書きされるため）  

| 状態 | すること |
|---|---|
| 設定ファイルが無い | [references/interview.md](references/interview.md) に従う。プロジェクトのハーネスから読み取れるものは、自分で調べて確定する。読み取れないものだけを質問する。結果は [assets/settings.template.md](assets/settings.template.md) の形で保存し、内容をユーザーに見せて、確認を取る。そのあと、手順1へ進む |
| 設定ファイルがある | 質問せずに、その内容を使う。下の「ハーネスの文書の確認」を行ってから、手順1へ進む |
| 「設定を見直したい」と言われた | interview.md の質問をやり直し、変わった項目だけを、設定ファイルに反映する |

- 設定ファイルは、チームで共有する（Git に入れる）ものである。保存したら、Git に入れるかどうかを、ユーザーに確かめる。  
- 設定の `| 項目 | 値 |` の表（場所と名前）は、スクリプトが読む（`scripts/common.py` の `read_settings()`）。項目の名前は変えない。  
- 手元の作業フォルダ（既定：`.agents/state/design-doc-revision/<案件名>/`）は、使い捨ての作業用ファイル（取得した設計書の写し・取得の記録・変更箇所一覧・確認資料・作ったスクリプト・バックアップ）の置き場である。Git に入れない。`.gitignore` に `/.agents/state/design-doc-revision` が無ければ、書くことをユーザーに提案する。  
- 設定ファイルに書いてある内容と、実際のプロジェクトが食い違ったとき（場所がつながらない、フォルダが無い、など）は、自分で直さずに、食い違いをユーザーに伝える。  

### ハーネスの文書の確認（設定ファイルがあるとき、毎回）

設定の「読む文書（ハーネス）」の表にある文書を、実際に読む（読んだ内容を、以降の手順で使う）。  
前回読んだ時点の最終更新（コミットID。リポジトリの外にある文書は、更新日時）と比べる。  

```bash
git log -1 --format=%h -- <文書のパス>   # 文書の最終更新のコミットID
```

- **変わっていた文書があるとき：**「運用の文書が前回から変わっています：<文書名>」と、1行で知らせる。質問はせずに、変わった内容で、このあとの手順を行う。  
- **文書が見つからないとき：**どこに移ったかを、ユーザーに聞き、設定に反映する。  
- 実行が終わったら、読んだ時点の最終更新を、設定に書き戻す（書き戻したことを報告に1行で添える）。  
- 設定の「追加の項目」は、手順の該当する箇所で、必ず読み、従う。  

## 1. 修正対象を確かめる

課題の本文の作業項目、またはコメントに、修正対象（ファイル・シート・項目）の洗い出しがあれば、それを正とする。自分で、広く探し直さない。  
無ければ、ユーザーに、対象を確かめる。  

このスキルが扱うのは、共有の場所の設計書だけである。  
コードと、設計書の外にあるテスト仕様書などは、このスキルでは直さない。  

設計書を直したあとの進め方（実装・試験など）は、設定の「設計書を直したあとの進め方」に書いた手順書に従う。  
手順書を読み、手順9の報告のときに、ユーザーに案内する。設定が「なし」なら、案内しない。  

## 2. 作業フォルダを作る

**作る前に、ユーザーに確かめる。** ① レビュー用の置き場の場所（前例があるときは、前例と違う点を、はっきり示す）。② 手元の作業フォルダは、置き場の案件のフォルダと、同じ構成にする。③ 合意後の反映先。確かめないまま、フォルダを作らない（作り直しは、ローカルとサーバーの両方に及ぶ）。  

設定の「段階（区分）ごとの対応」があるときは、直す設計書がどの区分のものかで、置き場と反映先が変わる。流れは、どの区分でも同じである（置き場に上げる → レビュー担当者がレビューする → 合意後に、正本へ反映する）。  
区分を使うときは、変更箇所一覧・確認資料・アップロードのスクリプトの仕様JSONに、`"server_root"`（区分の置き場の親フォルダ）を書く。`folder_name` は、案件のフォルダ名にする。  
このとき、`fetch_from_source.py`・`check_server_unchanged.py` は、設定の「正本の場所」だけを想定している。ほかの反映先は、元にしたファイルを `nablarch-basic-design-excel` の `scripts/track_sources.py` で記録し、反映のスクリプトは、`reflect` の `root` と `base_file` で作る（手順7）。  

`<手元の作業フォルダ>/<案件名>/` を作る。直下に `README.md` を置く。書き方は [references/readme-template.md](references/readme-template.md)。同じ場所にある、過去の案件の README も参考にする。  

## 3. 正本から取得する

```bash
python <スキル>/scripts/fetch_from_source.py --folder <作業フォルダ> "<正本の中の相対パス>"...
```

- `<スキル>` は、このスキルのディレクトリである。  
- 読み取りだけ。手元にすでに同じ名前があれば、止まる（直した内容を消さないため）。  
- 取得した時点の最終更新日時と SHA-256 を、取得の記録ファイル（既定：`取得の記録.json`）に残す。READMEの配置表に貼れる行も出る。  
- 設定ファイルは、作業フォルダから親へたどって探す。見つからないときは、環境変数 `DESIGN_DOC_REVISION_SETTINGS` で、設定ファイルのパスを指定する。  

## 4. 設計書を直す

種類ごとに、設定の「設計書の種類ごとの使うスキル」の表にあるスキルを使う（既定は次のとおり）。  

| 直すもの | 使うスキル |
|---|---|
| Excel の設計書 | `nablarch-basic-design-excel`（版を上げる・変更履歴・赤字の決まりを含む） |
| 処理フロー図（`.drawio`） | `process-flow-diagram`（既にある図の直し方に従う） |
| 機能別ER図 | `feature-er-diagram-drawio` |

- **既存の Excel の版を上げるときは、`revise_workbook.py` で一度に行う。** 値の反映・行の追加・行の高さ・赤字・変更履歴・構造の検証を、仕様 JSON 1つで流す（`nablarch-basic-design-excel/scripts/`）。  
  仕様 JSON は、`nablarch-basic-design-excel/assets/examples/revise_spec.example.json` を参照する。変更の中身は、`mapping`（書く値）と `groups`（変更のまとまり）に書く。  
  どの `groups` にも属さない変更があれば、書き漏れとして止まる。  
  ```bash
  python <スキルの置き場>/nablarch-basic-design-excel/scripts/revise_workbook.py <仕様JSON>
  ```
  source は変えないため、仕様 JSON を直して、何度でも流し直せる。  
- 直したセルは赤字にし、前の版の赤字は黒に戻す。表紙の版数と変更履歴の行も更新する。（`revise_workbook.py` が行う）  
- 変更履歴の古い行に、決めた日や課題番号が書かれていても、勝手に書き直さない（合意済みの履歴のため）。書き直すかは、ユーザーに確かめる。  
- 直したあとは、全シートを画像にして、見た目を確かめる（`nablarch-basic-design-excel/scripts/preview_workbook.py <xlsx> <出力フォルダ>`。Windows と Excel が必要）。1シートだけなら、`export_sheet_preview.py`。  
- 補足のシートを足すときは、同じ案件の既存の設計書にある補足シートを見本にして、書式と、目次・本体の参照も合わせる。  
- 外部インタフェース設計書の「目的・概要」には、仕様だけを書く。仕様どおりに出したデータを、誰が・何に使うか（取り込み先など）は、仕様の範囲外のため書かない。  

## 5. 変更箇所一覧を作る

**設計書を直したら、必ず作る。** 作るまで、レビューを依頼しない（「守ること」）。  
直した設計書は、すべて載せる（処理フロー図のメモ1行の修正も、載せる）。  

Excel の設計書は、`revise_workbook.py` の仕様 JSON の `groups` から、行を下書きできる（同じ変更を、何度も書かない）。  
メタ JSON（`assets/examples/change_list_meta.example.json`）に、件名・要約・要確認の説明・対象ファイル・Excel 以外（図など）の行を書き、下書きする。  

```bash
python <スキル>/scripts/draft_change_list.py <メタJSON> <変更箇所一覧の仕様JSON>
```

できた JSON を、確かめて、直してから、下の `build_change_list.py` に渡す。表紙の版数と変更履歴の行は、自動で足される。  
下書きを使わず、仕様 JSON（`assets/examples/change_list.example.json`）を手で書いてもよい。  

確認先の呼び名は、既定では設定の「レビュー担当者の呼び名」である。変えるときは、仕様 JSON に `"recipient": "<呼び名>"` と書く。  

```bash
python <スキル>/scripts/build_change_list.py <仕様JSON> "<作業フォルダ>/変更履歴/変更箇所一覧_YYYY-MM-DD_<件名>.xlsx"
```

要確認の行が上に集まる。決まりは [references/change-list.md](references/change-list.md)。  

## 6. 確認資料を作る

相手に判断・対応してもらうこと（変更箇所一覧の「要確認」の行）があるときは、必ず作る（設定の「確認資料の要否の基準」に従う）。作るまで、レビューを依頼しない（「守ること」）。  
確認先が既定と違うときは、仕様 JSON に `recipient` を書き（手順5と同じ）、ファイル名にも確認先を入れる（`確認資料_<確認先>_YYYY-MM-DD_<件名>_作成中.xlsx`）。  
確認先が非エンジニアのときは、[references/confirm-doc.md](references/confirm-doc.md) の「読み手が非エンジニアのときの判断基準」に従う。特に、CSV や画面は、相手が開いたときの見え方を、実際のデータの例で再現する（仕様 JSON の `examples`）。  

何を載せるかを先に決める。**課題の「報告」の節と、ユーザーの指示から選び、推測で候補を挙げない。** 決まりは `references/confirm-doc.md`。  

```bash
python <スキル>/scripts/build_confirm_doc.py <仕様JSON> "<作業フォルダ>/変更履歴/確認資料_YYYY-MM-DD_<件名>_作成中.xlsx"
```

- レビューが済むまで、名前の末尾に `_作成中` を付ける。済んだら外す（アップロードのスクリプトは、`_作成中` を上げない）。  
- ユーザーが手で直したあとは、再生成せず、いまのファイルを直接直す（手直しを消さないため）。  

## 7. スクリプトを作る

**作る前に、置き場の場所と、合意後の反映先を、ユーザーに確かめる。** 確認しないまま、置き場所を決めない（ローカルの作業フォルダと、サーバーの置き場の場所は、違うことがある）。  

```bash
python <スキル>/scripts/make_scripts.py <仕様JSON> --folder <作業フォルダ>
```

置き場へ上げる `アップ_レビュー用置き場_<suffix>`（`suffix` は仕様JSONの値）と、正本へ反映する `正本反映`（それぞれ .ps1 と .bat）が、作業フォルダに出る。  
仕様 JSON は `assets/examples/scripts.example.json` を参照する。雛形は `assets/templates/` にあり、場所・名前は、設定の値と仕様 JSON で埋まる。  

- スクリプトは、作るだけで、実行しない。実行は、ユーザーが行う（ドライラン → 確認 → 実行の順に進む）。  
- 上げる資料の名前に `_作成中` が残っていないか（確認資料の名前を外したか）を、作る前に確かめる。  
  レビュー中の確認資料を、作成中の名前のまま上げ直すときは、ユーザーの指示を受けて、仕様JSONの `allow_in_progress` に、その資料を書く（`upload` にも書く）。  
- **仕様JSONの `move_scope` を、必ず決める。** 上げるとき、置き場の既存のファイルを `old\` へ移す範囲である。  
  - `all`（省略時）：置き場の `.xlsx`・`.drawio` のすべてを移す。上げない資料も、置き場から無くなる（確認資料・ほかの設計書など）。置き場の資料を、すべて上げ直すときだけ使う。  
  - `uploaded`：今回上げる資料と、同じ場所・名前のものだけを移す。**一部だけを直したときは、こちら**。  
  - ドライランに、「今回は上げないのに、old\ へ移される」の警告が出たら、`move_scope` と上げる資料の一覧を見直す。  
- 一部のスクリプトだけを作り直したいときは、`--only upload`（置き場へ上げる）か `--only reflect`（正本へ反映する）を付ける（作業フォルダの、もう一方のスクリプトを上書きしない）。  
- 反映先が複数のとき（段階（区分）を使うときなど）は、`reflect` の各件に、`root`（反映先のフォルダ。設計書のルートからの相対パス。省略時は正本）と、元の版の SHA-256（`base_file`＝元の版の写し、または `sha256`。取得の記録でもよい）を書く。新しく置くものは `new: true`。`reflect_name` で、反映のスクリプトの名前を変えられる。実行は、レビュー担当者の合意のあとである。  

## 8. 見た目と整合を確かめる

- 作業フォルダの `変更履歴/` に、変更箇所一覧（と、要確認があるときは確認資料）が揃っているか。  
- 取得した版から、正本が変わっていないか。  
  ```bash
  python <スキル>/scripts/check_server_unchanged.py <作業フォルダ>
  ```
  不一致なら、止まって、変更の内容を確かめ、取り込み直すかを、ユーザーと決める。  
- 変更箇所一覧・確認資料・設計書の、版数・変更履歴・桁数などの数値が、お互いに食い違っていないか。  
- 確認資料の、設計書へのリンクが、作業フォルダから開けるか（取得したファイルの配置と同じ相対パス）。  
- スクリプトの構文（PowerShell の `Parser.ParseFile`）。  

## 9. 報告する

手順5・6の資料を作り、手順8で確かめたあとに、報告する。資料が無いうちは、報告も、レビューの依頼もしない。  

した内容（直したファイルと内容）、確認してほしい点、未対応を、まとめて報告する。  
レビューしてもらう資料（変更箇所一覧・確認資料）の置き場所も、あわせて伝える。  
ファイルサーバーに触れる操作（アップロード・反映）は、まだ行っていないことを、はっきり書く。  
設定の「設計書を直したあとの進め方」があれば、その手順を読んで、次にすることを案内する。  
ハーネスの文書の最終更新を設定に書き戻したときは、そのことを1行で添える。  

## このスキルが扱わないもの

- 設計書の中身を決めること（何を直すかは、課題とユーザーが決める）。  
- レビュー担当者との合意を取ること、チャットなどへの送信（ユーザーが行う。依頼されたときだけ、文面を作る）。  
- 正本への反映の実行、レビュー用の置き場へのアップロードの実行（ユーザーが、スクリプトで行う）。  
- Excel・図の編集そのもの（設計書スキルが行う）。
