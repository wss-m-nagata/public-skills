# 作業フォルダの README の雛形

作業フォルダの直下に置く `README.md` の書き方である。  
`<…>` を埋める。ファイルサーバーに上げない（社内用）。  
文は、句点（。）ごとに改行し、行末に半角スペース2つを付ける（ビューアでも改行される）。  
プロジェクトに README・文書の書き方の決まりがあれば、それを優先する。  

````markdown
# <件名> ドキュメント管理方針

## 本フォルダの使い方（YYYY-MM-DD）

<何を直すか（1〜2文）>（<課題の番号・URL>）。  
本フォルダは、そのために直す設計書を、ローカルで修正するための作業フォルダである。  

正本（<正本の場所>）の設計書が正である。  
本フォルダには、**直す設計書を正本から取ってきて置き、ここで直す**。  
過去の案件の資料を、修正のベースにしない。  

<今回の変更の表：項目 / 変更前 / 変更後>

## ファイルサーバー上の設計書

<レビュー用の置き場のパス>（本フォルダのコピー先）と、<正本のパス>（合意後の反映先）を書く。  
作業前に読む文書（ファイルサーバー側の README・運用の文書）があれば、挙げる。  
ファイルサーバーにつながらず読めない場合は、作業を止めて報告すること。  

### ローカルでの作業ルール

- 設計書はローカルで修正し、ユーザーと内容を確認して合意してからファイルサーバーへ上げる。ファイルサーバー上のファイルを直接編集しない。
- `README.md` などの Markdown は社内用で、ファイルサーバーに上げない。
- 旧版はファイルサーバーだけに置き、ローカルには置かない。
- 課題と未決事項は、課題管理のツールで管理する。

### 修正から共有までの手順

1. 正本から修正対象の最新ファイルを取得する（`fetch_from_source.py`。更新日時と SHA-256 を記録する）。
2. ローカルで設計書を修正する（Excel は `nablarch-basic-design-excel`、処理フロー図は `process-flow-diagram`、など。設定の「設計書の種類ごとの使うスキル」に従う）。
3. `変更履歴/変更箇所一覧_YYYY-MM-DD_<件名>.xlsx` を作る。レビュー担当者への確認が要る変更を明示する。
   確認が要る事項があるときは、確認資料（`変更履歴/確認資料_YYYY-MM-DD_<件名>_作成中.xlsx`）も作る。
4. 変更箇所一覧と確認資料が揃ってから、社内でレビューし、ユーザーと合意する。（資料が無いうちは、レビューを依頼しない）
5. レビュー用の置き場へ上げる（`アップ_レビュー用置き場_<suffix>.bat`）。既存の版は、`old/` へ退避される。
6. ファイルサーバーの版と、ローカルが一致しているかを確認する。
7. レビュー担当者へ修正を報告し、変更箇所一覧を添えて合意を取る（チャット等への送信は、ユーザーの指示があるときだけ）。
8. 合意の後、正本へ反映する（`正本反映.bat`）。

## 設計書の配置

<設計書の置き場の型（フォルダ）と、取得元（正本の配下）を、表にする。個別のファイル名は並べず、フォルダ（型）で書く。状態（作成済みなど）は書かない>

取得した時点のファイルの最終更新日時とハッシュ値は、取得の記録ファイルに残す（READMEには書かない）。

### 変更履歴フォルダの資料

<変更箇所一覧・確認資料の、名前の決まりだけを書く。状態（作成中・レビュー済みなど）は書かない。作成中かどうかは、ファイル名の `_作成中` で分かる>

## 対象範囲

<直すもの／直さないもの。個別のAPI・テーブルの列挙は、課題への案内にする>
````

## 段階（区分）を使うとき

設定に「段階（区分）」があり、その区分の作業フォルダを作るときは、雛形のうち次の点が違う。  

- 「ファイルサーバー上の設計書」には、置き場（区分ごとの親フォルダの下）と、合意後の反映先（設定の「段階（区分）ごとの対応」の表）を書く。  
- 「修正から共有までの手順」の反映は、その区分の反映先へ行う。  
- 「設計書の配置」は、取得元ではなく、作る資料の置き場の型を書く（状態は書かない）。  
- 区分の構成の説明は、ファイルサーバー側の文書に任せ、READMEには、案件ごとの作業領域と、設計書の場所だけを書く。  

## 書くときの注意

- 相対的な表現（「現在」「最近」）には、日付を添える。  
- 作業フォルダにあるスクリプト（アップロード・反映）の対象ファイルは、前回のままのことがある。今回の対象に作り直したことを、1行書く。  
- 修正の中身の詳細は、課題と変更箇所一覧に任せ、README には、何をどこに置いたかだけを書く。  
- 状態（作成済み・レビュー済みなど）と、個別のファイル名・API の列挙は、README に書かない（更新のたびに古くなり、信用されなくなる）。
