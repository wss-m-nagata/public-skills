# 確認・レビューを依頼するメッセージの決まり

レビュー用の置き場に上げた資料（変更箇所一覧・確認資料）について、チャットやチケット管理ツールで、確認を依頼するメッセージの書き方である。  
送信は、ユーザーが行う。依頼されたときだけ、文面（案）を作る。  

## 基本の考え方：資料とメッセージで、同じことを二度読ませない

- 確認する人は、資料を開いて確認する。メッセージにも同じ内容があると、両方を読むことになり、負担になる。  
- **資料に書いてあることは、資料を見てもらい、メッセージは簡潔にする。** メッセージには、「何の対応か」「資料はどこか」「資料に何が書いてあるか（一言）」だけを書く。  
- **同じ依頼を、複数の経路で送るときは、内容を1か所（記録に残るほう）に書き、もう一方は、「〇〇に書きました。ご確認をお願いします」の一文にする。**  
- 内容に触れるときは、「〜について、不明な点が出ました。確認をお願いしたい点が〇つあります」のように、件数と、話題の見出し程度にとどめる。  
  中身（選択肢・変更前後・例）は、書き写さない。  
- 資料だけでは伝わらない、判断が必要なこと（認識の違いなど）と、最優先で見てほしい一点があるときだけ、その一点を足す。無ければ、足さない。  

## 構成

次の順に書く。該当しない節は、省く。  

1. 宛先。  
2. 何の対応か。（課題管理の項目があれば、番号・名前・URL を添える。確認する人が、経緯を知らない前提で書く）  
   - 経緯を知っている人には、課題の番号を、一言添える程度でよい。  
   - 経緯を知らない人（別の組織など）には、課題と、何を直したかの要点を、一文で添える。  
3. 資料の置き場所。フォルダのパスと、その下のファイル名。ファイル名は、省略せず、全部書く。  
   - 資料から設計書を開けるとき（変更箇所一覧に、対象のファイルが載っているときなど）は、設計書のファイル名は並べず、確認の入口になる資料だけを書いてよい。  
   - 確認資料が無いときは、「確認資料はありません。変更箇所一覧に沿って、ご確認をお願いします」と書く。  
   - 同じフォルダに、別の人宛ての資料が見えるときは、「〇〇宛てで、確認事項ではありません」と一言添える。  
4. ご確認のお願い。資料に沿って確認してもらう一文。  
5. 期限。  

## 期限

- 通常は、メッセージを送る日の翌営業日から数えて、**3営業日以降**にする。今週の残りの営業日が3日以上あれば「今週中を目処に」、足りなければ「来週中を目処に」。休日は、除いて数える。  
- **課題の優先度と期限を見る。** 優先度が高いときなど、上の目途が、課題の期限を過ぎるときは、課題の期限に収まる書き方にする。  
- 期限は、「目処に」を付けて、ゆるく書く。  
- **優先度が高く、課題の期限が迫っているときは、理由と、日付・時間帯を書く。** 「急ですが」を添えて、お願いする形にする。  

## 読み手が非エンジニアのとき

- 内容は、さらに手短にする。専門用語（データ型・ID など）を、メッセージに増やさない。  
- 確認する点が複数あるときは、「確認をお願いしたい点が〇つあります」と件数だけ書き、中身は、確認資料に任せる。  
- 宛先は、ツールのメンション機能で指定する。  
- この基準は、確認先ごとの指摘を受けるたびに、ここへ足していく。  

## 書き方

- API は、名称（ID）の形で書く。ID だけで書かない。  
- 人名・他の組織の文書の節番号は、資料には書かない。メッセージの宛先は、メンションでよい。  
- 投稿の前に、次を確かめる。  
  - 置き場に、資料が上がっていて、サーバーと手元の SHA-256 が一致すること。  
  - 正本の元のファイルが、取得時から変わっていないこと。（`scripts/check_server_unchanged.py`）  
  - メッセージに書いた URL・パス・ファイル名が、正しいこと。  
  - 確認する人が、資料を置いた場所を開けること。
