# 確認資料の決まり

レビュー担当者へ、確認・お願い・共有・報告をまとめて渡す Excel である。  
`scripts/build_confirm_doc.py` が作る。  

## 何を載せるか

- 課題の「報告」の節と、ユーザーの指示から選ぶ。**推測で候補を挙げない。**  
- 相手に、**判断・対応してもらうもの、ご承知おきいただくものだけ**を載せる。設計書の変更のすべては、変更箇所一覧に載せる。  
- 相手に判断も対応も要らず、共有する必要も無いものは、載せない（変更箇所一覧には残す）。  
- 実装の完了報告と、つなぎ込みの依頼は、普段は含めない（別に行う）。  
- 相手の担当外のものは、載せない。担当の範囲は、設定の「追加の項目」と、ハーネスの文書に従う。  
- 人名は書かない。他の組織の文書の節番号・決定の番号は書かず、中身を直接書く。  
- **「確認済み」「決まっている」と書くときは、いつ、どの資料で確認したかを示す。** 仕様JSONの `refs` に、ファイル名・場所・シート・回答を、省略せずに書き、リンクにする。示せないときは、「確認済み」と書かない。  
- **DDL（テーブル・列・インデックスなど）を変えるときは、変える定義そのものを、`code` で載せる。** 文章や表で言い換えず、相手が、定義を見て判断できるようにする。  
- 資料の文章を、そのまま書き写さない。資料に沿う一文と、最優先の一点だけを書く。  

## 作るかどうか

設定の「確認資料の要否の基準」に従う。  
設定に無いときの既定は、次のとおり。  

- 相手に判断・対応してもらうこと（変更箇所一覧の「要確認」の行）が1つでもあれば、作る。  
- 1つも無ければ、作らなくてよい（変更箇所一覧は、必ず作る）。  

## 読み手が非エンジニアのときの判断基準

確認先が、依頼元の業務担当者や要件定義のチームなど、エンジニアではない人のときは、次の基準で書く。  
**この基準は、確認先ごとの指摘を受けるたびに、ここへ足していく。**  

- **仕様の説明ではなく、実際のデータの例で見せる。** 項目ID・データ型・桁数・DB の名前などで説明しない。  
- **成果物（CSV・画面など）は、相手が開いたときの見え方を、そのまま再現する。**  
  - CSV は、1行目が列名、2行目以降がデータ（1人・1件ずつ）で、列が横に並ぶ見え方にする。「項目／変更前／変更後」を縦に並べた表だけで説明しない。  
  - 仕様 JSON の `examples`（`grid_example`）で作る。行の名前は、「1行目：列名」「2行目：山田さん（回答済み）」のように、ファイルの行として書く。  
  - 列が多くて横に入らないときは、段に分けて折り返す。段ごとに、列名の行が付く。折り返していることと、実際のファイルでは1行に並ぶことを、補足に書く。  
  - 途中は、「…（省略）」にする。省略した範囲を、補足に書く。  
  - 値が無いところは、「（空欄）」と、灰色で示す。  
- 例の値は、実際にありそうな値にする（伏せ字にしない）。人名は、架空の名前にする。  
- 変更前と変更後の比較は、相手に必要なときだけ載せる。内部の用語（データの持ち方・テーブル名など）は、使わないか、使うときは意味を添える。  
- 数値の見積もりは、前提と、「概算」であることを併記する。  

## 確認先の呼び名とファイル名

確認先の呼び名は、設定の「レビュー担当者の呼び名」である。仕様 JSON の `recipient` で、資料ごとに変えられる（帯の文「【共有のみ】…」「【解決済み】…」に入る）。  
変更箇所一覧の仕様 JSON にも、同じ値を書く。  

確認先が複数あるときは、ファイル名に確認先を入れる。  

- 既定の確認先宛て：`確認資料_YYYY-MM-DD_<件名>.xlsx`  
- 別の確認先宛て：`確認資料_<確認先>_YYYY-MM-DD_<件名>.xlsx`（作成中は、末尾に `_作成中`）  

## 種別

シート名は `確認① …`・`依頼① …`・`共有① …`・`報告① …`（種別ごとに、①から数える。自動で付く）。  

| 種別 | 使うとき | 確認欄 | タブ・帯 |
|---|---|---|---|
| 確認 | 相手に判断してほしい | □ 問題なし □ 要修正 □ 要相談 | 既定の色 |
| 依頼 | 修正・対応をお願いする | □ 対応します □ 対応不要 □ 要相談 | 既定の色。「お願いしたいこと」を、赤・太字で書く |
| 共有 | 判断・対応は要らないが、ご承知おきいただきたい | □ 問題なし □ 要修正 □ 要相談（任意） | タブをグレー。上部に帯「【共有のみ】…」 |
| 報告 | 報告のみ。回答は要らない | なし | 確認欄を置かない |

- 相談済み・解決済みのシートは、`resolved: true` にする。帯「【解決済み】…」が付き、タブがグレーになる。  
- 概要のシート一覧でも、共有・解決済みは、グレーにし、冒頭に【共有のみ】【解決済み】が付く（自動）。  

## 構成

- 1ファイル。先頭に「概要」、以降は**1シートにつき1つの論点**。  
- 概要：目的、確認していただく資料（置き場所・変更箇所の一覧・反映の時期）、各シートの見方、シート一覧、ご確認のお願い。  
- 論点のシート：タイトル（資料名と `（2/4）` のような通し番号）、帯（共有・解決済みのみ）、**対象の設計書（最初の見出し）**、確認したい内容、変更の内容（表）、お願い（依頼のみ）、確認欄。  

## 対象の設計書の書き方

- ファイル名を省略せずに書く（電文 ID だけに略さない）。  
- 1行に1つのファイルを書き、クリックで開けるリンクにする。  
- リンクは、確認資料から見た相対パスにする。作業フォルダでの配置と同じにする（設定の「構造を保つフォルダ」の下は同じ構成。それ以外は、作業フォルダの直下）。自動で作られる。  
- ファイル名のあとに、直したシートと行を（）で添える。  
- 本文や表の中で設計書に触れるときも、ID だけにせず、名前を添える。  

## 書き方

- 文章を減らし、表で示す。経緯・決定日は書かない（決まったことは、結果だけ）。  
- 事実（設計書の記載、項番、型、行番号）は、実際のファイルから取る。推測しない。  
- 例の数字は、例であると分かるようにする。  
- 見積もりなど、概算の数値には、概算であること（上限ベース・実測は未実施 など）を書く。  

## 進め方

1. 論点を確定する（上の「何を載せるか」）。  
2. 仕様 JSON を書き（`assets/examples/confirm_doc.example.json`）、作る。名前の末尾は `_作成中`。  
3. PDF にして画像で、はみ出し・隠れが無いかを確かめる。  
4. ユーザーがレビューする。手直しがあれば、再生成せず、いまのファイルを直接直す。  
5. 確定したら、`_作成中` を外す。置き場へ上げるのは、アップロードのスクリプト（ユーザーが実行する）。  
6. 回答の経路は、別に決める。資料には書かない。依頼のメッセージは、`message.md` に従う（資料に書いてあることを書き写さず、簡潔にする）。
