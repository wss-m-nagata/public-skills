# A5:SQL Mk-2 ER図 (.a5er) エディタ

## これは何をするスキルか

1. **目的**: A5:SQL Mk-2 のER図ファイル(.a5er)を、AIが安全に解析・編集・新規生成できるようにするためのスキルである。
2. **`.a5er`とは**: A5:SQL Mk-2 が使うER図ファイルで、見た目はINIファイルに似ているが、1行の中にカンマ区切り・ダブルクォート囲み・独自エスケープが混在する「Complex値」を多用する形式である。
3. **公式リファレンスの参照**: 作成・編集にあたっては、必ず公式仕様書のコピーである `references/a5er_specification.md` を参照すること。
   ここに存在しないキーやセクションを生成してはならない(編集ポリシー参照)。
4. **このSKILL.mdの位置づけ**: 全項目を網羅する仕様書とは違い、迷いやすい点・あいまいになりやすい点を整理した要点集である。
   ここに書ききれない詳細(レアケースのオブジェクトなど)が必要な場面では、明示的に参照先を示す。

## 絶対に守る編集ポリシー

ユーザーから次の3つが明示的に要求されている。

理由も併記するので、なぜ重要かを理解した上で守ること。

1. **不要な並び替えをしない。**
   触っていない行の順序やカラムの並び順は変えない。
   A5:SQL Mk-2 はGUIで開くたびに配置情報などを保持しており、無関係な行の並び替えは差分(diff)を無駄に大きくし、ユーザーが本当の変更点を追えなくなる。
2. **仕様書に存在しない要素を生成しない。**
   `references/a5er_specification.md` に無いキーやセクションを新規に作らない。
3. **仕様が不明・曖昧な場合は、編集を実行せずユーザーに質問する。**
   例えば「コメントを追加して」とだけ言われた場合、テーブルのコメントか、特定カラムのコメントか、あるいは論理名とコメントを結合した文字列(`GenerateCommentStatement_Separator` 相当)なのかは自明ではない。
   推測で書き換えると、ユーザーの意図と違うものがER図に残ってしまう。
   少しでも解釈が割れる場合は、具体的にどちらか尋ねる。

これらは制約というより「ユーザーの既存の作業を壊さない」ための指針だと捉えること。

曖昧な点は安全側(=聞く)に倒す。

## 基本ワークフロー

1. **対象ファイルを特定する。**
   パスが与えられていなければ尋ねる。
2. **現状を読む。**
   ファイルは **UTF-8 (BOM付き)** で保存されている。
   書き込みもBOM付きUTF-8を維持すること。
   まず `[Manager]`(ページ定義など全体設定)、`[Entity]`(テーブル)、`[Relation]`(`[Relationship]`と表記されることもある。リレーション)の3種類のブロックをテキストとして眺め、何が書いてあるかを把握する。
   `[View]`, `[Subtype]`, `[Shape]`, `[Line]`, `[Comment]` などのレアケースのブロックは、ユーザーの依頼がそれに関係する場合のみ読めばよい(下記「ファイル形式クイックリファレンス」参照)。
3. **Complex値を編集するときは `scripts/a5er_tool.py` を活用する。**
   `Field=`, `Index=`, `Position=`, `PageInfo=` などの1行は、手動でカンマ位置を数えて編集すると壊れることがある(日本語の論理名にカンマや引用符が含まれることもある)。
   複雑な値の組み立て方は下記「ツールの使い方」を参照する。
4. **実際のファイル変更は Edit ツールで、変更が必要な行だけを置き換える。**
   ファイル全体を読み込んで丸ごと書き直す必要はない。
5. **編集後に整合性チェックを行う。**
   ```
   python scripts/a5er_tool.py validate <対象ファイル>
   ```
   これは「重複した物理名」「存在しないエンティティ/カラムを参照しているRelation」「存在しない列を参照しているIndex」を検出する(`.a5er`自体の構文チェックではなく、あくまで参照整合性のチェック)。
   指摘が出た場合、それが今回の編集で意図せず発生したものであれば修正する。
   ユーザーが意図してテーブルを消した結果リレーションが浮いた、というようなケースは、そのまま消すべきか残すべきかをユーザーに確認する(ポリシー3)。
6. **何を変更したかを簡潔に報告する。**
   どのセクション・どの行を変更したかが分かるように伝える。
   新規にER図を生成した場合は、ヘッダの`# A5:ER FORMAT:n`が参照している仕様書のバージョンより、ユーザーの実際のA5:SQL Mk-2が新しいことがあり、開いたときに「古いバージョンで保存されたものです」という警告が出ることがある旨も併せて伝える。
   データが壊れているわけではなく、そのまま開けることも伝える。

## ツールの使い方 (scripts/a5er_tool.py)

このスクリプトは「壊れやすいエスケープ処理」を毎回手作業でやらずに済ませるためのものであり、ファイル全体を書き換えるツールではない。

用途は、ある1行のComplex値を読み取る/組み立てるときの「正しい文字列」を作ることに限定される。

```bash
# 文字列のエスケープ/デコード
python scripts/a5er_tool.py escape 'カンマ,や"引用符"を含む文字列'
python scripts/a5er_tool.py unescape '\Qあいう\Q'

# Field行を読み取って構造化する(既存の値を正確に把握したいとき)
python scripts/a5er_tool.py parse Field '"ユーザーID","id","Serial","NOT NULL",0,"","",$FFFFFFFF,""'

# Field行を組み立てる(JSONで指定したキーだけを反映。指定しなかった末尾項目は「未指定」として省略される = 元のファイルに存在しなかった項目を作り出さない)
python scripts/a5er_tool.py build Field '{"lname":"ユーザーID","pname":"id","dtype":"Serial","notnull":"NOT NULL","pk_order":0,"default":"","comment":"","color":"$FFFFFFFF","option":""}'

# Index行
python scripts/a5er_tool.py parse-index 'users_ix1=0,user_name,birthday'
python scripts/a5er_tool.py build-index '{"index_name":"users_ix1","unique_flag":0,"columns":["user_name","birthday"]}'

# Position / PageInfo / DomainInfo / CommonField / Relationの Position も同様に
# parse <schema> / build <schema> で扱える。schema名は以下のいずれか:
#   Field, PageInfo, DomainInfo, CommonField, Position, RelationPosition

# 編集後の参照整合性チェック
python scripts/a5er_tool.py validate path/to/diagram.a5er
```

**実践的な使い方**: 既存の1行を少しだけ変えたい場合は、まず `parse` でJSONにデコードし、変更したいキーだけをそのJSONの中で書き換えて `build` に渡し、出力された文字列で元の行を Edit ツールに置き換える。

これにより、意図しないサブフィールドの書式変化(引用符の有無など)を防げる。

## ファイル形式クイックリファレンス

詳細・レアケース(`[View]`, `[Subtype]`, `[Shape]`, `[Line]`, `[Comment]`, `DomainInfo`, `CommonField`, ヘッダとフッタの置換文字列など)は必ず `references/a5er_specification.md` を参照すること。

ここでは頻出する `[Entity]` と `[Relation]` の要点だけを載せる。

### `[Entity]` (テーブル)

```
[Entity]
PName=物理名          <- 必須。ファイル内の全オブジェクトでユニーク(大文字小文字区別なし)
LName=論理名
Comment="コメント"     <- EscapedString。無くてもよい
Field="論理名","物理名","データ型","NOT NULL",キー順,"デフォルト値","コメント",色,"オプション","追加オプション"
Index=インデックス名=ユニークフラグ,カラム1,カラム2,...
Position="ページ名",X,Y[,幅,高さ]
```

- `Field` の `キー順` は主キーなら `0` から始まる整数、主キーでなければ空。
  複合主キーは複数のFieldに0,1,2...と順に振る。
- `色` は `$AARRGGBB` 形式で、`$FFFFFFFF` はデフォルト色を意味する(必須項目)。
- `Position` はページごとに1つ必要(同じテーブルを複数ページに置ける)。
  `ページ名` は `[Manager]` の `PageInfo` で定義したページ名と一致させる。

### `[Manager]` の `PageInfo` (用紙サイズ)

新規にER図を生成するときは、`PageInfo` の用紙サイズを小さく取りすぎないこと。  
用紙サイズは上下左右5mmが余白として引かれ、残りの範囲にテーブルを配置する(0.1mm単位)。  

例えば`A4Landscape`は297mm×210mmしかなく、テーブルが数個を超えると簡単にあふれて、はみ出た部分が描画されなくなる。  

テーブル数が多い、またはテーブル数が事前に分からない場合は、迷わず大きめの用紙サイズ(`A2Landscape`や`A1Landscape`など)を選ぶこと。  
小さすぎて配置がはみ出るより、大きすぎて余白ができるほうが実害はない。

### `[Relation]` (リレーション = 外部キー相当)

A5ERにはFK専用のセクションは無く、**`[Relation]` がFKを兼ねる**。

「FKを追加/変更/削除して」は「Relationを追加/変更/削除して」と読み替えてよい。

```
[Relation]
Entity1=親エンティティの物理名
Entity2=子エンティティの物理名
Fields1=親側の関連カラム(カンマ区切り)
Fields2=子側の関連カラム(カンマ区切り)
RelationType1=カーディナリティ(親側)
RelationType2=カーディナリティ(子側)
PName=外部キー制約名          <- 省略可
Position="ページ名",ラインモード,線位置1,線位置2,線位置3,端子位置1,端子位置2,"頂点座標リスト"
```

- `RelationType`: `0`=指定なし, `1`=0または1, `2`=1, `3`=0以上, `4`=1以上, `5`=N個固定。
  典型的な「1対多」は親側 `2`(1)、子側 `3`(0以上) または `4`(1以上)。
- `Position` のラインモードやパラメータが分からない/どう見せたいか不明な場合は、`Position="Main",0,5000,5000,5000,R,R,""` をベースに `0` (自動)を使えばよい。
  位置の微調整はA5:SQL Mk-2側のGUIに任せる前提でよい。

## 操作別ガイド

以下は、要求された操作それぞれが、どのキーを触ることに相当するかの対応表。

実際の値の組み立ては必ず「ツールの使い方」の手順を使う。

| 依頼 | 触るもの |
| --- | --- |
| A5ERファイルの解析 | ファイル全体を読み、`[Entity]`/`[Relation]`などを列挙。必要なら `validate` で整合性も報告 |
| ER図の編集 | 以下の個別操作の組み合わせ |
| 新規ER図生成 | ヘッダコメント(`# A5:ER FORMAT:19` / `# A5:ER ENCODING:UTF8`)+ `[Manager]`(`PageInfo`必須。用紙サイズは小さく取りすぎない。下記「`[Manager]`の`PageInfo`」参照)+ `[Entity]`/`[Relation]` を新規作成する |
| テーブル追加 | 新しい `[Entity]` ブロックを追加。`PName`が他と重複しないか要確認 |
| テーブル削除 | 該当 `[Entity]` ブロックを丸ごと削除。参照している `[Relation]` があれば、消すかどうかユーザーに確認(ポリシー3) |
| テーブル名変更 | `PName=` を変更 **かつ** 全ての `[Relation]` の `Entity1=`/`Entity2=` の同名箇所を追随して変更 |
| カラム追加 | 対象Entityの既存 `Field=` 行の末尾に新しい `Field=` 行を追加(並び替えない) |
| カラム削除 | 該当 `Field=` 行を削除。同エンティティの `Index=` や他の `[Relation]` の `Fields1`/`Fields2` がそのカラムを参照していないか確認し、参照があれば対応方針をユーザーに確認 |
| カラム変更 | `parse Field` → 該当サブフィールドだけ変更 → `build Field` → 該当行を置換 |
| PK変更 | 対象Fieldの `キー順` を編集。単一PKにするなら他のFieldの `キー順` は空に戻す。複合PKなら0,1,2...の順を維持 |
| FK追加・変更・削除 | `[Relation]` ブロックの追加・編集・削除(上記参照) |
| インデックス追加 | 対象Entityに `Index=` 行を追加(`build-index`を使う) |
| コメント追加 | テーブルコメント(`[Entity]`の`Comment=`)かカラムコメント(`Field`の7番目の項目)か曖昧なら質問する |
| 論理名変更 | テーブルなら `LName=`、カラムなら `Field` の1番目の項目(論理名) |
| リレーション追加 | 新しい `[Relation]` ブロックを追加。`Entity1/2`, `Fields1/2`, `RelationType1/2`, `Position` を指定 |
| リレーション削除 | 該当 `[Relation]` ブロックを削除(同じEntity間に複数リレーションがある場合は `Fields1/2` で対象を特定) |

## 曖昧なときに聞くべき質問の例

- 「コメント追加して」→ テーブル自体のコメントか、特定カラムのコメントか。
- 「salesテーブルにフィールドを1個足して」→ 論理名・物理名・データ型・NOT NULL/NULL許容・デフォルト値など、`Field` の各項目のうちどこまで指定されているか確認する(最低でも論理名・物理名・データ型は必要)。
- 「usersを削除して」でリレーションが繋がっている→ 関連する `[Relation]` も一緒に削除してよいか確認する。
- ページ(`PageInfo`)が複数あるファイルで、新規テーブルをどのページに置くか指定が無い→ 既存の関連テーブルと同じページを提案しつつ確認する。

## 参照ファイル

- `references/a5er_specification.md` — 公式仕様書の全文(バージョン、`[Manager]`の全項目、`[View]`, `[Subtype]`, `[Shape]`, `[Line]`, `[Comment]` など、ここに書ききれない詳細はすべてここにある)。
- `scripts/a5er_tool.py` — エスケープ/デコード/エンコード/整合性チェックの補助スクリプト。
  `python scripts/a5er_tool.py --help` で全コマンドを確認できる。
