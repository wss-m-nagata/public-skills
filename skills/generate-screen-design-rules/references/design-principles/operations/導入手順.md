# 画面設計の基本原則を、プロジェクトに導入する手順

ユーザーから、「原則をプロジェクトに導入したい」と言われたときの手順。
問い合わせに答えるだけのときは、この手順を進めない。

規約を作成・更新する手順（`SKILL.md` の実行手順0〜8）とは、別の作業である。
規約の優先順位は、そのまま守る（原則は、DADS・Carbonの値や、確定済みの規約を上書きしない）。

## 成果物

出力先（`SKILL.md` の手順0で決めた場所。既定は `docs/rules/screen-design-rules/`）に、次のファイルを作る。

- `設計原則適用方針.md`：原則ごとの適用可否と、規約での担保先をまとめたもの（ひな形：`${CLAUDE_SKILL_DIR}/assets/design-principles-template/設計原則適用方針.md`）

## 手順

### 1. 目的と対象を確認する

次の点をユーザーに確認する。

- 導入の目的（新規のシステムに最初から導入する／既存の規約に追加する／レビューの観点として使う、など）
- 対象のシステム、主な利用者、利用環境（画面サイズ、ブラウザなど）
- 利用シーン別原則（A-1〜A-4）の対象かどうか（事務職などが、日常的に長時間使い、多数の伝票・レコードを連続処理するシステムか）
- 既に規約（出力先）があるか

### 2. 原則を説明する

`一覧.md` を使い、分類ごとに原則を紹介する。
ユーザーが知りたい原則は、`principles.json` から、「何をすべきか」「なぜ必要か」「比較例の要約」を説明する。

### 3. 適用可否を確認する

原則ごとに、次のいずれかを、ユーザーに確認して決める。

| 区分 | 意味 |
|---|---|
| 必須 | プロジェクトの規約として、必ず守る |
| 推奨 | 守ることが望ましい。業務条件によっては例外を認める |
| 対象外 | このプロジェクトでは適用しない（理由を書く） |

- 分類単位で先に決めてから、原則単位で例外を確認すると、速く進む。
- 法令・適用基準等の要求事項は、任意に対象外にしない。
- 次の原則は、条件によって結論が変わるため、条件を確認する。
  - 3-8（時間制限）：時間制限が、システム上の都合で決まっているか。現在の制限時間で足りない業務があるか。顧客の要求を聞いたうえで、必要な場合に対応する。実装・運用の負担が大きい。
  - 4-3（エラー防止）：基本は、入力を確定した時点で検証する。例外とする項目（重複しやすいIDなど）を決める。
  - 5-4・5-5：画面幅、倍率、コントラスト比などの数値は例。採用する値を決める。
  - 2-5・2-8：「出し過ぎない」と「隠し過ぎない」の両立。隠す項目の基準を決める。

### 4. 規約との対応を確認する

`原則と規約の対応.md` を使い、適用する原則（必須・推奨）が、規約のどのファイル・章で担保されるかを確認する。

- 既に規約に書いてある場合は、その箇所を `設計原則適用方針.md` に書く。
- 規約に該当する章がない場合は、次のいずれかをユーザーに確認する。
  - 適切な規約本文に追加する方法を検討し、理由と管理台帳での対応を残す。
  - 別の資料で定義する（用語集、ショートカット一覧など）。
  - 対象外にする。
- 規約テンプレートの構造は、独自判断で変更しない。章が足りないときは、改善案としてユーザーに提示する。
- 原則と規約が矛盾する場合は、規約の優先順位に従い、矛盾の内容をユーザーに確認する。

### 5. 適用方針を書く

ひな形（`${CLAUDE_SKILL_DIR}/assets/design-principles-template/設計原則適用方針.md`）を、出力先にコピーして、埋める。
ひな形には、全原則の行（表示番号・原則名）が入っている。「前提」の表と、各原則の「適用」「理由・条件」「規約での担保先」「状態」を埋める。

記入例：

| 表示番号 | 原則名 | 適用 | 理由・条件 | 規約での担保先 | 状態 |
|---|---|---|---|---|---|
| 2-4 | 重要な情報と操作を分かりやすく配置する | 必須 | — | `layout.md` 5. Main Content、`components.md` 2. Button | 確定 |

- 「適用」は、必須・推奨・対象外のいずれか。
- 「状態」は、規約と同じ、`確定` / `暫定` / `要確認` を使う。
- 原則名は、`principles.json` の `name` を、変更せずに書く。
- 規約で担保できていない原則は、「規約での担保先」に「なし」と書き、状態を `要確認` にする。
- 数値の例（画面幅、倍率、コントラスト比、制限時間など）は、プロジェクトで定めた値を書く。

### 6. レビュー観点を渡す（希望があれば）

ユーザーが、画面レビューや結合テストの確認項目として使いたい場合は、適用する原則のレビュー観点（`principles.json` の `review`）を、「No.｜観点」の表にして渡す。
チェックシートに貼り付けやすいよう、結合セルは使わない。

### 7. 確認事項を更新して、完了を確認する

- `要確認` の項目は、適用方針の対象を明示して `デザインシステム管理台帳.md` に反映する（`SKILL.md` の手順8に従う）。プロジェクトに別の管理場所の決まりがある場合はそれに従い、台帳から参照する。
- 次を確認する。
  - 全原則（41件）に、必須・推奨・対象外のいずれかが付いている。
  - 対象外の原則に、理由がある。
  - 規約で担保できない原則が、`要確認` として残っているか、ユーザーが対応を決めている。
- ユーザーに、適用方針の内容を確認してもらい、修正があれば反映する。
