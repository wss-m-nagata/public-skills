# 画面設計の基本原則（問い合わせ対応用の参照資料）

業務Webアプリの画面設計で考慮する基本思想を整理した資料。
画面設計の原則について質問されたときに、この資料で答える。

## 位置づけ

- 共通原則37件と、利用シーン別原則4件（長時間・高頻度利用の業務システム向け）、計41件。
- 各原則に、「何をすべきか」「なぜ必要か」「OK/NG比較例」「レビュー観点」がある。
- **デジタル庁・GOV.UKなどの公開資料を参考に、業務アプリ向けに再構成した提案であり、公式文書の逐語的な原則一覧ではない。**
- すべての原則を全システムに一律適用するものではない。各プロジェクトで、利用者・業務・利用環境を踏まえて、必須・推奨・対象外を判断する。ただし、法令・適用基準等の要求事項は、任意に除外しない。
- 規約の値（色・余白・部品の寸法など）を決めるものではない。値は、規約テンプレートと DADS / Carbon で決める。**原則は、DADS・Carbonの値や、確定済みの規約を上書きしない。** 矛盾するときは、ユーザーに確認する。

## ファイル

| ファイル | 内容 |
|---|---|
| `一覧.md` | 原則の索引（表示番号・通し番号・原則名・比較例の題名） |
| `principles.json` | 原則の詳細（何をすべきか・なぜ必要か・比較例・レビュー観点）。画像の項目は含まない |
| `業務Webアプリ_画面設計原則.xlsx` | 人が読む資料。OK/NG比較画像が入っている（画像は、`scripts/extract_principle_images.py` で取り出す） |
| `VERSION.txt` | 版・件数・作成元 |
| `operations/導入手順.md` | ユーザーから、原則を導入したいと言われたときの手順（適用方針のひな形は、スキルの `assets/design-principles-template/` にある） |
| `operations/原則と規約の対応.md` | 原則が、規約テンプレートのどのファイル・章で担保されるかの目安 |

## 問い合わせへの答え方

1. 質問された原則を特定する。表示番号（例：`2-4`）、通し番号（例：`No.9`）、原則名、キーワードのいずれかで、`一覧.md` から探す。
2. `principles.json` で、その原則の次の項目を読んで答える。
   - `name`（原則名）、`what`（何をすべきか）、`why`（なぜ必要か）
   - `examples`（比較例）：`condition`（業務条件）、`ng_summary`、`ok_summary`、`ng_screens`・`ok_screens`（画面の流れ）、`note`（補足）
   - `review`（レビュー観点）
3. 比較例の画像が必要なときだけ、下の「画像の取り出し方」で、Excelから取り出す。通常は、`ng_summary`・`ok_summary` の文章で答える。
4. 複数の原則にまたがる質問（例：「統一に関する原則は？」）は、`一覧.md` で関連する原則を挙げ、それぞれの違いを説明する。
5. 質問されたこと以外は、書き足さない。

## 画像の取り出し方

比較例のOK/NG画像は、`業務Webアプリ_画面設計原則.xlsx` に入っている。
次のスクリプトで、原則・比較例を指定して取り出す（Pythonの標準ライブラリだけで動く）。

```bash
python ${CLAUDE_SKILL_DIR}/scripts/extract_principle_images.py <表示番号> [--example N] [--out 出力先]
```

| 例 | 内容 |
|---|---|
| `... extract_principle_images.py 2-8` | 2-8のすべての比較例の画像 |
| `... extract_principle_images.py 1-3 --example 2` | 1-3の比較例②だけ |
| `... extract_principle_images.py A-1 --out ./images` | 出力先を指定 |

- ファイル名は、`<表示番号>_ex<比較例の番号>_<ng|ok>_s<画面の順番>.png`（例：`1-3_ex1_ng_s2.png`＝1-3の比較例①、NG例の2画面目）。
- 画面の名前（「① 社員一覧」など）は、`principles.json` の `ng_screens`・`ok_screens` に、画面の順番どおりに入っている。
- 取り出した画像は、画面と注釈（番号・点線枠・凡例）が入った、PNG（256色以下に減色）である。
- 画像をユーザーに見せる、資料に貼る、といった依頼があったときだけ取り出す。質問に答えるだけなら、取り出さない。

## 答えるときの注意

- **公式の記載と、独自の判断を区別する。** 参考資料との対応が確認できているものは、次のとおり。それ以外の原則は、「参考資料を参考に整理した提案」と答え、公式のルールとは言わない。

  | 原則 | 確認できている参考資料の記載 |
  |---|---|
  | 2-7 今どこにいるか | ガイドブック3.4.2（自己記述性。ナビゲーション）、3.5.6（一貫したナビゲーション） |
  | 2-8 結果や機能の存在 | ガイドブック3.4.2、3.5.1（気づきやすくする） |
  | 3-8 時間制限 | ガイドブック3.4.5（制御可能性。時間を制限しない、延長できる） |
  | 5-6 通知・ポップアップ | ガイドブック3.5.2（注意を逸らさないようにする） |
  | 4-3 エラー防止（比較例③） | GOV.UK Design System の Validation：フィールドから離れた時点では検証せず、続ける・送信の操作時に検証する。比較例③は、その例外（重複しやすいIDなど） |
  | 5-5 誰でも操作できる（比較例②） | DADSのローカルデザインシステム：テキストと背景色のコントラスト比4.5:1以上、非テキストは3:1以上 |

  ガイドブックは、デジタル庁「ユーザビリティ導入ガイドブック」（DS-671.1）第3章。
- **数値は例。** 画面幅（1024px）、表示倍率（200%）、制限時間（30分）などは、例として置いた数値。採用する値は、プロジェクトで定める。
- 各原則の適用可否・優先度は、この資料では確定していない。プロジェクトで判断する。
- 比較例の企業名・個人名・業務データは、架空のもの。
- 比較例は、OK例を唯一の正解にしていない。業務条件で結論が変わる場合は、`condition` と `note` に書いてある。
- 原則を統合する・削除する、といった提案には、答えない。そのような変更は、原則を管理している人が判断する。

## 導入したいと言われたとき

ユーザーから、原則をプロジェクトに導入したいと言われたときは、`operations/導入手順.md` に従う。
問い合わせに答えるだけのときは、導入手順を進めない。
