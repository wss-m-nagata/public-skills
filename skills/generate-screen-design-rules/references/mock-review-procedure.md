# 規約のモック確認手順

規約の文章だけでは、値どおりに画面で表示されるか、操作できるかが分からない。
規約を確定する前に、確認用のモック一式を作り、規約の値を測り、ユーザーに見せて、指摘を規約へ反映する。

## 流れ

1. 規約の値で、モック一式を作る。
2. 規約の値どおりかを、ブラウザーで測る。
3. 規約に書いておらず、自分で決めた点や迷った点を洗い出し、規約に書き足す。次の観点も、必ず確かめる。
   - **例外規定の当てはめ**: 規約の例外規定（例: メニューの階層で、下の項目が1つだけの場合の扱い）を、プロジェクトの実際のメニュー項目・画面（手順0で確認した一覧）に当てはめ、利用者の意図と合うかを確かめる。
   - **すべての画面で同じ位置に出るものの有無**: 戻るボタン、画面名など、画面全体で共通のものが、規約で定めた種類の画面すべてに出るかを確かめる。
   - **部品ライブラリの既定の表示**: 表のフッター、日付の選択、ダイアログのボタンなどで、英語の文言や、規約にない操作（件数の選択など）が出ていないかを確かめる。
   - **選択状態を示す色と、装飾の色の重なり**: 表の見出し、選択行、通知などの色が、意味を持つ色（成功、警告、エラー、選択中など）と、取り違えられないかを確かめる。
   ユーザーに見せる前の事前の確認であり、ユーザーの指摘の代わりではない。ユーザーに見せる前の事前の確認であり、ユーザーの指摘の代わりではない。
4. ユーザーにモックを見せ、「この見た目と操作でよいか」を確認する。
5. ユーザーの指摘（「ここは違う」「こうすべき」）を、規約へ反映する。
6. 反映したら、モックを作り直し、もう一度見せる。指摘がなくなるまで繰り返す。

## 詳細

- **置き場所**: 一時的な資料のため、リポジトリの外の作業用の一時フォルダーに作る。プロジェクトに決まりがあれば、それに従う。規約から参照する参考例（`assets/`）には入れない。
- **構成**: `index.html` から、各画面へリンクで移れるようにする。次の画面を、スキルが決めて作る。プロジェクトの画面の種類に合わせて、増減してよい。
  - トップ（Header、Header直下の共通の領域、Side Navigation、本文の枠）
  - メニューを開いた状態（階層、表示の起点、本文との重なり、マスクの有無、開閉のキー操作）
  - 検索＋一覧（検索条件、件数、表、編集欄、フッターのボタン。操作の区分を選ぶ部品がある場合は、それも含める）
  - 登録・編集（入力欄、ラベル、エラー、ボタン）
  - ダイアログとトースト（削除の確認、操作結果の通知）
- **値**: 規約で定めた値（色、文字、余白、ボタンの高さ、入力欄の幅、フォーカスの線、キーの割り当て）を、そのまま使って作る。
- **測る**: ブラウザーで開き、規約の値どおりかを測る。文字の大きさ、ボタンの高さ、入力欄の幅、色、フォーカスの線を測る。
  フォーカスの線は、Tabキーで、すべての部品（メニューやダイアログの中の部品を含む）を順に移して確認する。
  キーの割り当ては、実際にキーを押して動くことを確認する。マウスとキーボードで、結果が同じになることも確認する。
- **迷った点を洗い出す**: 作る過程で、規約に書いておらず、自分で決めた点や、迷った点を一覧にする。規約に書き足し、理由も書く。ユーザーの判断が要るものは、確認する。
- **ユーザーに見せる**: `index.html` のパスを示し、「この見た目と操作でよいか」を確認する。直す指示があれば、規約を直して、モックを作り直す。
- **現行の規約や画面との食い違い**: モックが、現行の規約や、実際の画面と食い違ったときは、どちらが正かを、ユーザーに確認する。モックにだけ付けた部品（覆いなど）が原因のことがあるため、モックの独自の追加物かどうかを、先に確かめる。
- **配信と一時ファイル**: ブラウザーの自動操作で、ファイル（`file:`）を直接開けないときは、一定時間で自動的に終了する簡易サーバーで配信する。スクリーンショットなどの一時ファイルは、リポジトリの外に保存する。
- **終わったあと**: モックは、規約の確認のためだけに使う。残すのは、規約本文と、規約から参照する参考例（`assets/`）だけにする。
- **画面がすでにある場合**: モックに加えて、実際の画面でも、同じ値を測る。
