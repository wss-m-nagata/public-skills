# 画面設計規約

このディレクトリは、画面設計書からフロントエンドを生成する際に参照する、プロジェクト固有の画面設計規約です。

最終的な規約は、人が読んで理解・修正しやすいことを優先し、**Markdown** で管理します。

## AIによる利用

この規約は、人が画面設計時に参照するだけでなく、Claude CodeなどのAIが画面を生成する際にも利用します。

AIが参照する必要があるルールは、必要に応じて以下の形式で記載します。

```md
> [AI]
> - このルールに従って画面を生成すること。
> - 記載された値や配置を独自に変更しないこと。
```

`[AI]` の記載がないルールについても、通常の画面規約としてAIは参照します。

## 規約の優先順位

画面の見た目や構成を決める場合は、次の順番で判断します。

1. このディレクトリに記載されたプロジェクト固有の規約
2. デジタル庁デザインシステム（DADS）
3. DADSで不足する部分のみ IBM Carbon Design System
4. 上記に定義がない場合は `design-standards` Skill

> [AI]
>
> * Carbonの色・文字・ボタンデザインなどでDADSを上書きしないこと。
> * Carbonは主に、業務システム全体の構成やナビゲーション、UIの使い分けを補うために利用すること。


## 状態の見方

各ルールの状態は、[デザインシステム管理台帳.md](./デザインシステム管理台帳.md)で管理します。

| 状態      | 意味                                   |
| ------- | ------------------------------------ |
| **確定**  | プロジェクトの正式な規約として利用する                  |
| **暫定**  | DADS / Carbonなどをもとに仮設定している。変更要否を確認する |
| **要確認** | プロジェクト情報がないと決められない。規約作成時に確認する        |

規約作成が完了した時点では、原則として **「暫定」「要確認」を残さない** ものとします。

確認が必要な項目（`暫定` / `要確認`）と確認内容も管理台帳にまとめています。
プロジェクトで確認事項を別の場所で管理する場合は、その参照先を台帳に記載します。

## 各項目に付くメタ情報について

各ルールの `出典` `参照ヒント` `ローカル参照` などの情報は、管理台帳にまとめます。

* `出典` / `参照ヒント`: この項目がDADS / Carbonのどこを参考にしたかを示します。
* `ローカル参照`: `generate-screen-design-rules` Skillの中に同梱されている、DADS / Carbon原文の抜粋ファイルへのパスです。**このプロジェクトのリポジトリ内には存在しません。** 規約を見直す・更新する際にSkillが原典へ素早く戻るための情報であり、人が直接開くためのものではありません。

これらのメタ情報は、規約の中身（下に書かれている具体的な値・ルール）を理解するために読む必要はありません。規約はメタ情報や外部サイトを見に行かなくても、本文（説明・規約・確認事項）だけで判断できるように書くことを原則とします。

## ユーザーによる修正

この規約はAIやSkillだけで更新するものではありません。  
プロジェクトメンバーがMarkdownを直接編集して構いません。

必要に応じて、以下の内容も規約に追加できます。

* OK例 / NG例
* 画面キャプチャ
* レイアウト図
* 実際のソースコード
* 判断理由
* 例外ルール
* 補足説明

このディレクトリに、次のファイルを置きます。

| ファイル               | 内容                                    |
| ------------------ | ------------------------------------- |
| `デザインシステム管理台帳.md` | 項目ごとの状態、確認事項、出典、参照先 |
| `デザインシステム実現方式.md` | 規約に対応するライブラリ、部品、設定、参考例と必須実装 |
| `foundations.md`   | 色、余白、文字、角丸、影、ブレークポイントなど               |
| `layout.md`        | Header、Side Navigation、Content、Gridなど |

| `components.md`    | Button、Input、Select、Table、Dialogなど    |
| `page-patterns.md` | 検索一覧、詳細、登録・編集などの標準画面構成                |

## 画像の管理

画面構成、OK例 / NG例、コンポーネント配置例など、文章だけでは伝わりにくい内容は `assets/` 配下に画像を配置します。

### ファイル名

画像ファイル名は、内容が分かる英小文字の `kebab-case` を推奨します。

例：

```text
assets/
├── application-shell.png
├── search-list.png
├── edit-form.png
├── button-layout-ok.png
└── button-layout-ng.png
```

### Markdownからの参照

```md
![検索＋一覧画面の標準レイアウト](./assets/search-list.png)
```

画像だけでは判断できないルールは、必ずMarkdown本文にも文章で記載します。

## ソースコードの記載

画面規約に対応するソースコードは、必要に応じて[デザインシステム実現方式.md](./デザインシステム実現方式.md)に記載します。

ソースコードは、**「参考例」** と **「必須実装」** を明確に分けて記載します。

### 参考例

画面規約の意図や利用イメージを分かりやすく伝えるための例です。

実装時に、このコードやコンポーネントをそのまま使用する必要はありません。

```md
> **参考例**
```

```html
<page-header title="ユーザー一覧"></page-header>
```

### 必須実装

画面の見た目や操作を統一するため、特定の共通コンポーネントや実装方法を使用する必要がある場合に記載します。

この記載がある場合は、原則として指定された方法に従います。

```md
> **必須実装**
```

```html
<primary-button>
  登録
</primary-button>
```

例えば、以下のような内容を必須実装として指定できます。

* 指定された共通コンポーネントを使用する
* 独自のButtonやInputを作成しない
* 指定されたレイアウトコンポーネントを使用する
* 画面間で見た目や操作を統一するため、特定の実装方法を使用する

## 画面規約と実装規約の違い

このディレクトリでは、主に **「画面をどう見せるか」** を定義します。

例：

* どの色を使うか
* 余白をどう統一するか
* 文字サイズをどうするか
* ボタンをどこに配置するか
* HeaderやSide Navigationをどう構成するか
* 一覧画面や編集画面をどう構成するか

画面の見た目や操作を統一するために、特定の共通コンポーネントや実装方法を使用する必要がある場合は、実現方式に「必須実装」として記載し、対応する画面規約を示します。

一方、以下のような画面の見た目に直接関係しない一般的な実装ルールは、フロントエンド実装規約として別途管理します。

* CSSやTailwind CSSの記述方法
* ファイルやコンポーネントの命名規則
* ディレクトリ構成
* Server Component / Client Componentの使い分け
* 状態管理の方法
* ESLintなどのコーディングルール

画面の統一性に直接必要な実装指定は実現方式に記載し、一般的な実装ルールはフロントエンド実装規約で管理します。
