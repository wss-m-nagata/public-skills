# 記入要領: 単体テスト仕様書(Webサービス／バッチ)

## 資料の目的

1つの取引（Webサービスなら1つのAPI、バッチなら1つのバッチ）について、単体テストで**何を・どの観点で・どこまで**確かめるかを一覧にする。
**取引1つにつき1ファイル**作成する（ファイル名の `(取引ID)_(取引名)` を実際の値に置き換える）。

テスト仕様のシートには、テスト観点カタログの観点が、あらかじめ1行ずつ並んでいる。
カタログは「一般的なテスト観点」であり、その機能固有の決まり（設計書に書かれた個別の業務要件）を確かめる観点は、カタログに無いことがある。
次の3段階で埋める。

1. **その機能にある分類（大項目〜詳細）を整理し、無い分類の行はシートから消す。**
   例：メール送信が無い機能では「メール処理」の行を消す。参照だけのAPIでは「DB操作」の「登録」「更新」「削除」を消す。
   消した分類は、仕様書には残さない。
2. **設計書の記述を順に見て、それぞれを確かめる観点を当てる。当てはまる観点がカタログに無ければ、追加観点として足す。**
   見る設計書は、システム機能設計書（入力データ定義・処理詳細・出力データ定義など）と、それが参照する外部インタフェース設計書・テーブル定義書など。
   特に、権限・閲覧範囲・状態による動きの違いのような業務の決まりは、カタログの観点だけでは抜けやすい。
   例：「一般ユーザーは、自分の部署のデータしか見られない」「退会した会員はログインできない」。
3. **残した分類の観点ごとに、「テストケースを書く」か「対象外理由を書く」かのどちらかを必ず埋める。**
   どちらも空の観点が残っていなければ、その機能にある観点の抜けが無い（全量を確かめた）と言える。
   対象外の行は灰色にし、テストする行（白）と見分けられるようにする。

## シートの種類と使い分け

単体テストは、テストする範囲で3つに分かれる（Nablarchシステム開発ガイドのサンプルプロジェクトの単体テスト標準）。
仕様書は、システム機能設計書1つにつき1つ作り、次の表で「作る」になっているシートを入れる。

| テストの範囲 | シート（作成後のシート名） | 内容 | Webサービス | バッチ |
|---|---|---|---|---|
| モジュール単位 | `<テストターゲット名>_クラス単体` | クラス（コンポーネント）を対象にするテスト | ロジックが複雑なもの（コンポーネント設計書を作ったもの）だけ作る | ロジックが複雑なもの（値の変換・ページング・外部の呼び出しなど、リクエスト単体だけでは確かめにくい処理を持つもの）だけ作る |
| 画面・バッチ単位 | `<リクエストID>_リクエスト単体` | 1つのAPI（1エンドポイント）、1つのバッチごとのテスト | **必ず作る** | **必ず作る** |
| ユースケース単位 | `取引単体` | 複数の処理から成る、業務のまとまりのテスト | 作らない（1つの設計書に1エンドポイントのため） | 複数のリクエストから成る取引のときだけ作る |

- バッチのクラス単体は、サンプルプロジェクトの単体テスト標準では作らないことになっている。
  このスキルでは、ロジックが複雑なバッチに限り、Webサービスと同じくクラス単体を作ってよいとする。
  テストのコードと仕様書のケースを、クラス単体の「テストコード」の列で1つずつ対応づけ、確かめた範囲を示すためである。
- `build_unit_test_spec.py` は、この表に合わない組み合わせをエラーにする。
- 使わない種類のシートは残さない（`build_unit_test_spec.py` は、定義に無い種類のシートを消す）。
- クラス単体のシートは、テスト対象のクラス・モジュールの数だけ作る。
- クラス単体で確かめず、リクエスト単体で確かめる観点は、クラス単体のシートで「リクエスト単体テストで確認するため対象外」とする。
- シート名は31文字以内。`[ ] : * ? / \` は使えない。

## 見出し（5〜8行目）

「<項目名>：<値>」の形で、ラベルと同じセルに書く（例：`機能名：顧客管理`）。

| 項目 | 書く内容 |
|---|---|
| 機能名 | システム機能一覧の機能名 |
| 取引名 | 取引の名前（ファイル名と同じ） |
| テストターゲット名 | クラス単体：テスト対象のクラス・モジュール名。リクエスト単体：リクエストを受けるクラス・ハンドラー名 |
| リクエストID | リクエスト単体のみ。WebサービスAPI一覧のAPI ID など |

PJ名（1行目）・サブシステム名（4行目）・作成者・作成日・更新者・更新日は、`変更履歴` シートから自動で表示される数式なので、書かない。

## 表の列

| 列 | 書き方 |
|---|---|
| ケースNo | 数式で自動で振られる（「詳細-観点-テスト内容」の連番）。**書かない** |
| 大項目・中項目・小項目・詳細・観点 | テスト観点カタログのまま。**書き換えない**。カタログに無い観点は「追加観点」として行を足す（下記） |
| 対象外理由 | その観点をテストしない理由。テストケースを書く観点では空欄。対象外の行は、観点から右を灰色にする |
| 対応設計書・対応箇所 | その確認の根拠になる設計書と、その中の箇所（節・シート・項目）。例：`システム機能設計書`／`2.4. 処理詳細` |
| テスト内容 | 何をするか。前提条件があるときは、**先頭に `【前提】…` と書き、改行してから操作を書く** |
| 想定結果 | 何が起きれば合格か。観測できる形で書く（返り値・ステータスコード・DBの状態・ログなど） |
| テストコード | クラス単体のみ。そのケースを確かめるテストのコードの場所（例：`test_client_service.py::test_顧客を登録できる`） |
| テストデータシート名・データNo | リクエスト単体・取引単体のみ。試験で作るデータがあるときに書く。シート名には `試験データ`、データNoには、そのケースが使うデータのまとまりの番号（`D01` など）を書く。使わなければ空欄（書き方は、下の「試験データのシート」） |
| 実施者・実施日・実施結果・確認者・確認日 | 実施の記録。実施結果は `OK` / `NG` から選ぶ |

### 試験データのシート

リクエスト単体・取引単体の試験で、データを作る必要があるときは、**別のファイルに分けず、同じ仕様書の末尾に「試験データ」のシートを足して書く**（Excel だけで、試験の前提が確認できるようにするため）。

- **ケースの前提・テスト内容には、データの中身を並べない。** 「試験データを作る。」のように書き、中身は、データNoで、このシートに任せる。
- **データは、テーブルごとに、カラム名と、実際に入れるレコードで書く。** 「主な値」のような概要では、仕様書を見て、試験できることが確認できないため。
  - カラムが多いテーブルは、試験に関係しないカラムを割愛してよい。割愛したことは、表の上の注記に書く。
  - 日時のように、実行のたびに変わる値は、「試験の実行時の1日前」のように、相対的に書く。
  - 環境ごとに値が違うもの（採番された ID など）は、名前（マスタの名称など）で書き、「名前から ID を引く」と注記する。
- **共通データ（試験では作らず、環境に入っている前提のデータ）は、「入れるものの SQL ファイル名」ではなく、「入っている前提のレコード」で書く。** SQL ファイルの名前や置き場所は変わり得るため、書くと、仕様書も直すことになる。
- **個別データ（試験で作り、終わったら消すデータ）には、データNoと、そのデータを使うケースを書く。** 作る順（外部キーの順）に、テーブルを並べる。
- シートの形は、`scripts/add_test_data_sheet.py` で作る（A〜D列は幅3の見出し用、データは E 列から。共通データを先、個別データを後に並べる）。定義の書式は、スクリプト冒頭のdocstringを参照。

### 1つの観点に、テストケースが複数あるとき

観点の行の下に行を足し、2件目以降のケースを書く（ケースNoの3つ目が `1-1-1`、`1-1-2` … と増える）。
足した行の分類・観点の列は空欄にする。

### 対象外理由の書き方

「なぜこの観点でテストしなくてよいか」が、読んだ人に分かるように書く。

- 機能が無い：`メール送信が無いため対象外`
- ほかのテストで確かめる：`リクエスト単体テストで確認するため対象外`
- ほかの活動で確かめる：`アノテーションを机上確認するため対象外`

観点の取捨選択の考え方（Nablarchシステム開発ガイド「テスト項目の検討」）：
- プロジェクトに関係しない観点（その機能が無いもの）は外す。
- 残った観点も、「そのテストでバグが見つかる見込みが低い」「レビューや次の工程のテストで見つかる」「バグがあっても影響が軽い」ものは、理由を書いて外してよい。

### 追加観点（カタログに無い、プロジェクト独自の観点）

設計書の記述に当てはまる観点がカタログに無いとき（上の「資料の目的」の2）に足す。
カタログの観点の行の後ろに行を足し、観点の列に書く。
カタログに無い大項目を足すときも、残した分類のどれかの観点の後ろに置く（`after` で指定する）。
新しい詳細（または小項目・中項目・大項目）として始めるときは、その列にも書く。
足した行も、カタログの観点と同じく、テストケースか対象外理由のどちらかを埋める。

## 作り方（ローカル実行）

手で行を足すと、ケースNoの数式・罫線・入力規則・印刷範囲がずれるため、`scripts/build_unit_test_spec.py` で組み立てる。

1. テスト項目を、定義ファイル（JSON）に書く。書き方は `build_unit_test_spec.py` の冒頭の説明を参照する。
   - `分類` に、その機能にある分類（大項目〜）を書く。書いていない分類の行は、シートから消える。
   - 設計書の記述を順に見て、確かめる観点を当てる。カタログに無いものは `追加観点` に書く。
   - 観点は、空のテンプレートでのケースNoの前2つ（「詳細-観点」。例：`3-2`）で指定する（組み立てた後のケースNoは、消した行の分だけ詰まる）。
   - 残した分類のうち、まとめて対象外にするものは、`対象外` に分類と理由を書く。
   - 表紙・変更履歴の内容（PJ名・サブシステム名・会社名・部門名・変更履歴）は `document` に書く。
   - 前提条件は `前提` に書くと、テスト内容の先頭に `【前提】…` として入る。
2. 組み立てる。
   ```bash
   python scripts/build_unit_test_spec.py "assets/templates/フォーマット/単体テスト仕様書(Webサービス)_(取引ID)_(取引名).xlsx" <定義json> <出力パス> --cases-json <ケース一覧json>
   ```
   どちらも埋まっていない観点が残っていると、その観点の番号を挙げてエラーになる（書きかけの確認だけなら `--allow-unaddressed`）。
   表紙・変更履歴も、このスクリプトが書く（このテンプレートに『目次』シートは無い）。
3. `export_sheet_preview.py` でテスト仕様のシートをPDFにし、行の高さ・折り返しを目で確かめる。
   PDFをReadツールで開けない（`pdftoppm`が無い）ときは、PyMuPDFでPNGにして開く（`SKILL.md`の手順9）。

### 版を上げるとき（変更箇所を赤字にする）

既存の仕様書の版を上げるときは、その版で変えた箇所だけを赤字にし、前の版の赤字は残さない。
定義ファイル（JSON）の、変えたケース・観点に `"changed"` を付けて、組み立て直す。
組み立て直すので、前の版の赤字は消え、今の版で `"changed"` を付けた箇所だけが赤字になる（前の版の `"changed"` は消す）。

| 付ける場所 | 指定 | 赤字になるセル |
|---|---|---|
| ケース（`cases` の1件） | `true` | そのケースの、値のある列の全部（対応設計書・対応箇所・テスト内容・想定結果・テストコードなど） |
| ケース | 列名のリスト（例：`["想定結果", "テストコード"]`） | 指定した列だけ |
| 追加観点・対象外理由の記入 | `true` | 分類と観点（対象外理由の記入は、対象外理由）の全部 |
| 追加観点・対象外理由の記入 | 列名のリスト（例：`["観点"]`） | 指定した列だけ |

- 1つでも付けると、表紙の版数も赤字になる。
- 変更履歴にも、新しい版の行を足す（`document` の `変更履歴`）。
- 新しい観点を足すときは、既存のケースNoがずれないよう、追加観点の並びの最後に足す。

`--cases-json` には、組み立てた結果の全行（ケースNo・分類・観点・テスト内容・想定結果・テストコードなど）が出る。
openpyxlで書いたファイルにはケースNo（数式）の計算結果が入らないため、ケースNoを確かめたり、ほかの仕組み（テストのレポートなど）で使ったりするときは、こちらを使う。
