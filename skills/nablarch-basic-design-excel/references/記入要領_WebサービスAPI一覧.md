# 記入要領: WebサービスAPI一覧

## 資料の目的

対象サブシステムが公開するREST APIの一覧表。
「①API全体の前提（ベースURL・バージョン）」と「②APIごとの詳細一覧」の2段構成。②の表はNo./API ID/API名称/処理概要に加え、プロトコル・HTTPメソッド・URL・データ形式・電文ID・対応取引まで含む10項目である。

## ①概要（シート『1』7〜11行目）

| 位置 | 項目名 | 記入内容 | 記入例（B1顧客管理システム） |
|---|---|---|---|
| 7行目 | 概要文 | 「[システム名]が提供するRESTful WebサービスのAPIの一覧である。」の`[システム名]`部分を実際のシステム名に置き換える | 固定文をそのまま使用可 |
| 10行目 | コンテキストルート | 全APIに共通するベースパス | `/`（B1の例）／`/account/api/v1`（Nablarch標準サンプルの業務別パス例） |
| 11行目 | APIバージョン | APIのバージョン表記 | `v1` |

## ②API一覧（16〜17行目が見出し、18行目以降がデータ）

| 項目名 | 記入内容 | 記入例（B1顧客管理システム） |
|---|---|---|
| No. | 通し番号 | 1, 2, 3... |
| API ID | システム機能一覧・システム機能設計書と対応するID | `B10101`, `B10102`, `B10103` |
| API名称 | 機能の名称（体言止め） | 顧客検索、顧客詳細取得、顧客登録 |
| 処理概要 | 1〜2文程度の処理内容説明（「〜する。」で統一） | 「指定された検索条件に合致する顧客を検索し、検索結果を返却する。」 |
| プロトコル | ※プルダウン：`HTTP,HTTPS` | HTTPS |
| HTTPメソッド | GET/POST/PUT/DELETE等 | GET |
| リクエストURL | エンドポイントパス。`:`始まりはパスパラメータの意味 | `/clients`, `/clients/:clientId` |
| データ形式（request／response） | ※プルダウン：`-,XML,JSON` | JSON／JSON |
| 文字コード | 電文の文字コード | UTF-8 |
| インタフェース（入力電文ID／出力電文ID） | 対応する外部インタフェース設計書(JSON)の電文ID | 入力＝`-`（GETの場合）、出力＝`B10101P` |
| 処理対象取引（取引ID／取引名） | システム機能一覧・システム機能設計書の取引ID・取引名と一致させる | `B10101`／顧客検索 |

## 記入時のポイント

- **API IDと処理概要は、システム機能設計書(Webサービス)の該当シートと1対1で対応させる**。先にシステム機能一覧でID採番を確定させておくと、この一覧はほぼ転記だけで埋まる。
- 「インタフェース（入力電文ID／出力電文ID）」は、外部インタフェース設計書(JSON)のファイル名（電文ID部分）と一致させる。GETのようにリクエストボディが無い場合は入力電文IDを「-」にする。
- コンテキストルートは全社／全システムでURL設計方針が決まっていることが多いので、先にアーキテクトへ確認しておく。
