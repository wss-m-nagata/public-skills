# 記入要領: システム機能設計書(バッチ)

## 資料の目的

1つのバッチ取引について、起動パラメータ・処理内容・入出力・終了コード・処理詳細（ロジック）・出力データの編集仕様までを定義する。
**バッチ取引につき1ファイル**作成する。1つの取引の中に複数のバッチ処理（ステップ）がある場合は、シート『2』を処理数分コピーする。
※B1顧客管理システムのようにバッチを持たないシステムでは、この資料は不要（Must4の対象外にできる）。

## シート『1.1. バッチ取引概要』

**このシート名は固定名であり、リネームしない**（目次にも`1.1. バッチ取引概要`と固定の文言で載っており、`2.`のシートのようなプレースホルダーではない）。取引概要の内容が薄い・見出しの言い換えのようなテキストになっていないか（下記参照）に注意する。

**列の構造に注意**：D列（8〜34行目）は`取引ID`・`取引名`・`取引概要`・`起動条件`・`前提事項`という**固定ラベル**であり、書き込み対象ではない（上書きしないこと）。実際の値は**H列**に書く。

| 位置（行） | 項目名 | 記入内容 |
|---|---|---|
| 8行目 | 取引ID | ラベルはD8（固定）。値は**H8**にバッチ取引の識別ID（例：`BA10601`）を書く |
| 9行目 | 取引名 | ラベルはD9（固定）。値は**H9**にバッチの名称（例：期間内プロジェクト一覧出力バッチ）を書く |
| 10行目〜（ラベルD10〜G29の結合セルは固定） | 取引概要 | 値は**H10から下方向**に、バッチが何をするかを書く。1文（または一まとまりの内容）ごとに別の行（H10、H12、H13…のように）に分け、間に空行を1行はさんで区切る。**1つのセルに複数文を詰め込んで長文をべた書きしない**（下記「取引概要の書き方」を参照） |
| 30行目〜（ラベルD30〜G33の結合セルは固定） | 起動条件 | 値は**H30から下方向**に、いつ・何をトリガに起動するかを書く（例：日次バッチとして深夜0時に起動） |
| 34行目〜（ラベルD34〜G41の結合セルは固定） | 前提事項 | 値は**H34から下方向**に、起動前に満たされているべき条件を書く（無ければ「なし。」をH34に） |

### 取引概要の書き方

- 取引概要・起動条件・前提事項は、1つのセルに`\n`で複数行を詰め込むのではなく、**1文（または一まとまりの内容）ごとに別の行のセル**（H10, H12, H13…）に分けて書く。公式サンプルも実際にこの書き方をしている（例：`H10`＝「口座振替結果をシステムに反映する。」のように、1行1文を目安に書く）。
- 用意されている行数（取引概要は10〜29行目、起動条件は30〜33行目、前提事項は34〜41行目）で書ききれない場合が実際にはほとんど無いはずだが、それでも足りない場合は、行を潰さず罫線・書式を保ったまま範囲を広げることを検討する。

### 1.2. バッチ処理一覧（44〜59行目）

見出し：`No. / バッチ処理ID / 処理名 / 常駐 / 多重化要否(プロセス/スレッド) / 処理概要`

この取引が複数の処理ステップ（例：ワークテーブル登録→本テーブル登録）から成る場合、その一覧をここに記載する。
常駐バッチかどうか、多重実行を許容するかをプロセス単位・スレッド単位で記載する。
**「常駐」は常駐バッチの場合「○」を記入する。「多重化要否」はプロセス・スレッドそれぞれ、必要な場合「○」、不要な場合「-」を記入する**（Excelセルコメントより）。

## シート『1.3. バッチ処理フロー』

このシートには、あらかじめ「凡例」（論理テーブル・帳票・取引ID・条件分岐・結合子・処理の開始/終了等の記号の意味を示す図形）が用意されている。**この凡例と同じ記号を使って、このバッチ取引の実際の処理の流れを表す図（フローチャート）を作成し、凡例の横または下に配置する。**

- 図の作り方は、Mermaidでフローチャートを作成して画像化し、シートに貼り付ける方法を基本とする（`scripts/insert_flow_diagram.py`を使用。凡例の記号との対応は目安でよく、Mermaidの標準的な図形（開始/終了=角丸、処理=四角、分岐=ひし形）で表現する）。Mermaidのソースコードは、画像の枠外（AM列以降）に**テキストとして**貼り付けておく（後から見た人が図の内容を追跡・修正できるようにするため）。
- **実行環境に`mmdc`（画像化ツール）が無い場合、`insert_flow_diagram.py`は自動的に画像挿入をスキップし、Mermaidソースの貼り付けのみ行う。** この場合スクリプトが出力する案内文をそのままユーザーに伝え、ソースから画像を作成して手動で貼り付けてもらうよう依頼すること（自分で画像化しようとしない）。
- **ノード数が多いフローは画像が縦に長くなり、既存の凡例と重なることがある**。`insert_flow_diagram.py`は挿入前に概算の重なりチェックを行い、重なりの可能性があれば結果に`overlap_warning`を返す。この判定は行高・列幅の概算に基づく目安なので、警告が出た場合（出なくても心配な場合）は`scripts/export_sheet_preview.py`でこのシートをPDF化し、実際に重なっていないか目視確認すること（Windows＋Excelがある環境限定）。重なっている場合は、アンカーセルを凡例の無い位置にずらすか、`flowchart LR`（左右方向）に変更して縦幅を抑える。
- Mermaidでの作成が難しい場合は、図形オブジェクト（四角・ひし形・矢印等）で直接描いてもよい。
- 処理フローの内容は「2.6 処理詳細」の記述と矛盾しないようにする（フローは全体の流れの可視化、処理詳細はロジックの文章化という役割分担）。

## シート『2. バッチ処理ID(バッチ処理名)』（実際は`2. BA10601(期間内プロジェクト一覧出力)`のようにリネームする。括弧は半角。Webサービス版は全角括弧だが、こちらは半角なので注意）

**このシートは公式テンプレートのプレースホルダー名（`2. バッチ処理ID(バッチ処理名)`。「バッチ処理ID」「バッチ処理名」は角括弧が付いているわけではなく、この文字列そのものがプレースホルダー）のまま提供される。** 内容を記入したら、`scripts/rename_sheet.py`で実際の値（例：`2. BA10601(期間内プロジェクト一覧出力)`）にリネームする。手動でシート名を書き換えるとタイプミスが起きやすいため、リネームは必ずこのスクリプトを使う。リネームし忘れたまま「2. バッチ処理ID(バッチ処理名)」という汎用名で出力しない。

### 2.1. 処理概要（8〜10行目）

`処理単位 / 処理順序 / リカバリ方法`

- 処理単位：処理の実施単位を記述する。
- 処理順序：入力データを処理する順番を記述する（例：ユーザ管理テーブル.ユーザIDの昇順）。キーが複数ある場合は優先順位の高いキーから順に左から並べる（例：契約テーブル.契約日の昇順＞契約テーブル.契約IDの昇順）。
- リカバリ方法：複雑な場合は別紙に記述する。

### 2.2. 起動パラメータ（13〜18行目）

見出し：`No. / パラメータ名 / 必須 / パラメータ値 / 説明 / パラメータ名(物理)`

起動時に渡すパラメータを列挙する。**システム共通の起動パラメータ以外に必要なパラメータがある場合のみ記述する**（システム共通の起動パラメータの設定値は方式設計書側に書き、システム機能設計書には記述しない）。「パラメータ名(物理)」はプログラム内で使う実際の変数名。
「必須」は必須「○」、省略可「-」を記入する（省略したときの動作は「説明」欄に記述する）。
「パラメータ値」は設定可能な値を記述する。具体的な値がある場合は`[値]:[値の意味]`（例：`0:指定なし、1:指定あり`）、無い場合は`[設定値名]([書式])`（例：`請求日(yyyyMMdd)`）の形式で書く（いずれもExcelセルコメントより）。

### 2.3. 処理結果一覧（21〜26行目）

見出し：`No. / 終了コード / 障害コード / 処理結果`

正常・異常それぞれの終了コードと発生条件を記載する。

### 2.4. 入出力一覧（29〜35行目）

見出し：`No. / 入出力名 / 種別 / I/O / DBアクセス種別(C/R/U/D/ﾛｯｸ対象) / 備考`（Webサービス版と同じ形式）

**記載範囲（Excelセルコメントより）**：当バッチ処理で作成/参照/更新/削除を行う**全て**のテーブル/ファイル/電文/帳票/メールを記述する。バリデーションのために参照するテーブルも記述する。**当バッチ処理が呼び出す共通コンポーネントが使用するテーブル/ファイル/電文/帳票/メールは記述しない**（呼び出し先の内部実装まで一覧に含めない）。

### 2.5. 入力データ定義（38〜56行目）

対象（テーブル／ファイル・メール・電文）ごとに区切って記載する。

- 2.5.1. `[入力対象（テーブル名）]`：見出しを実際のテーブル名に変更した上で、
  - 「取得項目」表（`No./取得元/取得項目/必須/ドメイン名/備考`）：どのテーブルのどの項目を取得するか。**バリデーションのために取得・参照するデータはここに記述しない**（Excelセルコメントより）。**「必須」列の選択肢は`○`/`-`**（テーブル定義書の`○`/`×`とは異なるので注意。詳細は`記入要領_共通シート.md`）。
  - 「取得条件」：抽出条件（WHERE句に相当する条件）を自由記述。ファイルを全件読み込む場合等、特に無い場合は「-」と記述する。
- 2.5.2. `[入力対象（ファイル名/メール名/電文名）]`：「【外部インタフェース定義書_XXX】を参照。」の下に、ファイルID/メールID/電文IDのいずれか、およびファイル名/メール名/電文名のいずれかを記載する。**「ファイルID」「ファイル名」は固定ラベルであり、電文の場合でも文字列は変更しない**。値はラベルの**右隣の結合セル**に書く。
  ⚠️**行番号は絶対ではない**：未編集の`フォーマット/`テンプレートでは`E56:G56`="ファイルID"ラベル→値は`H56:L56`、`M56:O56`="ファイル名"ラベル→値は`P56:AG56`だが、これはあくまで元テンプレートでの例に過ぎない。この行より前（2.4・2.5.1等）で`insert_row_block.py`・`extend_table_rows.py`を使っていれば、その分だけ行番号がずれる。**書き込み前に必ず、対象ファイルの実際のセルで「ファイルID」「ファイル名」の文字列がどの行にあるかを確認してから、その右隣の列に書くこと**（`extract_structure.py`を対象ファイルに対して再実行し、「ラベル→値入力セルの候補」を確認するのが確実）。行番号を記入要領の記載のまま鵜呑みにしない。

**入力対象が2つ以上ある場合**（例：テーブルを2つ参照する）は、2.5.1（または2.5.2）のブロックをその数だけ複製する必要がある。手動でセルをコピーすると結合セル・入力規則の複製漏れや後続セクション（2.6.等）の上書き事故につながるため、`scripts/insert_row_block.py`でブロック単位（見出し行から次の見出し行の直前まで）を複製し、後続内容を自動的に下にずらすこと。このシート（`表紙`・`変更履歴`・`目次`以外の詳細シート）は使用対象に含まれる。

### 2.6. 処理詳細（59〜88行目）

`(1) [処理名称]` の形で処理をステップに分けて自由記述する広いエリア。実際の業務ロジック（集計方法、更新順序、トランザクション制御、異常時のロールバック方針等）を記述する。
**処理は目的（入力、各種業務処理、出力等）に分割して記載する**（Excelセルコメントより）。例：`(1) ○○バリデーション` `(2) ○○取得` `(3) ○○集計` `(4) ○○登録`

**この領域は罫線も結合セルも無い完全な空白であり、必要な表はその場で新規に作る**。表が必要かどうか、必要ならどんな列構成にするかは、**そのステップで実際に何を伝える必要があるか**で決める（後述のプリセットに当てはめられそうかで決めない）。`scripts/insert_adhoc_table.py`で作成する（詳細は`SKILL.md`のローカル実行の手順を参照）。

- 公式サンプル（口座振替結果ワークテーブル作成）で実際によく使われていた列構成として、`--preset validation`（`No./バリデーション名/バリデーション内容/メッセージID/埋め込み文字列/後続バリデーションの続行判定`）・`--preset error_response_batch`（`終了コード/障害コード/メッセージID/埋め込み文字列`）・`--preset parameter`（`パラメータ/設定値`）を用意している。**これらは「必ず使うべき型」ではなく、内容が自然に当てはまる場合だけ使う時短用のショートカット**であり、当てはまらなければ無理に使わない。
- プリセットに当てはまらない表（当てはまる場合でも列数・見出しを調整したい場合を含む）は、既存の表（`2.4 入出力一覧`等）の書式を借用しつつ列定義JSONを自作する。
- プリセットの列位置は字下げ無しの場合の例。サンプルには`(a)/(b)...`のように1段階字下げした位置に同じ表を置く例が多数あり（バリデーション表が1シート内で6回、字下げ位置で繰り返し使われている）、その場合は列を1〜2列右にずらす必要がある（プリセットをそのまま使わず、列定義JSONで調整すること）。

### 2.7. 出力データ定義（89〜124行目）

出力先の種類ごとに3パターンの書き方がある。

- 2.7.1. `[処理名(登録)]：[処理対象（テーブル名）]` — 新規登録する場合。`No./項目名/編集元（ファイル/テーブル名・項目名）/編集仕様/備考` の表で、登録する各カラムの値がどこから来てどう編集されるかを記載。
- 2.7.2. `[処理名(更新/削除)]：[処理対象（テーブル名）]` — 更新・削除する場合。「更新条件」を自由記述したうえで、同様の編集仕様表を記載。
- 2.7.3. `[処理名(出力)]：[処理対象（ファイル名/メール名/電文名）]` — ファイル・電文として出力する場合。「(1) 項目定義」で外部インタフェース定義書を参照指示し、「(2) 編集仕様」で `No./項目ID/項目名/編集元（ファイル/電文/テーブル・項目名）/編集仕様/備考` を記載。ここも2.5.2と同様、「ファイルID」（未編集テンプレートでは`F115:H115`）「ファイル名」（同`N115:P115`）は固定ラベルであり、値はそれぞれ右隣の結合セルに書く。**行番号が絶対でないことは2.5.2の注記を参照**（このシートは2.5.2よりさらに後ろにあるため、行のズレが累積しやすい）。

同じバッチ処理の中で複数の出力先がある場合は、2.7.1〜2.7.3をそれぞれ複数回（2.7.1, 2.7.2...のように）繰り返す。この場合も2.5.と同様、`scripts/insert_row_block.py`でブロックごと複製すること。

## 記入時のポイント

- 「2.4 入出力一覧」「2.5 入力データ定義」「2.7 出力データ定義」のテーブル名は、テーブル定義書の論理テーブル名と一致させる。
- 「2.6 処理詳細」「2.7 出力データ定義」は分量が多くなりがちで、調査・整理資料の記述が薄いと不明点が多く出る部分。
- ジョブ間の実行順序・依存関係そのものは、この設計書ではなく「ネット・ジョブフロー」（Must4の対象外）に記載する。
