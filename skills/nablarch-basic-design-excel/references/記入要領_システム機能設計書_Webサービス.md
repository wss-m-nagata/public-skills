# 記入要領: システム機能設計書(Webサービス)

## 資料の目的

1つのAPI（取引）について、入出力・処理結果・処理詳細（ロジック）・出力データの編集仕様までを詳細に定義する。
**取引（API）1つにつき1ファイル**作成する（ファイル名の`(取引ID)_(取引名)`部分を実際の値に置き換える）。

## シート『1.1. Webサービス取引概要』

**このシート名は固定名であり、リネームしない**（目次にも`1.1. Webサービス取引概要`と固定の文言で載っており、`2.`のシートのようなプレースホルダーではない）。取引概要の内容が薄い・見出しの言い換えのようなテキストになっていないか（下記参照）に注意する。

**列の構造に注意**：D列（8〜34行目）は`取引ID`・`取引名`・`取引概要`・`前提事項`という**固定ラベル**であり、書き込み対象ではない（上書きしないこと）。実際の値は**H列**に書く。

| 位置（行） | 項目名 | 記入内容 | 記入例（B10101_顧客検索） |
|---|---|---|---|
| 8行目 | 取引ID | ラベルはD8（固定）。値は**H8**にこの取引固有のIDを書く | `B10101` |
| 9行目 | 取引名 | ラベルはD9（固定）。値は**H9**に取引の名称を書く | 顧客検索 |
| 10行目〜（ラベルD10〜G29の結合セルは固定） | 取引概要 | 値は**H10から下方向**に書く。1文（または一まとまりの内容）ごとに別の行（H10、H12、H13…のように）に分け、間に空行を1行はさんで区切る。**1つのセルに複数文を詰め込んで長文をべた書きしない**（下記「取引概要の書き方」を参照） | H10=「指定された検索条件に合致する顧客を検索し、検索結果を返却する。」／H12=「該当する顧客が存在しない場合は、空の配列を返却する。」 |
| 30行目 | API ID | ラベルはD30（固定）。値は**H30**にWebサービスAPI一覧のAPI IDと**一致させて**書く | `B10101` |
| 31行目 | API名称 | 値は**H31**。WebサービスAPI一覧のAPI名称と一致させる | 顧客検索 |
| 32行目 | リクエストURL | 値は**H32**。エンドポイントパス | `/clients` |
| 33行目 | HTTPメソッド | 値は**H33**。GET/POST/PUT/DELETE等 | `GET` |
| 34行目〜（ラベルD34〜G41の結合セルは固定） | 前提事項 | 値は**H34から下方向**に、取引概要と同じ書き方で書く（なければ「なし。」をH34に） | なし。 |

### 取引概要の書き方

- 取引概要・前提事項は、1つのセルに`\n`で複数行を詰め込むのではなく、**1文（または一まとまりの内容）ごとに別の行のセル**（H10, H12, H13…）に分けて書く。公式サンプルも実際にこの書き方をしている（例：`H10`＝「指定口座への振込を依頼する。」、1行空けて`H12`＝「振込要求電文を受け取り、振込依頼レコードを作成する。」、`H13`＝「その後、…返送する。」）。
- 用意されている行数（取引概要は10〜29行目、前提事項は34〜41行目）で書ききれない場合が実際にはほとんど無いはずだが、それでも足りない場合は、行を潰さず罫線・書式を保ったまま範囲を広げることを検討する。

## シート『1.2. 処理フロー』

このシートには、あらかじめ「凡例」（論理テーブル・帳票・取引ID・条件分岐・結合子・処理の開始/終了等の記号の意味を示す図形）が用意されている。**この凡例と同じ記号を使って、この取引の実際の処理の流れを表す図（フローチャート）を作成し、凡例の横または下に配置する。**

- 図の作り方は、Mermaidでフローチャートを作成して画像化し、シートに貼り付ける方法を基本とする（`scripts/insert_flow_diagram.py`を使用。凡例の記号との対応は目安でよく、Mermaidの標準的な図形（開始/終了=角丸、処理=四角、分岐=ひし形）で表現する）。Mermaidのソースコードは、画像の枠外（AM列以降）に**テキストとして**貼り付けておく（後から見た人が図の内容を追跡・修正できるようにするため）。
- **実行環境に`mmdc`（画像化ツール）が無い場合、`insert_flow_diagram.py`は自動的に画像挿入をスキップし、Mermaidソースの貼り付けのみ行う。** この場合スクリプトが出力する案内文をそのままユーザーに伝え、ソースから画像を作成して手動で貼り付けてもらうよう依頼すること（自分で画像化しようとしない）。
- **ノード数が多いフローは画像が縦に長くなり、既存の凡例と重なることがある**。`insert_flow_diagram.py`は挿入前に概算の重なりチェックを行い、重なりの可能性があれば結果に`overlap_warning`を返す。この判定は行高・列幅の概算に基づく目安なので、警告が出た場合（出なくても心配な場合）は`scripts/export_sheet_preview.py`でこのシートをPDF化し、実際に重なっていないか目視確認すること（Windows＋Excelがある環境限定）。重なっている場合は、アンカーセルを凡例の無い位置にずらすか、`flowchart LR`（左右方向）に変更して縦幅を抑える。
- Mermaidでの作成が難しい場合は、図形オブジェクト（四角・ひし形・矢印等）で直接描いてもよい。
- 処理フローの内容は「2.4 処理詳細」の記述と矛盾しないようにする（フローは全体の流れの可視化、処理詳細はロジックの文章化という役割分担）。

## シート『2. 取引ID（取引名）』（実際は`2. B10101（顧客検索）`のようにリネームする。括弧は全角）

**このシートは公式テンプレートのプレースホルダー名（`2. 取引ID（取引名）`。「取引ID」「取引名」は角括弧が付いているわけではなく、この文字列そのものがプレースホルダー）のまま提供される。** 内容を記入したら、`scripts/rename_sheet.py`で実際の値（例：`2. B10101（顧客検索）`）にリネームする。手動でシート名を書き換えるとタイプミスが起きやすいため、リネームは必ずこのスクリプトを使う。リネームし忘れたまま「2. 取引ID（取引名）」という汎用名で出力しない。

### 2.1. 入出力一覧（8〜12行目）

見出し：`No. / 入出力名 / 種別 / I/O / DBアクセス種別(C/R/U/D/ﾛｯｸ対象) / 備考`

- 種別はプルダウン：`-, テーブル, 電文, I/Fファイル, 帳票, 電子メール` のいずれかを選ぶ（自由記述不可）。
- I/Oは入力(`I`)/出力(`O`)。
- DBアクセス種別は該当する操作の列に `○` を付ける（該当しない列は `-`）。

### 2.2. 処理結果一覧（17〜23行目）

見出し：`No. / HTTPステータスコード / 処理結果`

正常系（200・201等）と異常系（400・404・500等）をすべて列挙し、それぞれ発生条件を説明文で記載する。

### 2.3. 入力データ定義（26〜38行目）

- 2.3.1. 項目定義：まず「【外部インタフェース定義書_XXX】を参照。」という注記の下に、対象の**電文ID／電文名**を記載する。**「電文ID」「電文名」は固定ラベルであり、上書きしない**。値はラベルの右隣の結合セルに書く。
  ⚠️**行番号は絶対ではない**：未編集の`フォーマット/`テンプレートでは`E31:F31`="電文ID"ラベル→値は`G31:L31`、`M31:N31`="電文名"ラベル→値は`O31:AH31`だが、これは元テンプレートでの例に過ぎない。この行より前（2.1・2.2等）で`insert_row_block.py`・`extend_table_rows.py`を使っていれば、その分だけ行番号がずれる。**書き込み前に必ず、対象ファイルの実際のセルで「電文ID」「電文名」の文字列がどの行にあるかを確認してから、その右隣の列に書くこと**（`extract_structure.py`を対象ファイルに対して再実行し、「ラベル→値入力セルの候補」を確認するのが確実）。
- その下の表（見出し34〜35行目）：`No / パラメータ（論理名・物理名） / 必須 / ドメイン名 / 備考`
- ここは概要レベルの対応表であり、型・桁・必須の詳細な一次情報は「外部インタフェース設計書(JSON)」側に書く（二重管理を避けるため）。

### 2.4. 処理詳細（42〜89行目）

- `(1) [処理名称]` の形で、処理をステップに分けて自由記述する広いエリア（1つの処理につき約48行分の記入スペースがある）。
- ここに実際の業務ロジック（バリデーション内容、検索条件の組み立て方、更新順序、トランザクション制御等）を記述する。
- **処理は目的（入力、各種業務処理、出力等）に分割して記載する**（Excelセルコメントより）。例：`(1) ○○バリデーション` `(2) ○○取得` `(3) ○○集計` `(4) ○○登録`
- **文章だけでは誤解されるリスクが高い仕様は、図表や数式を使って理解しやすく書く**（同コメントより）。
- **この領域は罫線も結合セルも無い完全な空白であり、必要な表はその場で新規に作る**。表が必要かどうか、必要ならどんな列構成にするかは、**そのステップで実際に何を伝える必要があるか**で決める（後述のプリセットに当てはめられそうかで決めない）。`scripts/insert_adhoc_table.py`で作成する（詳細は`SKILL.md`のローカル実行の手順を参照）。
  - 公式サンプル（振込依頼作成）で実際によく使われていた列構成として、`--preset validation`（`No./バリデーション名/バリデーション内容/メッセージID/埋め込み文字列/後続バリデーションの続行判定`）・`--preset error_response_web`（`HTTPステータスコード/障害コード/メッセージID/埋め込み文字列`）・`--preset parameter`（`パラメータ/設定値`）を用意している。**これらは「必ず使うべき型」ではなく、内容が自然に当てはまる場合だけ使う時短用のショートカット**であり、当てはまらなければ無理に使わない。
  - プリセットに当てはまらない表（当てはまる場合でも列数・見出しを調整したい場合を含む）は、既存の表（`2.1 入出力一覧`等）の書式を借用しつつ列定義JSONを自作する。
  - プリセットの列位置は字下げ無しの場合の例。サンプルには`(a)/(b)...`のように1段階字下げした位置に同じ表を置く例もあり、その場合は列を1〜2列右にずらす必要がある（プリセットをそのまま使わず、列定義JSONで調整すること）。

### 2.5. 出力データ定義（90〜106行目）

- 2.5.1. 項目定義：「【外部インターフェース定義書_XXX】を参照。」の下に対象の**電文ID／電文名**を記載する。ここも2.3.1と同様、「電文ID」（未編集テンプレートでは`E95:F95`）「電文名」（同`M95:N95`）は固定ラベルであり、値はそれぞれ右隣の結合セルに書く。**行番号が絶対でないことは2.3.1の注記を参照**（このシートは2.3.1よりさらに後ろにあるため、行のズレが累積しやすい）。
- 2.5.2. 編集仕様（見出し100〜101行目）：`No. / 項目ID / 項目名 / 編集元（電文/テーブル名・項目名） / 編集仕様 / 備考`
  - レスポンス電文の各項目が、どのテーブル・どの電文のどの項目から、どういうロジックで編集（変換・計算・整形）されるかを1項目1行で記載する。
  - ここが実質的な「入力→出力の変換ロジック」の一次情報になる。

## 記入時のポイント

- 「2.1. 入出力一覧」のテーブル名は、テーブル一覧・テーブル定義書の論理テーブル名と完全一致させる。
- 「2.2. 処理結果一覧」は、外部インタフェース設計書（応答電文）のエラーコード定義と対応させる。
- 「2.3」「2.5.1」は電文ID/電文名を明記するだけにとどめ、項目の型・桁の詳細は外部インタフェース設計書に書く。
- 「2.4 処理詳細」「2.5.2 編集仕様」は分量が多くなりがちなので、調査・整理資料の記述が薄い場合はここで最も多くの追加確認（不明点の質問）が発生しやすい。

## 注意（実例とテンプレートの差異）

このリポジトリのB1顧客管理システムの実例は、Spring Framework版向けに独自調整された**古い書式**であり、2.3の項目定義欄が「No./パラメータ名/説明」という簡略構成になっているなど、公式Nablarchテンプレート（電文ID/電文名＋No/パラメータ(論理名/物理名)/必須/ドメイン名/備考）とは**構造が異なる**。
内容の書き方の参考にはなるが、**セルの位置・列構成は必ず最新の空テンプレート（フォーマット側）に合わせる**こと。B1実例をそのままコピーしてはいけない。
