# Nablarch基本設計書Excel 作成・更新スキル

## 目的

バックエンドの基本設計書を、独自の書式ではなくNablarch開発標準のフォーマットに沿って標準化して作成・維持することを支援する。フォーマットが逸脱すると、他プロジェクトとの一貫性やレビュー性が損なわれる。

この目的を達成するには、次の2つの手段を両方とも満たす必要がある。

1. **書くべき内容を正しく確定すること** — 誰に何を確認し、どの資料を読むか（「内容を確定する（ユーザーとのやり取り）」）
2. **確定した内容を、標準フォーマットを壊さずにExcelへ反映すること** — 結合セル・数式・プルダウン等を保持したまま書き込む（「内容を確定する」完了後、「ローカル実行の手順」または、Claude for Microsoft 365の場合は`plugin_guide.md`）

以降のセクションはこの2つの手段を具体的に説明する。「Excelを壊さない」こと自体は目的ではなく、手段②を確実に行うための技術的な補足に過ぎない。

## このスキルが対象とする範囲（Must4）

Nablarch開発標準の基本設計書のうち、バックエンド（画面を持たないAPI/バッチ系システム）の基本設計として**最低限必須**な4カテゴリ・8テンプレートを対象にする。

| カテゴリ | テンプレート |
|---|---|
| ①機能一覧 | システム機能一覧 |
| ②機能設計書 | システム機能設計書(Webサービス)／システム機能設計書(バッチ) |
| ③インタフェース | 外部インタフェース一覧／外部インタフェース設計書(JSON)／WebサービスAPI一覧 |
| ④データモデル | テーブル一覧／テーブル定義書 |

ドメイン定義書・コード設計書・メッセージ設計書・採番一覧・ジョブフロー設計・単体テスト仕様書・画面系設計書は対象外。  
これらが必要になった場合は、[Nablarch開発標準の設計ドキュメント](https://github.com/nablarch-development-standards/nablarch-development-standards/tree/main/030_%E8%A8%AD%E8%A8%88%E3%83%89%E3%82%AD%E3%83%A5%E3%83%A1%E3%83%B3%E3%83%88)とこのスキルを参考に作成すること。

## なぜこのスキルが必要か

前段の手段②（標準フォーマットを保ったまま安全に内容を反映すること）は見た目以上に難しく、実際に検証しないと分からない技術的な落とし穴がいくつもある。実際に検証して分かった問題を機械的に防ぐのが、このスキルのローカル実行部分の役割。

1. **PJ名/システム名/サブシステム名は「変更履歴」シートにしか書けない** — 他の全シートのこの欄は`変更履歴`シートを参照する数式になっており、直接上書きすると数式が消える。
2. **テーブル定義書の「データ型」プルダウンは既定でOracle型名** — 本プロジェクトはPostgreSQL採用のため、着手前に対応方針の確認が必要。
3. **シートを複製すると入力規則(プルダウン)が消える** — openpyxlの`copy_worksheet()`の既知の制約。`duplicate_sheet.py`はこれを補って明示的にコピーする。
4. **一覧系テンプレートは記入可能行数(罫線が引かれた範囲)に限りがある** — 特に外部インタフェース一覧は約9〜10行しかなく、実プロジェクトではすぐ不足する。
5. **外部インタフェース設計書(JSON)のチェックボックス型フォームコントロール(VML/ctrlProps)はopenpyxlで読み込んで保存すると跡形もなく消える** — セルの入力規則やDrawingMLの図形とは別の仕組みのため、`restore_shapes.py`でも復元できない。このテンプレートでは同じ選択肢を「□ 選択肢」のセル文字列(該当するものを`☑`に書き換える形式)で表現している(対象セル・選択肢は`記入要領_外部インタフェース設計書_JSON.md`の「選択欄」を参照)。
6. **表紙にあった「関係者外秘」等のテキストボックス(図形)は、`openpyxl`で保存すると跡形もなく消える** — セルコメントとは別の図形(DrawingML)であるため。この図形自体はユーザーの判断で削除せず保持する方針。表紙のプロジェクト名・成果物名・サブシステム名等はセルベースのレイアウト(J12/J14/J16=見出し、J19=版数、I21=最終更新日、J23/J25=数式、J28/J30=会社名・部門名)に再設計済みだが、機密区分の図形は別物として維持しているため、`apply_mapping.py`等はすべて`scripts/restore_shapes.py`(`save_with_shapes()`経由)でこの図形を毎回復元している。詳細は`記入要領_共通シート.md`。
7. **シートを複製すると、複製元シートにあった図形(画像・図表・注意書き等)は複製先に引き継がれない** — `duplicate_sheet.py`は結合セル・書式・入力規則はコピーするが、図形のコピーには対応していない(`restore_shapes.py`は「元ファイルの同名シート」にしか図形を戻せない設計のため、新規複製シートには原理的に対応できない)。外部インタフェース設計書(JSON)の「【レコード名】」シートがこれに該当していたため、そこにあった注意書きの内容はセル文字列としても持たせて対策済み(セル値は`copy_worksheet()`で複製先に引き継がれるため)。他のテンプレートで同様の図形を複製する必要が生じた場合は、同じ考え方(セル文字列として複製前に埋め込む)を検討すること。
8. **変更履歴シートの「担当者」列（AF列）を埋めないと、全シートの「作成」「変更」欄が空欄のままになる** — この列は一覧の6列（No./版数/変更日/区分/変更箇所/変更内容）に紛れて見落としやすい。
9. **グレーアウトされたセルは「記入不要」を意味するが、`apply_mapping.py` は塗りを見ないので書けてしまう** — 白いセルだけが記入対象。記入前に対象セルの塗りを確認すること。特に外部インタフェース設計書(JSON)の「2. レコード構成」は、記入できるのがレコード名1行だけである。
10. **表がブロックに分かれているシートがある** — 外部インタフェース設計書(JSON)の『【レコード名】』は3ブロック×7行で、1ブロックが1レコードに対応する。入力規則の範囲は表より1行広く、そこに書くと枠外へはみ出す。詳細は `構造メモ_外部インタフェース設計書_JSON.md` の「読み取りにくい点の補足」を参照。
11. **`extend_table_rows.py` は表の下に別のブロックがあると使えない** — 行を挿入せず下の領域を上書きするため、既存の結合セルと衝突して失敗する。その場合は `insert_rows.py` を使う。
12. **複数行の内容をセル内改行で書いても表示されない** — データ構成サンプルやレコード構成イメージのような欄は、1行につき1セルへ書く（Excelへ改行付きテキストを貼り付けたときと同じ形）。階層は列をずらして表す。

これらの詳細と根拠は`references/`配下の各ファイルに記載している。このSKILL.mdでは概要と手順だけを示す。

## 実行環境に応じた2つの進め方

ユーザーがどちらの環境で作業しているかを確認し、適切な方を使う。判断に迷う場合は聞く。

どちらの環境でも、まず後述の「内容を確定する（ユーザーとのやり取り）」を済ませてから、以下の手順で実際にExcelへ反映する。

### A. ローカル環境（Claude Code等、スクリプトを実行できる場合）— 推奨

`scripts/`内のPythonスクリプトで、値の反映を確実に・安全に行う。詳細手順は「内容を確定する」の後にある「ローカル実行の手順」を参照。

### B. Claude for Microsoft 365（Claude in Excel）— スクリプトを実行できない場合

内容確定後、`references/plugin_guide.md`に従い、「編集対象の空テンプレート」「記入サンプル」「記入要領」「構造メモ」の4点をすべて読み込ませた上で、決まった指示文（`plugin_guide.md`内に記載）を使って依頼する。このスキルが提供するスクリプトはここでは使えない（Claude for Microsoft 365はスクリプトを実行できないため）。

## 内容を確定する（ユーザーとのやり取り）

Excelへの書き込み（手段②）に進む前に、必ずこのセクションを済ませる。ここを飛ばして仮の値や推測でセルを埋めると、たとえフォーマットとしては壊れていなくても内容として誤った基本設計書になり、標準化された基本設計書の作成・維持を支援するという目的を果たせない。

1. **対象範囲を確認する**：Must4のうちどのテンプレート・どのインスタンス（どの機能／どのテーブル／どのインタフェース）を今回作成・更新するのかをユーザーに確認する。一度にすべてを作ろうとせず、対象を明確にしてから着手する。
2. **調査・整理資料を取り込む**：基本設計前の調査・整理資料（ユーザーが用意したメモ、既存のソースコード、DB定義等）が提供されている場合は、先に読み込み、記入要領が求める項目に対応づける。資料に無い項目は次のステップで質問する。
3. **記入要領と照らして内容を確定する**：対象テンプレートに対応する記入要領・構造メモ（＋`記入要領_共通シート.md`）を読み、どこに何を書くか・何に注意すべきかを把握した上で、実際に書く内容を確定する。不明点・矛盾点（資料に無い項目、命名規則の揺れ、テーブル定義書のデータ型不整合等）は仮の値を置かず、その場でユーザーに質問する。
4. **確定した内容をユーザーに提示する**：特に分量が多い項目（システム機能設計書の処理詳細など）や、機能ID・テーブル名のように後続の設計書全体に波及するキー項目は、Excelに書き込む前に内容をユーザーに提示し確認を得る。1シート分をまとめて確定してから次に進めばよく、逐一の細かい確認は不要。

内容が確定したら、次の「ローカル実行の手順」（Bの場合は`plugin_guide.md`）でExcelに反映する。

## ローカル実行の手順

前段の「内容を確定する」が完了していることが前提。編集対象の入力ファイルは、対象の設計書ファイルが既に存在する場合はそれ（`設計書/`配下）、新規に作る場合は`assets/templates/フォーマット/`の空テンプレートをコピーしたものを使う。

**⚠️一連の処理の「元ファイル」には、必ず`フォーマット/`配下のテンプレート、またはそこから始まる自分自身の出力ファイルを使う。`サンプル/`・`B1実例/`・`A1実例/`配下のファイルは記入内容の参考として読むだけにとどめ、スクリプトの「元xlsxパス」引数には絶対に指定しない。** `フォーマット/`配下のテンプレートは生成AIが扱いやすいようフォームコントロールや図形オブジェクトを意図的に極力減らして作られているが、サンプル・実例ファイルは人が手作業で編集したものであり、原本のNablarch標準どおり表紙が図形ベースのままで`[プロジェクト名]`等の古い表示を含む図形を持っている。誤って元ファイルに指定すると、その図形がそのままコピーされ、セルベースで表示されているプロジェクト名等に古い図形ベースの表示が重なって二重表示される。詳細は`記入要領_共通シート.md`の該当節を参照。

**成果物の出力先（以下の各コマンドの`<出力パス>`）は、ローカル実行の場合`プロジェクトルート直下`の`.agents/state/nablarch-basic-design-excel/`配下に統一する。** ここでいう「プロジェクトルート」は、このスキルが組み込まれているプロジェクトそのものの最上位ディレクトリを指す（`設計書/`・`sourcecode/`等と同じ階層。通常は`.git`があるディレクトリ）。**スキル自身のディレクトリの中に`.agents/`を作ってはいけない。** カレントディレクトリがどこであっても、必ずプロジェクトルートからの絶対パスまたは相対パスで指定すること。ディレクトリが存在しない場合は作成する。中間生成物（シート複製直後・行拡張直後のファイル等）も含め、このディレクトリ配下に置く。

各ステップでファイルが更新されるたびに、`verify_layout.py`の比較対象は**その直前のステップで使った入力ファイルと、そのステップの出力ファイル**にする（常に一番最初の空テンプレートと比較するわけではない）。シート複製・行拡張は意図的な構造変更なので、最初の空テンプレートと最終成果物を直接比較すると、その意図的な変更まで差分として検出されてしまい、いつまでも`OK`にならない。

1. **（必要な場合）シートを複製する**：テーブル定義書に2つ目以降のテーブルを追加する、外部インタフェース設計書(JSON)に2つ目以降のレコードを追加する等、「1インスタンス＝1シート」型のテンプレートで新しいインスタンスが必要な場合は、先に`scripts/duplicate_sheet.py`でシートを複製する。
   ```bash
   python scripts/duplicate_sheet.py <元xlsxパス> <複製元シート名> <新シート名> <出力パスA> --before-sheet データ
   ```
   検証する場合は`python scripts/verify_layout.py <元xlsxパス> <出力パスA>`を実行し、「シート構成が変化」（新シート追加）以外の差分が出ていないことを確認する（新シート追加自体は意図した変更なのでNGとして扱わない）。
2. **（必要な場合）シートをリネームする**：システム機能設計書の「2. 取引ID（取引名）」のように、複製せず唯一のシートの名前だけをプレースホルダーから実際の値に置き換える場合は、`scripts/rename_sheet.py`を使う。**手動でシート名を書き換えない**（角括弧の有無・括弧の全角半角を間違えやすい）。プレースホルダーの正確な文字列は対象テンプレートの記入要領を確認する（目次に書かれた表記とシート名自体の表記が異なる場合がある）。
   ```bash
   python scripts/rename_sheet.py <元xlsxパス> <現在のシート名> <新しいシート名> <出力パス>
   ```
   シート名がExcelの上限（31文字）を超える場合や、使用できない文字（`[ ] : * ? / \`）が含まれる場合はエラーで拒否されるので、記入要領の指示に従って短縮する。
3. **（必要な場合）複数行から成るセクションごと複製・拡張する**：「1インスタンス＝1シート」型テンプレートの詳細シート内に、`2.5.1. [入力対象（テーブル名）]`のような複数行にまたがる小節が複数個必要な場合（例：入力対象テーブルが2つ以上ある）は、`scripts/insert_row_block.py`でその小節ブロックごと複製する。次のステップの単純な1行単位の行拡張とは別物なので混同しないこと。
   ```bash
   python scripts/insert_row_block.py <直前ステップの出力パス> <シート名> <ブロック開始行> <ブロック終了行> <複製数> <開始列> <終了列> <出力パス>
   ```
   ブロックより後ろにある内容（次のセクション見出し等）は自動的に複製数分だけ下にずらされ、上書きされない。**`表紙`・`変更履歴`・`目次`シートには絶対に使わないこと**（この3シートは行・列の構成が固定であり、使用するとレイアウトが壊れる。スクリプト自体もこの3シート名を指定するとエラーで拒否する）。使用対象は一覧系テンプレートの本体シート、または「1インスタンス＝1シート」型テンプレートの詳細シートに限る。
   **開始列・終了列の指定を誤ると、指定範囲の外側にある章見出し（例:「2.5. 入力データ定義」が本文より1列左のC列にある等）がシフト・複製の対象から漏れてズレる。** このスクリプトは対象列範囲の外に値があれば実行前にエラーで検出するが、それでも迷う場合は`export_sheet_preview.py`（後述）でシートをPDF化し、見出しがどの列にあるか目視確認してから列範囲を決めること。（意図的に一部の列だけを対象にしたい場合のみ`--allow-partial-columns`でこの検出を無効化できる）
4. **（必要な場合）行を1行単位で拡張する**：記入可能行数が不足する場合は、先に行を増やす。**表の下が空き領域なら`scripts/extend_table_rows.py`、表の下に別の表やブロックがあるなら`scripts/insert_rows.py`**を使う。対象テンプレートの記入可能行数の目安は`構造メモ_*.md`の「使用範囲の目安」「罫線が設定されているセル」「読み取りにくい点の補足」を見て判断する。
   ```bash
   # 表の下が空き領域のとき（一覧系テンプレート等）
   python scripts/extend_table_rows.py <直前ステップの出力パス> <シート名> <最終データ行番号> <追加行数> <開始列> <終了列> <出力パスB>

   # 表の下に別の表やブロックがあるとき（外部インタフェース設計書(JSON)の『【レコード名】』シート等）
   python scripts/insert_rows.py <直前ステップの出力パス> <シート名> <挿入位置の行番号> <追加行数> <書式の見本にする行番号> <出力パスB>
   ```
   検証する場合は直前ステップの出力（無ければ元xlsxパス）と`<出力パスB>`を比較し、「結合セルが追加された」「入力規則が変化」等が追加した行の範囲だけであることを確認する。
   指定した範囲内に既に値が入っているセル（次のセクションの見出し等）がある場合はエラーで拒否される（見出し行を上書きしないための安全対策）。この場合、行数を減らすか、複数行から成るセクションごとずらしたいのであれば前のステップの`insert_row_block.py`を使う。意図的にそのまま上書きしたい場合のみ`--allow-overwrite`を付ける。
5. **（処理詳細等の自由記述エリアに表が必要な場合）新規の表を作る**：システム機能設計書の「処理詳細」（Web:2.4／バッチ:2.6）は罫線も結合セルも無い完全な空白エリアであり、公式サンプルでは実際にバリデーション表・エラー応答表・パラメータ表等をその場で新規作成している。`apply_mapping.py`はセルの値しか書けず、`extend_table_rows.py`・`insert_row_block.py`はどちらも「既存の表」が無いと使えないため、罫線・結合セル付きの新規の表を作る場合は`scripts/insert_adhoc_table.py`を使う。
   ```bash
   python scripts/insert_adhoc_table.py <直前ステップの出力パス> <シート名> <見出し行番号> <データ行数> - <見出し書式の元セル> <データ書式の元セル> <出力パス> --preset <プリセット名>
   ```
   見出し・データセルの罫線やフォントは、同じファイル内の既存の表（多くの場合「2.1/2.4 入出力一覧」の見出し行・データ行）から借用するため、既存セルの座標を`<見出し書式の元セル>`・`<データ書式の元セル>`に指定する。列構成は**そのステップで実際に何を伝える必要があるかで決める**（後述のプリセットに当てはめられそうかで決めない）。`--preset validation`／`error_response_web`／`error_response_batch`／`parameter`は、たまたま確認できた2つの公式サンプルによく出てきた3パターンを毎回手で列定義JSONを書かずに済むようにした**時短用のショートカット**であり、必ず使うべき型ではない。内容が自然に当てはまらない場合は無理に使わず、列定義JSONを自作する（`insert_adhoc_table.py`のdocstring参照）。対象範囲に既存の値・罫線があれば安全確認で拒否される。
   このスクリプトは見出し文字列と表の構造（罫線・結合セル）だけを作る。データ行の値は後述の`apply_mapping.py`で反映する。
6. **（処理フロー図が必要な場合）Mermaidフロー図を挿入する**：システム機能設計書の「処理フロー」系シートにMermaid記法のフローチャートを画像として挿入する場合は`scripts/insert_flow_diagram.py`を使う。
   ```bash
   python scripts/insert_flow_diagram.py <直前ステップの出力パス> <シート名> <mermaidファイルパス> <画像アンカーセル> <ソース貼り付け開始セル> <出力パス>
   ```
   `mmdc`（`@mermaid-js/mermaid-cli`）が使える環境では画像を生成して挿入し、Mermaidソースも指定セルにテキストとして貼り付ける。`mmdc`が無い環境では画像挿入を自動的にスキップし、ソースの貼り付けとユーザーへの案内文のみ出力するので、その案内文をそのままユーザーに伝えること。ノード数が多いと画像が縦に長くなり既存の図形（凡例等）と重なることがあり、その場合は`overlap_warning`が返る（行高・列幅の概算に基づく目安に過ぎないため、警告が出たら後述の`export_sheet_preview.py`で必ず実際の重なりを確認する）。
7. **値を反映する**：確定した内容を「シート名→セル座標→値」のマッピングJSONにまとめ、`scripts/apply_mapping.py`で反映する。**PJ名/システム名/サブシステム名は必ず`変更履歴`シートのE1/E2/E3に書く**（他のシートに書くと数式が壊れ、エラーで拒否される）。
   ```bash
   python scripts/apply_mapping.py <ここまでの直前ステップの出力パス(シート複製・行拡張をしていなければ元xlsxパス)> <マッピングJSONパス> <出力パスC>
   ```
   数式セルへの書き込みや罫線範囲外への書き込みは自動的に拒否される。拒否された場合は、記入要領・構造メモに立ち返って原因（セルの取り違え、行数不足等）を確認する。安易に`--force-formula-overwrite`や`--allow-outside-border`で押し切らない。
   `変更履歴`シートにE1（PJ名）・E3（サブシステム名）を書けば、表紙のJ23・J25セル（数式）にも自動反映される。
   `変更履歴`シートのD列（変更日）に日付を書き込む際は`YYYY-MM-DD`形式の文字列で渡せばよい（`apply_mapping.py`が自動でExcelの日付型に変換する。日付型にしないとI21の最終更新日の数式が正しく計算できない）。
   プルダウンの選択肢自体（テーブル定義書の「データ」シートの型一覧等）と、それに依存する値は、同じ呼び出しでまとめて書き込んでよい（`get_validations_map`が同じ呼び出し内での更新を考慮して判定するため、選択肢を書き換えた直後の値でも誤って警告が出ることはない）。

   **表紙のJ12・J16（見出しのプレースホルダー）とJ28・J30（会社名・部門名）は静的テキストであり、8テンプレートすべてで別途セル指定で書き込む必要がある。** これらは**必ず`--allow-outside-border`が要る**。表紙シートの罫線は「関係者外秘」の小さな枠(D11:P17)にしかなく、これらのセルはテンプレートの構造上もともとその外側にあるため(テーブル一覧・外部インタフェース設計書(JSON)等、テンプレートの種類によらず共通)。本文の値（一覧の各行、テーブル定義書の各列等）と同じ呼び出しで一緒に`--allow-outside-border`を付けると、本文側の座標ミスによる罫線範囲外書き込みまで一律に許可してしまい検出できなくなるため、**必ず本文とは別のマッピングJSON・別の`apply_mapping.py`呼び出しに分け、この4セルだけに絞って指定する**。
   ```bash
   # 本文は厳格に検証する(既定のまま。--allow-outside-borderは付けない)
   python scripts/apply_mapping.py <直前ステップの出力パス> <本文のマッピングJSON> <出力パスC>

   # 表紙のJ12・J16・J28・J30だけを別呼び出しで反映する
   python scripts/apply_mapping.py <出力パスC> <表紙4セルだけのマッピングJSON> <出力パスC2> --allow-outside-border
   ```
   以降のステップ（構造検証）は最終的な`<出力パスC2>`を対象に行う。

   **外部インタフェース設計書(JSON)テンプレートに限り、ここまでの構造ステップを`apply_mapping.py`で直接行わず、専用スクリプト`scripts/build_external_if_json.py`を使う。** このテンプレートは『【レコード名】』シートが3ブロック構成（1ブロック7行）になっており、項目数が7を超えるたびに行挿入とブロック間のずれ調整が必要になるため、マッピングJSONを手で組み立てると座標を間違えやすい。電文の定義（電文ID・入出力項目・サンプル値等）をJSON1ファイルにまとめ、シート複製・行挿入・値反映・チェック欄の切り替えまで一括で行う。
   ```bash
   python scripts/build_external_if_json.py "assets/templates/フォーマット/外部インタフェース設計書_(電文ID)_(電文名)_(JSON).xlsx" <電文定義json> <出力パス>
   ```
   電文定義JSONの書式は`scripts/build_external_if_json.py`冒頭のdocstring、記入内容の決まりは`記入要領_外部インタフェース設計書_JSON.md`を参照。実行後の検証（次のステップ）は他のテンプレートと同様に`verify_layout.py`で行う。
8. **構造を検証する**：直前のステップで`apply_mapping.py`に**最初に入力したファイル**（シート複製・行拡張をしていなければ元xlsxパス）と、**最終的な出力ファイル**（表紙4セルの別呼び出しをした場合は`<出力パスC2>`、していなければ`<出力パスC>`）を比較し、値以外のレイアウトが変化していないことを確認する。
   ```bash
   python scripts/verify_layout.py <直前ステップに最初に入力したファイル> <直前ステップの最終的な出力ファイル>
   ```
   ここは値の反映しか行っていないステップなので、`OK`が出るまでは完了として報告しない。差分がある場合は原因を特定し、`apply_mapping.py`の使い方（数式セルを誤って対象にしていないか等）を見直す。
9. **（Mermaidフロー図を挿入した場合・長文セルを多数記入した場合）見た目を確認する**：`verify_layout.py`は結合セル・入力規則等の構造は検証できるが、実際の見た目（図形同士の重なり、長文セルの折り返し・はみ出し）までは分からない。この環境にWindows＋Excelがあれば、`scripts/export_sheet_preview.py`でシートをPDF化して確認する。
   ```bash
   python scripts/export_sheet_preview.py <出力パスC> <シート名> <出力PDFパス> [印刷範囲]
   ```
   出力したPDFはReadツールで直接開いて視覚的に確認できる。特に`insert_flow_diagram.py`で`overlap_warning`が出た場合は、必ずこのスクリプトで実際に重なっていないか確認すること。Windows＋Excelが無い環境（Claude for Microsoft 365等）では使用できないため、その場合はユーザーに目視確認を依頼する。
10. **ユーザーに報告する**：反映したセル一覧、警告、`verify_layout.py`の結果を要約して伝える。目次シートの手動更新が必要な場合（シート複製・リネーム時）はその旨も伝える。

マッピングJSONの形式や各スクリプトのオプションの詳細は、各スクリプトの`--help`、またはファイル冒頭のdocstringを参照。

## 判断に迷ったら

- 記入要領に無い項目・列が出てきた場合：仮の値を置かず、その場でテンプレートの構造を再確認し、必要なら記入要領を更新してから進める。
  ```bash
  python scripts/extract_structure.py <xlsxパス> <出力md>
  ```
- Excelの数式・チェックボックス・条件付き書式など、`scripts/`のツールで読み書きできない要素に当たった場合：無理にopenpyxlで対処しようとせず、ユーザーに「Excelで直接確認・編集が必要」と伝える。
- `verify_layout.py`が「図形（テキストボックス等）が失われたシート」を報告した場合：`apply_mapping.py`等はsave_with_shapes()経由で自動的に図形を復元するため、通常は起きない。それでも発生した場合のみ、手動で復元する。
  ```bash
  python scripts/restore_shapes.py <元xlsxパス(図形あり)> <加工後xlsxパス(図形なし)> <出力xlsxパス>
  ```
