# 開発メモ（このスキルを流用・改修する人向け）

このファイルは、スキルを**利用する**AIが読む必要はない（`SKILL.md`からもリンクしていない）。
スキル本体（`SKILL.md`・`references/*.md`）は「今どう扱うべきか」というルールだけを残す方針にしたため、
検証・修正の過程で分かった経緯・判断根拠・失敗事例はすべてここに退避した。
このスキルを別プロジェクトに複製して改修する人が、同じ失敗を繰り返さないための記録。

## 表紙・図形まわりで実際に発生した事故

- PJ名/システム名/サブシステム名を`変更履歴`シート以外のE1〜E3に直接入力すると、他シートの数式（`変更履歴`シートを参照する`IF(INDIRECT(...))`）が壊れる事故を、ローカルスクリプトのテスト中に実際に発生させて確認した。
- 表紙の「関係者外秘」等の機密区分図形は、`openpyxl`で読み込んで保存すると跡形もなく消えることを実機検証で確認した（`restore_shapes.py`で対応）。
- **サンプル・実例ファイルを処理の「元ファイル」に指定すると、表紙が二重表示になる事故を実際に発生させた**。原因は、`assets/templates/サンプル/`・`B1実例/`配下のファイルが人手編集の産物で、原本どおり図形ベースの表紙（`[プロジェクト名]`等の古い表示を含む）を保持していたこと。eval再実行（後述）で、with_skill/without_skillの6件全ての出力ファイルで発生した（1件だけの偶然ではなく、起きやすい失敗パターンだと判断）。再現手順・詳細は本ファイル末尾の「evalワークスペースでの発見」を参照。
- この事故の再発防止として、`verify_layout.py`に`shape_anchor_counts()`によるシートごとの図形個数チェックを追加した（有無だけでなく個数の増加を検知する）。

## 外部インタフェース設計書(JSON)のチェックボックス→「□ 選択肢」化の経緯

原本のNablarch公式テンプレートには、媒体・データ形式・授受方式・暗号化・処理サイクル・入出力種別の各項目にExcelのチェックボックス型フォームコントロール（`ctrlProps`、29個）が使われていた。これは`openpyxl`で読み込んで保存すると跡形もなく消える（`restore_shapes.py`でも復元できない仕組みのため）。実際、このスキルが配布していた空テンプレートは、既にこのチェックボックスを失った状態だった。

対応は3段階を経た。

1. **最初の設計（誤り）**：チェックボックスのVML/ctrlProps定義をXMLレベルで機械的に読み取り、8項目をそれぞれ1セルのプルダウン（データ入力規則）にした。この際、実在しない「フィールドセパレータ＝有り」という選択肢を作ってしまい、また「階層構造（XML形式）／（JSON形式）」を、本来はデータ形式の選択肢の一部であるにもかかわらず、独立したセル(U19)に誤って分離してしまった。
2. **ユーザーによる目視確認**：ユーザーが実際にExcelでサンプルファイルを開いて確認した結果、(a) プルダウンは分かりにくいこと、(b) フィールドセパレータには実際は選択肢が無い（対象外として取り消し線が引かれている）こと、(c) 階層構造はデータ形式の一部であること、が判明。ここでプルダウン方式から「□ 選択肢」方式への変更、フィールドセパレータの誤った選択肢の削除、階層構造の統合を行った。
3. **ユーザー自身によるセル配置の手直し**：それでもなお元のレイアウト（縦横の配置、1選択肢1セル）とズレていたため、ユーザー自身が実機を見ながら現在のセル配置（`E7`/`I7`、`E18`/`E19`、`U18`/`AB18`/`U19`/`AB19`/`U20`/`AB20`、`E22`/`E23`、`U22`/`Y22`/`AD22`/`U23`/`Y23`、`E25`〜`R27`）に修正した。

この過程で、テンプレートに元々付いていたExcelのセルコメント（媒体・データ形式・フィールドセパレータ・改行コード・レコード長が「JSON形式では記載不要」である旨、暗号化の3パターンの説明、【レコード名】シートの各列の記入基準等）を一つずつ確認し、記入要領に反映した。これらのセルコメントは、最初の`記入要領_外部インタフェース設計書_JSON.md`作成時には見落としており、ユーザーの指摘で気づいた。

## 記入要領を書いた際に判明した、前回版の欠落項目

各記入要領は、以前のバージョンで項目の洗い出しが不十分だった箇所があり、以下を補完した。

- `記入要領_WebサービスAPI一覧.md`：②の表がNo./API ID/API名称/処理概要の4列だけだったが、実際はプロトコル・HTTPメソッド・URL・データ形式・電文ID・対応取引まで含む10項目あった。
- `記入要領_システム機能設計書_Webサービス.md`：2.1・2.2・2.3の一部しかカバーしておらず、実際の処理ロジックを記述する2.4・2.5節が抜けていた。
- `記入要領_システム機能設計書_バッチ.md`：起動条件・処理概要一覧・入力/出力データ定義・処理詳細・出力データ定義の大部分が抜けていた。
- `記入要領_テーブル定義書.md`：PK/INDEX/初期値/暗号化対象/項目定義/備考の各列が抜けていた。INDEXの記述も推測に基づいていたため、Excelコメント原文（ユーザー確認済み）に置き換えた。
- `記入要領_外部インタフェース一覧.md`：授受方式以降の列（合計13項目中の後半）が抜けていた。
- `記入要領_外部インタフェース設計書_JSON.md`：多くの項目が抜けていた上、【レコード名】シートの列構成をB1実例（旧仕様）から誤って転記していた。
- `記入要領_共通シート.md`：変更履歴シートの「担当者」列（AF列）を完全に見落としていた（一覧の6列に紛れて気づきにくい）。
- `記入要領_システム機能一覧.md`：見出し行を「機能ID〜機能説明」までしか記載しておらず、実際は「取引ID」以降の列も存在した。

## evalワークスペースでの発見（`nablarch-basic-design-excel-workspace/iteration-2`）

`evals/evals.json`の3ケースを、with_skill（スキルを明示）・without_skill（スキル名を明示しない）の両条件でエージェントに実行させ、`grade_eval.py`で機械採点した。

- **without_skillでもスキルが発見・使用された**：SKILL.mdのdescriptionが「スキル名が明示されていなくても使用する」という強めの記述になっているため、Claude Codeの仕組み上、baselineを明示的にスキル無しにすることができなかった。3件のbaselineエージェントすべてが、実際に`duplicate_sheet.py`・`apply_mapping.py`・`restore_shapes.py`等を使用していたことをレポートで確認した。そのため今回の再実行は、厳密な「with_skill vs without_skill」のA/B比較にはなっていない。
- **サンプル/実例を元ファイルに使う事故が6件中6件で発生**：上記「表紙・図形まわりで実際に発生した事故」を参照。with_skill/without_skillどちらの条件でも、エージェントは記入内容の参考にサンプル・実例ファイルを開いた後、`restore_shapes.py`等の「元ファイル」引数にそれを指定してしまっていた（`00_work_base.xlsx`のような、処理の最初の時点で既に表紙の図形が2〜3個に増えていたことを確認）。この発見を受けて、`記入要領_共通シート.md`・`SKILL.md`にサンプル/実例を元ファイルに使わないことを明記し、`verify_layout.py`に図形個数チェックを追加した。
- **エージェントの自己報告は必ずしも正確でない**：2件のエージェントが「表紙が原本レイアウト（図形のみ）のままだった」「特定セルが数式でなく静的テキストだった」と報告したが、実際にファイルを開いて確認したところどちらも誤りだった（テンプレート自体は正しい状態）。採点は自己報告の文章ではなく、実際のxlsxファイルを`grade_eval.py`で機械的に検証する方式にしているため、この種の誤報告は採点結果には影響していない。
- **add-customer-tableの評価で有意差が出た**：with_skillは6/6合格。without_skill（実質的には同じスキルを使った別試行）は、複製したシート名を「顧客」ではなく「1 顧客」としてしまい、5項目中4項目が不合格になった。extend-interface-list・system-function-list-headerの2件は両条件とも全項目合格で、差が出なかった（アサーションが弱いか、タスクが単純すぎる可能性がある）。
- 生成物：`nablarch-basic-design-excel-workspace/iteration-2/benchmark.json`・`benchmark.md`・`review.html`（iteration-1との比較付き）。
